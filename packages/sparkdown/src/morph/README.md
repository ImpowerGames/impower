# Morph bake

A `morph` declaration (see `../compiler/morph/`) says how a portrait moves between its drawn states. This directory turns that declaration and one image variant's artwork into an artifact a player can animate: ordered render parts, numeric frames for every moving drawing, the apertures that clip eyeballs and shadows, and a static rest render with those apertures applied. The geometry itself comes from `@impower/spark-morph`; this code finds the drawings, decides what pairs with what, and packages the result.

Every host runs the same code. The bake (`bake.ts`) is a pure function of the artwork text, the variant's attribute selection and the morph's recipe. Hosts differ only in where the artwork comes from and who keeps the result (`hosts.ts`, `assetService.ts`).

## What compilation emits

Compilation never bakes. Binding a morph to images needs only the attribute vocabulary, which every host has, while baking needs the SVG source, which the web editor's compiles do not carry. So the compiler fills `program.morphs` (`channel.ts`) with two tables:

- `recipes`: each morph's `MorphRecipe` as canonical JSON, once per morph. A recipe holds the transition policies, the keyframes' state selections and the clip entries after inheritance. A root `depth` of `rest`, the default, is left out of the text, so a morph that keeps it has the recipe it would have without the field. Its `paints` entries keep their authored order with each colour written as `formatColor` writes it, so equal colours give one recipe; a morph with none leaves the field out. A label's `partner` is a list in written order, each label once, and is left out when unset, when it names only the label itself, and on a label a clip lists in `between`, so a morph without it keeps its recipe text. Timing and layer poses are not in it, so retiming a blink does not invalidate any baked geometry.
- `variants`: for each image variant a morph plays on (an `active` binding: compatible groups, resting where the morph starts), a `MorphRef` keyed by the variant's context name, the name an image directive resolves to.

A reference is about 600 bytes on a served host and less where the art is inline. It names the morph, the root image, the variant's canonical selection and the groups the morph drives, plus a `key`. The key is a hash of the bake format, the artwork's version (its served `src`, which carries the file signature, or a hash of the inline data), the selection and the recipe text, so anything that would change the artifact changes the key. Dormant variants (explicitly closed eyes) and skipped ones get no reference; compilation reports skipped ones on the morph block.

The channel is built on every compile, with or without validation, and reused while the context revision and the effective morphs are unchanged. It is a separate channel rather than a field on the `filtered_image` structs because those structs are shared between compiles and may only carry derivations of their own inputs, while a reference also depends on the script's morph declaration.

## Resolving a reference

`createMorphHost` resolves a reference through one `MorphBakeService`:

- With `ref.src` and a `fetch`, the asset service bakes. In the web editor `src` is the variant's filtered-image URL (`/file:/…svg?v=…&attributes=…`) with `&morph=<recipe>&key=<key>` appended. The service worker (`impower-dev/src/workers/sw.ts`) and the dev server's mirror both answer it with `serveMorphAsset`: the artifact as JSON, or with `&morph_output=rest` its rest render as SVG. The worker caches artifacts in the `morph-artifacts` bucket by the file's content digest, the selection, the recipe and the bake format, never by the request URL. One file, selection and morph name is one consumer: writing its new artifact deletes the ones an older signature or an older recipe of that morph left, and past `MORPH_ARTIFACT_CACHE_ENTRIES` the oldest entries go. Like the filtered images beside it, the service bakes the file as it is when asked, so a reference minted before an edit gets the edited art's artifact under its own key until the next compile mints the new one. A page abandoning its request does not stop the worker's bake, which finishes and is cached for the next request.
- Without `src`, the host reads the artwork itself and bakes in process: `inlineMorphSource` reads the program's inline `image.data` (VS Code, local compiles), `fetchedMorphSource` fetches the root image's `src` (a player with plain file assets). The language server reads its watched files directly, because it holds every artwork's text on every host.

Readiness is static first. A consumer keeps showing the variant's ordinary `filtered_src` until the artifact arrives, and keeps it for good if resolving fails. `MorphArtifactSlot` packages this for one consumer: `set(ref)` starts a request and abandons the previous one; a result whose key the slot no longer holds is released unseen, so a late bake for an older source or recipe generation never attaches; a failure leaves the slot `failed`, which means "stay static".

Cancellation is per consumer. Aborting a request rejects that caller only; the shared bake is cancelled when no caller is still waiting for it, and the bake observes that between drawings. A caller arriving after everyone else abandoned a bake starts a fresh one.

## Caching and lifetime

`MorphBakeService` coalesces concurrent requests for one key into one bake and reference-counts what it keeps. A `MorphHandle` holds one reference until `release()`. Unreferenced artifacts are evicted oldest-use-first once the service holds more than `maxArtifacts` artifacts or `maxBytes` of unreferenced ones; referenced artifacts are never evicted. `handle.url(…)` creates an object URL for the rest render or a part on first use, and the service revokes it when the artifact leaves the cache. `onEvent` reports each bake (with its time and size) and each eviction, so a host can watch its cache. `invalidate` drops the artifacts of an edited or deleted artwork; one still held goes when its last handle is released, and new requests bake again. Edits change keys anyway, so invalidation only returns memory sooner.

Reusable geometry is kept apart from consumer-specific artifacts. The service keeps one geometry cache per artwork content (bounded by `maxSources` and `maxGeometryPerSource`) holding the root-space morph result of each drawing pair and method (failures included, so a cached bake reports what a fresh one would), its sampled frames in each element space, and the aperture samples of each edge set. Variants of one artwork that differ in groups the morph does not drive (an outfit, a gaze) reuse all of that instead of searching for the same correspondences again; only parts and visibility are rebuilt, a few milliseconds on the test fixtures against hundreds for a first bake. The defaults in `MORPH_CACHE_DEFAULTS` are starting bounds, not measured budgets.

## What a bake does

1. Reads the artwork with the attribute module's own walk, so every element carries the layer key visibility is evaluated with. Artwork carrying a style sheet, or markup that may bring one in (a `<style>` element anywhere, empty or not, any `<link>` element, since its relationship can be spelled with character references, an `<?xml-stylesheet?>` instruction, or a DOCTYPE with an internal subset, whose entities a browser expands into markup) keeps its static render with one `unsupported-element` error: a sheet's rules could decide which drawings show, what composites and what each part references, and the bake reads only attributes and inline `style` attributes.
2. Binds the variant with the same rules compilation used (`bindVariant`). A variant that is no longer active, because its art changed since compiling, bakes to a static artifact with a diagnostic.
3. Builds each driven group's schedule. A keyframe state equal to where the morph starts is the variant's own resting choice, so an authored `open-wide` returns to `open-wide`, and each folder keeps its own default. An omitted first or last keyframe is the resting state, as in CSS.
4. Evaluates visibility for each state of each group with the others at rest, without publishing the probe-only diagnostics (`look-with-closed-eyes`) a hypothetical selection raises. A layer whose visibility changes with a group belongs to it; a layer two groups both switch is an error.
5. Splits paint order into runs of static and live leaves. Live leaves are the groups' state layers and every clip target; a compositing ancestor (opacity below 1, a filter, a mask, a blend mode, isolation, whether from its attributes or its inline style) that holds both makes all of its leaves live, because splitting it would change how it composites. Art the author hid with `display: none` is no leaf, read from the inline declaration that takes effect (the last important one, else the last) or else the attribute. An inline style is read within a closed grammar (`svgDocument.ts`): names and values in ASCII, with space, tab and line breaks between tokens, declarations ended by `;`, each with an optional trailing `!important`. Each run becomes a part: a full SVG document with the root's sizing, every ancestor's transform and inherited style, and the transitive closure of the resources it references (gradients that inherit gradients, clip paths whose contents use patterns), its kept ancestors' own references included. A resource copied out of its place sits inside groups that repeat what its original ancestors passed down, so a `currentColor` stop keeps its color, and whatever those ancestors reference (a pattern under `<defs fill="url(#paint)">` needs `#paint`) is in the part's closure too. Ids are namespaced under the artifact's prefix and every supported reference is rewritten: `url(#…)` in attributes and inline styles, and `href`/`xlink:href`.
6. Pairs each segment's appearing and disappearing drawings by identical nonempty effective label (the nearest labelled ancestor's) with `pairShapes`, in root user space, so ancestor transforms are honoured. Each drawn element is a pairing unit; a labelled group's elements all carry its label. Unlabelled drawings never pair. A drawing whose effective label has a `partner` list, and whose geometry the bake reads, pairs by that list first wherever one pose of a segment draws it and the other does not (see Partners below).
7. Applies policy, resolved field by field from the nearest configured label up to the root: `blend = morph` runs the explicit `method`, falling back with a diagnostic when it fails; `fade`, `cut` and `scale` apply to paired and unpaired drawings alike; an unpaired drawing under `blend = morph` uses its `fallback`; `depth` chooses which drawing of a moving pair carries it (see `draw` under Playing an artifact). A drawing inside a clip target holds through the segment instead, so the moving aperture alone decides what shows.
8. Forms apertures from each clip entry's `between` edges: the bend tracks of the paired drawings with those labels (two open lashes converging on one closed lash are two tracks and one aperture). `between` lists the labels the clip accepts, and a variant uses the ones its artwork draws, so one morph serves a portrait that labels both lashes `eyelash-right` and one that labels them `eyelash-top-right` and `eyelash-bottom-right`; distinct labels pair one to one, which is how an author keeps lashes from pairing across each other where nearest position would cross them. Edges that are not bend morphs, compound edges, a lone edge, three edges sharing tips, an edge inside its own target, a clip none of whose labels the artwork draws, or edges that never move disable the morph for the variant with a diagnostic. Between the rest poses an edge's boundaries are the frame its track draws there, split in two at its tips (`BendTrack.edges`), so the aperture meets the lashes the player draws; at a rest pose they are the authored outline. An aperture that closes to nothing is valid. A closed aperture is its midline traced out and back, so an opening blended towards it closes onto the lashes' line rather than onto the chord between their tips. Every sample of an aperture is resampled to the same number of points along its outline, so a player blends neighbouring samples point by point. Beside each aperture table entry, `apertureEdges` holds, per sample and per loop, the frames the loop's two edges draw there, each as a closed polyline (a drawing in straight segments keeps its points; a curved one is sampled eight points per segment), in root space as the apertures are.
9. Wraps each clip target in a group masked by its entry's aperture, in both the live part and the rest render. The masked group undoes the transforms around the target and a group inside it redoes them (both written at full precision), so the mask is on an element whose space is root space, the apertures' own. The target's own clip paths and masks stay on it, so they intersect. The rest render is the variant's static render, unchanged except for those wrappers and their masks. An aperture mask's path is the rest outline, filled and stroked `APERTURE_REACH` (1) screen pixel past it on each side with a non-scaling stroke, at any size the picture is drawn. The outline lies on the edges drawn around the opening, and a clip edge and a drawn edge that coincide are each antialiased against what lies beneath them, which leaves a one-pixel seam of the layer under the targets; the reach moves the mask's edge under the edges, which paint over the targets at rest as the still image draws them. Away from rest a player gives the aperture the same reach, clipped to where the moving edges draw (see playing an artifact below): moving edges taper toward the opening's corners, thinner there than the reach, and on art whose closed state paints beneath the open eyes the closed lashes lie under the targets, so an unclipped reach would show the targets past the edges. Closure is judged loop by loop, since one clip entry may hold several eyes: a rest loop whose area is at most 1% of the widest loop its entry opens to (an eye resting closed) is not stroked, and when some loops are closed the open ones are stroked by a second path. A non-scaling stroke in a mask is drawn through the space of the element the mask is on, which is why that element's space is root space: under any transform around the target, scaled, skewed or rotated, the reach is the same. A browser composes those matrices in single precision, which moves the target by about 2^-24 times the parent space's condition number times the size of the coordinates involved, translations included; where that could exceed a ten-thousandth of the apertures' extent, the aperture is a clip path in the parent's space, the aperture mapped into it, with no reach. The path's paint is spelled out (opaque fill and stroke), since a mask's content inherits from the artwork root rather than from the masked drawing. Drawn inline, as the player draws a live portrait, the reach is one device pixel; drawn as an image (`rest` in a hover, preview or CSS mask), it is one pixel of the artwork's own size, scaled with the image. The mask's region is the apertures' bounds grown by their own size.

### Partners

A label's `partner` names, in priority order, the labels whose drawing its own drawings take in a pose that does not draw them. A source is a drawing of such a label that one pose of a segment shows, as itself or carried, and the other does not; its other pose is the end that does not show it. The first listed label the other pose draws, among the drawings of the same group, decides. The label's own name decides by pairing by name, as step 6 pairs (`pairShapes`, failures included); without its own name in the list a label never pairs by name. Another label decides by its drawing whose box centre, curves included, is nearest the source's, the first in paint order on a tie (the rule `drawingIn` applies to `depth` carriers). A drawing never splits, and several sources may take one partner drawing. A source whose other pose draws none of its labels keeps today's behaviour, its fallback or holding inside a clip target, with one `partner-missing` warning per bake whose message every variant shares.

The arrival frame is the source drawn in the partner drawing's shape: the partner's geometry in root space mapped into the source's own space, with the source's own paint, at the source's place in paint order. `depth` does not apply. The source's blend, resolved from its label as for any drawing, decides how it gets there: `morph` runs its `method` from the shape it leaves to the shape it reaches, as an ordinary `morph` transition between the nodes of those two drawings marked `partner`, drawn on the source itself (a carrier of it for a basic shape or a node another track draws on) and with no `paint` record, so it keeps its paint and takes no `paints` entry; a method that fails, or a missing `method`, uses the fallback as for any pair. `fade` fades its own shape out while the arrival frame fades in, `cut` holds its own shape to the segment's end and then shows the arrival frame, and `scale` shrinks its own shape while the arrival frame grows from nothing, each with the arrival frame on a hidden carrier of the source where both shapes show. A source inside a clip target follows its partner rather than holding, so its target's aperture keeps clipping it.

The source is carried: it stays drawn as its arrival frame at the segment's end, while the group holds that pose and at the start of the next segment. A segment leaving a pose that carries a source treats it as a drawing of its own label leaving that pose in the shape it carries, and applies the same list: back to its own shape where the next pose draws it, onto the next pose's partner drawing, into a same-labelled drawing where its own name decides (paint blending between the two as a pair's does), or out by its fallback from the carried shape, or holding there inside a clip target, where it draws none. The variant's rest pose shows exactly the still, so it carries nothing: a segment arriving at the rest pose hides the arrival frame at its end, and a segment leaving it starts with the source hidden and moves it out of the arrival frame. A source entering from a pose that does not carry it does the same.

A segment records what carrying needs. `shapes` holds the path data, in the node's own user space, of each carrier that draws an arrival frame or a carried shape in that segment's `fade`, `cut`, `scale` or `hold` transitions; `carry.from` and `carry.to` hold the nodes the start and end poses show as carried shapes, with their path data.

Frames are sampled at `MORPH_BAKE_SAMPLES` (8) evenly spaced progress values, the geometry package's tuning point, and mapped into the moving element's own user space so a player sets its `d` directly. A segment that moves the same drawings back reuses the earlier segment's frames and apertures reversed; geometry lives in the artifact's `frames` and `apertures` tables and transitions point into them.

## Playing an artifact

`render.ts` draws an artifact at any pose as one SVG and is the executable statement of these rules; a live player follows the same ones.

- Parts paint bottom to top and overlay exactly (they share the root's view box and sizing). Static parts never change. A player drawing several inline copies of a live part gives each copy its own id prefix with `namespaceMorphMarkup`.
- A live part's markup is the rest pose: leaves another state shows carry an inline `display: none`, so the parts composed as written match the rest render. A player shows and hides leaves through that inline declaration. Nothing outranks it: a live leaf carries no inline `display` or `display` attribute of its own (art the author hid is no leaf), and artwork carrying a style sheet is never baked live. At a keyframe, a group shows the leaves `visibility[group][state]` lists and hides its others; leaves outside every group are always drawn.
- Progress arrives already eased by the morph's timing; nothing here eases again. Within a segment, a frame blends its two nearest samples linearly, from the last sample backwards when the geometry reference is `reversed`.
- At either end of a segment the authored drawings show as they are, never their sampled frames: the start pose is the `from` leaves' own geometry and the end pose the `to` leaves'. A live part writes every drawing exactly as authored (a path's `d` with its relative commands and arcs, a basic shape as the shape it is), so the parts draw what the rest render does; a basic shape that moves draws its frames on a carrier written as the equivalent `<path>`, so a player can set its `d`.
- `morph`: between the ends the `draw` leaf takes the blended geometry, and at the end the `to` leaf's own drawing takes over, so a destination several tracks share is drawn once. A moving drawing paints at the depth its layer has in the pose its `depth` names, in both directions, so its stacking holds for the whole morph: `draw` is whichever of `from` and `to` that pose shows. `depth` resolves field by field like the other policies, by the nearest configured label of the drawing that leaves; its default, `rest`, names the variant's rest pose, the pose the static image shows, so by default the live layer order always matches the still. A named state is one the keyframes name for a group the morph drives (`eyes.closed`), and the state the morph starts from stands for the variant's own resting choice, as it does in the keyframes. Where a named pose shows neither drawing (a segment of a multi-keyframe morph that does not reach it), `draw` is a carrier of that pose's drawing of the same label in the same group (one whose geometry the bake reads; the one whose box centre, curves included, is nearest `from`'s when it has several), so the stacking holds through every segment; the drawing itself may be held, fading or another pair's end in that segment, so it keeps its own role. Where it draws no such drawing, or names another group than the one the drawing changes with, the rest pose decides instead, and `draw` is `from` when the rest pose shows neither too; the default `rest` never looks past `from` and `to`. A label with moving drawings none of which the named pose places gets a `depth-ignored` warning; a one-sided drawing under it moves on no track and is not counted. One element carries one shape, so where several tracks draw on one drawing (two open lashes converging on the closed lash a variant rests on), the second and later tracks draw on carriers: hidden copies of that drawing written right after it in its part, with no ids, which no state shows. Every track of a basic shape draws on a carrier, written as the equivalent `<path>`, so the shape's own markup is never replaced. Paint follows the shape: where the two drawings' fill colour, stroke colour, `fill-opacity`, `stroke-opacity` or own `opacity` differ, or the drawing `draw` copies differs from them, the transition's `paint` records both ends' values of those properties, and between the ends `draw` is written with their blend at the segment's progress, inline and important where its markup's own declaration is, so a carrier never shows its source drawing's paint between poses. At the ends nothing is written and the authored drawings show as they are. Each drawing's value is its inline style (the last important declaration, else the last) or else its attribute, else what it inherits from its ancestors (all but `opacity`), with `currentColor` read through `color`, else the SVG initial value (black fill, no stroke, opacities 1). Paint is read within a closed grammar (`paint.ts`): a fill or stroke as a colour or `none`, `color` as a colour or `currentColor`, an opacity as a number or percentage, any of them as `inherit` or `initial`, with an optional trailing `!important`, in ASCII with space, tab and line breaks between tokens. When any declaration that decides a paint lies outside it (another CSS-wide keyword, `all`, `var()`, a comment, an escape, an XML character reference in an inline style, which the bake reads as written and a browser decodes, other whitespace, non-ASCII text), that paint is unknown and the pair stays unblended, as an unreadable paint does. Colours read as hex, `rgb()`, `rgba()`, `hsl()`, `hsla()`, a named colour or `transparent` (`color.ts`) and blend in gamma-encoded sRGB with premultiplied alpha; a `none` fill or stroke is the other end's colour at zero alpha, so paint present at one end only fades in or out. Opacities blend linearly. Gradients blend too (`gradient.ts`): where both ends fill or stroke with a bare `url(#id)` naming gradients of the same kind (linear or radial) with the same number of stops, the same `gradientUnits` and the same `spreadMethod`, and the drawing `draw` copies would not already show the same gradient at both ends, the transition's `gradients` records both ends, each resolved through its `href` chain (each attribute from the first gradient in the chain that sets it, coordinates only from gradients of the first one's kind, and the stops of the first that has any). Each node a gradient blends on gets its own copy of it (one for each way the gradients it carries are built: kind, units, spread and stop count), written unreferenced in the live part that draws the node, under the artifact's id prefix, so the authored drawing and other carriers keep theirs; between the ends `draw` paints with `url(#copy)` and the copy takes the blend: coordinates and stop offsets linearly, stop colours as solid paint blends (each stop's `stop-opacity` folded into its alpha), and `gradientTransform` entry by entry. A `userSpaceOnUse` gradient is placed in `draw`'s user space as its own drawing shows it, the map from that drawing's space folded into its transform; an `objectBoundingBox` gradient keeps its unit coordinates and follows the moving shape's box. The fill or stroke's opacity blends as a colour's does wherever both ends paint with matching gradients, a copy or not. A gradient is read within a closed grammar: no inline `style` or `transform` attribute on any gradient in the chain, nothing but `stop` elements in them, links of the form `#id` through `href` or `xlink:href` (its prefix bound to the XLink namespace) to other gradients, gradients and stops in the SVG namespace, `gradientUnits` and `spreadMethod` spelled exactly, coordinates and offsets as plain numbers or percentages no larger than 1e300 (a percentage in `userSpaceOnUse` only at zero, since any other resolves against a viewport), a `gradientTransform` of the six transform functions with plain numbers and matrix entries no larger either, stop colours in the paint grammar (an inline style on a stop declaring nothing but `stop-color`, `stop-opacity` and `color`), and nothing that may set `color-interpolation` on the gradients, their stops or their ancestors (the attribute, the property, `all`, or an inline style the paint grammar cannot split). A fill or stroke either end paints with anything else (a pattern, a gradient outside the grammar, a gradient against a colour, gradients that differ in kind, stop count, units or spread, or colour syntax the reader does not know) records neither it nor its opacity, and the shape keeps the paint of the node it draws on. Stroke width and the other stroke geometry, and what composites on an ancestor, stay with that node. `fade` multiplies the leaves' own opacity, read from the inline declaration that takes effect when they have one, since that outranks the attribute, and written back inline, important when that declaration was; `cut` holds `from` until the end; `scale` follows its frames on its `draw` leaf (the drawing itself, or a path carrier for a basic shape), is invisible at its zero endpoint and is the authored drawing at its full one; `hold` stays drawn.
- `paints`: the artifact's `paints` lists, in authored order, each entry that applies to the variant. An entry with a `when` applies where the variant's rest pose draws a layer that needs that state, through its own name or an ancestor's (a condition on the state's group that accepts only that state or its refinements); one without applies wherever the morph plays. The bake reads a selection that picks the state but draws nothing that needs it as not applying. Where it applies, the entry's `nodes` are the drawings of its target labels (on the drawing or an ancestor) that the pose shows, among those that change with the pose's group and those no driven group switches (which the bake makes live so a frame can recolour them), and its `tracks` are the `morph` tracks of segments arriving at or leaving the pose whose end there is one of them, by the node each draws on, with the paint the track shows at its two ends without the entry (its `paint` record, else the paint its ends share). A target label the pose draws nothing of gets a `paint-target-missing` warning. While the group holds the pose, its target drawings take the entry's colour. In a segment arriving at the pose the colour moves in linearly over the segment's last `span`, with weight `w = clamp((p - (1 - span)) / span)` at segment progress `p`, mixed in sRGB over the paint each drawing shows without the entry (`none` is the entry's colour at zero alpha); a segment leaving the pose mirrors it. Tracks take the mix on the node they draw on, and so do target drawings both poses show, a drawing no driven group switches among them; a pose drawing showing as itself (at the segment's end, fading, cut or scaling in or out) takes the colour. `span = 0` changes the colour only where the pose's own drawings show. A drawing or track whose own paint the bake cannot read takes the colour only at full weight. Drawings a frame hides are not written, inline and important where the markup's own declaration is, as blended paint is; a property the entry leaves out keeps the drawing's own paint. Where two entries recolour one drawing, the later wins. The rest render and the parts as written never carry an entry's colour, and a static artifact has none.
- Carried drawings (Partners, above): strictly between a segment's ends, a carrier the segment's `shapes` lists takes that path data wherever a transition shows it, unless a `morph` or `scale` frame already gives it geometry. At the segment's start and end every carrier `shapes` lists hides, and the nodes `carry.from` (at the start) or `carry.to` (at the end) lists show with their path data, in their own paint. A group holding a pose after a segment shows that segment's `carry.to` the same way, and a group holding the pose it starts from shows none.
- A clip entry's aperture in a segment is that segment's `apertures` entry, written into every aperture `clipTargets` lists for the entry; outside its segments an aperture keeps its last pose. Between two samples the aperture is their point-by-point blend at the precision path data is written with (`aperturePathData`). Each sample spaces its points along its own outline, so point k of two samples need not be the same place on the opening and the blend can cross itself; where it does, or passes through one of its own points, the part winding the way the wider sample does is kept, so the aperture drawn between two samples is a simple loop. A progress that falls on a sample draws that sample as stored. An aperture written with anything but its rest outline keeps its reach, clipped by a clip path the mask holds (`poseAperture`) to the aperture and, around each loop still open, the drawings of its two edges, blended the same way from `apertureEdges` (`apertureReachPathData`). Those are the moving drawings the player draws, so the reach puts the targets under the edges' antialiased inner edges and nowhere the edges do not cover. That hides the reach only where the edges paint over the targets, so a segment's clip entry lists in `reach`, per aperture, the loops whose own two moving edges both have homes after every drawing of the aperture's target in paint order (a carrier paints right after its home). A loop is judged by its own edges alone, so one eye's lashes do not take the reach from another eye's targets in the same clip entry; a loop whose edges paint beneath the target, as under a named `depth` or on a variant resting closed whose closed lashes paint beneath the whites, keeps its area alone. The moving drawings are drawn strictly between a segment's ends; at either end the poses' own drawings take over, and a closed state's may paint beneath the targets, so the closed keyframe and a held state draw the aperture's area alone. The clip path's rule is spelled out (`clip-rule:nonzero`): a clip path's content inherits the artwork root's, which exported art often sets to `evenodd`, and the clip's loops overlap.

`morphFrameState` is these rules as data: for a pose of every driven group it lists the leaves that show and hide, the path data and paint a moving leaf takes, the values of each gradient copy it paints with, the factor a fading leaf's opacity is multiplied by and the path data of each aperture and of where it may reach, and leaves everything else to the markup. `renderMorphFrame` and `renderMorphAt` draw it as one SVG; a live player applies it to the parts it keeps on the page with `poseLeaf`, `poseGradient` and `poseAperture`, starting each leaf, gradient copy and aperture path from its markup every frame and writing a leaf's `url(#copy)` under its own id prefix.

## Timing

A morph's timing is not in its recipe or artifact, so retiming bakes nothing again. A player schedules each occurrence with a `MorphTimeline` (`timeline.ts`): the first play starts after `delay`, each later one after a quiet gap drawn uniformly between `iteration_delay_min` and `iteration_delay_max` (none without bounds), and `iterations` counts the plays. The timeline answers where an occurrence is at a time: waiting for its first play (drawn at rest), partway through a play, in a gap holding the end pose of the play before, done holding the terminal pose of a finite sequence, or off (`iterations = 0`). Each occurrence draws its gaps from its own seeded stream (`morphRandom`), so a seed reproduces a schedule and two occurrences never share one.

A play's progress is directed (`reverse` and the `alternate` directions run some plays backwards) and then mapped once through the morph's `easing` (`easing.ts`, the CSS timing functions `easingProblem` accepts, `steps(3)` being `steps(3, end)`). The result is a keyframe offset, and `morphPosesAt` finds each group's segment at that offset and its progress within it: nothing eases a segment, a fade or an aperture again.

## Playing in the web player

The engine puts a morph's reference on the image write that shows its variant (`UIModule.getMorphContent`): the reference, the morph's timing with its defaults, an identity of its definition (recipe and timing) and the image's place among the write's images, counted in the CSS it paints them with (`cssList.ts`), so a literal listing several images keeps the count. A write carries references, never artifacts, so it stays small and its JSON deduplicates as before; a write with no morph on its images carries nothing new. A reference with no asset service behind it (inline art, as VS Code and local compiles carry it) names art only the program holds, so the game bakes it with `inlineMorphSource` and sends the page the artifact once per key and connection (`morph/artifact`, plain JSON as an asset service's response is). An image two morphs play on stays still and the game warns, since each artifact draws the whole image and declaration order is not the author's choice of which one plays.

The page's `MorphPlayback` (`spark-web-player/src/app/morph/`) belongs to the overlay and outlives the UI managers a re-render swaps in. For each written background layer it resolves the references through its host (the asset service named by `ref.src`, as the web editor's service worker is, or the artifact the game sent) and keeps the static image the write put up while they are pending, and for good if they fail. Once one is ready the layer is drawn in a shadow root: each image in paint order, static ones as CSS backgrounds with the layer's own size, position and repeat, live ones as the artifact's parts inline, each copy with its own id prefix, placed on the rectangle CSS would have drawn the static image in (`backgroundFit.ts`), from the span's fractional padding box and snapped to device pixels as the browser snaps a background image. The placement is taken again when the span resizes and after every screen op, since a style or class change can move the image without resizing the span. A mask shows the artifact's rest render in place of its static image and never moves.

A morph's phase belongs to its logical occurrence, not to the span drawing it: the target and content element, the image's place in the composition, the character, the morph and its definition, and the engine's epoch, which loads, restarts and resets advance. A compatible write (another expression of the same character) or a reconciling re-render draws the same occurrence at the same phase; the outgoing layer of a crossfade freezes on its last frame until its fade ends and is then released with its artifact references. A different character, an edited definition, a new epoch, a new PLAY session, previewing another place and time stepped backwards start occurrences again at rest. Phase is never saved.

During PLAY the application's clock drives playback, so pausing the story freezes every morph on its exact frame and stepping the clock moves them. A stopped preview never starts that clock; playback runs on animation frames of its own instead, which advance nothing in the story. The `Animate portraits` preference (`game/setAnimatePortraits`) returns every morph to rest and keeps it there, paused or not; turning it on starts each one on a fresh cycle. It holds for artifacts still pending too. `MorphPlayback.preempt` holds an occurrence at rest until released and then resumes its schedule where it stopped, the seam a later explicit transient behavior takes a portrait over by.

## Diagnostics

A bake reports what it could not do as `MorphBakeDiagnostic`s with the morph, layer and element they concern; their `uri` and `variant` name the consumer the bake ran for. Several consumers can share one artifact key (the same art in two files, two names for one selection), so the language server bakes each key once and publishes its diagnostics on every artwork whose reference has that key, through the existing asset diagnostic delivery and merged with the compile's own. Each problem shows once per artwork, naming every variant it affects. A drawing pair that fails in one segment and again in the segment that moves it back is one problem. Declaration problems stay on the morph block, where compilation puts them. Intentional one-sided art, `blend = cut` flipbooks with no pairs, and a closed-eye aperture of zero area are not reported. A source whose `partner` labels a pose next to it does not draw is reported once per artwork as `partner-missing`, naming the variants.

## Limits

- One morph's rest apertures per preview: a variant two clipping morphs play on previews with the first one's.
- A pairing unit is one drawn element. Art that splits one shape across several elements with different paint pairs element by element.
- Text, images and `<use>` instances inside state layers fade or cut; they have no geometry to morph or scale.
- A shape whose geometry the bake cannot read exactly (a length in a unit other than `px`, such as a percentage of the viewport, a length padded with whitespace CSS does not skip, such as a no-break space, or an inline style setting a geometry property such as `r` or `d`) has no geometry either: it fades or cuts with an `unsupported-element` warning, and its parts keep it as authored.
- A reference to drawn art (a `<use>`, or a clip path, mask or pattern that uses it, from a part's own drawings or the groups kept around them) keeps the variant static, with an `unsupported-element` diagnostic, when the morph would split the referenced art between the referencing part and another, or when the referenced art is a state layer or clip target in another part, where the copy could not follow it, or when it holds a drawing that moves on a carrier (a basic shape, or a drawing several tracks draw on), which is hidden while the reference still names it. Unchanging art is copied whole, even when a compositing group keeps it in a live part. The check counts what a copied resource's original ancestors reference even where the resource overrides that property, so it errs towards the static render, never towards a copy that stands still.
- Artwork carrying a style sheet keeps its static render, whatever its rules say; inline `style` attributes and presentation attributes are the styling a morph can play.
- Artwork with an inline style outside the bake's grammar keeps its static render, with one `unsupported-element` error naming the element, its layer and the declaration. Outside the grammar is non-ASCII text or other whitespace, a character reference, a comment, an escape, a string, a brace or bracket block, a parenthesis left open or holding a semicolon, an `all` declaration, a `var()`, `env()` or `attr()` value, a `!` other than one trailing `!important`, a `display` value other than `none` and the single keywords every browser draws an SVG element with (`inline`, `block`, `flex`, `grid`, the table keywords and their kin; not `contents`, which hides most SVG elements), an empty or CSS-wide value (`inherit`, `initial`, `unset`, `revert`, `revert-layer`) of a compositing property, and an opacity, inline or as an attribute, that is not a number or a percentage. A browser drops a value it does not accept and keeps the declaration before it, so a value the bake cannot vouch for could hide that one from it. The static render keeps every attribute as written, trimmed of XML whitespace only, so padding such as a no-break space reads in it as it does in the artwork. Each can change which drawings show, what composites or what moves in a way a plain reading misses; reading less than a browser does is safe, reading something differently is not. Paint keeps its own grammar inside this one.
- A `transform-origin` attribute, or an inline style setting `transform`, `translate`, `rotate`, `scale`, `transform-origin`, `transform-box` or an `offset-*` property, moves a drawing in a way the bake does not follow: the drawing fades instead of moving, and a clip target under it disables the morph, each with an `unsupported-transform` diagnostic. Only `transform` attributes are mapped.
- Artwork with a `transform` attribute outside the transform-list grammar (`affine.ts`) keeps its static render, with one `unsupported-transform` error naming the element, its layer and the attribute. The grammar is the six transform functions (`matrix`, `translate`, `scale`, `rotate`, `skewX`, `skewY`) with their argument counts and plain numbers that fit a double, the arguments and the functions each separated by XML whitespace (space, tab, line breaks) or one comma, with XML whitespace around the list. Outside it are a no-break space or other non-XML whitespace, a unit such as `5px`, a stray token, an empty or doubled separator, functions written with nothing between them and a list whose matrix overflows. A browser drops most of these or reads them differently, so a drawing the bake moved by one would not move where the artwork shows it. A few it draws as written, such as functions with nothing between them (`translate(5)scale(2)`); the grammar declines those too, since reading less than a browser does is safe.
- Drawings and clip targets inside a nested `<svg>` viewport are not mapped; a drawing there fades instead of moving, and a clip target there disables the morph, each with a diagnostic.
- A live layer is placed by its computed `background-size` and `background-position`; a repeating layer, or a size or position the player cannot read, keeps its static image.
- A live layer drops its parts' scripts, embedded documents (`iframe`, `object`, `embed`), event handler attributes and `javascript:` links, which a CSS background image would never run. Other external references in the art load as they would in any inline SVG.
