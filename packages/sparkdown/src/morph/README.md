# Morph bake

A `morph` declaration (see `../compiler/morph/`) says how a portrait moves between its drawn states. This directory turns that declaration and one image variant's artwork into an artifact a player can animate: ordered render parts, numeric frames for every moving drawing, the apertures that clip eyeballs and shadows, and a static rest render with those apertures applied. The geometry itself comes from `@impower/spark-morph`; this code finds the drawings, decides what pairs with what, and packages the result.

Every host runs the same code. The bake (`bake.ts`) is a pure function of the artwork text, the variant's attribute selection and the morph's recipe. Hosts differ only in where the artwork comes from and who keeps the result (`hosts.ts`, `assetService.ts`).

## What compilation emits

Compilation never bakes. Binding a morph to images needs only the attribute vocabulary, which every host has, while baking needs the SVG source, which the web editor's compiles do not carry. So the compiler fills `program.morphs` (`channel.ts`) with two tables:

- `recipes`: each morph's `MorphRecipe` as canonical JSON, once per morph. A recipe holds the transition policies, the keyframes' state selections and the clip entries after inheritance. Timing and layer poses are not in it, so retiming a blink does not invalidate any baked geometry.
- `variants`: for each image variant a morph plays on (an `active` binding: compatible groups, resting where the morph starts), a `MorphRef` keyed by the variant's context name, the name an image directive resolves to.

A reference is about 600 bytes on a served host and less where the art is inline. It names the morph, the root image, the variant's canonical selection and the groups the morph drives, plus a `key`. The key is a hash of the bake format, the artwork's version (its served `src`, which carries the file signature, or a hash of the inline data), the selection and the recipe text, so anything that would change the artifact changes the key. Dormant variants (explicitly closed eyes) and skipped ones get no reference; compilation reports skipped ones on the morph block.

The channel is built on every compile, with or without validation, and reused while the context revision and the effective morphs are unchanged. It is a separate channel rather than a field on the `filtered_image` structs because those structs are shared between compiles and may only carry derivations of their own inputs, while a reference also depends on the script's morph declaration.

## Resolving a reference

`createMorphHost` resolves a reference through one `MorphBakeService`:

- With `ref.src` and a `fetch`, the asset service bakes. In the web editor `src` is the variant's filtered-image URL (`/file:/…svg?v=…&attributes=…`) with `&morph=<recipe>&key=<key>` appended. The service worker (`impower-dev/src/workers/sw.ts`) and the dev server's mirror both answer it with `serveMorphAsset`: the artifact as JSON, or with `&morph_output=rest` its rest render as SVG. The worker caches artifacts in the `morph-artifacts` bucket by the file's content digest, the selection, the recipe and the bake format, never by the request URL. One file, selection and morph name is one consumer: writing its new artifact deletes the ones an older signature or an older recipe of that morph left, and past `MORPH_ARTIFACT_CACHE_ENTRIES` the oldest entries go. Like the filtered images beside it, the service bakes the file as it is when asked, so a reference minted before an edit gets the edited art's artifact under its own key until the next compile mints the new one. A page abandoning its request does not stop the worker's bake, which finishes and is cached for the next request.
- Without `src`, the host reads the artwork itself and bakes in process: `inlineMorphSource` reads the program's inline `image.data` (VS Code, local compiles), `fetchedMorphSource` fetches the root image's `src` (a player with plain file assets). The language server reads its watched files directly, because it holds every artwork's text on every host.

Readiness is static first. A consumer keeps showing the variant's ordinary `filtered_src` until the artifact arrives, and keeps it for good if resolving fails. `MorphArtifactSlot` packages this for one consumer: `set(ref)` starts a request and abandons the previous one; a result whose key the slot no longer holds is released unseen, so a late bake for an older source or recipe generation never attaches; a failure leaves the slot `failed`, which means "stay static".

Cancellation is per consumer. Aborting a request rejects that caller only; the shared bake is cancelled when no caller is still waiting for it, and the bake observes that between drawings. A caller arriving after everyone else abandoned a bake starts a fresh one.

## Caching and lifetime

`MorphBakeService` coalesces concurrent requests for one key into one bake and reference-counts what it keeps. A `MorphHandle` holds one reference until `release()`. Unreferenced artifacts are evicted oldest-use-first once the service holds more than `maxArtifacts` artifacts or `maxBytes` of unreferenced ones; referenced artifacts are never evicted. `handle.url(…)` creates an object URL for the rest render or a part on first use, and the service revokes it when the artifact leaves the cache. `onEvent` reports each bake (with its time and size) and each eviction, so a host can watch its cache. `invalidate` drops the artifacts of an edited or deleted artwork; one still held goes when its last handle is released, and new requests bake again. Edits change keys anyway, so invalidation only returns memory sooner.

Reusable geometry is kept apart from consumer-specific artifacts. The service keeps one geometry cache per artwork content (bounded by `maxSources` and `maxGeometryPerSource`) holding the root-space morph result of each drawing pair and method (failures included, so a cached bake reports what a fresh one would), its sampled frames in each element space, and the aperture samples of each edge set. Variants of one artwork that differ in groups the morph does not drive (an outfit, a gaze) reuse all of that instead of searching for the same correspondences again; only parts and visibility are rebuilt, a few milliseconds on the test fixtures against hundreds for a first bake. The defaults in `MORPH_CACHE_DEFAULTS` are starting bounds, not measured budgets.

## What a bake does

1. Reads the artwork with the attribute module's own walk, so every element carries the layer key visibility is evaluated with. Artwork carrying a style sheet, or markup that may bring one in (a `<style>` element anywhere, empty or not, any `<link>` element, since its relationship can be spelled with character references, an `<?xml-stylesheet?>` instruction, or a DOCTYPE with an internal subset, whose entities a browser expands into markup) keeps its static render with one `unsupported-element` error: a sheet's rules could decide which drawings show, what composites and what each part references, and the bake reads only attributes and inline `style` attributes.
2. Binds the variant with the same rules compilation used (`bindVariant`). A variant that is no longer active, because its art changed since compiling, bakes to a static artifact with a diagnostic.
3. Builds each driven group's schedule. A keyframe state equal to where the morph starts is the variant's own resting choice, so an authored `open-wide` returns to `open-wide`, and each folder keeps its own default. An omitted first or last keyframe is the resting state, as in CSS.
4. Evaluates visibility for each state of each group with the others at rest, without publishing the probe-only diagnostics (`look-with-closed-eyes`) a hypothetical selection raises. A layer whose visibility changes with a group belongs to it; a layer two groups both switch is an error.
5. Splits paint order into runs of static and live leaves. Live leaves are the groups' state layers and every clip target; a compositing ancestor (opacity below 1, a filter, a mask, a blend mode, isolation, whether from its attributes or its inline style) that holds both makes all of its leaves live, because splitting it would change how it composites. Art the author hid with `display: none` is no leaf, read from the inline declaration that takes effect (the last important one, else the last) or else the attribute. An inline style is read with its braces, semicolons and `!important` found outside comments, strings and unquoted `url(…)`. Each run becomes a part: a full SVG document with the root's sizing, every ancestor's transform and inherited style, and the transitive closure of the resources it references (gradients that inherit gradients, clip paths whose contents use patterns), its kept ancestors' own references included. A resource copied out of its place sits inside groups that repeat what its original ancestors passed down, so a `currentColor` stop keeps its color, and whatever those ancestors reference (a pattern under `<defs fill="url(#paint)">` needs `#paint`) is in the part's closure too. Ids are namespaced under the artifact's prefix and every supported reference is rewritten: `url(#…)` in attributes and inline styles, and `href`/`xlink:href`.
6. Pairs each segment's appearing and disappearing drawings by identical nonempty effective label (the nearest labelled ancestor's) with `pairShapes`, in root user space, so ancestor transforms are honoured. Each drawn element is a pairing unit; a labelled group's elements all carry its label. Unlabelled drawings never pair.
7. Applies policy, resolved field by field from the nearest configured label up to the root: `blend = morph` runs the explicit `method`, falling back with a diagnostic when it fails; `fade`, `cut` and `scale` apply to paired and unpaired drawings alike; an unpaired drawing under `blend = morph` uses its `fallback`. A drawing inside a clip target holds through the segment instead, so the moving aperture alone decides what shows.
8. Forms apertures from each clip entry's `between` edges: the bend tracks of the paired drawings with those labels (two open lashes converging on one closed lash are two tracks and one aperture). `between` lists the labels the clip accepts, and a variant uses the ones its artwork draws, so one morph serves a portrait that labels both lashes `eyelash-right` and one that labels them `eyelash-top-right` and `eyelash-bottom-right`; distinct labels pair one to one, which is how an author keeps lashes from pairing across each other where nearest position would cross them. Edges that are not bend morphs, compound edges, a lone edge, three edges sharing tips, an edge inside its own target, a clip none of whose labels the artwork draws, or edges that never move disable the morph for the variant with a diagnostic. An aperture that closes to nothing is valid. A closed aperture is its midline traced out and back, so an opening blended towards it closes onto the lashes' line rather than onto the chord between their tips. Every sample of an aperture is resampled to the same number of points along its outline, so a player blends neighbouring samples point by point.
9. Wraps each clip target in a group masked by its entry's aperture, in both the live part and the rest render. The masked group undoes the transforms around the target and a group inside it redoes them (both written at full precision), so the mask is on an element whose space is root space, the apertures' own. The target's own clip paths and masks stay on it, so they intersect. The rest render is the variant's static render, unchanged except for those wrappers and their masks. An aperture mask's path is the rest outline, filled and stroked `APERTURE_REACH` (1) screen pixel past it on each side with a non-scaling stroke, at any size the picture is drawn. The outline lies on the edges drawn around the opening, and a clip edge and a drawn edge that coincide are each antialiased against what lies beneath them, which leaves a one-pixel seam of the layer under the targets; the reach moves the mask's edge under the edges, which paint over the targets at rest as the still image draws them. The reach applies only on frames whose aperture is the rest outline. Every other frame (mid-blink, the closed keyframe, a held closed state) draws the aperture's area alone, as a clip of its outline would, so the antialiased seam can still show for the few frames of a blink: moving edges taper past the opening's corners, and on art whose closed state paints beneath the open eyes the closed lashes lie under the targets, so a reach there would show the targets past the edges. A rest outline that encloses no area (a morph that rests closed) has no stroke. A non-scaling stroke in a mask is drawn through the space of the element the mask is on, which is why that element's space is root space: under any transform around the target, scaled, skewed or rotated, the reach is the same. The path's paint is spelled out (opaque fill and stroke), since a mask's content inherits from the artwork root rather than from the masked drawing. Drawn inline, as the player draws a live portrait, the reach is one device pixel; drawn as an image (`rest` in a hover, preview or CSS mask), it is one pixel of the artwork's own size, scaled with the image. The mask's region is the apertures' bounds grown by their own size.

Frames are sampled at `MORPH_BAKE_SAMPLES` (8) evenly spaced progress values, the geometry package's tuning point, and mapped into the moving element's own user space so a player sets its `d` directly. A segment that moves the same drawings back reuses the earlier segment's frames and apertures reversed; geometry lives in the artifact's `frames` and `apertures` tables and transitions point into them.

## Playing an artifact

`render.ts` draws an artifact at any pose as one SVG and is the executable statement of these rules; a live player follows the same ones.

- Parts paint bottom to top and overlay exactly (they share the root's view box and sizing). Static parts never change. A player drawing several inline copies of a live part gives each copy its own id prefix with `namespaceMorphMarkup`.
- A live part's markup is the rest pose: leaves another state shows carry an inline `display: none`, so the parts composed as written match the rest render. A player shows and hides leaves through that inline declaration. Nothing outranks it: a live leaf carries no inline `display` or `display` attribute of its own (art the author hid is no leaf), and artwork carrying a style sheet is never baked live. At a keyframe, a group shows the leaves `visibility[group][state]` lists and hides its others; leaves outside every group are always drawn.
- Progress arrives already eased by the morph's timing; nothing here eases again. Within a segment, a frame blends its two nearest samples linearly, from the last sample backwards when the geometry reference is `reversed`.
- At either end of a segment the authored drawings show as they are, never their sampled frames: the start pose is the `from` leaves' own geometry and the end pose the `to` leaves'. A live part writes every drawing exactly as authored (a path's `d` with its relative commands and arcs, a basic shape as the shape it is), so the parts draw what the rest render does; a basic shape that moves draws its frames on a carrier written as the equivalent `<path>`, so a player can set its `d`.
- `morph`: between the ends the `draw` leaf takes the blended geometry, and at the end the `to` leaf's own drawing takes over, so a destination several tracks share is drawn once. A moving drawing paints at the depth its layer has in the variant's rest pose, the pose the static image shows, in both directions, so the live layer order always matches the still: `draw` is whichever of `from` and `to` the rest pose shows, and `from` when it shows neither. One element carries one shape, so where several tracks draw on one drawing (two open lashes converging on the closed lash a variant rests on), the second and later tracks draw on carriers: hidden copies of that drawing written right after it in its part, with no ids, which no state shows. Every track of a basic shape draws on a carrier, written as the equivalent `<path>`, so the shape's own markup is never replaced. `fade` multiplies the leaves' own opacity, read from the inline declaration that takes effect when they have one, since that outranks the attribute, and written back inline, important when that declaration was; `cut` holds `from` until the end; `scale` follows its frames on its `draw` leaf (the drawing itself, or a path carrier for a basic shape), is invisible at its zero endpoint and is the authored drawing at its full one; `hold` stays drawn.
- A clip entry's aperture in a segment is that segment's `apertures` entry, written into every aperture mask `clipTargets` lists for the entry; outside its segments an aperture keeps its last pose. An aperture written with anything but its rest outline drops the mask's stroke (`poseAperture`), so its reach past the outline applies at rest only.

`morphFrameState` is these rules as data: for a pose of every driven group it lists the leaves that show and hide, the path data a moving leaf takes, the factor a fading leaf's opacity is multiplied by and the path data of each aperture mask, and leaves everything else to the markup. `renderMorphFrame` and `renderMorphAt` draw it as one SVG; a live player applies it to the parts it keeps on the page with `poseLeaf` and `poseAperture`, starting each leaf and mask path from its markup every frame.

## Timing

A morph's timing is not in its recipe or artifact, so retiming bakes nothing again. A player schedules each occurrence with a `MorphTimeline` (`timeline.ts`): the first play starts after `delay`, each later one after a quiet gap drawn uniformly between `iteration_delay_min` and `iteration_delay_max` (none without bounds), and `iterations` counts the plays. The timeline answers where an occurrence is at a time: waiting for its first play (drawn at rest), partway through a play, in a gap holding the end pose of the play before, done holding the terminal pose of a finite sequence, or off (`iterations = 0`). Each occurrence draws its gaps from its own seeded stream (`morphRandom`), so a seed reproduces a schedule and two occurrences never share one.

A play's progress is directed (`reverse` and the `alternate` directions run some plays backwards) and then mapped once through the morph's `easing` (`easing.ts`, the CSS timing functions `easingProblem` accepts, `steps(3)` being `steps(3, end)`). The result is a keyframe offset, and `morphPosesAt` finds each group's segment at that offset and its progress within it: nothing eases a segment, a fade or an aperture again.

## Playing in the web player

The engine puts a morph's reference on the image write that shows its variant (`UIModule.getMorphContent`): the reference, the morph's timing with its defaults, an identity of its definition (recipe and timing) and the image's place among the write's images, counted in the CSS it paints them with (`cssList.ts`), so a literal listing several images keeps the count. A write carries references, never artifacts, so it stays small and its JSON deduplicates as before; a write with no morph on its images carries nothing new. A reference with no asset service behind it (inline art, as VS Code and local compiles carry it) names art only the program holds, so the game bakes it with `inlineMorphSource` and sends the page the artifact once per key and connection (`morph/artifact`, plain JSON as an asset service's response is). An image two morphs play on stays still and the game warns, since each artifact draws the whole image and declaration order is not the author's choice of which one plays.

The page's `MorphPlayback` (`spark-web-player/src/app/morph/`) belongs to the overlay and outlives the UI managers a re-render swaps in. For each written background layer it resolves the references through its host (the asset service named by `ref.src`, as the web editor's service worker is, or the artifact the game sent) and keeps the static image the write put up while they are pending, and for good if they fail. Once one is ready the layer is drawn in a shadow root: each image in paint order, static ones as CSS backgrounds with the layer's own size, position and repeat, live ones as the artifact's parts inline, each copy with its own id prefix, placed on the rectangle CSS would have drawn the static image in (`backgroundFit.ts`), from the span's fractional padding box and snapped to device pixels as the browser snaps a background image. The placement is taken again when the span resizes and after every screen op, since a style or class change can move the image without resizing the span. A mask shows the artifact's rest render in place of its static image and never moves.

A morph's phase belongs to its logical occurrence, not to the span drawing it: the target and content element, the image's place in the composition, the character, the morph and its definition, and the engine's epoch, which loads, restarts and resets advance. A compatible write (another expression of the same character) or a reconciling re-render draws the same occurrence at the same phase; the outgoing layer of a crossfade freezes on its last frame until its fade ends and is then released with its artifact references. A different character, an edited definition, a new epoch, a new PLAY session, previewing another place and time stepped backwards start occurrences again at rest. Phase is never saved.

During PLAY the application's clock drives playback, so pausing the story freezes every morph on its exact frame and stepping the clock moves them. A stopped preview never starts that clock; playback runs on animation frames of its own instead, which advance nothing in the story. The `Animate portraits` preference (`game/setAnimatePortraits`) returns every morph to rest and keeps it there, paused or not; turning it on starts each one on a fresh cycle. It holds for artifacts still pending too. `MorphPlayback.preempt` holds an occurrence at rest until released and then resumes its schedule where it stopped, the seam a later explicit transient behavior takes a portrait over by.

## Diagnostics

A bake reports what it could not do as `MorphBakeDiagnostic`s with the morph, layer and element they concern; their `uri` and `variant` name the consumer the bake ran for. Several consumers can share one artifact key (the same art in two files, two names for one selection), so the language server bakes each key once and publishes its diagnostics on every artwork whose reference has that key, through the existing asset diagnostic delivery and merged with the compile's own. Each problem shows once per artwork, naming every variant it affects. A drawing pair that fails in one segment and again in the segment that moves it back is one problem. Declaration problems stay on the morph block, where compilation puts them. Intentional one-sided art, `blend = cut` flipbooks with no pairs, and a closed-eye aperture of zero area are not reported.

## Limits

- One morph's rest apertures per preview: a variant two clipping morphs play on previews with the first one's.
- A pairing unit is one drawn element. Art that splits one shape across several elements with different paint pairs element by element.
- Text, images and `<use>` instances inside state layers fade or cut; they have no geometry to morph or scale.
- A shape whose geometry the bake cannot read exactly (a length in a unit other than `px`, such as a percentage of the viewport, or an inline style setting a geometry property such as `r` or `d`) has no geometry either: it fades or cuts with an `unsupported-element` warning, and its parts keep it as authored.
- A reference to drawn art (a `<use>`, or a clip path, mask or pattern that uses it, from a part's own drawings or the groups kept around them) keeps the variant static, with an `unsupported-element` diagnostic, when the morph would split the referenced art between the referencing part and another, or when the referenced art is a state layer or clip target in another part, where the copy could not follow it, or when it holds a drawing that moves on a carrier (a basic shape, or a drawing several tracks draw on), which is hidden while the reference still names it. Unchanging art is copied whole, even when a compositing group keeps it in a live part. The check counts what a copied resource's original ancestors reference even where the resource overrides that property, so it errs towards the static render, never towards a copy that stands still.
- Artwork carrying a style sheet keeps its static render, whatever its rules say; inline `style` attributes and presentation attributes are the styling a morph can play.
- A `transform-origin` attribute, or an inline style setting `transform`, `translate`, `rotate`, `scale`, `transform-origin`, `transform-box` or an `offset-*` property, moves a drawing in a way the bake does not follow: the drawing fades instead of moving, and a clip target under it disables the morph, each with an `unsupported-transform` diagnostic. Only `transform` attributes are mapped.
- Drawings and clip targets inside a nested `<svg>` viewport are not mapped; a drawing there fades instead of moving, and a clip target there disables the morph, each with a diagnostic.
- A live layer is placed by its computed `background-size` and `background-position`; a repeating layer, or a size or position the player cannot read, keeps its static image.
- A live layer drops its parts' scripts, embedded documents (`iframe`, `object`, `embed`), event handler attributes and `javascript:` links, which a CSS background image would never run. Other external references in the art load as they would in any inline SVG.
