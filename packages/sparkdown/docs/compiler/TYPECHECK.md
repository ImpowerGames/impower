# Type checking

Sparkdown type checks Luau code with a port of Luau's own type checker, the "new solver", in `src/compiler/typecheck/`. The port follows Luau at commit `7d5f73364fdbbaa984fa545071630eba73cfea98` (the commit `src/tests/luau-conformance/upstream/typecheck-cases.json` pins), configured as Luau's CI runs the new solver: every flag whose name does not start with `Debug` or `Test` is on. Each file is named after the Luau file it ports (`ConstraintSolver.cpp` is `ConstraintSolver.ts`) and says so in its header; `LICENSE-luau.txt` in that directory holds Luau's license. Its types print exactly as Luau's `toString` prints them, and its warnings carry Luau's messages, so Luau's own tests are its specification (see `src/tests/luau-conformance/typecheck/README.md`).

## What is checked

The checker reads the Luau AST that `readLuauAst.ts` builds from Sparkdown's syntax tree, the tree the editor highlights, so the checker and the highlighter read the same text as Luau. The converter reads the tree's Luau tokens the way Luau's parser reads Luau text, because the tree keeps operators as flat chains and types without precedence while the checker needs Luau's own tree, locations and name resolution; `src/tests/compiler/luauTreeAst.test.ts` checks that it builds the AST Luau's parser builds. Positions are the document's own, counted in UTF-16 code units. Builtin definitions are prepared JSON ASTs, generated at build time by the pinned official Luau parser and decoded into checker nodes by `DefinitionFile.ts`. The compiler does not load that parser or parse definition text at runtime; see [`scripts/DEFINITION_AST.md`](../../scripts/DEFINITION_AST.md) for generation and the internal definition API.

- A `.luau` file loaded with `run` is one module.
- A `.sd` file is checked in units: its prelude (the Luau statements outside any scene or branch, and every `function` definition, which Sparkdown lowers to a file-level function wherever it is written) and one unit per scene, or branch outside any scene, that holds Luau statements. A flow is checked as the body of a function whose parameters are the flow's, with the prelude's names and type aliases in scope at the types the prelude's check gave them.
- A branch inside a scene runs in its scene's call-stack element, where the scene's locals and those its other branches set are visible, so it is checked as part of its scene's unit, in document order, with its named parameters declared as a `local` on its header line, each holding a value of type `any` as an argument does (so one without an annotation is `any`, not `nil`). At runtime `...` reads the arguments of whichever of the scene and its branches took a `...` last, so the unit's function takes `...` when the scene or any branch in it does, with the type they all give theirs as written, or no type where they differ.
- A parameter list whose text is not a Luau parameter list, because the grammar ended it early (a `...` inside a parameter's function type does, #876) or it is not yet closed, is read as the runtime binds it: the names the list holds, each typed `any`, and `...` if one is in it. A list whose text is Luau's keeps its annotations, whatever follows it in the header.

Narrative is left out: where story stands between two Luau tokens, the statement before it ends there, as it does at the end of the unit's Luau. The parts of a Luau line that are Sparkdown's own are nodes of their own in the AST (`AstStatSparkdown*` and `AstExprSparkdown*` in `Ast.ts`), which the checker reads as `SparkdownReading.ts` says: a statement marked with `&` as the statement; a `store` declaration as an assignment of its values to its names; a `choose` block as the statements among its choices and in its `then` clause, which run in its flow's scope. Sparkdown's own expressions (alternators such as `plural(n)|one="is"|other="are"`, divert targets such as `-> place`, regular expressions such as `@/a+/`, and `new`) are values of type `any`, so the statement that holds one is checked as written around it, and a `new`'s arguments are checked; a double-quoted string that interpolates (`"{x}"`) is a `string`. A divert-target type (`-> place` where a type stands) is `any`. A branch parameter's initial value is `any`.

Every unit sees Luau's builtin globals (Luau's builtin definitions, loaded as Luau loads them) and, typed `any`, every name the program declares in Sparkdown (scenes, branches, defines, stores, functions in other files) and the namespaces Sparkdown's runtime adds to Luau's standard library, such as `count`. Each of those names is a type as well, since a define declares one, so `c: companion` needs no Luau declaration of `companion`.

`LuauDocumentChecker.ts` turns a document into units and checks one; `SparkdownTypechecker.ts` holds the environment and the cache; `SparkdownCompiler.validateTypes` runs them after the program's context is built.

## Modes

As in Luau, a module is checked in one of three modes: `nonstrict` (the default), which reports what is certainly wrong; `strict`, which also infers the types of unannotated code and reports every mismatch; and `nocheck`, which reports nothing.

- The project's mode is `config.typecheck.mode`. `builtins.sd` defines it as `"nonstrict"`; a project changes it with `define typecheck as config with mode = "strict" end`.
- A `.sd` file's `typecheck:` front matter field sets that file's mode. It is not shown on the screenplay's title page.
- A `.luau` file's `--!strict`, `--!nonstrict` or `--!nocheck` first line sets that file's mode, as it does in Luau. Neither the web editor nor the VS Code extension registers `.luau` files as scripts by default (both use `*.{sd}`), so this applies where a host registers them.

The more specific setting wins. A mode Sparkdown does not know in the config or the front matter is warned about where it is written (`UnknownTypecheckMode`), and the next setting applies. In a `.luau` file, a `--!` directive Luau does not know, a mode directive with more on its line or given twice, and a directive after the first token are warned about as Luau's linter warns about them (`CommentDirective`, from the part of Luau's `lintComments` that `Linter.ts` ports), and Luau's rule applies: only an exact mode directive before the first token sets the mode. A `--!nolint` does not silence these warnings, since Sparkdown has no lint suppression (see `LINTS.md`).

## Diagnostics

Every type diagnostic is a warning whose `code` is the Luau error kind (`TypeMismatch`, `UnknownSymbol`, ...), with Luau's message as plain text (a printed type such as `<T>(T) -> T` is not markdown) and its exact range. Luau counts a column in UTF-8 bytes; the checker counts in the document's UTF-16 code units, in its ranges and in a message that names a column (`to close '(' at column 8`). Syntax is the grammar's to report, so the converter's syntax errors are not shown, with two exceptions, which are reported as errors with the code `SyntaxError`, Luau's message and its range. The first is a type that is missing or cannot start with the token where one must stand, an annotation written with `::`, and an annotation with no name before it (`Expected type, got '='`, `Expected identifier when parsing expression, got '::'`, `Expected identifier when parsing variable name, got ':'`, `Expected identifier when parsing table field, got ':'`). The second is an expression that is missing or cannot start with the token where one must stand (`Expected identifier when parsing expression, got 'local'`, `Expected expression after ',' but got ')' instead`), a member access with no name after its `.` or `:` (`Expected identifier, got '='`, `Expected identifier when parsing method name, got 'end'`, `Expected '(', '{' or <string> when parsing function call, got 'end'`), a function value with a name (`Expected '(' when parsing function, got 'named'`), and a statement that is a value but not a call (`Incomplete statement: expected assignment or a function call`, `Expected identifier when parsing function name, got '('`). The grammar reads a type or an expression only far enough to find where it ends, so it has no point at which it expected one; Luau's parser has one wherever a type or an expression can stand, and so does the converter. The converter marks each of these errors with what it finds malformed (`LuauSyntaxError.malformed`: a type, an annotation, an expression or a statement), and the checker reports the marked ones and no others.

What is reported is one error per mistake: one error for each malformed construct, and every independent mistake its own error; an error that Luau's parser reports only because it is recovering from an earlier one is not reported. That is the specification, and the tests in `MalformedExpressionAtEveryPosition.test.ts` pin it. Luau's parser recovers from an error by reading a new statement from the token after it, so the converter, which reads as Luau's parser does, leaves an error unmarked when it follows from an earlier one through that recovery:

- an error at the first token of a statement that begins on the line where the statement before it stopped at its error, with no `;` between (`x + 1` is an error at `x`, then at `+` and at `1`; `t.a.return 1` is an error at `return`, then at `1`; but `print(1, ) 1 +` reports both errors, as the call reads its `)`), or of a statement whose block begins where its holder stopped at an error (`function f(): ?number end` is an error at `?`, then at `number`; but in `if 1 + then x + 1 end` the reading finds `then`, and the error at `x` is the author's own), or whose holder began in such a recovery, on the holder's line;
- every later error in a statement whose first error is at its first token, which Luau's parser reads on as a call or an assignment (`{1 +}`, `'a' ..`, `, 2`);
- an error a statement's earlier error leads to, which Luau reports from the same token or an earlier one (`Incomplete statement` from `t` after the missing name in `t.a.return 1`);
- an error at the closer of a bracket the reading gave up on, or between the bracket and that closer where it stands where a statement must begin, which the reading then skips (`print((1 + local y = 2)` before a line `)` reports only the error at `local`).

An error further into a statement the reading began after a recovery is the author's own (`t.a.return x = 2 +;` reports the missing name at `return` and the missing operand at `;`, and `local a = 1 +` before a line `local b = 2 +;` reports both). Where Luau's parser reports one token again as it recovers, the token is reported once, with the first error.

Where the tree ends a statement, so does the reading, and what the statement lacks there is Sparkdown's own syntax's to report: at story between two Luau tokens, at a scene's `end`, and before a statement the tree begins on a new line that Luau's parser could read on into, one that begins with a name (`x = 6`, `goto done`, `type T = ...`, `const c = 1`, `define ...`) or with `function` and a name (`STATEMENT_BREAKS` in `LuauUnitNodes.ts`). The validator and the lowerer report a missing expression themselves exactly where the checker does not read on to the token after it (`checkerReadsOnTo`): where the checker does not read the Luau (a `store` declaration), where the tree ends the statement first, or where the token found is a `:` at the start of an assigned value or an if expression's arm, the `::` of a cast or the `:` of a method call with nothing before it. An error in a `store` declaration or at a token that is Sparkdown's own (`&`, `store`, `choose`) is Sparkdown's to report. A type that story ends before is the checker's to report, as at the end of the unit's Luau: `Expected type, got <eof>`. An error at the end of the Luau a unit holds (`got <eof>`) ends at the start of the next line, as Luau's does at the end of a file that ends with a line break, and so does a missing type whose line ends before the token found instead (`local w:` before a line `local z = 1` is `0:8-1:0 Expected type, got 'local'`): the range covers where the type should stand, not the token on the later line that Luau's range runs to. An error at a label (`::name::`), which Sparkdown adds to Luau's syntax, is not reported. Unlike Luau's parser, the reading does not end a block at a `return`, `break` or `continue`: Sparkdown reads the statements after one as its block's, never run, and the unreachable-code lint reports them (see `LINTS.md`). The validator reports a malformed type only where the checker does not read the Luau: in a scene's or branch's parameters and in Sparkdown's own constructs, such as a `store` declaration, with the message and range the checker would give there (a `::` after a parameter's name is `Expected ')' (to close '(' at column 8), got '::'`, and a type missing before a line of story is `got <eof>`). The checker leaves out its `Unknown global` warning where Sparkdown's own resolver reports the name (``Cannot find variable named `x` ``) at a range that holds the read, so a read is reported once. The resolver does not yet report a read in a `local` statement in a scene or branch (#992), and there the checker's warning is the report; a top-level `local` whose initializer reads an unknown name is reported by both, the resolver's warning at the start of the document, until the resolver places it (#992). Checking never changes the compiled program.

## Incremental checking

Each unit's result is cached under its document, its key, its mode and what it can see: the names the program declares, and for a flow the check of its file's prelude, which is its only view of the prelude. The converter reads each unit in its own lines (`ReadOptions.unitLines` in `readLuauAst.ts`): the lines that hold its Luau tokens, numbered from 0, with the document line of each kept beside it, so a unit's AST is the same however many lines of story, or of other units, stand between its statements, and whatever they say. A unit's key is read from its tokens: each token's kind, text and position in the unit's lines, where story or the tree ends a statement, where the reading starts and, for a `run` file, where its Luau ends; a comment other than a `--!` directive is not part of it. An edit checks again only the units whose key changes, unless it changes the prelude's key, which checks every flow of that file again, or changes the names the program declares, which checks every unit again. A result depends on nothing else, so a check that reuses results gives exactly what a check from scratch gives (`src/tests/compiler/typecheckIncremental.test.ts`).

## Limits

- A name another file declares is `any`, whatever its declaration says.
- Sparkdown's own constructs (defines, scenes as values, diverts) are not typed; annotations inside definitions are not read.
- The Luau inside Sparkdown's own constructs (an alternator's subject and arms, such as a `match`'s, a divert's arguments, the statements of an alternator block) is not checked.
- A malformed type annotation is reported only where its type cannot begin (see `docs/runtime/DIVERGENCES.md`).
