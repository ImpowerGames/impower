# Plan actions

The observation file `plan` reads is `{ "sessions": { "<id>": { "state": "running|idle|archived|absent" } }, "tasks": { "<id>": { "state": "running|completed|failed|stopped|<other>" } } }`, written from what your runner reports.

`plan` gives every ticket one action with its reason, and reports beside them the wake sweep (`sweep`: the transcripts to read, the running writers not read, and reviewer launches that died before their journal) and the periodic check-in (`checkIn`), as [writer reports](writer-reports.md) and [starting a run](start.md) describe. Act on each ticket as follows.

| Action | Meaning and next step |
| --- | --- |
| `dispatch` | Every blocker's merged deliverable is on origin/main and capacity allows a writer on the named route: claim and start it. |
| `wait-dependency` | The reason names each blocker that is open or closed without its merged deliverable on origin/main, or the parent ticket whose own writer is still held. No stacked branches: wait for the merge or for that writer to be settled. A start already recorded under a held parent stays recorded. |
| `wait-handoff` | A planned handoff stopped new dispatch: nothing starts, nothing is opened, no brief is resent and no existing work is continued until the next coordinator plans, as [checkpoints](checkpoints.md) describe. |
| `wait-capacity` | Writers already hold the concurrency limit, or free disk admits no further writer now (consider the bounded disk recovery; the next plan admits writers against the disk it frees). |
| `adopt-pr`, `adopt-worktree` | Work for the ticket exists: find its writer and record it with `adopt`; a writer adopted by its process takes `--session <id>` as well, since a process alone does not say which session wrote. Never start a second writer beside it. Once its writer is known to have ended, `claim --operation continue --evidence` starts a new writer on the route the entry's `continueWith` names, keeping the branch, worktree and the PR's started rounds; `continueBlocked` says why no route can. On a ticket that gained sub-issues, the existing work also holds those sub-issues until its writer is settled, and is never continued. |
| `answer-request` | The writer asked for a decision whose answer has not been delivered: decide or `relay` it, record `answer` and send the message it prints, then record `answered`, as [writer reports](writer-reports.md) describes. A detached CLI writer whose turn ended gets the answer by `resume`, with the printed message as the prompt. |
| `update-contact` | A coordinator before this one briefed the writer, which still reports there: record `contact`, send the notice it prints, then record `contacted`, before any brief resend reaches the writer. An open request is answered first, since the answer carries the same contact line. |
| `settle-delivery` | The writer has not acknowledged its brief within one check-in interval: the delivery failed or the coordinator id was wrong. Settle it now as the wake routine in [writer reports](writer-reports.md) describes, never by waiting. |
| `observe` | The owner is running. |
| `collect-report` | The owner ended its turn: read its report or question from its transcript and answer it. A detached CLI writer whose turn ended with no report recorded since its last start may have stopped on a wait: record its report with `result`, its request with `request`, or `resume` it to continue the work it left. |
| `reconcile-pending` | A recorded start has no confirmed outcome: settle it with `reconcile` (a detached start, found by a process naming its launch directory), `launched` or `withdraw --evidence` before any retry, as the reason says. A resent brief with no recorded outcome is settled from the writer's transcript or resent with `deliver --retry`; an open of a writer's session with no confirmed outcome is settled from the app's session list with `opened`, and a resume with no recorded outcome with `reconcile`, never by running either again. On a ready PR it is a merge or readiness change with no confirmed outcome: settle it with `checkpoint.mjs reconcile-operations` from a fresh snapshot, never by calling again. |
| `blocked-owner-unknown` | The owner's state is unknown, or a start was claimed on another host: observe it before anything replaces it. A writer or start on another host is settled only by an observation made on that host. |
| `release` | The owner was observed to end, after its final report, or on a ticket already closed: read its transcript, then release it with that evidence; an open ticket becomes eligible again. |
| `stop-writer` | The writer runs another model, effort or permission mode than requested, by its acknowledgement, its report or the preflight's observed verdict: stop it and keep its evidence. It is never relaunched on a substitute. |
| `blocked-route` | No offered route runs the writer model at the ticket's effort (a retired route is named with its reason), or the coordinator is not in bypass permissions mode: report the reasons to the user. |
| `assign-effort` | The ticket has no Effort value. Estimate one from its scope, evidence and verification work, publish it and read it back through the [issue-fields procedure](../../references/issue-fields.md), comment the value with its rationale and any material uncertainty on the ticket, and include it in your next report. Then snapshot and plan again; the ticket is admitted like any other. An existing Effort is never changed. |
| `decision-needed` | An Effort option with no writer effort, duplicate open PRs, a closed ticket without its deliverable, a held writer outside the parent issue or on a ticket that gained sub-issues, or sub-issues nested past GitHub's limit: report it with a recommendation. |
| `merge-gate` | A ready PR under an invocation that grants the merge: run `integration.mjs gate`, and merge with `integration.mjs merge` only when it admits the head, as [integration](integration.md) describes. Each refusal names what to settle first. Until the record settles its writer (released, or adopted and released), that writer may still be finishing and keeps its place; the reason says so, and `adopt` records it. |
| `await-maintainer` | The run records that the maintainer merges (`--merging maintainer`, for a request that stops at ready PRs), so this ready PR waits for the maintainer to merge it, and its dependents keep waiting until its merge commit is on origin/main. Its writer keeps its place as under `merge-gate`. |
| `delivered-by` | Another slice's PR delivers the ticket. A ticket is claimed by another listed ticket when that ticket's open or merged PR on its own branch closes it, or when its body names it with a closing keyword as `#N`, `owner/repo#N` or the issue's URL, outside HTML comments (a reference to another repository than the tickets repository names nothing); a claim by a container or by a ticket that is itself delivered or contested delivers nothing and plans the claimed ticket as `decision-needed`, a claimed ticket delivers none of its own sub-issues, and a claim on a container plans that container as `decision-needed` while its sub-issues are planned individually; a delivered ticket's own undelivered blockers hold its deliverer at `wait-dependency`, and only its deliverer's merge completes it or admits its dependents; a PR claim outranks a body claim, so a slice whose own PR closes its sub-issue keeps it whatever a sibling's body says. A Task or Feature slice whose sub-issues are all Bugs, none resolving to another ticket's claim or to a conflict, delivers them; an umbrella whose Bugs other slices claim is a container, never dispatched for them. A delivered ticket is never dispatched, never counted as a writer place and never merged on its own; it becomes `done` once the deliverer's merge commit is on origin/main and GitHub has closed it. The slice's entry lists what it delivers under `delivers`, and its brief asks the writer for a closing reference to each. The brief fixes that list when it is printed, so a Bug re-parented under the slice afterwards has no closing reference in its PR, stays open when the PR merges and plans as `decision-needed`; [slicing](slicing.md) never adds a Bug to a dispatched slice. A ticket with a PR of its own is always its own slice; a closed, unmerged PR delivers nothing; two slices whose PRs both close a ticket, or a deliverer merged on main with the ticket still open, plan as `decision-needed`; a writer, pending start or worktree on a delivered ticket plans as `decision-needed` or `adopt-worktree`, keeps its place, and holds the deliverer at `wait-dependency` until it is settled. |
| `done`, `container` | Delivered, or planned through its own sub-issues. Once every ticket is `done` or `container`, verify the parent issue as [integration](integration.md) describes. A sub-issue closed as completed before the run began (its first coordinator's start), with no open or merged PR of its own and no writer, pending start or worktree, is `done` as history, "closed before the run, delivered outside it", and so is a closed Bug such an umbrella carries; it holds no writer place, is never dispatched, counts as a delivered blocker for the tickets that wait on it and does not count against verification; its closure reason and time are part of the scope the final gate compares, so a reopen and close during the run stops the gate. A ticket the run saw close without its deliverable, or one closed as not planned, stays `decision-needed`. A closed ticket whose worktree remains here and whose writer the record has not settled keeps that writer's place, as the reason says: adopt and release the writer, or remove the merged worktree through clean-worktrees. |

An adopted writer is recorded with the model and effort it actually runs, and verified against the ticket's Effort, so a mismatch plans as `stop-writer`. An owner's state comes from the observation file for sessions and tasks. A detached writer on this host is live while its recorded wrapper runs or while any process names its launch directory, which the writer carries on its own command line; a failed process census, or a process recorded on another host, leaves it unknown.
