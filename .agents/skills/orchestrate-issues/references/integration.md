# Integration and the parent issue's completion

The commands are `node .agents/skills/orchestrate-issues/integration.mjs <command>`; `merge`, `verify-issue` and `close-issue` take `--record`, `--coordinator` and `--expect-revision` like the run helper's.

## Who merges

`init` and `resume` record who merges, beside the quoted request: `--merging coordinator` when the user explicitly asked to orchestrate the parent issue, `--merging maintainer` when the request stops at ready PRs. The helpers refuse a coordinator grant whose quoted request asks to stop at ready or not to merge, and a record without the decision leaves merging to the maintainer. A later request in the coordinator's own session is recorded the same way by running `init` or `resume` again with it: the record then quotes that request, who merges follows it, and `resume` saves the change to the state branch, so a request that stops at ready PRs takes the merge back; the replaced request stays in the record's log. Whether a message is a request at all, rather than a discussion of the skill, is your reading of it: a discussion starts no run, so nothing is recorded.

## The merge gate

`gate --record <run.json> --ticket N --pr P` takes a fresh snapshot of the parent issue and reads the PR, the branch's protection, the comments of the PR's review thread (the PR, or ticket N once the run's tickets live apart from its code), the review journals, main's own push runs of the Test Suite workflow and, last, main, changes nothing, and admits the PR's current head only when every condition below holds. Otherwise it names each one that fails.

- Authority: the run records that the coordinator merges, under the grant and a quoted request that names orchestrate-issues and the parent issue; the coordinator never wrote for the ticket; and checkpoints are enabled, so the merge's intent can be saved where another machine finds it.
- Scope: the ticket is a sub-issue of the parent issue in the snapshot, not a container and not a ticket another slice's PR delivers (`delivered-by` in [plan actions](plan-actions.md), whose merge is that slice's); the PR is its one open PR, its branch names the ticket, it closes the ticket (once the run's tickets live apart, by a closing reference to the tickets repository's issue of that number, never a code repository issue of the same number), targets main, is open and marked ready, and no earlier merge of it is unsettled.
- Review: every planned reviewer of every round has exited, every launcher finished, every report is on the review thread with its adjudication, and the round audit holds, all read through the same accounting as [review checkpoints](review-checkpoints.md). From round 3 on, the decision in force is a published finish or acceptance decided at the last completed round; a question to the maintainer or a repair in force holds the merge until a later decision replaces it. Then the head is either the last independently reviewed commit, with the writer's final report recorded by `issue-run.mjs result` naming that commit and no outstanding finding or verification gap, or the head an acceptance of unreviewed corrections names, which this record published and read back. Either may be followed by clean merges of main: two-parent merges whose other parent is on main and whose remerge diff is empty. Any other commit after it, whether a correction, a non-behavioral tail or a conflict resolution, is unreviewed: the writer's next round within its limit, or a checkpoint decision on that head, settles it. Ordinary review-pr's disclosed non-behavioral exception does not admit a merge here.
- CI: every check on the head has finished, each check's latest run counts, none failed (a cancelled or timed-out run counts as failed until it is diagnosed and run again), and each required gate ran and passed. The required gates are the Test Suite workflow's `test-suite` job and whatever branch protection and rulesets require. A skipped job is reported as skipped, not as a check that ran, and a skipped required gate refuses the merge.
- Integration: GitHub reports the PR mergeable (`CLEAN` or `HAS_HOOKS`), and main's own CI is not red. The head need not contain main as the remote holds it now: requiring that made every merge into main invalidate every other waiting PR, which then re-merged main and reran its CI, so several coordinators merged one PR per CI run and the workflow's cancel-in-progress threw away half the reruns. Instead the gate records the main commit the head's CI covered (the merge base of the head and main) and admits the head, and main's push run of the Test Suite after the merge is the check on the combination that landed. A red main freezes every merge: while the latest completed, uncancelled push run of that workflow on main failed, no PR merges until main is fixed or reverted and its next run is green; a pending run on the newest main, or runs the token cannot list, hold nothing. When a branch does merge main cleanly it keeps its review, and the head then covers main again. A branch GitHub reports `BEHIND` has protection that requires an up-to-date branch, and merges main as before. A repository that requires a merge queue is left to the maintainer, since the gate does not drive one.

## Merge

Every irreversible GitHub call, the merge and the closure's report and close, goes through one final gate, `finalGate` in `integration.mjs`, and no caller orders these reads itself. It reads, in this order: from the state branch, that this coordinator still owns the parent issue and that the operation's own intent is saved there; a fresh snapshot; every premise of the call on that snapshot, including the premises' own slower reads such as CI, protection and review comments; the parent issue's scope once more, its slices with their states and then its acceptance section, which must match the snapshot; and main, last. The scope read catches a slice that left, joined or reopened, or a criterion that changed, while the snapshot and the premises were being read. The call is made only when every read holds, and it is the GitHub write alone: a lookup it needs, such as an earlier copy of the final report, runs before the gate. A read that fails leaves the call unmade and records the operation as not run, and a call that throws counts as made, since it may still land. `integration.test.mjs` checks this order and requires every reordering or removal of the five reads to fail that check.

`merge --record --coordinator --expect-revision --ticket N --pr P` runs the gate, records the merge intent with the admitted head and how it was admitted, saves it to the state branch, and passes the call through the final gate: a takeover, a scope, head or main that changed while the intent was saved or the final gate read its evidence, or a failed save, stops the merge before GitHub is called and records it as not run. The call is `gh pr merge P --merge --match-head-commit <head>`, never with `--admin` or `--auto`, so a push after the gate makes GitHub refuse it and branch protection still applies. The outcome is what GitHub reads back: merged at that head is `confirmed`, with its merge commit, the main commit it landed on and, when that is not the main the head's CI covered, that CI never ran on the combination before main's own run; GitHub's own refusal (a GraphQL error or a 4xx status) is `failed`; anything else is `uncertain`, since a request GitHub did not refuse may still land: a call that was interrupted, failed without GitHub's answer or reported success while the PR reads back open (at its head or after another push), a merge at another head, or no read-back. A merge the gate does not admit records nothing and exits 2; a recorded outcome other than `confirmed` exits 1.

An unsettled merge blocks every later merge of that PR, here or after a takeover. Settle it with `checkpoint.mjs reconcile-operations --snapshot <fresh snapshot>`: GitHub's state decides, never what the call reported, and a merge it confirms records the main commit it landed on and whether the head's CI covered it, as a merge confirmed directly does, or says that could not be read. A merge the reconciliation finds not applied is retried only through the gate again.

A merged PR's dependents become eligible once its merge commit is on origin/main, which the next snapshot reads; under `--merging maintainer` they wait for the maintainer's merge. A slice whose PR needs a correction after review goes back to its writer, whose round count continues.

## Verify and close the parent issue

Once every slice is delivered, `criteria --record <run.json>` prints the checklist in the parent issue's Acceptance criteria section: everything under that heading up to the next heading of its level or higher, nested headings included, each checkbox with its indented continuation lines. A checkbox is any list item GitHub renders as a task: a `-`, `+` or `*` bullet or an ordered `1.` or `1)` item, inside a blockquote too. Lines inside fenced code are examples: a heading there ends nothing and a checkbox there is no criterion. Check each criterion against the assembled implementation on main, using the existing regression, tooling and live-verification workflows it calls for, and write the evidence file `{ "criteria": [ { "criterion": "<exact text>", "status": "met|unmet", "evidence": ["<what shows it>"], "gap": "<what is missing>" } ] }` with every criterion exactly once. Then run `verify-issue --record --coordinator --expect-revision --evidence <file> --out <report.md>`, which takes its own fresh snapshot and reads the criteria from it.

The verdict is complete only when every slice that is not a container is closed with its merged deliverable on main, no operation is unsettled, and every criterion is met with evidence. Merged PRs with an unmet criterion stay incomplete, with the gap named. The helper refuses a criterion marked met without evidence or unmet without a gap; it cannot judge whether the evidence shows the criterion, which is the coordinator's reading, published in the report. A complete verification describes one main commit, one acceptance section (bound by its hash, so prose around the checkboxes counts too) and one set of slices: once main moves, the parent issue's acceptance section or slices change, a slice is no longer closed with its deliverable on main, or an operation (a closure of the parent issue included) is unsettled, the plan stops reporting the parent issue complete and the closure refuses until it is verified again.

The report the verification writes is the final report: each slice with how it merged (a ticket another slice's PR delivers names that slice in its row and shares its merge) (through this run's gate as reviewed completion or under a named acceptance, or outside the gate, and whether it landed on a main its own CI never covered, so that main's push run was the first check of the combination), every acceptance of unreviewed corrections the record published with its range and whether that head merged, each criterion with its evidence or gap, the incomplete work, and the next action. `close-issue --record --coordinator --expect-revision --verification <id>` acts only on the latest verification, only when it is complete and still holds in a snapshot it takes itself. It saves its intent, then passes each of its two GitHub writes through the final gate: posting the report on the parent issue (or finding the copy an earlier attempt posted) and reading it back, where a change records the closure as not run with nothing posted or closed; then the close call, where a change leaves the posted report naming a verification that no longer holds and records the closure as not run. It closes the parent issue as completed and records the state GitHub reads back: closed is `confirmed`; a close never called, because the report was not posted, or refused by GitHub is `failed`; anything else is `uncertain`, settled by `reconcile-operations` before another attempt. An incomplete verification leaves the parent issue open: report its gaps and next action.

## Limits

The gate reads the protection the token can see; GitHub's own merge state still applies the rest. GitHub offers no transaction across these reads, so a premise can still change after its last read: the parent issue's scope and main are read last, and the window that remains is those last reads and the call itself. The last read of main immediately before the call leaves only the merge call itself between that check and GitHub's merge; a main that moved in that window records the merge as not run, and the gate is simply run again, which costs seconds rather than a CI run. Since an admitted head need not contain main, the combination that lands is checked by main's own push run after the merge, not before it: a merge that breaks main is found there, freezes later merges through the red-main rule, and is fixed or reverted on main; the outcome and the final report name every merge whose head's CI did not cover the main it landed on. The gate does not drive a merge queue. Review journals that ran on another machine are not on this one, and their rounds block the gate until they are read where they ran.
