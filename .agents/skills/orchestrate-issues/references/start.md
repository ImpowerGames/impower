# Starting a run

The commands below are `node .agents/skills/orchestrate-issues/issue-run.mjs <command>`.

## Your session, mode and title

Run `init` with `--record <dir>/run.json --checkout <main checkout> --repo <owner/name> --issue <N> --harness <your runner> --coordinator <your own session id> --coordinator-model <model> --coordinator-effort <effort> --coordinator-mode <permission mode> --slug <words> --invocation "<request>" --merging coordinator|maintainer`, adding `--writer-model` and `--concurrency` when the request names them. In Git Bash, prefix the command with `MSYS_NO_PATHCONV=1` so a request that begins with a slash reaches `init` intact; `init` refuses one the shell has rewritten into a drive path.

- `--coordinator` is your session identity, read as the [runner notes](../../RUNNERS.md) describe: a Claude desktop session's `local_<uuid>`, or a Codex thread's bare `<uuid>`. `init` validates that identity; it is not necessarily a message address. Writers on a title-addressed route resolve the recorded coordinator title through the runner's session listing and send to that title, using its listed ref to distinguish matches. Missing, renamed or ambiguous titles stop delivery for coordinator reconciliation; writers retain the session id and host as identity cross-checks. Briefs, resends, answers and takeover notices carry the same contact instruction.
- `--coordinator-mode` is the permission mode you run in now; a Codex coordinator records `bypassPermissions` only when it runs with approval policy `never` and the `danger-full-access` sandbox, its equivalent. The plan dispatches nothing until it is `bypassPermissions`, because writers launch in your own mode and writers on agent-launch tooling need bypass. Running `init` again in the same session records a switch.
- `--slug` is two to four lowercase words from the parent issue's title, joined by hyphens, as a resolve-issue branch slug is. `init` records your session title `ORCH #<N>: <slug words>`, and the title hook then refuses shell commands until you rename the session to exactly that title, as the runner notes describe. A coordinator resumed on a session that already carries the title is not asked again, and a takeover keeps the title the record holds.

`init` resolves the writer model, sets the concurrency bound and refuses a second coordinator for the same parent issue; continue in the one it names, or ask the maintainer. It prints `dispatchBlocked` while your recorded mode holds dispatch.

A writer launched as a native child reports through its native collaboration capability to the parent task address supplied at launch, after confirming the parent identity. That address is distinct from the desktop thread UUID and title. An app writer outside that native tree uses the transcript fallback. A separate CLI process has no verified route into the native tree and retains its transcript fallback. The runner configuration supplies each route's concrete contact mechanism.

`plan` and `claim` sample the host for new writer dispatch. Detached `launch` checks again before creating the launch directory and starting the process. For an external app or native start, run `start-check --record <run.json> --coordinator <id> --expect-revision <revision> --ticket <N> [--observations <file>]` immediately before calling the runner's spawn operation. Use the returned assignment only for that pending start. `launched` records the outcome after the spawn. If admission refuses, keep the pending intent and follow the existing reconciliation or evidenced withdrawal steps before retrying.

The memory budget leaves 1.5 GiB of available physical memory and budgets another 0.5 GiB per proposed source writer. Windows and strict Linux overcommit mode also leave 4.5 GiB of commit headroom and budget another 0.5 GiB per start. Windows measures commit limit minus committed bytes. Linux modes 0 and 1 use the physical budget because the commit counters do not impose the strict limit in those modes. On other hosts the plan reports the physical free-memory sample and whether direct commit is available. This budget covers source writer dispatch. Tests, reviews, installs and browsers retain their own admission rules.

The host's writer places are its total physical memory at 2 GiB per writer, rounded down: a 15.8 GiB host has 7 and a 31.1 GiB host has 15. `init` records that count as the run's concurrency bound unless `--concurrency` names one, and a resumed run keeps the bound it recorded until a takeover records a new one. The same count is the machine-wide limit: every admission check samples the host's total memory and refuses a start while the writers executing or pending across all runs on the host fill it, beside the available-memory and commit budgets above. Writer places are independent of the 8 machine-wide reviewer slots and the 3 test-suite reservation slots, at most 2 of which serve writers. Writers beyond those slots start and work, then queue on the slots during review and tests.

Before an external follow-up starts a new turn for a retained native writer, use the same `start-check` with `--assignment <existing launch UUID> --observations <file>`. Capture a fresh observation under the exact task or session handle. Include `state` (completed for a task, idle for a session), `host`, `assignment`, current run `revision`, and the runner-confirmed `model`, `effort` and `permissionMode`. Run the check immediately before the external follow-up and use only its returned handle and assignment. This read-only check preserves the existing owner and answer. Follow the normal answer delivery and reconciliation steps around the actual send.

For a native owner recorded by `adopt` without a launch UUID, pass `--owner-handle <exact task or session handle>` in place of `--assignment` and omit `assignment` from that handle's observation. The owner stays scoped to the specified run, revision, ticket and host, and the check returns its handle. A claimed owner still requires its assignment UUID.

Pass `--observations <file>` to `plan`, `claim` (including continuations), detached `launch` or `resume`, and external `start-check` when you have current runner evidence. Refresh the run-scoped observations before each boundary. Without a current observation, native execution remains unknown and admission falls back to measured resources alongside known load. Detached `resume` checks admission both before recording intent and after saving it. A refusal after the save records that no spawn ran and preserves the previous owner for a later attempt.

Admission uses observations and existing run records. Different coordinators can sample the same spare resources before either allocation appears. The external runner can also start after the sample has changed. The per-run revision guard protects record updates. There is no atomic machine cap across coordinators or across the external spawn boundary.

## Two repositories

A run works across the repositories `.agents/repos.json` names, at the position its cutover switch has when `init` runs, and keeps them until it ends. Pull requests, CI, protection, merges and writers' branches are always in the code repository, which `--repo` names. The parent issue and its slices, their dependencies, Effort and comments, each PR's [review thread](../../references/publishing.md#the-review-thread), the status comment, checkpoint decisions, the final report and the state branch with the run record are in the tickets repository: the code repository while the switch is off, and the internal repository once it is on, which `init` then records beside it. Once tickets live apart, a ticket's PRs are the shared account's PRs whose head branch names it (`<type>/<N>-`, with or without a prefix); a search for its number only narrows the list. The coordinator pointer is then keyed by the internal repository, so an internal issue never meets a code repository issue of the same number.

## The periodic check-in

The coordinator checks in every 30 minutes whether or not a writer messaged it. Writers message at every decision point; the check-in catches a message that was lost and a writer that died. The interval follows from the prompt cache, which lasts an hour: the scheduler fires a recurring job up to 10 percent late, so an hourly job can miss the cache and re-read the whole context at full price, which costs more than the two cheaper check-ins it replaces.

`schedule --record <run.json>` prints the job: its cron expression, its prompt (the wake routine in [writer reports](writer-reports.md) against this record) and the capability of your runner that creates it. Create it, then record it with `check-in --job <id>`; a runner with no scheduling capability records `check-in --none <reason>` and runs the wake routine at the start of every turn instead. The record keeps the job, its expiry and the `schedule` command, so a resuming coordinator recreates the job with that command. `check-in --job` also records the runner process that armed the job and whether the runner confirmed tracking it, or that the runner offers no confirmation; the runner configuration (`checkIn` in `.claude/writer-defaults.json`) says how both are observed and how long the runner keeps tracking a job. Each plan reports the job under `checkIn` as `missing`, `recreate` (after a takeover), `expired`, `rearm` (armed by an earlier runner process, or longer ago than the runner's tracking window), `unconfirmed` (the runner has not confirmed tracking it), `unidentified` (the runner process cannot be identified, so a restart cannot be ruled out) or `scheduled`, with the next step for all but the last. A runner may stop protecting a job its process still fires, so a coordinator re-arms on `rearm`, `unconfirmed` and `unidentified` by removing the job, creating it again and recording the new one. Every check-in ends by recording what it did with `checked-in --outcome "<what it did>"`, or `--outcome "no change"`.
