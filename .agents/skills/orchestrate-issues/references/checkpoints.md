# Checkpoints, handoff and resume

The run record lives on the coordinator's machine. A portable copy of it is published as checkpoints on the parent issue's state branch, `orchestrate-state/issue-<N>` in the tickets repository (the code repository while the cutover switch is off; the internal one, through a remote of the checkout whose URL names it, once the record names it), and one status comment on the parent issue links the exact checkpoint commit. A coordinator on any machine, account or harness starts from the parent issue number alone. The commands below are `node .agents/skills/orchestrate-issues/checkpoint.mjs <command>`. A run started under the skill's previous name keeps its `orchestrate-state/feature-<N>` branch and its version 1 checkpoints as history: `discover`, `resume` and the other commands refuse such a run, naming the last commit before the rename, and that run is continued from a checkout of that commit with its own helpers.

## What a checkpoint holds

Each checkpoint commit holds `checkpoint.json` and `brief.md` (the takeover brief), and its first parent is the previous checkpoint. It is pushed without force, so Git refuses an update built on a checkpoint that is no longer current. GitHub stays the authority for issue state, PR heads and bases, review comments and adjudications, CI and published decisions: the checkpoint carries only what GitHub cannot hold, namely coordinator ownership, each start's intent and confirmed outcome, writer and process identities with the host each runs on, worktree, review-job and artifact references, recorded writer reports, intended operations on PRs, references to decisions published on PRs, and an inventory of each writer's work on its host (whether its head is pushed, whether files are unfinished, a stale handoff lock, its PR's review jobs with their planned and completed reviewers). The inventory is kept per location, one entry per worktree on its host, and each host observes and retires only its own locations; another host's entries pass through every checkpoint unchanged until that host observes them again. A location stays while a writer holds it or while anything in it exists only there, whether or not a writer still holds the ticket; when its worktree is gone, the last observation is kept with its time, and anything never observed is reported as unknown rather than clean. Snapshots are kept apart, per ticket. A snapshot is never judged to hold a location's work: every location with unfinished files or unpushed commits is reported as possibly holding work only on its host, with its last observed state and time, beside the ticket's retrievable snapshot, so a destination may be sent to check a source that holds nothing more but is never told that source-only work is safe. Unfinished work is what Git would record plus the raw bytes of files Git has seen change since it last indexed them, so an edit a clean filter or line-ending conversion hides counts until Git re-indexes the file. Contents of files reach it only through a planned handoff's snapshot. A string that looks like a credential or an authenticated endpoint refuses the whole publication. A snapshot is refused, and stays on its host, when one is in its files or in any commit (message or files) that the checkpoint's own remote does not already hold, even if another remote holds it; the one exception is the public code repository's remote once the state branch is in the internal repository, since history it holds is already public. A snapshot made offline is checked against the branches last fetched from that remote and checked again against what the remote reports before any checkpoint carries it; one that fails is left out and its work is reported as existing only on its host.

## Start and automatic checkpoints

Before `issue-run.mjs init`, run `discover --repo <owner/name> --issue <N> --checkout <main checkout>`. When it finds a checkpoint, take the run over with `resume` below instead of starting it again. Otherwise run `init`, then `enable --record <run.json> --coordinator <session> --expect-revision <n>`, which refuses a parent issue another coordinator already checkpoints and publishes checkpoint 1. `--repo` is always the code repository. Once the switch is on, `discover`, `resume`, `retrieve` and `sync-summary` find the state branch on the checkout's remote of the internal repository and `enable` publishes there, refusing until such a remote exists (`git remote add internal https://github.com/<tickets>.git`); `--remote` may name that remote, never the code repository's. A run keeps the repositories it started with, and a takeover from a checkpoint of the other switch position is refused. Each checkpoint names its tickets repository, so a code repository issue and an internal issue of the same number never read, render or publish each other's state.

From then on every `issue-run.mjs` command that changes the record publishes a checkpoint after the change and reports it under `checkpoint`. Exit code 3 means the change is recorded locally but no checkpoint holds it: start nothing and send nothing it records the intent for, and publish again with `publish --record --coordinator` once the remote is reachable. A save counts only after the remote head and the content read back; a failed or uncertain push is reported as such and is never described as saved, and an outdated copy of the record is refused rather than published over newer state. `launch` and `open` refuse to start anything until the intent they act on is saved, and `open` saves its own intent before handing a session to the app, so an abrupt end leaves a recorded intent rather than an untracked writer or session. They also refuse a start claimed on another host. A merge and the parent issue's closure record their own intent and outcome through `integration.mjs merge` and `close-issue`, each saving its intent before GitHub is called; a change of a PR's readiness is recorded first with `intent --kind ready --ticket --pr --expect-head <full sha>` and settled with `outcome --id --state confirmed|failed|uncertain --evidence`. Every review checkpoint decision that `review-checkpoint.mjs published` has read back is linked from the next checkpoint, which `review-checkpoint.mjs` does not publish itself; the comment on the PR's review thread stays the decision's authority, and a takeover before that checkpoint restores it from that thread. Any other decision published on GitHub, such as a maintainer's answer, is linked with `reference --pr --url --kind`; the record keeps the link, not a copy.

A refusal that names another coordinator means the run was taken over: stop, make no further change, and report that to the user.

`issue-run.mjs plan` also publishes its summary when it differs from the last one, so the status comment lists every ticket (done, waiting and active) with its action and reason, and the remaining work. The status comment is rewritten from the saved checkpoint after every save and read back. If that fails, the checkpoint stays saved and the result says so; `sync-summary --repo --issue --checkout` rewrites it from the state branch without repeating anything else. A summary naming an older checkpoint than the branch head is stale, and the branch head wins.

## Planned handoff

1. `prepare-handoff --step stop` stops admission: every plan shows new work, a claimed start's next step and a new writer's brief as `wait-handoff`, the start and brief commands refuse, and a checkpoint records it.
2. Ask every reachable writer to reach a safe boundary: push verified commits, finish or leave alone a running review, and end its turn. Never interrupt a review to hurry the handoff.
3. Write the observation file from what your runner reports for each writer, then run `prepare-handoff --step publish --observations <file>`. It snapshots every owned worktree on this host that has unfinished files, records each writer's observed state with this host, and publishes the snapshots, the inventory and the brief. Writers still running or in an uncertain state are listed as such; a cancellation request or a status message is not an exit. If the checkpoint is not saved, the snapshots stay in the record and the next successful `publish` carries them.

A snapshot is shaped like a stash: its parents are the worktree's head and a commit of its index, and it is reachable only from the state branch. It is made in a copy of the index, so the writer's worktree, index, branch and any review freeze are unchanged, and it is checked against the files again before it is published. Each staged, edited or new file is stored byte for byte, past Git's line-ending and filter conversions, and `retrieve` writes those bytes back the same way. A worktree with an unmerged index or changed submodules is not snapshotted and is reported as such. Every later checkpoint keeps naming the snapshot, also after its writer is released, its worktree is gone or another host adopts the work; the locations beside it are still reported, since anything changed after it exists only where it was made. A snapshot is work in progress, never review or completion evidence. Ignored files are not part of it.

## Resume on another machine, account or harness

1. `resume --record <new run.json> --checkout <main checkout> --repo --issue --coordinator <own session id> --harness --coordinator-model --coordinator-effort --coordinator-mode --invocation "<the user's request>" --merging coordinator|maintainer --evidence "<why the previous coordinator no longer coordinates>"`. The takeover is real only once its own checkpoint is pushed on top of the one it read; a second destination racing for the run is refused. A refusal sets the new record aside. When the outcome is uncertain (the push may have landed), or the command stopped after its push, the record stays: run the same command again in the same session, and it settles the outcome from the state branch and finishes the local setup. Your authority comes from this session's invocation, including who merges (`--merging maintainer` when it stops at ready PRs); the previous coordinator's invocation, authority and decisions stay in the record as evidence. Writers already running keep their recorded model and effort. New and replacement writers use your harness's default writer model unless the previous invocation's explicit model override still applies (it carries over) or your invocation names one. Route preflights confirm every new route before dispatch, and review-pr chooses reviewers against the actual new writer.
2. Act on every entry of `limitations` before anything replaces the work it names:
   - `owner` and `pending`: a writer or a start on another host stays unknown. A destination's own view of another host proves nothing; an absent PID, an unlisted session or a missing launch directory there is not an exit. Settle it only with an observation made on its own host, by its coordinator there or the maintainer, recorded in the observation file with that `host` (and, for a process, its recorded `start`, and for a detached writer `launchDirUnused: true` once no process there names its launch directory, since the recorded process is only its wrapper); `withdraw` and `launched` of another host's start need `--observed-on <that host>`, and the start itself runs only there. Unrelated eligible tickets continue meanwhile.
   - `unpublished`: the named host held unfinished files or unpushed commits at the time given, and they may exist only there, whether or not a snapshot of the ticket exists. Check that host and recover anything the snapshot lacks before restarting or overwriting that work, or report the loss to the maintainer.
   - `snapshot`: `retrieve --repo --issue --checkout --ticket N --worktree <new path>` recreates the files and staged state in a new worktree and checks both. Plan again: the worktree is then existing work to adopt or continue.
   - `handoff-lock`: only `node scripts/agent-handoff.mjs recover-lock <worktree>` on the lock's host removes it, after confirming its coordinator and child are gone.
   - `operation`: run `reconcile-operations --snapshot <file>` with a fresh snapshot. A PR merged at the intended head confirms a merge; an open PR still at that head means it did not apply and may be retried through the merge gate; a moved head, or a merge at another head, means the decision no longer applies. A closed parent issue confirms its closure.
3. Recreate the periodic check-in with the `schedule` command the record carries, as [starting a run](start.md) describes: the job was session-scoped and ended with the previous coordinator. The takeover keeps the parent issue's session title; rename your session to the title. The id, mode and `--slug` are checked as `init` checks them; a checkpoint that carries a title keeps it, and the slug gives the title to one that carries none.
4. Snapshot GitHub and plan as usual, and read the writer reports as [writer reports](writer-reports.md) describes.

A review continuation belongs to the writer session that submitted it. Never claim it from another session or present another session as its originator. Once that writer is observed to have ended on its host, its job is cancelled and released there as the review supervisor describes, and a new writer continues the PR: the round count continues from the PR's posted rounds, and the review journals' planned and completed reviewers and their latest launched attempt, carried in the inventory, show which reviewers a round still owes. A change of model, account, session or machine never resets rounds or makes an earlier acceptance apply to a new head.

## Limits

A checkpoint cannot recover work that was never pushed or snapshotted from a machine that is gone, and a destination cannot observe or stop processes on another machine. Detailed logs, review-job directories and private artifacts stay on their host; the checkpoint names where they are.
