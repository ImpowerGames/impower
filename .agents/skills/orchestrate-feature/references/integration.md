# Integration and the Feature's completion

The commands are `node .agents/skills/orchestrate-feature/integration.mjs <command>`; `merge`, `verify-feature` and `close-feature` take `--record`, `--coordinator` and `--expect-revision` like the run helper's.

## Who merges

`init` and `resume` record who merges, beside the quoted request: `--merging coordinator` when the user explicitly asked to orchestrate the Feature, `--merging maintainer` when the request stops at ready PRs. The helpers refuse a coordinator grant whose quoted request asks to stop at ready or not to merge, and a record without the decision leaves merging to the maintainer. A later request in the coordinator's own session is recorded the same way by running `init` or `resume` again with it: the record then quotes that request, who merges follows it, and `resume` saves the change to the state branch, so a request that stops at ready PRs takes the merge back; the replaced request stays in the record's log. Whether a message is a request at all, rather than a discussion of the skill, is your reading of it: a discussion starts no run, so nothing is recorded.

## The merge gate

`gate --record <run.json> --ticket N --pr P` takes a fresh snapshot of the Feature and reads the PR, the branch's protection, the PR's comments, the review journals and, last, main, changes nothing, and admits the PR's current head only when every condition below holds. Otherwise it names each one that fails.

- Authority: the run records that the coordinator merges, under the grant and a quoted request that names orchestrate-feature and the Feature; the coordinator never wrote for the ticket; and checkpoints are enabled, so the merge's intent can be saved where another machine finds it.
- Scope: the ticket is a sub-issue of the Feature in the snapshot, not a container; the PR is its one open PR, its branch names the ticket, it closes the ticket, targets main, is open and marked ready, and no earlier merge of it is unsettled.
- Review: every planned reviewer of every round has exited, every launcher finished, every report is on the PR with its adjudication, and the round audit holds, all read through the same accounting as [review checkpoints](review-checkpoints.md). From round 3 on, the decision in force is a published finish or acceptance decided at the last completed round; a question to the maintainer or a repair in force holds the merge until a later decision replaces it. Then the head is either the last independently reviewed commit, with the writer's final report recorded by `feature-run.mjs result` naming that commit and no outstanding finding or verification gap, or the head an acceptance of unreviewed corrections names, which this record published and read back. Either may be followed by clean merges of main: two-parent merges whose other parent is on main and whose remerge diff is empty. Any other commit after it, whether a correction, a non-behavioral tail or a conflict resolution, is unreviewed: the writer's next round within its limit, or a checkpoint decision on that head, settles it. Ordinary review-pr's disclosed non-behavioral exception does not admit a merge here.
- CI: every check on the head has finished, each check's latest run counts, none failed (a cancelled or timed-out run counts as failed until it is diagnosed and run again), and each required gate ran and passed. The required gates are the Test Suite workflow's `test-suite` job and whatever branch protection and rulesets require. A skipped job is reported as skipped, not as a check that ran, and a skipped required gate refuses the merge.
- Integration: the head contains main as the remote holds it now, so CI ran on the code that would land, and GitHub reports the PR mergeable (`CLEAN` or `HAS_HOOKS`). When main moves, the branch merges it again and CI runs on the new head; a clean merge keeps the review. A repository that requires a merge queue is left to the maintainer, since the gate does not drive one.

## Merge

`merge --record --coordinator --expect-revision --ticket N --pr P` runs the gate, records the merge intent with the admitted head and how it was admitted, saves it to the state branch, confirms on the state branch that this coordinator still owns the Feature and that this merge's intent is there, runs the gate once more on a fresh snapshot, and reads main one last time: a takeover, a scope, head or main that changed while the intent was saved or the second gate read its evidence, or a failed save, stops the merge before GitHub is called and records it as not run. The call is `gh pr merge P --merge --match-head-commit <head>`, never with `--admin` or `--auto`, so a push after the gate makes GitHub refuse it and branch protection still applies. The outcome is what GitHub reads back: merged at that head is `confirmed`, with its merge commit and the main commit it landed on; GitHub's own refusal (a GraphQL error or a 4xx status) is `failed`; anything else is `uncertain`, since a request GitHub did not refuse may still land: a call that was interrupted, failed without GitHub's answer or reported success while the PR reads back open (at its head or after another push), a merge at another head, or no read-back. A merge the gate does not admit records nothing and exits 2; a recorded outcome other than `confirmed` exits 1.

An unsettled merge blocks every later merge of that PR, here or after a takeover. Settle it with `checkpoint.mjs reconcile-operations --snapshot <fresh snapshot>`: GitHub's state decides, never what the call reported, and a merge it confirms records the main commit it landed on, as a merge confirmed directly does, or says that could not be read. A merge the reconciliation finds not applied is retried only through the gate again.

A merged PR's dependents become eligible once its merge commit is on origin/main, which the next snapshot reads; under `--merging maintainer` they wait for the maintainer's merge. A slice whose PR needs a correction after review goes back to its writer, whose round count continues.

## Verify and close the Feature

Once every slice is delivered, `criteria --record <run.json>` prints the checklist in the Feature's Acceptance criteria section: everything under that heading up to the next heading of its level or higher, nested headings included, each checkbox with its indented continuation lines. A checkbox is any list item GitHub renders as a task: a `-`, `+` or `*` bullet or an ordered `1.` or `1)` item, inside a blockquote too. Lines inside fenced code are examples: a heading there ends nothing and a checkbox there is no criterion. Check each criterion against the assembled implementation on main, using the existing regression, tooling and live-verification workflows it calls for, and write the evidence file `{ "criteria": [ { "criterion": "<exact text>", "status": "met|unmet", "evidence": ["<what shows it>"], "gap": "<what is missing>" } ] }` with every criterion exactly once. Then run `verify-feature --record --coordinator --expect-revision --evidence <file> --out <report.md>`, which takes its own fresh snapshot and reads the criteria from it.

The verdict is complete only when every slice that is not a container is closed with its merged deliverable on main, no operation is unsettled, and every criterion is met with evidence. Merged PRs with an unmet criterion stay incomplete, with the gap named. The helper refuses a criterion marked met without evidence or unmet without a gap; it cannot judge whether the evidence shows the criterion, which is the coordinator's reading, published in the report. A complete verification describes one main commit, one acceptance section (bound by its hash, so prose around the checkboxes counts too) and one set of slices: once main moves, the Feature's acceptance section or slices change, a slice is no longer closed with its deliverable on main, or an operation (a closure of the Feature included) is unsettled, the plan stops reporting the Feature complete and the closure refuses until it is verified again.

The report the verification writes is the final report: each slice with how it merged (through this run's gate as reviewed completion or under a named acceptance, or outside the gate, and whether it landed on a main CI never checked), every acceptance of unreviewed corrections the record published with its range and whether that head merged, each criterion with its evidence or gap, the incomplete work, and the next action. `close-feature --record --coordinator --expect-revision --verification <id>` acts only on the latest verification, only when it is complete and still holds in a snapshot it takes itself. It saves its intent, takes a fresh snapshot and checks every premise again, reads main once more after that snapshot's slower reads (a change in any of these records the closure as not run, with nothing posted or closed), posts the report on the Feature (or finds the copy an earlier attempt posted), reads it back, and as the last step before the close call confirms on the state branch that this coordinator still owns the Feature with this closure's intent saved there, then checks every premise once more on a fresh snapshot with main read last (a change there leaves the posted report naming a verification that no longer holds, and records the closure as not run), closes the Feature as completed and records the state GitHub reads back: closed is `confirmed`; a close never called, because the report was not posted, or refused by GitHub is `failed`; anything else is `uncertain`, settled by `reconcile-operations` before another attempt. An incomplete verification leaves the Feature open: report its gaps and next action.

## Limits

The gate reads the protection the token can see; GitHub's own merge state still applies the rest. The last read of main immediately before the call leaves only the merge call itself between that check and GitHub's merge; without branch protection that requires an up-to-date branch, a PR merged in that moment can land on a main its CI never ran on, and the outcome and the final report say so. The gate does not drive a merge queue. Review journals that ran on another machine are not on this one, and their rounds block the gate until they are read where they ran.
