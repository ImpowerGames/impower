# Skill installation recovery

## Migration and recovery

Fresh checkouts install links through postinstall. An existing checkout can retain ignored driver state, browser profiles or personal skills in a real harness skills directory after Git moves the tracked files. The installer intentionally refuses that populated directory, including during npm install, so it cannot discard local work. An agent handling this refusal must reconcile the contents before retrying; silently treating a refused install as success would leave discovery incomplete.

An app-created worktree can instead contain a real copy of the canonical skills, including stale content or different line endings. When every copied path has a real canonical counterpart of the same type, with no extra paths, links or hardlinks, the refusal names `node scripts/link-agent-skills.mjs --adopt-copy <absolute-backup-parent>`. Supply an existing private directory outside the checkout with no linked ancestors. This explicit repair moves each eligible copy intact into a unique backup directory there before installing its shared link. The CLI prints the backup paths before mutation; retain the output and backups, including after a later link creation failure. Different file content is preserved, not reconciled or discarded. Copies with personal extra paths, profiles, driver state or unsafe entries still require the manual reconciliation below.

After adoption, rerun `node scripts/link-agent-skills.mjs` and preflight. A root postinstall refusal identifies a discovery repair, not proof of missing dependencies: inspect the install output and use preflight's dependency probes before deciding whether packages need reinstalling.

Use canonical driver status commands to inspect both drivers; each reads its existing-checkout state fallback. Stop the recorded servers through those drivers before moving any state or profile. If ownership or shutdown cannot be established, preserve the data and report the blocked migration rather than guessing.

Preserve the populated directory in a private backup outside the checkout before removing its entry from the harness directory. Verify the resolved source and backup paths and use one filesystem API to move it; never recursively remove it. Reconcile any personal skill files with the canonical source without overwriting existing files. Preserve browser profiles and OPFS projects; restore each profile to the corresponding canonical skill directory only when that destination is absent. Keep the backup until its contents have been verified. Do not restore stopped server state as if it described a running server. Then rerun the installer and verify all links and both harness catalogs. This reconciliation needs judgment about personal files, so the installer does not automate it.

For links that are broken or point at another checkout after a move or copy, run `node scripts/link-agent-skills.mjs --repair-links`. That explicit option replaces link entries without modifying their targets. Classification resolves each link and refuses unexpected resolution errors; an absent target cannot be distinguished from a disconnected volume. Before any mutation the CLI prints planned actions with each repaired entry's raw previous target. Retain that output: if a later creation fails, it identifies the entries and targets needed for recovery. The returned records also retain action and previousTarget. The default installer refuses foreign or broken links until this recovery is selected.

A harness skills directory that is a real directory holding nothing but links, one per skill, is a link entry too: it holds no data of its own, so the default installer refuses it naming this option, and `--repair-links` unlinks each entry (a dangling one left by a renamed skill included), removes the empty directory and puts the shared link in its place, recording each entry's raw previous target. Real copied files require `--adopt-copy`; `--repair-links` alone never replaces them. A linked tool parent is always refused.
