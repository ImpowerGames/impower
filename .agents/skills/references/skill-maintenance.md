# Maintaining shared skills

Before changing workflow prose, inspect its callers and tests. Keep essential protections in the entrypoint and conditional details behind links at the step that needs them. Do not require readers to load every reference. After editing skill prose or a hook, run `node scripts/check-agent-tooling.mjs --tier skills`, which finishes in about a minute; `--only <path substring>` narrows it further while iterating, and the unfiltered command runs the whole inventory including the driver, bench and reviewer-process checks. Stage new checks first so Git-based discovery includes them, and review CI triggers and sparse-checkout inputs; a new check under `scripts/` or a driver skill belongs to the drivers tier, whose CI leg runs only when the paths its `driver-changes` job lists change. The context-loading check validates links and entrypoint budgets; portability checks keep shared instructions free of vendor and tool names; landing-pad checks protect resolve-issue's step order. Warning inventory includes references, so relocating a warning does not remove it from coverage. Update prompt-builder tests when moving the reviewer template.

The checks verify mechanical properties only (template boundaries, placeholder counts, forbidden names), never wording, so prompts and skills can be reworded freely; the one exception is a skill's restatement of a helper's exported vocabulary, which the interface exercise item below names. The review workflow's rules are therefore kept by the editor, not by a check. Before publishing an edit to the review-pr skill, confirm each of these is still stated somewhere a reader following the workflow reaches it:

- Independence: the writer and reviewer are distinct configured model routes from different vendors, a same-vendor reviewer is allowed only after the cross-vendor route was blocked by a usage limit or on the user's explicit request, the launch arguments select the reviewer route, and one undirected reviewer is always present.
- Reviewer duties, inside the delimited prompt block: an independent first pass recorded before reading other current-round reports; test honesty and repository rules checked by every reviewer; unverified concerns and coverage gaps labelled separately from confirmed findings; no edits inside the repo tree; destructive experiments only in a scratch repository.
- Lens triggers: a change to Sparkdown syntax, completions, hover, diagnostics, user docs or the editor interface includes the author-experience lens, and a change touching `definitions/yaml/sparkdown.language-grammar.yaml` or `packages/sparkdown/src/compiler/lower/` includes the grammar-conventions lens; each reads its reference first and runs no suite. Only the author-experience lens raises the reviewer count to at least two beside the undirected reviewer; the grammar-conventions lens is a trigger without a floor and rides the undirected reviewer when the PR is sized at one.
- Process discipline: reviewers run as separate fresh processes, the coordinator waits for each to exit and confirms its report landed, and a missing comment alone never justifies a relaunch.
- Adjudication: every finding gets a disposition on the PR (accepted, rejected, already covered or deferred), behavior-changing corrections are themselves independently reviewed, each report is adjudicated and corrected before the round's next reviewer launches, and the writer settles its own suspicions by experiment rather than waiting for a reviewer to raise them.
- Rounds: a round's reviewers are fixed before its first launch and corrections between them neither add a reviewer nor start a round, the autonomous cap is three rounds, extensions need explicit user authorization recorded by the launcher (a named limit or a delegation of the choice to the coordinator, bounded at ten rounds), nothing resets the count, and exhausting the cap never grants readiness.

Before publishing an edit to the feature review skills or their shared reference, confirm each of these is still stated where a reader following the workflow reaches it:

- Independence: the session compares the ticket's `Filed by <model> at reasoning effort <effort>` line with its own model and stops in a same-model session; a ticket without the line asks the user which model filed it.
- Interface exercise: the four items an element needs (location, trigger, states, failure view) are the same in the experience skill, the interface exercise helper and the file-feature publishing reference's example block, and the four walkthrough tasks and the record's three columns are the same in the experience skill and the helper. The helper's check pins the helper's words; the portability check holds the skill's restatement of all three groups, and the example's four items, to those words.
- Anchoring: a finding reaches the user only with a `file:line` at the named commit, a quoted scenario the tickets do not cover or contradict themselves on, or a documented comparison with a named peer system; a finding that adds capability is a proposed follow-up unless the design forecloses it.
- Interview: findings are grouped into one decision per design question and asked in rounds with the evidence, the recommended resolution and the edit it implies; "just decide" is marked "decided by default"; an unattended session posts the round and applies nothing.
- Apply: every edited body is read back, undecided items are marked "Open", follow-ups are filed only on request, and one summary comment on the parent names the model, the commit and what changed.

For a command failure or missing procedure encountered during skill use, read [feedback reporting](feedback-reporting.md) before reporting. Prefer a driver refusal or check that prevents the mistake over a new warning. Certain fixes may accompany the active PR in their own commit, with Notes for reviewers naming them; complex mechanisms belong in the standing feedback inbox. Preserve contributor observations and stable problem/session identities.
