# Maintaining shared skills

Before changing workflow prose, inspect its callers and tests. Keep essential protections in the entrypoint and conditional details behind links at the step that needs them. Do not require readers to load every reference. After editing, run `node scripts/check-agent-tooling.mjs`; stage new checks first so Git-based discovery includes them, and review CI triggers and sparse-checkout inputs. The context-loading check validates links and entrypoint budgets; portability checks keep shared instructions free of vendor and tool names; landing-pad checks protect resolve-issue's step order. Warning inventory includes references, so relocating a warning does not remove it from coverage. Update prompt-builder tests when moving the reviewer template.

The checks verify mechanical properties only (template boundaries, placeholder counts, forbidden names), never wording, so prompts and skills can be reworded freely. The review workflow's rules are therefore kept by the editor, not by a check. Before publishing an edit to the review-pr skill, confirm each of these is still stated somewhere a reader following the workflow reaches it:

- Independence: the writer and reviewer are distinct configured model routes, the launch arguments select the reviewer route, and one undirected reviewer is always present.
- Reviewer duties, inside the delimited prompt block: an independent first pass recorded before reading other current-round reports; test honesty and repository rules checked by every reviewer; unverified concerns and coverage gaps labelled separately from confirmed findings; no edits inside the repo tree; destructive experiments only in a scratch repository.
- Process discipline: reviewers run as separate fresh processes, the coordinator waits for each to exit and confirms its report landed, and a missing comment alone never justifies a relaunch.
- Adjudication: every finding gets a disposition on the PR (accepted, rejected, already covered or deferred), and behavior-changing corrections are themselves independently reviewed.
- Rounds: the autonomous cap is three rounds, extensions need explicit user authorization recorded by the launcher, nothing resets the count, and exhausting the cap never grants readiness.

For a command failure or missing procedure encountered during skill use, read [feedback reporting](feedback-reporting.md) before reporting. Prefer a driver refusal or check that prevents the mistake over a new warning. Certain fixes may accompany the active PR in their own commit, with Notes for reviewers naming them; complex mechanisms belong in the standing feedback inbox. Preserve contributor observations and stable problem/session identities.
