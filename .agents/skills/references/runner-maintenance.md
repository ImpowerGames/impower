# Runner discovery, shell and hooks maintenance

## Discovery, paths and shell selection

The installed Windows Claude file glob did not traverse a skills junction in the discovery acceptance probe, while its native catalog discovered all nine skills. Use the native catalog or canonical paths for explicit enumeration; do not treat an empty glob over an ignored link as an empty skill set.

Bash examples require Git for Windows bash on Windows, ordinarily `C:/Program Files/Git/bin/bash.exe`. Generic `bash` can resolve to the unavailable WSL launcher. Use PowerShell's `&` with that absolute path for shell checks. POSIX uses its installed bash. Use native paths for process argument arrays and `pathToFileURL` for Windows dynamic imports; quote paths in shell commands.

Shared hook functions live in `.agents/hooks/`. Claude's `.claude/settings.json` and thin `.claude/hooks/` entry points and Codex's `.codex/hooks.json` invoke that source. Node is required; the launch wrappers convert runtime failures into blocking exit 2. Both cover direct generated-language edits, typed issue creation, shared stash mutation and local test runs wider than the files under work: the local-test hook refuses a Vitest call that names no existing test file, a package `npm test`, `npm run test`, `pnpm test` or `yarn test` whose script may run Vitest, and the typecheck with no project filter, and allows `node scripts/test-suite.mjs`. It follows literal directory changes in the same command to check file arguments, reads the payload's `cwd` as the starting directory, and does not follow a directory, file or invocation built from a variable or alias, or a command string handed to another program such as the redgreen driver's `--test`. In a PowerShell reading they also refuse a relative path passed to a .NET file call, and a `gh` `--jq` or `-q` filter containing a double quote, because Windows PowerShell 5.1 drops embedded double quotes from native arguments however the string is quoted; such a filter goes through the POSIX shell.

Both runners also enforce the resolve-issue session title. A PostToolUse hook on shell commands derives the title from a `git worktree add -b <type>/<issue>-<slug> <path>` command that Bash or PowerShell would run (not quoted, escaped or commented out), confirms with `git worktree list` in the session's directory that a worktree now exists at that path on that branch (Codex also runs PostToolUse after failed commands and reports only their output), records the title in a per-session file under the system temp directory (`impower-session-titles/<session key>.json`, where the key is the SHA-256 of the session id), and returns the exact rename instruction as context. A PreToolUse gate then denies shell commands for that session until the rename. On Claude, a PostToolUse hook on `mcp__*__set_session_title` clears the record when the title matches exactly and the call targets this session. On Codex, the PostToolUse matcher also covers `set_thread_title`, but that tool exists only in hosts that offer it and whether its calls reach hooks is unverified; the Codex CLI has no rename tool. Any runner without a rename tool clears the record with the acknowledgement command the hook message names (`node .agents/hooks/session-title.mjs confirm <session key>`); the gate lets through only that command, naming this checkout's script and this session's key. No documented way for a hook to set the title directly was found on either runner, so the gate remains.

Codex CLI 0.154.0 loads project hooks for a session in a linked worktree from the main checkout's `.codex/hooks.json` (the app-server `hooks/list` reports that `sourcePath`), while the hook commands resolve their scripts from the session's own Git root. A `.codex/hooks.json` change on a branch therefore has no effect in Codex until it reaches the main checkout; to accept one earlier, copy the branch's file over the main checkout's, run the fresh session with `--dangerously-bypass-hook-trust` for the changed definitions, and restore the original immediately. Safe artifact writing and the other AGENTS rules remain instructions unless a dedicated check enforces them.

Codex project hooks require a trusted project and review of the current hook definitions through `/hooks`; changes require renewed trust. Installation of skill links does not grant hook trust. Verify the configured hooks are enabled before claiming enforcement. The Codex adapter reads both shell dialects because its `Bash` tool name also represents PowerShell, and extracts every patch target including rename destinations. Claude's explicit shell names select their own dialect. Windows hook commands use `commandWindows`; POSIX commands resolve from the Git root so nested working directories work. These are project-local definitions for a session started in this checkout, not global hook definitions. Codex runs them in the session cwd, independently of a shell call's `workdir`; the live workdir probe in the audit verifies this distinction. Claude's generated-file entry requires `CLAUDE_PROJECT_DIR` explicitly and refuses a missing or invalid root with a recovery instruction.

These are static guardrails, not an enforcement boundary against evasion. Variable-built commands, aliases, wrapper scripts and generated-file writes through shell programs are outside these checks. Codex does not run PreToolUse again for `write_stdin`, and hosted or specialized tool paths can bypass hooks. Avoid interactive shell input for guarded operations. Hooks do not wake an idle coordinating session; use the awaited handoff runner for automatic implement/review exchanges. See the official [hooks documentation](https://learn.chatgpt.com/docs/hooks) for coverage and trust semantics. Acceptance must capture actual allowed and denied tool calls in fresh sessions, with destructive operations replaced by inert functions in printed scratch repositories; a unit test or enabled feature flag alone is insufficient.

The official [skills documentation](https://learn.chatgpt.com/docs/build-skills) and [non-interactive execution documentation](https://learn.chatgpt.com/docs/non-interactive-mode) describe discovery and CLI execution. Local acceptance evidence records the installed versions and commands actually exercised; documentation alone is not evidence of a successful run.
