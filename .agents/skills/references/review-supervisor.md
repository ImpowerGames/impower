# Supervised review continuation

Opt in from the originating Windows Codex desktop task with its inherited authenticated app-tools endpoint, or an explicitly registered native Windows Claude CLI 2.1.270 session. Both adapters preserve writer settings and send no model or permission overrides. Linux automatic mode, Claude desktop and unverified versions are unavailable; Windows and Linux retain [awaited handoff](../review-pr/HANDOFF.md) and shared tooling support. Independent native CLI reviewers must remain alive throughout execution; early-exiting wrappers are unsupported. The two-direction production acceptance record remains required before marking this feature complete.

Author a JSON plan with the editor in private storage outside every checkout and Git administrative directory. `worktree` is the canonical reviewed worktree, `jobDir` a new absolute directory whose parent exists, `head` and `base` full immutable SHAs, and `pr` the PR number. Supply explicit `writer`, `writerEffort`, `reviewer`, and `permissions` as `{ "approvalPolicy": "<native policy>", "sandboxPolicy": <native policy object> }`. `destination` contains the exact originating `threadId`, `turnId`, `cwd`, and absolute native `rollout` path. Preflight verifies the rollout's session and turn identity, model, effort and permission object against these declarations and reads the authenticated host's current destination. It records only configuration fields, not raw prompts or credentials. The native rollout reader is bounded to 128 MiB; an oversized or unavailable record requires awaited mode.

`reviews` is one to four independent coverage entries: unique `id`, `transport` from the [native reviewer mapping](runner-review.md), absolute native `executable`, explicit string `args`, absolute `prompt`, `effort`, and `permissions` (the native CLI permission mode). This first route requires exactly one `--model`/`-m`, `--effort`, and `--permission-mode` argument matching those declarations, plus `--output-format json`. Use native Claude review arguments inspected for the installed CLI; the reviewed route has native process lifetime rather than a detached wrapper. Before validating its report or starting another reviewer, the launcher requires a final JSON result with `type: result`, `subtype: success`, `is_error: false`, and `stop_reason: end_turn`, as well as confirmed successful process exit. A missing or interrupted result fails closed. Result inspection is bounded to 16 MiB. The prompt contains the filled review-pr contract and declared coverage. Reports from one independent first pass must not be included in another's prompt. Supply `round`, `completedReviewRound`, and the existing handoff recovery fields `reviewedHead`, `finalCorrections`, `reviewRoundLimit`, and `extendedReviewAuthorization` when applicable. Recovery never resets counts. No job authorizes another round by itself.

The reverse provider direction uses a separate native JSONL reviewer mapping and explicit artifact/posting permissions in [runner notes](runner-review.md). Coverage, rounds, reports and process-exit gates remain shared.

Before accepting a Codex job, preflight enumerates the connected host's read/send schemas and refuses missing or changed required arguments. The supplied base must resolve to an existing commit. Private destination transport/configuration fields remain in the plan; only thread, turn and working-directory identity enter the delivered envelope. Mutation contention receives a bounded retry for worker registration, reviewer admission, cancellation and CLI claim, without retrying a host send.

For a native CLI writer, follow the provider's [originating-session registration](runner-review.md) before submitting the plan. Its private registration supplies identity and configuration; it never authorizes a replacement writer. The shared lifecycle below applies to both adapters.
The shared handoff recovery validator checks round limits and final-correction evidence before reserving the freeze.

Native argument validation follows each transport's explicit [runner mapping](runner-review.md). Fallback models, settings, agents and prompt overrides are rejected. Auxiliary model usage metadata does not establish which model wrote the report. Native stdout contains the result protocol; stderr is retained separately in `stderr.log`, so a diagnostic after the result does not replace it. The launcher records its actual argument vector. Worker and reviewer environments strip inherited `CLAUDE_*`, `CODEX_*` (including `CODEX_HOME`), `NODE_REPL_*` and `CUA_*` variables; the monitor retains its own authenticated endpoint. This is a routing boundary, not filesystem or general credential isolation. Codex reviewers receive their explicitly configured private authentication home and authorized report access through the runner mapping. Reviewers disable optional Git index locks during inspection.

For native Claude reviewers, supported permission modes are `default`, `acceptEdits`, `plan` and `dontAsk`; bypass modes and positional scripts are refused. This route uses normal saved authentication; environment-only Claude authentication and a custom `CLAUDE_CONFIG_DIR` are unsupported. Executables must exist as files before job acceptance. Coordinator and review-job store Git calls isolate case-insensitive Git environment overrides and use hidden subprocesses with ignored stdin; host preflight retains its separate conformance containment checks.

Run `node scripts/review-supervisor.mjs submit <absolute-plan.json>`. Successful acceptance creates a durable job and worktree freeze, then launches a detached reviewer worker and a separate event/continuation monitor with inherited host authentication. Submit awaits both native spawn outcomes and up to thirty seconds for durable monitor registration, or verifies an existing live monitor's recorded ownership. It records an early monitor exit or unresolved registration before rejecting; registration timeout does not kill the process or replay reviewer work. A known pre-spawn log-open failure records that no worker launched; an ambiguous worker launch remains blocked for investigation and is never retried automatically. Ending the writer turn or disconnecting a status client does not stop either process. The worker serializes the planned reviewers through the existing four-slot launcher. A monitor restart never repeats reviewer work.

Commands take an absolute job directory:

- `status` reports durable state and evidence.
- `events <job> <cursor>` replays events after a sequence cursor. `watch <job> <cursor>` stays connected and streams new JSONL events; reconnect using the last received cursor. Every event has a stable ID and sequence. Receiving an event is separate from native continuation acceptance.
- `run <job>` starts or reconnects a monitor without launching reviewers. One exact process identity and generation owns `monitor.lock`; a second live monitor returns its owner. The monitor uses the private job directory as its working directory. It automatically observes reconnects and unavailable local observations for ten minutes, then records actionable `monitor-suspended` state. Missing worker registration suspends after one minute. These deadlines are checked between bounded transport calls. Live worker identity is sampled at most once per thirty seconds until completion is recorded; completion triggers actual exit verification. Pending delivery is observed every ten seconds. Missing rollout context or an unavailable PID observation cannot authorize delivery or release and is retried within the observation window; a positively changed destination/configuration stops advancement.
- `recover <job>` first attempts recovery of mutation and monitor locks using exact OS owner identity, then starts monitoring. Live, unreadable or ambiguous owners and interrupted recovery markers remain blockers. `resume <job>` additionally clears a prior blocked state and revalidates the same job. These commands retain completed reviews, round counts and submission intent; none repeats a send after intent. Existing reviewer slot/lock recovery still follows the handoff procedure.
- `start-worker <job>` can complete an interrupted initial submission only when no worker launch intent exists. Once intent exists, an unregistered worker remains uncertain and cannot be replayed. Inspect its launch evidence; do not create another paid job as a recovery shortcut.
- `cancel <job>` first durably cancels the workflow and suppresses its pending outbox and subsequent reviewer launches. It then attempts workflow-specific host queue removal, followed by cooperative host turn cancellation even if removal fails or times out. The current Codex app bridge exposes neither verified operation, so both are reported as unsupported. An already running reviewer remains tracked until its actual exit; cancellation does not claim it stopped. Native Stop/Escape keeps its host meaning and does not cancel the workflow.
- `release <job>` releases a cancelled/blocked or failed-launch job's worktree only after its registered worker is confirmed absent and its handoff lock is absent. A durable `worker-exit-observed` record preserves an independently observed exit; `worker-finished` alone never proves exit. Unreadable process identity or unknown spawn registration remains locked for investigation. It never signals a process.

After all planned coverage has valid posted reports and the worker has actually exited, the monitor verifies the frozen repository, head and base and persists one continuation envelope. That envelope names the job, unique continuation ID, reports, coverage, reviewed SHAs, round, exact destination and authorized adjudication step. One admission transaction persists submission intent and invokes the host, retaining the request even if lock cleanup fails. A crash before intent can safely resume admission. Only a trusted adapter's explicit `not-sent` response, produced before any frame write, records `dispatch-refused` and permits revalidation; crashes and ambiguous transport outcomes never permit blind resending. A disconnected host preserves pending work, including after the monitor suspends. Active delivery may join the same originating turn; the unique ID, rather than a new-turn assumption, identifies acceptance. The bridge can hide active items until turn completion. Reconciliation examines at most ten newest-first turns per pass, requesting one turn per page and at most 20,000 characters per item. Missing, truncated or older evidence remains uncertain; restarting the same job preserves that no-resend constraint. Recoverable provider evidence failures retain their diagnostic in the journal without discarding the job.

The continuation instructs the original writer to run its exact `claimCommand` before changing files. Claim checks the originating task, cancellation and blocked states, unique ID, reviewer exit, frozen head and latest native model/effort/permissions again, durably records ownership transfer, then removes the freeze. Duplicate claims are idempotent. An acceptance receipt may truthfully arrive after workflow cancellation or within a receiving turn that subsequently fails; it proves delivery, not completed adjudication. Cancellation still refuses claim. A claimed job ends its monitor. The writer reads the full paginated reports and adjudicates under review-pr; an envelope covers only its planned reviews, and readiness still requires all normal review and CI gates. A continuation event does not mark the PR ready or authorize merging.

Retain the private `plan.json`, `events.jsonl`, `handoff.jsonl`, reviewer output/completion files and worker/monitor logs. A partial final event fails closed. A stale head, incomplete report, failed worker, uncertain ownership or changed destination cannot advance. The freeze coordinates participating launchers; ordinary external file edits are detected at validation and claim. There is no automatic cleanup or reset of ambiguous evidence.

If a stale mutation lock prevents safe journal writes, a token-owned `monitor-failure.json` records the failure independently and status exposes suspension. Monitor cleanup preserves the original error and retains ambiguous ownership for `recover`; it never removes a shared lock to make a diagnostic writable. Git failures retain command, code, status and signal without copying environment or raw output. Events/watch can replay journal entries missed by a disconnected run stream. A claim refused because the original model or permission policy changed requires restoring that configuration or cancelling and releasing after actual reviewer exit; claim never silently adopts a new policy.

Canonical native directory identity accepts equivalent path spellings while rejecting a different destination. Confirmed reconciliation identity/protocol mismatches stop immediately. Other receipt exceptions, including unexpected errors that the adapter cannot classify, conservatively leave acceptance unknown: their exact message is persisted as an observation, polling remains bounded, and no resend occurs. An observation is not a claim that its cause is harmless or transient; inspect its recorded reason when diagnosing suspension. Deadline reasons distinguish worker registration, worker identity (including finished workers whose exit remains unconfirmed), destination availability and delivery receipts. Terminal delivery, claim, cancellation and review failure take precedence over cleanup diagnostics. Retain diagnostic files as evidence; recovery does not automatically delete their history.

A failed or blocked reviewer chain creates a separate durable terminal envelope only when no successful-completion submission is already outstanding. It includes the handoff journal, exact terminal reason and required recovery action, and explicitly forbids a replacement reviewer. Terminal submission intent is recorded before host invocation, ambiguous delivery is reconciled without resend, and acceptance is recorded once for the job generation. A resumable monitor suspension stays durable-only because its successful continuation may still be pending; recovery resumes that same evidence instead of sending a competing terminal message.

Each automatic coverage entry requires distinct posted comment IDs. Reports must match the PR/head and have a GitHub creation time at or after their reviewer launch, compared at GitHub's whole-second precision. The launch machine requires an accurate clock relative to GitHub; clock skew can reject a fresh report, preserving it for investigation rather than weakening freshness or automatically relaunching a reviewer. Transient API reads receive bounded retry without relaunching a reviewer. These checks reject obvious reused or stale reports; they do not cryptographically prove model authorship, especially when reviewers share one authenticated GitHub account. Full report reading and adjudication remain required. Prior completed-round reports remain preserved; a new coverage entry cannot reuse their older IDs as its own report.
