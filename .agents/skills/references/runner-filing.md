# Delegated filing routes

New lifecycle records use version 2: the checkout leaf contains the ownership UUID without hyphens; the record, branch and marker retain the UUID identity. Version 1 records retain their original UUID leaf and strict ownership/removal checks, without migration or renaming. npm can protect a legacy UUID path or an ancestor in its prefix output; installation then refuses before mutation and preserves the record. Create a fresh supported reproduction only when its parent path is queryable: changing the leaf does not repair an unqueryable ancestor. Never decode protected output or relax physical identity verification.

The resolve-issue [outstanding work](../resolve-issue/references/follow-ups.md) sweep hands each out-of-scope item to a cheap filing route instead of reproducing it in the writer's own context. The route runs the file-bug or file-task skill in its own worktree and reports the ticket number.

| Runner      | Launch                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Claude Code | Agent tool with `subagent_type: filer-sonnet-5-5-low`, defined in `.claude/agents/filer-sonnet-5-5-low.md` (`claude-sonnet-5-5` at low effort); one agent per item, launched together, awaited before the handoff. |
| Codex       | A fresh `codex exec` process per item on the installation's lowest-cost model at low reasoning effort, with the same prompt body as the Claude definition; await process exit. |

The prompt for one item carries its `file:line`, one sentence on the symptom, the base commit, the PR number and the instruction to report the issue number or `Not filed` with the reason. Outside an orchestrate-issues run, the route [places each ticket](publishing.md#place-a-filed-ticket) under the parent whose Scope covers it with the parent's milestone, and reads the parent and milestone back, naming both in its report. The writer reads every filed ticket back, its parent and milestone included, before recording it in the PR body. When the runner offers no such route, the writer runs the sweep itself as the reference describes.

Under an orchestrate-issues coordinator, the prompt also names the coordinated parent issue, and the filed ticket carries a provenance line naming that parent and the PR it came from, with one sentence each on how it relates to the parent's goal and to the fix it came from; a reused open issue carries the line in the comment that adds the new evidence. The writer lists every ticket it, its filing routes or review-pr filed or reused in its final report to the coordinator, which confirms each from that line or the PR report and places it through its triage, so the route leaves placement to the coordinator and reports the ticket as awaiting it.

An orchestrate-issues coordinator files the same way: a follow-up a writer flags outside its ticket's scope, or any Bug or Task its run turns up, goes to the filing route with the item's location, symptom, base commit, PR and the parent issue, and the coordinator awaits it, reports the ticket number, and records and triages it like a writer's filing. It never proposes the filing to the maintainer as a session to start, since such a proposal waits on their approval by hand and an unattended run has none.

## Checked reproduction lifecycle

Verified PowerShell parameter starts include ASCII hyphen and its native en dash, em dash and horizontal bar prefixes (U+2013/U+2014/U+2015). These receive the same cleanup, location and New-Item role checks. Normalization applies only to raw parameter starts; whole quoted dash-name operands remain literal filenames. Other punctuation is not inferred as parameter syntax.

Claude Code 2.1.295 or later is required for the cleanup hook's host-level failure protection: `onFailure: "block"` blocks startup, timeout and invalid-output failures. The command wrapper also maps missing Node, a missing adapter and policy-process failures to blocking exit code 2, preserving successful checks and explicit denial JSON. Older runtimes can use that wrapper but do not provide the host-timeout guarantee; a timed-out hook may let the tool call continue. This project does not upgrade the CLI or enforce managed minimum-version settings.

Recognized child-shell command strings inherit the complete possible-location set and unresolved-location state. Their raw literal spelling is verified before recursion; ambiguous Bash quote concatenation or escapes at supported program positions refuse rather than invent an unrelated command. Verified single quoted Bash shell names use the existing shell-string recognizer. Unknown shell input requires both supported readings to allow, so a valid PowerShell child string whose Bash spelling is ambiguous may conservatively refuse; supply the actual PowerShell shell for that supported form. Substitutions are collected without execution positions, so relative mutations in them refuse when the surrounding command has location flow; verified absolute operands remain independent. More than three recursive shell-string/substitution levels refuse in a known repository, even for benign execution whose contents exceed that bound. Shallow benign commands and literal prose remain permitted. This is a conservative boundary within the supported recursion, not evaluation of arbitrary shell code or protection for unknown outside-repository execution.

Literal command strings are analyzed whether quotes or verified Bash escaped spaces carry them. Unverified command-string flags and Git worktree/add/remove or npm install/ci selector spellings refuse relevant operations instead of hiding a mutation. Non-operation arguments, such as Git status pathspecs/config values and npm help/config/cache values, do not become setup selectors. npm prefix parsing supports the explicitly checked literal option subset; unresolved prefixes before a plausible setup selector refuse. Quoted command wrappers such as 'env' or 'command' conservatively refuse in a known repository because their child positions cannot be established, even for benign execution; use the supported unquoted equivalent. Verified quoted shell names with supported command-string flags remain analyzed. Recognized env/sudo chdir options make only the child location unresolved: relative child mutations refuse, verified absolute cleanup operands stay independent, and the following parent command retains its original location state. The policy does not evaluate arbitrary wrappers, aliases, scripts or computed operation selection.

Bash ANSI-C and locale literal syntax at command or operation-selector positions is not decoded: it refuses in a known repository, even when its actual dispatch would be benign. Use ordinary verified command names and selectors. Literal prose and non-operation Git/npm data arguments remain permitted. Local repository discovery removes inherited Git environment overrides and sets LC_ALL, LANG and LANGUAGE to C, including case-insensitive aliases. Timeouts, permissions failures, broken metadata and unknown diagnostics refuse relevant operations; only Git's exact no-containing-repository result with no physical or lexical ancestor .git entry permits the source-checkout inventory fallback. The ancestor check is bounded to 512 entries per spelling and refuses unreadable identity or exhaustion. An incomplete repository whose metadata Git silently skips remains uncertain ownership. The guard does not infer that a failed discovery means an unrelated filesystem target.

The supported npm setup selectors include the CLI's explicit install aliases `add`, `i`, `in`, `ins`, `inst`, `insta`, `instal`, `isnt`, `isnta`, `isntal`, `isntall`, and ci aliases `clean-install`, `ic`, `install-clean`, `isntall-clean`. These receive the same ownership and literal checks as `install` and `ci`; arbitrary abbreviations, scripts and other npm verbs are not inferred as those operations.

Literal target identity follows each encountered link's raw destination as well as its final physical path. An outside alias pointing directly to a checkout's borrowed dependency junction cannot erase the intermediate checkout identity, even when the final external repository is not registered. More than 64 distinct links or an unreadable/cyclic physical chain refuses with the guarded helper route; this bounded check runs only for relevant direct operations. A link chain unrelated to this repository's registered checkouts remains outside the protection scope.

Recognized direct link setup (`ln -s`, `mklink`, and `New-Item` with literal Junction/SymbolicLink ItemType) touching a registered checkout's physical or traversed identity is refused and handed to the guarded lifecycle. This includes a fresh outside alias targeting a checkout and a new link inside it: the following command could use that link before pre-command inspection can observe it. The policy does not simulate future filesystem state. GNU symbolic-link forms inspect implicit cwd destinations, final-directory and `-t`/`-T`/`-n` destinations, and link contents relative to the physical destination parent (`-r` instead anchors its source at cwd). Abbreviated symbolic selectors refuse as uncertain. Plain `ln` hard links are outside this alias-creation boundary; already-recognized mklink /H retains its verified cwd target role. Windows Junction targets use cwd; unverified relative SymbolicLink roles and uncertain option layouts refuse. New-Item supports verified Path/leaf-Name/default-Path and Target/Value roles; non-leaf Name refuses rather than inventing a safe destination. Verified ItemType/Type selectors are excluded from pathname inspection; abbreviated selector candidates carrying a link type refuse as uncertain rather than silently losing recognition. Actual paths named Junction or SymbolicLink remain operands. Cleanup/location inspection preserves literal dash-prefixed operands after `--` (including a quoted Bash delimiter), quoted PowerShell operands and verified Path/LiteralPath parameters, including colon-bound values. Unrelated outside absolute links, ordinary npm/worktree setup and the lifecycle's internal workspace links remain supported.

Target and raw link-destination spellings retain parent components until linked ancestors have been inspected. A spelling such as node_modules/../file cannot erase dependency traversal before ownership checking. Ordinary parent paths through regular directories remain supported. Location transitions containing both parent components and traversed links retain uncertainty because shell logical and physical location modes can differ; relevant relative mutations then refuse, while verified absolute targets remain independent. This conservative linked-parent boundary also applies on Windows, where the operating system may normalize that spelling differently from POSIX.

Both routes use `scripts/filer-worktree.mjs` from the main checkout. Include this lifecycle in each item's prompt, including the stable filing session identity as `--owner`:

```sh
node scripts/filer-worktree.mjs create --root <absolute-main-checkout> --owner <filing-session>
node scripts/filer-worktree.mjs check --record <absolute-owner.json> --owner <filing-session>
node scripts/filer-worktree.mjs remove --record <absolute-owner.json> --owner <filing-session>
```

Create returns the worktree, branch, ownership record and private artifacts directory outside checkouts. The helper's Git calls and guarded cleanup child remove inherited Git overrides, pin diagnostics to C and enable `core.longpaths` without changing repository configuration. It installs dependencies independently with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`; tooling-only filing adds `--tooling-only` to create and can later use `install --record ... --owner ...`. Never borrow another checkout's install. Ordinary workspace links whose physical targets stay inside this worktree are allowed. Keep repro evidence in the returned artifacts directory and stop owned servers before cleanup. Removal verifies ownership and the unchanged initial commit, saves uncommitted changes and untracked probes as a binary patch under the artifacts directory's `leftovers/` (recorded in `owner.json`), resets the tree, delegates to guarded clean-worktrees removal, verifies the tree and registration disappeared, then removes the unchanged owned branch. No separate probe deletion is needed.

When only the filer's own shells hold the path, retry the same removal with `--defer`. The helper saves the leftover patch, records `cleanupPending` in the active ownership record and returns one `cleanup pending: <path> <branch>` line. Include that line and the record path in the filing report. It keeps the tree and branch and never stops or ignores a holding process; retry removal after the shells exit, or leave the recorded tree for clean-worktrees' normal clean/idle eligibility checks. Missing process ancestry or start-age evidence, unrelated shells and non-shell workers remain refusals even with `--defer`. Committed work, external links and uncertain ownership also remain preservation handoffs; report the record path and reason and never choose another deletion call. Artifacts remain for evidence.

The shared native hook and the other runner's adapter use the existing command tokenizer to refuse direct `git worktree remove`, and recognized direct deletion or dependency/worktree setup from an owned filing context. Location analysis keeps the actual initial cwd and every verified literal alternative, propagating relative transitions from each possibility; it never presumes a location change succeeded or executed. Relative mutations check all possibilities against the initial known repository inventory. More than eight states, unverified locations, ambiguous operands or stack restores refuse rather than truncate. Verified absolute operands are checked independently of location flow; quoted prose and comments are left alone. Target decoding supports quoted/escaped arguments, colon-bound PowerShell parameters, singleton literal groups/arrays and absolute FileSystem provider paths. Bash quote concatenation and unverified shell escapes, splatting, undecoded shell quotes and unsupported target syntax refuse relevant operations in a known repository, naming the helper route. Recognized canonical PowerShell cmdlets use their argument grammar locally; ambiguous rm/cd forms keep their own supplied shell reading. Unknown shell input requires both supported readings to allow, so a cmdlet elsewhere cannot change a Bash operand's decoding. Literal targets use physical registered-root identity, inspect linked ancestors before final resolution, and refuse links, exact registered checkout roots and directories containing them. Outside a Git checkout, relevant literal operations use only the hook's source checkout inventory; unrelated filesystem targets remain outside that policy. Direct recursive cleanup holding an internal junction is handed to the guard too, so a junction cannot hide an external descendant. These are bounded direct-command checks: computed paths outside a known repository, arbitrary/custom program aliases, and unsupported indirect evaluators are outside their coverage. They do not sandbox arbitrary code. The lifecycle helper repeats physical link and ownership checks regardless of hook availability; no recursive install scan runs for unrelated shell commands.

In a PowerShell reading, the installed built-ins `del`, `erase`, `rd`, `ri`, `rm`, and `rmdir` use Remove-Item roles; `ni` uses New-Item; `cd`, `chdir`, and `sl` use Set-Location; `pushd` and `popd` use Push-Location and Pop-Location. The explicit alias table is shared by recognition and canonical operand dispatch, including supported nested PowerShell command strings. Explicit Bash commands retain Bash grammar; unknown-shell input still requires both readings to allow. Custom aliases, profile overrides and arbitrary command resolution are not evaluated.

Recognized explicit CMD execution is refused in a known repository, including harmless calls, quoted/unquoted command strings and CMD reached through supported nested shells. CMD comments, switches, drive changes and expansion are not interpreted with the Bash reader. This intentional compatibility restriction also covers `cmd /c mklink`; use direct PowerShell/Bash commands or the guarded lifecycle instead. Literal prose mentioning CMD remains permitted. Outside a known repository, explicit CMD execution is outside this boundary's coverage; the supported lifecycle runs from the main or owned checkout and repeats its own checks.

On Windows, a rooted cleanup/setup operand without a volume (for example `\path` or `/path`) is refused in known repository contexts across the supported readers, including link destination/target roles. Such a spelling depends on the executing shell's current drive and is not independently fully qualified. Volume-less location changes retain uncertainty for relative mutations; genuinely fully qualified ordinary targets remain independently checked. This boundary does not emulate drive/provider state or provide arbitrary-code containment.

Supported npm setup destinations include `--prefix`/`-C` and `--workspace`/`-w`, with inline or separated literal values before or after the setup selector. Their values retain raw-shell verification and physical ownership checks; unresolved values refuse. Read-only commands and quoted documentation remain permitted. The helper requires a root manifest and verifies npm's physical local prefix using the same configuration and local/project mode as its install. It explicitly disables global, dry-run and lockfile-only modes while retaining prefix, registry/auth and config-file inputs. An unverifiable global prefix (including a value npm protects) or local/global prefix collision is refused before installation: repair the prefix configuration while preserving registry/auth settings, then retry the helper. This avoids npm's self-install branch without silently relocating system configuration. Direct-command analysis does not evaluate configuration files or arbitrary install scripts; use the checked helper for the lifecycle guarantee.
