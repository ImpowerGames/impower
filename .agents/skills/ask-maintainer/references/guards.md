# Guards on maintainer requests

Two repository hooks hold these rules in every harness that runs the shared hooks. A `gh issue` comment, edit, close or reopen, or a REST call that changes an issue, is refused on a number the tool knows as a request, and the refusal names the tool command to use instead. Issue, pull request and comment text that claims a maintainer decision is refused unless it cites a request whose answer `read` or `record` has seen; quoting an existing record in a blockquote or in quotation marks passes. A bare `#N` cites a request only in text published to the tickets repository; anywhere else, such as a pull request body, cite it as `<owner>/<repo>#N`, the autolink form `I-N` or its address. Only text sent to GitHub is checked, and a JSON or form request body is read for its `body` and `title`. When an agent went ahead because no answer came, write "decided by fallback" instead of naming the maintainer.

The hooks read the request index the tool keeps on this machine (`impower/maintainer-requests` under `%LOCALAPPDATA%`, or elsewhere under `$XDG_STATE_HOME` or `~/.local/state`): `file`, `tag`, `read`, `record`, `revise`, `withdraw`, `wait` and `answer-from-chat` add or update the requests they touch, and `list` adds every request in GitHub, open or closed. When the index cannot be read the hooks refuse the command and say to run `list`. Like the typed-issue hook, they read command text only, so an issue number or body built from a shell variable, or a call made from a wrapper script, is outside what they see.
