# Reviewer prompt template

All commands run from the worktree root unless stated otherwise.

<!-- review-prompt:start -->
> The writer model is `WRITER`; the reviewer model is `REVIEWER`. Review using these configured models.
>
> Context. You are reviewing a fix for issue #N in the Impower monorepo, round ROUND on PR #P at reviewed head HEAD. Confirm that HEAD is still checked out before reviewing and before posting; a changed head aborts the attempt. The change's goal for the people who use the product, as the coordinator states it from the issue or, when there is no issue, from the PR description, is: TASK. The diff is at `DIFF`; the working tree under review is the git worktree at `WORKTREE` — read files from there, not from the main checkout. Your lens is \<LENS\>; if that is `undirected`, you have no assigned lens and review the whole change however you see fit, reporting anything wrong with it, and otherwise focus on your assigned lenses. If your lens is `author-experience`, read `.agents/skills/review-pr/references/author-experience.md` in the worktree before anything else and perform the author's task in the running editor before you read the diff. Every reviewer, including an undirected reviewer, must check test honesty and repository rules as baseline responsibilities; the repository rules are in `AGENTS.md` at the worktree root and the files it links. PREVIOUS Record your complete independent first pass in a private file before reading any other current-round review report; prior-round reports remain available for checking corrections.
>
> Your job. Judge whether this change should merge as it stands. That means three questions, in this order: does it break anything, does it actually resolve the issue rather than its symptom, and does it leave the code in a state the next person can maintain. A change that passes its tests can still fail the second or third question, and a finding under any of the three is a finding.
>
> What counts as a finding. Report at one of two tiers, and label which. A defect is behaviour that is wrong: give severity, `file:line`, a concrete failure scenario (inputs → wrong output), and the code evidence or probe that establishes it. A quality finding is code that is correct today but costs someone later: give `file:line`, the specific consequence and who pays it (the next editor, the reader, the maintainer of a duplicate), and, where one exists, the surrounding code or existing helper it diverges from or duplicates. Quality findings are held to that evidence bar, not to taste: "this duplicates the helper at `file:line` and the two will drift" is a finding; "this could be cleaner" is not. Look in particular for duplication of code that already exists in the repository; divergence from the conventions of the surrounding code; new code, exports or configuration nothing uses; changes outside the scope of the issue; names or comments that misdescribe what the code does; comments that narrate how the code used to behave rather than what it does now; new public surface without a caller that needs it; errors caught and discarded; and a PR description that omits or misstates what the diff changes. Use exactly three severities: `blocking` for a defect, a repository-rule violation, or a test that does not prove what the PR claims; `should-fix` for a quality finding worth correcting before merge; `optional` for anything the writer may reasonably decline. Separately label unverified concerns and coverage gaps, stating what evidence is missing; do not present them as confirmed defects. Do not pad with non-findings, and if you cannot name the consequence of a quality finding it is not one.
>
> Test honesty. The change's tests must prove the fix: check that the regression test fails on the base revision without the fix and passes with it, that it exercises behaviour the issue describes rather than the implementation's internals, that nothing is skipped, focused or weakened to make the suite pass, and that any assertion the PR relies on actually asserts something. A test that would pass with the fix reverted is a `blocking` finding.
>
> Constraints. Do not edit, create, or delete any file inside the repo tree. Never run the change under review destructively against this machine's repository, its worktrees, or the shared VS Code data directory the extension driver serves builds from; every destructive experiment runs in a scratch repository under your private scratch directory, with `pwd` printed in the same command as any destructive call. Put every file you write under your own subdirectory `REVDIR`, never the writer's private scratch directory directly and never a directory that already has files in it. Before running vitest as a probe, check for a vitest process already running and wait for it to exit; the writer may be mid-suite, and the machine allows only one run at a time. A probe names the test files it needs, with a 1024 MB heap and one fork; do not run a whole package or the unfiltered typecheck, since the pull request's Test Suite and typecheck workflows run those and their results for the head are the evidence to read. If you mutate a copy of a file with JavaScript's `replace`, escape `$` in the replacement or pass a function, because a dollar sign followed by `&`, by a digit, or by another dollar sign is substituted and a corrupted copy reads as zero failures; read the copy back before trusting what it reports.
>
> Report format. Start with the heading `### Adversarial review — <LENS> (<MODEL>)`, where MODEL is the configured reviewer model, then a line naming round ROUND and reviewed head HEAD. Then a short `Coverage` section listing what you examined and what you ran, so that a report with no findings still records what was checked. Then the findings, most severe first, each with its tier and severity, and then the unverified concerns and coverage gaps. If you have no findings, keep the coverage section and end with the single line "No findings through this lens."
>
> Posting. When your review is done, post it as a comment on PR #P: write the full report to a markdown file under `REVDIR` (never inside the repo), using an editor tool rather than a heredoc. Then run `gh pr comment P --body-file <that file>`. Never pass `--body @-` — gh takes it as a literal string and posts a broken comment. Confirm the comment landed by listing the PR's comments with `gh api repos/ImpowerGames/impower/issues/P/comments --paginate --jq '.[] | [.id, (.body | split("\n")[0])] | @tsv'` and finding your heading among them.
>
> Whether or not the comment lands, return your full report as your final report — the same markdown, in full. If you cannot post at all (no `gh` on this machine, an auth failure, a denied permission), do not try to work around it and do not summarise: say in one line that you could not post and why, then return the whole report. The writer will post it for you.
