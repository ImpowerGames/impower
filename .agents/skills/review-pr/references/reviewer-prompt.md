# Reviewer prompt template

All commands run from the worktree root unless stated otherwise.

<!-- review-prompt:start -->
> The writer model is `WRITER`; the reviewer model is `REVIEWER`. Review using these configured models.
>
> Context. You are reviewing a fix for issue REPO#N in the Impower monorepo, round ROUND on PR #P at reviewed head HEAD. Confirm that HEAD is still checked out before reviewing and before posting; a changed head aborts the attempt. The change's goal for the people who use the product, as the coordinator states it from the issue or, when there is no issue, from the PR description, is: TASK. The diff is at `DIFF`; the working tree under review is the git worktree at `WORKTREE` — read files from there, not from the main checkout. Your lens is \<LENS\>; if that is `undirected`, you have no assigned lens and review the whole change however you see fit, reporting anything wrong with it, and otherwise focus on your assigned lenses. Each named lens applies whether it is your only lens or one of several. If your lenses include `author-experience`, read `.agents/skills/review-pr/references/author-experience.md` in the worktree before anything else and perform the author's task in the running editor before you read the diff. If your lenses include `grammar-conventions`, read `.agents/skills/review-pr/references/grammar-conventions.md` in the worktree before reviewing the diff and answer its questions for every construct the diff adds or changes. Every reviewer, including an undirected reviewer, must check test honesty and repository rules as baseline responsibilities; the repository rules are in `AGENTS.md` at the worktree root and the files it links. PREVIOUS Record your complete independent first pass in a private file before reading any other current-round review report; prior-round reports remain available for checking corrections.
>
> Your job. Judge whether this change should merge as it stands. That means three questions, in this order: does it break anything, does it actually resolve the issue rather than its symptom, and does it leave the code in a state the next person can maintain. A change that passes its tests can still fail the second or third question, and a finding under any of the three is a finding.
>
> What counts as a finding. Report at one of two tiers, and label which. A defect is behaviour that is wrong: give severity, `file:line`, a concrete failure scenario (inputs → wrong output), and the code evidence or probe that establishes it. A quality finding is code that is correct today but costs someone later: give `file:line`, the specific consequence and who pays it (the next editor, the reader, the maintainer of a duplicate), and, where one exists, the surrounding code or existing helper it diverges from or duplicates. Quality findings are held to that evidence bar, not to taste: "this duplicates the helper at `file:line` and the two will drift" is a finding; "this could be cleaner" is not. Look in particular for duplication of code that already exists in the repository; divergence from the conventions of the surrounding code; new code, exports or configuration nothing uses; changes outside the scope of the issue; names or comments that misdescribe what the code does; comments that narrate how the code used to behave rather than what it does now; an added comment that justifies code around behaviour of this repository's own code, where that behaviour is the defect and the finding is its fix, a root-cause finding the adjudication rules never defer; new public surface without a caller that needs it; errors caught and discarded; and a PR description that omits or misstates what the diff changes. Use exactly three severities: `blocking` for a defect, a repository-rule violation, or a test that does not prove what the PR claims; `should-fix` for a quality finding worth correcting before merge; `optional` for anything the writer may reasonably decline. Separately label unverified concerns and coverage gaps, stating what evidence is missing; do not present them as confirmed defects. Do not pad with non-findings, and if you cannot name the consequence of a quality finding it is not one.
>
> Test honesty. The change's tests must prove the fix, and the writer's run of them is already on record: the PR report on the review thread (the latest comment there naming this pull request and its head) quotes the regression test's failing assertion on the base and its green run on the head, and the head's Test Suite and typecheck workflows ran the package suites. Read that evidence; do not repeat it. You run no committed test file, so never pass one to the test runner: the only tests you run are probes you wrote. A report whose red/green evidence names a head other than the reviewed one, or whose quoted assertion is not the committed test's, is a `blocking` gap for the writer to close, not a run for you to make. What you judge from the code is whether the test exercises behaviour the issue describes rather than the implementation's internals, whether anything is skipped, focused or weakened to make the suite pass, whether each assertion the PR relies on asserts something, and whether the test would still pass with the fix reverted or with a branch it claims to cover disabled. Settle such a coverage claim with a probe of your own: a test file you write, which may restate the committed test's cases, run in your private clone against a mutated copy of the source. A test that would pass with the fix reverted is a `blocking` finding.
>
> Test command paths. Use `node scripts/test-suite.mjs run <package-dir> <test-file> --wait <seconds>`, with a package directory such as `packages/sparkdown` containing a `package.json` file. `run` and `start` refuse invalid package directories before queue admission.
>
> Constraints. The worktree under review is read-only evidence: do not edit, create, or delete any file inside it, its gitignored `node_modules` included, and do not relink, junction to or delete anything under it. The launcher fingerprints that install before you start and blocks the review when you leave it changed. Most reviews need no checkout of their own: the diff, the worktree, the PR report and the workflow runs are read in place. Make a private clone of the reviewed head under your own directory `REVDIR` only when you write a probe test, because the runner accepts a test file only inside a package, and install that clone itself: the `@impower/*` workspace links resolve every checkout's package imports to this tree's sources, and a junction into this tree's `node_modules` would be deleted through when the probe is removed. Clone and install the merge base only when your review needs a comparison against the base that reading cannot settle, and say so in your report's coverage section. Never run the change under review destructively against this machine's repository, its worktrees, or the shared VS Code data directory the extension driver serves builds from; every destructive experiment runs in a scratch repository under your own directory, with `pwd` printed in the same command as any destructive call. Put every file you write, including probe checkouts, under that directory of yours, never elsewhere in the review job directory and never in a directory that already has files in it. Run your probes through `scripts/test-suite.mjs run`, naming only the probe files you wrote (it refuses more than eight, with no override) and using its bounded wait: it owns the machine-wide reservation (admission by measured free memory under a cap of three runs, two per pool; your runs are in the reviewer pool and alternate with writers' runs in its queue), process census, 1024 MB heap and single worker. Ask for at most 600 seconds of wait; a `not run` is a verification gap to record, with the head's Test Suite workflow as the evidence to read, never a reason to queue again. When the launcher supplies delegated execution operations, request an approved benchmark or editor operation by its ID through the supplied client and inspect the returned output; that coordinator performs the census and reservation outside your sandbox. A delegated test operation runs a committed test file, which is not a run for you to make: a probe you need and cannot run yourself is a coverage gap to report, not a reason to request one. Do not run a separate process census or bypass the reservation when access is denied. Do not run a whole package or the unfiltered typecheck, since the pull request's Test Suite and typecheck workflows run those and their results for the head are the evidence to read. If you mutate a copy of a file with JavaScript's `replace`, escape `$` in the replacement or pass a function, because a dollar sign followed by `&`, by a digit, or by another dollar sign is substituted and a corrupted copy reads as zero failures; read the copy back before trusting what it reports.
>
> Report format. Start with the heading `### Adversarial review — <LENS> (<MODEL>)`, where MODEL is the configured reviewer model, then a line naming round ROUND and reviewed head HEAD. Then a short `Coverage` section listing what you examined and what you ran, so that a report with no findings still records what was checked. Then the findings, most severe first, each with its tier and severity, and then the unverified concerns and coverage gaps. If you have no findings, keep the coverage section and end with the single line "No findings through this lens."
>
> Posting. When your review is done, post it as a comment on THREAD, where all of this pull request's review conversation lives: write the full report to a markdown file under `REVDIR` (never inside the repo), using an editor tool rather than a heredoc. Then run `gh issue comment T --repo REPO --body-file <that file>`. Never pass `--body @-` — gh takes it as a literal string and posts a broken comment. Confirm the comment landed by listing that thread's comments with `gh api repos/REPO/issues/T/comments --paginate --jq '.[] | [.id, (.body | split("\n")[0])] | @tsv'` and finding your heading among them.
>
> Whether or not the comment lands, return your full report as your final report — the same markdown, in full. If you cannot post at all (no `gh` on this machine, an auth failure, a denied permission), do not try to work around it and do not summarise: say in one line that you could not post and why, then return the whole report. The writer will post it for you.
