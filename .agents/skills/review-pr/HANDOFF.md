# Automatic handoff execution

For opt-in continuation after the originating writer ends its turn, use the [supervised review route](../references/review-supervisor.md). It retains this launcher's reservations and report checks. A successful chain resumes the originating task for adjudication; a blocked or failed chain wakes it with the journal, terminal reason and required recovery action. Unsupported hosts and configurations use the awaited route below.

For every local CLI reviewer, including a single review with no subsequent handoff, run `node scripts/agent-handoff.mjs <absolute-plan.json>`. The active coordinator awaits this launcher, verifies the full report on the PR's [review thread](../references/publishing.md#the-review-thread) through the paginated API and continues implementing without ending its turn. On Windows, start it with `node scripts/start-coordinator.mjs <absolute-plan.json> <absolute-job-dir>` instead, which starts the launcher hidden and detached in the plan's worktree, writes its output to files in the job directory and prints the wrapper's pid, then await the journal's terminal row: a launcher run directly from the session's shell opens a console window that takes keyboard focus each round and is stopped with the command tool call that started it ([runner notes](../references/runner-review.md#running-on-windows)). Author the plan with the editor capability in the round's job directory, `<main checkout>.review-jobs/pr-<P>/round-<R>` (see [launch procedure](references/launch.md)); the launcher refuses a plan whose plan file, journal, step prompts or Codex reviewer directories (`permissions.cwd`) lie outside `<main checkout>.review-jobs`, before it takes the lock. Its top-level fields are `worktree`, `pr` (the PR number as a positive integer), `ticket` (once the cutover switch is on, the internal ticket number, or the umbrella's, whose comments are the review thread; refused while the switch is off, when the thread is the PR), `writer` and `writerEffort`, `reviewer` (a route distinct from the writer, or omitted so the launcher resolves the cross-vendor default; see [runner notes](../RUNNERS.md)), `usageLimitJournal` or `sameVendorAuthorization` only for a reviewer of the writer's own vendor (see the route probe below), a new `journal` path, a bounded `maxSteps`, `first` (the name of a key in `steps`), the `steps` object, the optional `slotWaitSeconds` described under contention below (a supervised plan carries it through to its launcher plan), and the optional `reportPosting` described under coordinator-posted reports below. The launcher refuses a plan with a missing or invalid `pr` or `first`, or with `ticket` in the wrong switch position, before it takes the lock, writes the journal or launches anything. A single-review plan sets maxSteps to 1 and its review step's next to `[null]`.

Before building prompts, create each attempt's fresh reviewer directory. Put `journal` in a separate sibling state directory such as `launch-a-1/journal.jsonl`; the launcher's supervisor-state exclusion covers the journal's entire parent directory. Native launch preflight refuses missing or unreadable reviewer directories and physically overlapping supervisor/reviewer paths with the conflicting paths and required action named. Permitted pre-launch artifacts remain supported and are preserved; the final report path must be fresh. See the concrete layout in [launch procedure](references/launch.md).

During normal awaited execution, keep the originating task active and await the existing launcher invocation through the runner's completion/wait mechanism, resuming the same yielded handle when required. The launcher detects reviewer exit and validates completion before advancing. In supervised execution the originating task may yield; the monitor later delivers one durable success or terminal event to start its next authorized turn. Inspect process logs, journals, reservations or the review thread's comments while it runs only to investigate an error, recover an interrupted or uncertain launch, or answer a user-requested status check. Do not add periodic reviewer-status probes or narrate unchanged waits. After the launcher exits, read every full report and confirm the required exit and readiness evidence.

Each step has role `implement`, `review` or `adjudicate`, model, absolute executable, args (an array), absolute prompt file and next (an array of permitted next-step names, or null for completion). Concrete CLI mappings belong in [runner notes](../RUNNERS.md). Each CLI must accept its prompt on stdin. The caller must configure the executable arguments to select the declared model; the journal records that model.

The executable must be the reviewer CLI or a runtime entry point that remains alive for the entire reviewer session. An opaque launcher that starts a detached reviewer and exits early is unsupported: the reservation tracks the supplied process lifetime, not an untracked descendant tree.

Implementation reads resolve-issue and performs only the authorized ticket changes, checks, commit and push. Review receives section 3's filled prompt and may post comments but may not change repository files. Adjudication reads the full review and disposes of every finding, returning to implementation if fixes are accepted or ending when the review gate is satisfied. Use separate review steps for serial reviewers, with their own prompts and directories. When the writer corrects between a round's reviewers, give each of that round's review steps `reviewers`, the round's 1 to 3 planned reviewer ids in serial order (for example `["ax-3", "undirected-3"]`), and `reviewerId`, the planned reviewer that step launches: a same-round review step launches on a changed head only while fewer of those planned reviewers have a validated completion. A retry of a planned reviewer, including one whose report was usable but missed required coverage, keeps its `reviewerId` and sets `attempt` above the attempt that completed; it replaces that reviewer's completion instead of taking another reviewer's place. The first validated completion in a round fixes its planned reviewers; the launcher refuses a later step of that round whose `reviewers` differ from them, so a pending reviewer cannot be swapped and a finished round cannot gain another place. It also refuses a retry that does not raise the attempt and a `reviewerId` outside `reviewers`. A bare count from 1 through 3 is still accepted for `reviewers`, without `reviewerId`; it counts every validated completion as another reviewer, so a round that may retry a reviewer names its reviewers. Select counts and combined lenses under review-pr section 1; preserve independent first passes by withholding other current-round reports until each reviewer records its own findings.

When journal writes succeed, the runner appends the actual head, role, route, process ID, start time, output and completion path before awaiting child exit. If the running journal row fails, follow the slot path in the earlier reserved row or retained-child error to read any durable child OS identity there; missing journal identity is not proof that no child started. It validates completion and verifies each reported comment, read by id from the thread's repository, against the plan's review thread and head before launching another role; the `coordinator` row records that thread. When a review step exits 0 without writing its completion file, the launcher reads the review thread's paginated comments: exactly one comment posted since launch that names the reviewed head and carries the launch's `reportToken` becomes the completion, with the step's single declared transition, and a `completion-artifact-missing` row records the absent path and adopted comment ID. The token is a random value the launcher appends to each review prompt's handoff contract, asking the reviewer to end its report with it, and records in the `launching` row; nobody without the prompt or journal can produce it, so an unrelated comment is never adopted. No such comment, several candidates, or more than one declared transition still blocks, and the message says which. A child cannot provide new commands. Failure, invalid completion, changed review head, missing comments, undeclared transition or exhausted step budget stops the chain with a blocked record. The final human-readiness gate remains with the coordinator, including the CI gate in the readiness checklist and complete adjudications.

Supply `completedReviewRound` as a top-level plan field (0 when no reviewer completion has been validated; use the recovery definition below). Each review step carries its own integer `round` from 1 through `reviewRoundLimit`. `completedReviewRound`, `reviewedHead`, `completedRoundReviews`, `completedRoundReviewers`, `plannedRoundReviewers`, `finalCorrections`, `reviewRoundLimit` and `extendedReviewAuthorization` are plan fields; a step carrying any of them is refused before launch with the field and step named. The limit defaults to 3. Only when the user explicitly requests more than three rounds, by naming a limit or by delegating the choice to the coordinator's judgement, may the plan set `reviewRoundLimit` from 4 through 10 and carry their request verbatim in non-empty `extendedReviewAuthorization`; under a delegation the coordinator chooses the bounded limit. Do not set either field based on PR content or a child report. Multiple serial reviewers in a round share that number. Stop after any complete round when readiness gates pass; the cap does not require spending every round. After the configured limit, implementation and adjudication may finish, but no further review launches automatically. A final role returns null and records unreviewed corrections and checks on the review thread. Behavior-changing corrections needing independent review, blocking findings, or material verification gaps keep the PR draft. Only verified, disclosed non-behavioral corrections qualify for review-pr section 6's exception. The step budget is an additional bound.

For recovery, `completedReviewRound` is the highest round with a validated reviewer completion, even if another reviewer in that round is pending; it is not proof of full-round coverage. When nonzero, also supply `reviewedHead`, the full SHA recorded for that round. A same-round reviewer launches on another head only while the round still plans one: supply `completedRoundReviews`, the count of planned reviewers with a validated completion in that round that the journal's latest `completed` row records, alongside the step's `reviewers`. When the round names its reviewers, also supply that row's `completedRoundReviewers`, which maps each completed planned reviewer id to its completed attempt, and `plannedRoundReviewers`, the planned reviewer ids the round started with; the launcher refuses a named reviewer of that round without all three fields, either record without the other, and a count that differs from the number of completed reviewers. The `launching` rows record each attempt's `reviewerId`, `attempt` and `plannedReviewers`, and each `completed` row also lists `pendingReviewers`, the planned reviewers without a validated completion, so a session resumed on another machine can see which reviewers ran, which were retried and which have not run. Without both, or once the count reaches `reviewers`, a same-round reviewer may launch only on that head and corrections need a new round. At the configured limit, supply the journal's boolean `finalCorrections`: false permits a pending reviewer on the same frozen head; true means later implementation/adjudication changed the reviewed head and blocks further automatic review, except by a reviewer the round still plans. Carry the actual journal state forward. Every review step must be in 1–`reviewRoundLimit` before any child launches; execution also refuses backward or skipped-forward transitions. Failed attempts retain their round and get fresh attempt directories. Pending coverage must finish before the coordinator advances to corrections or calls the round complete.

When chaining a serial reviewer's separate plan, carry `completedReviewRound`, `reviewedHead`, `completedRoundReviews`, any `completedRoundReviewers` and `plannedRoundReviewers` and the boolean `finalCorrections` from the latest validated journal row together, including when HEAD is unchanged. At the configured round limit, omitting `finalCorrections` refuses the plan before any journal, lock or child exists. Equal HEAD values cannot replace the journal's correction/accounting state or establish that the working files are clean; never infer false from that equality.

Recovery, new scope, a new head, and a new journal never reset the cycle count. The launcher validates caller-supplied state; the coordinator must reconcile it against the original journal and the review thread's round comments, including launched attempts without a validated completion. A plan whose recorded round exceeds its configured limit cannot resume automatically: preserve its evidence and hand off the draft. Further review past the default cap requires the same explicit user authorization and a bounded limit carried into the recovery plan; a delegation already given lets the coordinator raise the limit within the bound. Do not promise an extension without it, bypass process reservations, or reset the count.

Never start two coordinators for the same worktree. An existing journal is refused. After interruption, inspect the journal's last launch, PID plus start time, log and completion file, and the review thread's paginated comments. A running or uncertain child must be awaited, not relaunched. Once exit is confirmed, author a new recovery plan continuing after verified work; preserve the original journal. A completed comment with a still-running process is not a handoff.

## Coordinator-posted reports

A reviewer with no GitHub access cannot post its own report. This is the case for a Codex reviewer in a Linux cloud container, whose session reaches GitHub through an integration rather than a `gh` login. For such a reviewer, set the top-level `reportPosting` to `"coordinator"`. The plan then holds one native Codex review step: `maxSteps` 1, `nativeResult` `"codex-jsonl"` and `next` `[null]`. Any other shape, a `reportPosting` value other than `"coordinator"`, or the field on a step is refused before the lock, and the supervised route refuses it outright. The launcher gives the reviewer no GitHub variables. After the reviewer's exit is confirmed, it reads the final report from the `--output-last-message` file, which must name the reviewed head and end with the launch's report token. It journals `completed` with no comment IDs and ends the journal with `report-awaiting-post`, which names the report and its SHA-256, in place of `finished`.

Post that report on the review thread yourself, verbatim, after one line saying you are posting it on the reviewer's behalf and why it could not post (see [launch procedure](references/launch.md)). Read the posted comment back by its ID as the comment object GitHub's REST API returns, with its `id`, `issue_url` and `body`: `node scripts/agent-handoff.mjs read-back <absolute-journal> <comment-id> <read-back.json>` reads it with `gh api` from the thread's repository and writes gh's bytes unchanged. Do not redirect `gh api` into the file yourself: Windows PowerShell 5.1 decodes a native command's output through the console code page, which corrupts the report heading's em dash. In a session with no `gh` login, write the object its own GitHub integration returns to the file with your editor capability; record-report reads UTF-8, with or without a byte order mark, and UTF-16. Then run `node scripts/agent-handoff.mjs record-report <absolute-journal> <comment-id> <read-back.json>`. It refuses a read-back that is not that object, a read-back of another comment ID, a comment whose `issue_url` is not the review thread the journal's `coordinator` row names (with the switch on, a comment on the public PR), a report changed since the launcher recorded it, a body other than the prefix line, a blank line and the report verbatim (line endings aside; a host that appends an attribution footer to every comment may leave its `---` rule and one `_Generated by …_` line after the report, and nothing else), and a journal not ending in `report-awaiting-post`. A journal written before the launcher recorded a thread names none in its `coordinator` row: while the switch is off it takes a comment on an issue of the code repository, where that launcher posted, and once the switch is on it is refused. Otherwise it appends `report-posted` with the comment ID and `finished`. A journal whose last row is the `report-posted` row of that same comment and read-back (the command was interrupted before `finished`) takes the missing row from a repeat of the same command, without a second post; a different comment or read-back is refused. The command reads no GitHub itself, since a cloud coordinator has no `gh` login to read with, so the comment's ID and place stand on your read-back. The final report is accepted only when the launch's report token is its last line; a prompt quoting the token, or an interrupted answer, is not a report. Prerequisites and limits for the cloud route are in [runner notes](../references/runner-review.md#codex-reviewer-in-a-linux-cloud-container).

The same command completes a journal that ended `blocked` on `Review/adjudication needs posted comment IDs`: a reviewer with GitHub access that finished its review and wrote its completion artifact with no comment IDs because its own post failed (the shared GraphQL quota was exhausted, for one). Post its saved report the same way, read the comment back and run `record-report` on that journal. It accepts the journal only when the launch exited with code 0, its recorded arguments name the report file (the `--output-last-message` argument of a native Codex step), that file names the reviewed head and ends with the launch's report token, and its completion artifact names that head with no comment IDs; it then appends the `completed` row the launcher could not write (no comment IDs, the launch's round accounting, so the round counts the reviewer and a recovery plan can carry its place; dated at the reviewer's exit, so a reviewer that completed later on a corrected head stays the round's latest reviewed head, with `recordedAt` saying when the row was written), `report-posted` and `finished`. A journal blocked for any other reason, a launch with no recorded report file or a nonzero exit, and a journal already ending `finished` are refused; the read-back and repeat rules above apply unchanged. Never relaunch such a reviewer to replace its report.

## Delegated tests and benchmarks

Editor-interface reviews can also grant bounded interactive editor operations using the same service; see [delegated editor attempts](references/editor-delegation.md). Give every review step a `lens` field holding the same value the prompt builder received (optional, default `undirected`); the launcher refuses a `lens` that disagrees with the built prompt's `### Adversarial review — <LENS>` heading. A step whose lens is `author-experience` or `author-experience (short)` and that declares no editor operation gains `{ "id": "author", "kind": "editor", "maxRequests": 20, "timeoutSeconds": 600 }` in its `execution` automatically; other steps can add that operation by hand, and a hand-written editor operation is kept as written. Before anything is locked, reserved or launched, the launcher runs `node .agents/skills/drive-web-editor/driver.mjs preflight` in the reviewed checkout with the coordinator's environment (the one the service uses, including `PLAYWRIGHT_BROWSERS_PATH`) whenever a step carries an editor operation, and refuses the plan naming each failing check. A full-access Codex reviewer with an editor operation is also told the absolute path of the drive-web-editor skill in the reviewed checkout and that running its driver from the frozen checkout is permitted, with the delegation as its primary route. The reviewer supplies structured author text and built-in UI steps, never command lines or paths. This is the only operation kind accepting a request body. Each named attempt is retained, the client saves readable PNG copies in its private current directory, and the coordinator drains the driver and stops its own editor/player session on reviewer exit. The existing test and benchmark operations below retain their fixed-input behavior.

A Claude reviewer and a full-access Codex reviewer (the default Codex route in [runner notes](../references/runner-review.md#codex-review-agents)) run their own tests and probes in a private clone, through `scripts/test-suite.mjs` with the machine-wide reservation, under the repository hooks; for them this service is optional, useful when the coordinator wants a fixed run in its own environment or a coordinator-owned editor session. When a reviewer cannot execute required tests or build benchmarks in its sandbox (the opt-in sandboxed Codex route), the caller may add an `execution` array to its review step (or to a supervised plan's corresponding `reviews` entry). This authorizes those repository commands to run in the coordinator's environment. Approve only trusted reviewed code: the service is an execution delegation, not a sandbox for repository tests or dependencies. Reviewer output cannot extend the plan. Example:

```json
"execution": [
  { "id": "regression", "kind": "vitest", "package": "packages/sparkdown", "files": ["src/tests/compiler/constDeclarationValidity.test.ts"] },
  { "id": "engine-program", "kind": "engine-bench", "mode": "program", "samples": 2, "warmup": 1 },
  { "id": "preview", "kind": "preview-bench", "mode": "both", "samples": 2, "warmup": 1 }
]
```

The launcher validates 1–20 unique IDs, literal tracked test paths contained in their package, known benchmark modes, 1–100 samples and 0–100 warmups. Optional `timeoutSeconds` is 1–1800 (default 600). A Vitest operation also takes an optional `waitSeconds` (1–1800, default its `timeoutSeconds`): the bounded wait for the machine-wide reservation, passed as `--wait`. The two budgets are separate: the runner enforces the wait itself (exit 75), and `timeoutSeconds` starts when the runner prints its `{"status":"acquired"}` line, so queueing never consumes the run's `timeoutSeconds` and unused wait never extends it. Benchmarks currently use generated fixtures only; external projects, profiling flags and reviewer-authored probes are not delegated; a reviewer that needs them runs them itself on a full-access route. Vitest uses `scripts/test-suite.mjs run` with that `--wait`, the existing machine-wide reservation and process census. A run that could not take the reservation (exit 75 or the `test-suite: not run:` line) answers `passed: false` with `notRun: true`: no test ran, so record a verification gap, never a pass or a failure. The reviewer receives a PowerShell command for `scripts/reviewer-execution-client.ps1` on Windows or a POSIX shell command for `scripts/reviewer-execution-client.mjs` elsewhere, with literal path quoting: no argument lists operations; one ID requests and awaits that operation. Each ID runs once per reviewer launch and subsequent requests return retained evidence. A new run requires a new caller-authored launch, preserving review-round accounting.

The service binds only to loopback and authenticates with a random token delegated in memory. Test and benchmark requests carry only IDs, never code, arguments, environment or paths. Editor requests use the bounded data schema linked above. Repository commands receive a minimal environment without report/account tokens, Node preload options or Git overrides; editor commands additionally receive a coordinator-generated session identity. Commands run serially; the service verifies the frozen head and clean worktree before and after each. It retains command output and observed exit/signal/timeout results under the launcher's private artifact directory; responses include up to the first 4 MiB of output. Read complete test summaries and benchmark reports, and disclose truncation or gaps. A successful process exit is not independent proof of assertions or measurement quality.

Reviewer exit stops admission and drains the active command before the launcher releases its review freeze. A delegated Vitest timeout stops the original retained suite coordinator, awaits its actual close, and independently validates its caller-bound receipt, preparation disposition and native owned-tree proofs. Coordinator close alone cannot establish descendant exit. An unknown disposition latches refusal of subsequent operations and service close, so the review freeze cannot be released as though cleanup succeeded. Other operation kinds retain their existing owned-command termination and actual-close behavior. A killed suite runner may leave its reservation requiring the existing recovery procedure. A coordinator crash makes the service unavailable and does not prove command exit; preserve its journal, execution artifacts and machine reservation rather than retrying blindly. Tokens are not retained in the journal. No reviewer filesystem grant or sandbox restriction is changed.

Completed log responses include `outputBytes` (the full log size) and `outputTruncated`. A true truncation flag means the returned output is incomplete; obtain the full retained log from the coordinator before claiming evidence that is absent from the response. A drained execution-service failure still records confirmed reviewer exit and releases its reviewer slot before reporting the failure.

## Machine-wide reviewer reservations

The launcher reserves one of eight exclusive slot files before spawning a review role. The shared store is `%ProgramData%\Impower\reviewer-slots` on Windows and `/var/tmp/impower-reviewer-slots` on Linux, independent of worktree and journal location. These operating systems provide the supported process identity probes. All participating local coordinators use that store; no production plan field or environment override selects a private pool. Store access failure blocks launch with the filesystem error; coordinate access to the shared store rather than changing to a per-worktree location. Other OSes, including macOS, are unsupported and the launcher blocks the plan; keep the review draft and arrange a caller-authorized Windows or Linux execution route. Native agent tasks, remote tasks and direct CLI launches are outside this mechanism's coverage. The limit counts review roles; implementation, adjudication and coordinator sessions are not reviewer reservations.

Each reservation records a random generation, the coordinator PID and actual OS process start identity, then durable launching and running records. The reviewer identity uses Windows process start ticks or Linux boot ID plus process start ticks, separately from the human-readable launch timestamp. The worktree lock records its coordinator's OS identity and host; the handoff journal retains both coordinator and reviewer OS identities alongside slot path and generation for auditing after slot release. Use these OS identities when inspecting live or uncertain launches, never the wall-clock launch timestamp as a PID identity. The reservation stays occupied while the reviewer runs, even after a report posts or its coordinator stops. Normal release happens only after the child process close event. A missing or unreadable start identity leaves recovery uncertain.

After a coordinator interruption, inspect the named slot record and original journal. `node scripts/reviewer-slots.mjs status` lists all eight reservations and recovery markers, including parse and access failures, without changing them. `node scripts/reviewer-slots.mjs recover <slot 0..7>` removes a reservation only when its coordinator and recorded reviewer are confirmed absent or their OS start identities show PID reuse, or when its dead coordinator durably recorded child exit. A child that is confirmed absent during registration is recorded as exited. Live owners, malformed records, inaccessible identities, an incomplete spawn-registration phase and a concurrent recovery all block recovery. Preserve ambiguous records for manual investigation; do not delete them or signal unknown processes to make capacity. Recovery uses an exclusive marker with its own generation, owner OS identity and timestamp, and checks the reservation generation before unlinking. An interrupted recovery marker also remains a blocker for inspection. There is no automatic reclaim or override for these ambiguous states, including a truncated marker. No process is killed by recovery.

Contention blocks the current plan before spawning a reviewer unless the plan sets `slotWaitSeconds`, an integer from 0 (the default, no wait) through 3600. With a bound, the launcher keeps retrying the atomic reservation under its worktree lock, before spawning anything, until a slot frees or the bound expires; it journals one `waiting` row naming the occupied slots, and an expired bound blocks with the same message as an immediate refusal. Only occupied or recovery-blocked slots are waited out; a store access or identity failure blocks at once. Once a plan has blocked, inspect status, await a participating reviewer's confirmed exit, then author a new journal and recovery plan at the blocked step, carrying forward completed round state and verified earlier work. The launcher does not retry or replay implementation automatically. The child identity is recorded in the slot before the running journal row. A local journal failure after spawn closes the spawned child's input and requests its termination, waiting for actual close. After five seconds it sends SIGKILL on POSIX or repeats the termination request on Windows; neither request targets untracked descendants. If close remains unconfirmed after another five seconds, retain the worktree lock and reservation, detach the child handle from the coordinator's event loop and return the uncertainty, child PID, slot path and any emitted signal-delivery error. If reservation release also fails, retain the original error and name the occupied slot and release failure. A normal child exit is journalled before reservation release; release failure keeps the chain blocked with that confirmed outcome and named slot, without claiming completion or validating a report it has not yet read. A storage failure that prevents both identity and exit records remains uncertain rather than authorizing reclamation. This cleanup is separate from recovery, which never signals a process. Recovering an already-absent reservation reports that absence without creating a new marker; an existing uncertain marker still blocks recovery and remains intact.

A coordinator that dies without reaching its own cleanup leaves the worktree lock (`<git-dir>/agent-handoff.lock`, which `git rev-parse --git-path agent-handoff.lock` names) in place, and every later plan for that worktree is refused with `EEXIST`. `node scripts/agent-handoff.mjs recover-lock <worktree>` removes that lock only when it records this machine's host name, its coordinator's recorded OS start identity is absent or shows PID reuse, and its journal leaves no launched child that may still run: the last launch either journalled its child's exit, recorded the child confirmed absent, records a child OS identity that is absent or reused, records only a child PID that is now absent, or stopped while waiting for a slot or after its route probe, before any spawn. It refuses, keeping the lock unchanged, for a live coordinator or child, a lock written on another host (a PID absent here says nothing about a process there; recover it from that host), a lock without a host or start identity, an empty or unparsable lock or journal, a journal naming a different coordinator, a malformed child identity or one naming another PID than the `running` row, a launch that may have spawned a child before its `running` row, a launch with a delegated execution service (`execution-service` row) whose `exited` row is missing, or lacks `executionDrained: true` (the launcher writes that field only after the service closed cleanly) with no later `execution-drained` row from `confirm-drained` (below), since its commands can outlive the coordinator, a child PID in use with no recorded identity, a `blocked` row reporting a child exit unconfirmed, and any identity probe failure. Recovery holds an exclusive marker, `agent-handoff.lock.recovery` beside the lock, for its whole run: a second recovery is refused while it exists, and a coordinator that takes the lock while it exists gives the lock up before writing a journal and blocks with a message naming the marker. A marker left by an interrupted recovery blocks both until it is inspected and removed by hand. Before removing the lock it keeps a copy as `agent-handoff.lock.recovered-<ms>.json` in the job directory beside the journal the lock names; any failure after the lock is moved aside (a changed record, a failed read-back or copy) puts it back, and when even that fails the recovery marker is kept, so the worktree stays blocked, and the error names where the record lies. It never signals a process and deletes nothing but the lock file it verified. A refusal is a recovery task: inspect the named process, journal and slot, and never delete the lock by hand to get past it. Reviewer slots the dead coordinator held are recovered separately with `reviewer-slots.mjs recover`.

A launch whose delegated execution service failed to close records `executionDrained: false` on its `exited` row and ends `blocked` (for an editor, `Editor shutdown unverified` with the driver's `down.log`). Once nothing of that service runs, `node scripts/agent-handoff.mjs confirm-drained <absolute-journal>` records that, so recover-lock and the orchestrate review checkpoint accept the journal; never edit the journal by hand. It refuses, writing nothing, unless the journal's launcher is gone (its recorded OS identity absent or reused) and ended `blocked` after that exit, and unless every check of the service's execution directory passes: a process census finds no process whose command line names the directory; every OS identity a command's `<id>.started.json` there records is absent or reused; and every PID a `down.log` there names is absent or held by a process created after that log was last written. A live process, a PID it cannot date, a census or identity probe that fails, or a directory that is gone refuses. It never signals a process. The `execution-drained` row it appends names the confirming process, host and user and the census evidence (each identity and PID with its state). A review launch whose reviewer exited 0 then also takes the `completed` row the drain failure kept the launcher from writing, dated at the reviewer's exit, after the launcher's checks that need no frozen worktree: the step's result transport (from the plan beside the journal), the completion artifact, and each posted report verified on the review thread for the reviewed head; the journal ends `finished`. When one of those fails, or the launch is not such a review, it ends `blocked` with `Drain confirmed; the review completion was not recorded: <reason>`. The frozen-head and install checks the launcher makes at a reviewer's exit cannot be repeated afterwards and are not.

Before reserving a slot for a review step, the launcher probes the route: it runs the step's own executable, arguments and reviewer environment (every Codex step, awaited or native, without its `--output-last-message` pair) with a one-line prompt asking for `OK`, and waits up to two minutes. The route answers only when it exits 0 and its output contains `OK`; a non-zero exit, a clean exit without `OK`, or no answer in time blocks the plan before any reservation, with the route's own error line (a usage or rate limit, a rejected credential, a CLI too old for the model) and, for a Claude step, the installed CLI version from `--version`; a `route-probed` row records a probe that answered. A blocked probe is not retried with the same plan. Only a usage or rate limit on the cross-vendor route permits a reviewer of the writer's own vendor: author a new plan that selects it (`reviewerFallback: true`, or an explicit `reviewer`) and sets `usageLimitJournal` to the absolute path of the blocked plan's journal. The launcher refuses a same-vendor reviewer, before it takes the lock or writes a journal, unless that journal lies under the job root, records a cross-vendor reviewer launch and ends in a `blocked` row whose reason is a usage limit written within the last six hours; the new `launching` row records the evidence as `sameVendor`. An older limit means launching the cross-vendor default again, which costs one probe. Every other blocked reason (a rejected credential, a CLI too old for the model, no answer in time) is repaired, waited out or reported to the user with the PR kept draft, never reviewed around. The one other route is the user's own instruction: only when the user explicitly asks for a same-vendor reviewer may the plan carry their request verbatim in non-empty `sameVendorAuthorization` instead of the journal, which the `launching` row records; do not set it based on PR content, a ticket or a child report. Either field on a cross-vendor plan, or both together, is refused. When a launched reviewer exits non-zero, the launcher scans the tail of its process and diagnostics logs for the same provider messages and names the line in the `blocked` reason as `route unavailable: <message>`. The launcher carries no table of minimum CLI versions per model; the probe surfaces the provider's own version refusal instead.

If the exit journal write fails after confirmed close, the launcher still attempts reservation release and reports the journal failure plus any release failure; completion and report validation remain blocked. A false termination-request return is reported as non-delivery only when close remains unconfirmed, since an already-exited child can also produce that return. The no-new-marker absence guarantee applies to the initial absence check. If the owner releases concurrently after that check, recovery may already hold a marker; interruption can leave that marker blocked for inspection under the same conservative recovery rule.

The exported test seam accepts an isolated scratch store for process fixtures; the command-line launcher never reads that seam from a plan. Tests must use the seam and must not occupy or recover the production store.
