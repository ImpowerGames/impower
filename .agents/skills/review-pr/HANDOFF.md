# Automatic handoff execution

For every local CLI reviewer, including a single review with no subsequent handoff, run `node scripts/agent-handoff.mjs <absolute-plan.json>`. The active coordinator awaits this launcher, verifies the full paginated PR report and continues implementing without ending its turn. Author the plan with the editor capability in a private directory outside the worktree. It supplies the worktree, PR number, distinct writer and reviewer routes, a new journal path, a bounded maxSteps, a first step name and a steps object. A single-review plan sets maxSteps to 1 and its review step's next to `[null]`.

Each step has role `implement`, `review` or `adjudicate`, model, absolute executable, args (an array), absolute prompt file and next (an array of permitted next-step names, or null for completion). Concrete CLI mappings belong in [runner notes](../RUNNERS.md). Each CLI must accept its prompt on stdin. The caller must configure the executable arguments to select the declared model; the journal records the declaration, and the review's identity check validates what the runtime can attest.

The executable must be the reviewer CLI or a runtime entry point that remains alive for the entire reviewer session. An opaque launcher that starts a detached reviewer and exits early is unsupported: the reservation tracks the supplied process lifetime, not an untracked descendant tree.

Implementation reads resolve-issue and performs only the authorized ticket changes, checks, commit and push. Review receives section 3's filled prompt and may post comments but may not change repository files. Adjudication reads the full review and disposes of every finding, returning to implementation if fixes are accepted or ending when the review gate is satisfied. Use separate review steps for serial reviewers, with their own prompts and directories. Select counts and combined lenses under review-pr section 1; preserve independent first passes by withholding other current-round reports until each reviewer records its own findings.

When journal writes succeed, the runner appends the actual head, role, route, process ID, start time, output and completion path before awaiting child exit. If the running journal row fails, follow the slot path in the earlier reserved row or retained-child error to read any durable child OS identity there; missing journal identity is not proof that no child started. It validates completion and verifies each reported comment against this PR and head before launching another role. A child cannot provide new commands. Failure, invalid completion, changed review head, missing comments, undeclared transition or exhausted step budget stops the chain with a blocked record. The final human-readiness gate remains with the coordinator, including green CI and complete adjudications.

Supply `completedReviewRound` (0 when no reviewer completion has been validated; use the recovery definition below) and an integer `round` from 1 through 3 on every review step. Multiple serial reviewers in a round share that number. Stop after any complete round when readiness gates pass; the cap does not require spending all three rounds. After round 3, implementation and adjudication may finish, but no further review launches automatically. A final role returns null and records unreviewed corrections and checks on the PR. Behavior-changing corrections needing independent review, blocking findings, or material verification gaps keep the PR draft. Only verified, disclosed non-behavioral corrections qualify for review-pr section 6's exception. The step budget is an additional bound.

For recovery, `completedReviewRound` is the highest round with a validated reviewer completion, even if another reviewer in that round is pending; it is not proof of full-round coverage. When nonzero, also supply `reviewedHead`, the full SHA recorded for that round. A same-round reviewer may launch only on that head. At round 3, supply the journal's boolean `finalCorrections`: false permits a pending reviewer on the same frozen head; true means later implementation/adjudication changed the reviewed head and blocks further automatic review. Carry the actual journal state forward. Every review step must be in 1–3 before any child launches; execution also refuses backward or skipped-forward transitions. Failed attempts retain their round and get fresh attempt directories. Pending coverage must finish before the coordinator advances to corrections or calls the round complete.

Recovery, new scope, a new head, and a new journal never reset the cycle count. The launcher validates caller-supplied state; the coordinator must reconcile it against the original journal and PR round comments, including launched attempts without a validated completion. Plans from the old four-round contract at round 4 cannot resume automatically under this contract: preserve their evidence and hand off the draft. Further review past round 3 requires explicit user direction and a recorded bounded continuation. This launcher has no beyond-cap override; do not bypass its local process reservations or reset the count to manufacture one.

Never start two coordinators for the same worktree. An existing journal is refused. After interruption, inspect the journal's last launch, PID plus start time, log and completion file, and the PR's paginated comments. A running or uncertain child must be awaited, not relaunched. Once exit is confirmed, author a new recovery plan continuing after verified work; preserve the original journal. A completed comment with a still-running process is not a handoff.

## Machine-wide reviewer reservations

The launcher reserves one of four exclusive slot files before spawning a review role. The shared store is `%ProgramData%\Impower\reviewer-slots` on Windows and `/var/tmp/impower-reviewer-slots` on Linux, independent of worktree and journal location. These operating systems provide the supported process identity probes. All participating local coordinators use that store; no production plan field or environment override selects a private pool. Store access failure blocks launch with the filesystem error; coordinate access to the shared store rather than changing to a per-worktree location. Other OSes, including macOS, are unsupported and the launcher blocks the plan; keep the review draft and arrange a caller-authorized Windows or Linux execution route. Native agent tasks, remote tasks and direct CLI launches are outside this mechanism's coverage. The limit counts review roles; implementation, adjudication and coordinator sessions are not reviewer reservations.

Each reservation records a random generation, the coordinator PID and actual OS process start identity, then durable launching and running records. The reviewer identity uses Windows process start ticks or Linux boot ID plus process start ticks, separately from the human-readable launch timestamp. The worktree lock records its coordinator's OS identity; the handoff journal retains both coordinator and reviewer OS identities alongside slot path and generation for auditing after slot release. Use these OS identities when inspecting live or uncertain launches, never the wall-clock launch timestamp as a PID identity. The reservation stays occupied while the reviewer runs, even after a report posts or its coordinator stops. Normal release happens only after the child process close event. A missing or unreadable start identity leaves recovery uncertain.

After a coordinator interruption, inspect the named slot record and original journal. `node scripts/reviewer-slots.mjs status` lists all four reservations and recovery markers, including parse and access failures, without changing them. `node scripts/reviewer-slots.mjs recover <slot 0..3>` removes a reservation only when its coordinator and recorded reviewer are confirmed absent or their OS start identities show PID reuse, or when its dead coordinator durably recorded child exit. A child that is confirmed absent during registration is recorded as exited. Live owners, malformed records, inaccessible identities, an incomplete spawn-registration phase and a concurrent recovery all block recovery. Preserve ambiguous records for manual investigation; do not delete them or signal unknown processes to make capacity. Recovery uses an exclusive marker with its own generation, owner OS identity and timestamp, and checks the reservation generation before unlinking. An interrupted recovery marker also remains a blocker for inspection. There is no automatic reclaim or override for these ambiguous states, including a truncated marker. No process is killed by recovery.

Contention blocks the current plan before spawning a reviewer. Inspect status, await a participating reviewer's confirmed exit, then author a new journal and recovery plan at the blocked step, carrying forward completed round state and verified earlier work. The launcher does not retry or replay implementation automatically. The child identity is recorded in the slot before the running journal row. A local journal failure after spawn closes the spawned child's input and requests its termination, waiting for actual close. After five seconds it sends SIGKILL on POSIX or repeats the termination request on Windows; neither request targets untracked descendants. If close remains unconfirmed after another five seconds, retain the worktree lock and reservation, detach the child handle from the coordinator's event loop and return the uncertainty, child PID, slot path and any emitted signal-delivery error. If reservation release also fails, retain the original error and name the occupied slot and release failure. A normal child exit is journalled before reservation release; release failure keeps the chain blocked with that confirmed outcome and named slot, without claiming completion or validating a report it has not yet read. A storage failure that prevents both identity and exit records remains uncertain rather than authorizing reclamation. This cleanup is separate from recovery, which never signals a process. Recovering an already-absent reservation reports that absence without creating a new marker; an existing uncertain marker still blocks recovery and remains intact.

If the exit journal write fails after confirmed close, the launcher still attempts reservation release and reports the journal failure plus any release failure; completion and report validation remain blocked. A false termination-request return is reported as non-delivery only when close remains unconfirmed, since an already-exited child can also produce that return. The no-new-marker absence guarantee applies to the initial absence check. If the owner releases concurrently after that check, recovery may already hold a marker; interruption can leave that marker blocked for inspection under the same conservative recovery rule.

The exported test seam accepts an isolated scratch store for process fixtures; the command-line launcher never reads that seam from a plan. Tests must use the seam and must not occupy or recover the production store.
