# Automatic handoff execution

For every local CLI reviewer, including a single review with no subsequent handoff, run `node scripts/agent-handoff.mjs <absolute-plan.json>`. The active coordinator awaits this launcher, verifies the full paginated PR report and continues implementing without ending its turn. Author the plan with the editor capability in a private directory outside the worktree. It supplies the worktree, PR number, distinct writer and reviewer routes, a new journal path, a bounded maxSteps, a first step name and a steps object. A single-review plan sets maxSteps to 1 and its review step's next to `[null]`.

Each step has role `implement`, `review` or `adjudicate`, model, absolute executable, args (an array), absolute prompt file and next (an array of permitted next-step names, or null for completion). Concrete CLI mappings belong in [runner notes](../RUNNERS.md). Each CLI must accept its prompt on stdin. The caller must configure the executable arguments to select the declared model; the journal records the declaration, and the review's identity check validates what the runtime can attest.

Implementation reads resolve-issue and performs only the authorized ticket changes, checks, commit and push. Review receives section 3's filled prompt and may post comments but may not change repository files. Adjudication reads the full review and disposes of every finding, returning to implementation if fixes are accepted or ending when the review gate is satisfied. Use separate review steps for serial lenses, with their own prompts and directories. One undirected review is the default for internal skills work.

The runner appends the actual head, role, route, process ID, start time, output and completion path to its journal before awaiting child exit. It validates completion and verifies each reported comment against this PR and head before launching another role. A child cannot provide new commands. Failure, invalid completion, changed review head, missing comments, undeclared transition or exhausted step budget stops the chain with a blocked record. The final human-readiness gate remains with the coordinator, including green CI and complete adjudications.

Supply `completedReviewRound` (0 for a new cycle, the last finished round for recovery) and an integer `round` from 1 through 4 on every review step. Multiple serial lenses in a round share that number. Round 4 covers only changes since round 3's reviewed head and relevant callers. After round 4, implementation and adjudication may finish, but no further review launches automatically. A final role returns null and records any unreviewed corrections and its risk assessment on the PR. The coordinator keeps the PR draft if another independent review would materially reduce remaining risk, or marks it ready when another round would add little value and all readiness gates pass. The step budget is an additional bound. Recovery preserves the completed round count; newly added scope does not silently reset it.

For recovery, `completedReviewRound` is the highest round with a completed lens, even if another lens in that round is still pending. At round 4, also supply the journal's boolean `finalCorrections`: false permits a pending same-round lens; true means a later implementation/adjudication changed the head and blocks further automatic review. Carry the actual journal state forward rather than inferring corrections from the round number. Every review step's round must be an integer from 1 through 4 before any child launches; execution also refuses backward or skipped-forward round transitions.

Never start two coordinators for the same worktree. An existing journal is refused. After interruption, inspect the journal's last launch, PID plus start time, log and completion file, and the PR's paginated comments. A running or uncertain child must be awaited, not relaunched. Once exit is confirmed, author a new recovery plan continuing after verified work; preserve the original journal. A completed comment with a still-running process is not a handoff.

## Machine-wide reviewer reservations

The launcher reserves one of four exclusive slot files before spawning a review role. The shared store is `%ProgramData%\Impower\reviewer-slots` on Windows and `/var/tmp/impower-reviewer-slots` on Linux, independent of worktree and journal location. These operating systems provide the supported process identity probes. All participating local coordinators use that store; no production plan field or environment override selects a private pool. Store access failure blocks launch with the filesystem error; coordinate access to the shared store rather than changing to a per-worktree location. Other OSes, native agent tasks, remote tasks and direct CLI launches are outside this mechanism's coverage.

Each reservation records a random generation, the coordinator PID and actual OS process start identity, then durable launching and running records. The reviewer identity uses Windows process start ticks or Linux boot ID plus process start ticks, separately from the human-readable launch timestamp. The handoff journal links the slot path and generation to its reviewed head and output paths. The reservation stays occupied while the reviewer runs, even after a report posts or its coordinator stops. Normal release happens only after the child process close event. A missing or unreadable start identity leaves recovery uncertain.

After a coordinator interruption, inspect the named slot record and original journal. `node scripts/reviewer-slots.mjs recover <slot 0..3>` removes a reservation only when its coordinator and recorded reviewer are confirmed absent or their OS start identities show PID reuse, or when its dead coordinator durably recorded child exit. Live owners, malformed records, inaccessible identities, an incomplete spawn-registration phase and a concurrent recovery all block recovery. Preserve ambiguous records for manual investigation; do not delete them or signal unknown processes to make capacity. Recovery uses an exclusive marker and checks the reservation generation before unlinking. An interrupted recovery marker also remains a blocker for inspection. No process is killed by recovery.

The exported test seam accepts an isolated scratch store for process fixtures; the command-line launcher never reads that seam from a plan. Tests must use the seam and must not occupy or recover the production store.
