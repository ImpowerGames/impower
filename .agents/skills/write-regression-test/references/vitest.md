# Run Vitest safely

Commands run from the worktree root unless stated otherwise.

## Package verification

The Test Suite workflow is the package gate for a pull request, and the only source of a package result. Whole package suites are never run locally: push and read the workflow's run on the pushed head. A base-branch baseline also comes from that workflow, from its runs on the base branch (`gh run list --workflow test-suite.yml --branch main`), not from a local run on a base commit. The runner's `start` command, which runs a whole package, is refused by the repository hook with no override.

An existing run directory, such as one left by an earlier session, can still be read and continued:

```text
node scripts/test-suite.mjs status <run-directory>
node scripts/test-suite.mjs resume <run-directory>
node scripts/test-suite.mjs resume <run-directory> --retry src/tests/example.test.ts
```

A suite run asks the installed Vitest to discover configured includes/excludes using Vitest's own glob semantics, intersects those paths with Git's tracked inventory, rejects an empty manifest, and executes each file separately. Stage new tests first. Supported inputs are single Node test packages containing test/spec TS and TSX files, including files outside `src/tests`. Workspace, browser, typecheck and per-file pool-routing configurations are refused; use the individual package configuration. Configured test semantics remain in force.

Every child runs with a heap capped at 1024 MB, one fork and no file parallelism. A machine-wide reservation store coordinates participating worktrees: admission is gated on the machine's measured free memory and capped at three concurrent runs. Before admitting a run, and again before each execution unit (selection or discovery, each file, the combined report), the runner reads the free memory through the same transport as the process census, the free commit (`FreeVirtualMemory`) on Windows and `MemAvailable` on Linux. A reading below the floor of 4096 MB, one run's worst case (an engine process and a fork each capped at 1024 MB plus their native memory) with headroom, refuses the admission or delays the unit, and a reading that cannot be taken refuses like a denied census. The floor gates admissions and units only, and an admitted holder is never evicted: the machine's memory is taken by the desktop sessions, not the tests, so a fixed number of runs is unsafe when they fill it and too strict when they do not. A run declares its pool: the reviewer pool when its environment carries `IMPOWER_TEST_POOL=reviewer` (the handoff launcher gives its reviewers and its delegated execution service that variable) or the package it tests lies under a `*.review-jobs` directory, the writer pool otherwise, and any other value refuses. Each pool holds at most two of the three slots, so one slot is always reachable by the other pool. The census refuses a run while a foreign Vitest process runs: one whose parent chain, followed through every process on the machine, reaches none of the running slots' verified processes, such as a direct `npx vitest` call or an orphan of a holder whose record no longer counts as running. A running slot's coordinator is accounted for while its recorded identity still matches; when the coordinator is gone but the record still runs through its recorded launcher, helper or engine, those are accounted for instead, each only while its recorded identity matches. A pid is never trusted by number, since a direct call can inherit it, and a parent edge is followed only when the parent was created no later than the child, since Windows keeps a dead parent's pid on its children and that pid can belong to a holder's newer process by then. The unit gate takes its slot snapshot and its census under the store's guard, so no admission lands between them. A run whose directory a live coordinator already holds waits for that coordinator, whatever the slots say. A run that cannot be admitted writes a waiting row and polls; a row left by a run that was admitted is removed by the next transaction. When a slot and the floor allow an admission, the run admitted is the oldest waiter of the pool not admitted last, among the waiters whose pool can still take a slot, else the oldest overall, so a writer's one-file run is admitted within one admission while reviewer runs are queued and a reviewer's within one while writer runs are queued; a run without a wait never passes a waiter. `run` below takes the same admission. Process-table access failures and ambiguous reservations block execution. Recovery never kills processes.

Keep the complete command-tool result, including session ID and exit status. If the tool yields a session ID, poll that same session until its exit is confirmed; do not forward only its output text. A yield or missing output is neither a timeout nor a pass. Use `status` from another command to read durable progress. Identity checks can take time on a large installation; execution prints progress while scanning.

Resolve-issue writers keep extra captured logs under their [allocated writer attempt directory](../../resolve-issue/SKILL.md#0-preflight). Parent scratch directories can be shared by sibling agents; a fixed root log name can contain another writer's stale result. The runner's own durable per-attempt logs below remain the result evidence.

Each run lives under the worktree's Git directory, outside source discovery. `run.json` saves the manifest and attempts. Each attempt has an independent UTF-8 `output.log`, `vitest.json` and atomically updated `attempt.json`, with PID, OS start identity, actual exit status and signal when observed. Test caches also live there. `summary.json` compares the latest attempts with every manifest file and retains exact failed-test names/messages, skipped/todo names and incomplete files. Prior attempts remain available, including after an explicit failed-file retry. Do not concatenate logs through shell encoding conversions.

Only complete, matching text and structured results with a successful observed child exit can pass. Missing summaries, worker crashes, zero executed tests, malformed/partial reports, failed assertions and missing files fail verification even when an exit code is zero. A suite with unfinished files is incomplete. Read the summary and the relevant attempt logs before reporting counts.

Runtime preparation precedes reservation acquisition. A definite pre-engine admission refusal reports not-run/75; a setup failure after an observed discovery or selection retains that outcome and stops later admission. Once a helper is returned, completion listeners and original identities retain actual disposition. Availability faults after validated root start do not cancel its bounded result; protocol/identity uncertainty stays unknown. Failed persistence produces unpersisted evidence, and no later unit is admitted. Final journal-save failure cannot prevent the release attempt or replace a complete independently verified outcome.

Coordinator directory or initial journal I/O failure also reports not-run before its first child. Manifest and summary publication failures retain completed results beside journalError and observedAttempts, stop later admission, and suppress subsequent shared writes. Validation, stale-input and failed-discovery errors retain their failure semantics and any observed child evidence.

Once changed inputs establish a stale refusal, failure to publish the stale flag cannot make the command retryable. Resume, discovery and between-file refusals retain the stale error, any journalError and the children already observed by this invocation; successor journals remain untouched. A saved stale flag is checked before reconciling old attempts. A final identity change still returns the stale aggregate with its publication diagnostic, including when a completed resume launched no new child.

`resume` keeps verified completed results, retries interrupted attempts only after authenticated tree reconciliation, and retries failed or timed-out files only when explicitly listed after `--retry`. A discovery timeout without a complete manifest/configuration identity requires a fresh run; resume refuses it. An alive coordinator, launcher or helper prevents duplicate execution. A missing child is not a pass: modern attempts require a fresh bound terminal proof plus confirmed original helper and launcher exits. Missing, partial, foreign-attempt or changed-directory evidence remains unknown and blocks recovery. The one exception is a reservation taken before the current boot, detected by the system uptime being lower than the `heldUptime` recorded at acquisition: once its coordinator, launcher and helper identities are absent it is interrupted, and the next acquirer preserves it as `recovered-<token>.json`, because no process from before a restart can still run. A reservation without `heldUptime`, or one checked after the new boot has run longer than the old one had, stays unknown. Inspect the named reservation and journal; preserve ambiguous records for manual investigation rather than deleting locks or signalling unrelated processes. The shared reservation store is `%ProgramData%/Impower/test-suite` on Windows and `/var/tmp/impower-test-suite` on Linux; both platforms are supported. It holds the three slots, `reservation.json` (the slot a checkout on older code knows and honours), `reservation-2.json` and `reservation-3.json`, under one guard, the waiting rows `waiting-<token>.json`, `last-admitted.json`, which records the pool admitted last and steers the alternation only, and the recovery files described here; an interrupted slot is preserved as `recovered-<token>.json` and a dead waiter's row as `recovered-waiting-<token>.json`. Guards and claims are published with their owner already written, by hard-linking a private `creating-<pid>-<start>-<id>.tmp` file into place; such a file left by a creator that died before linking or removing it is swept once its pid and start time name no live process, and a live creator's is never removed. A transaction interrupted while creating/recovering ownership leaves a guard; when its recorded owner (pid and start time) names no live process, or it is empty and more than a minute old (left by a checkout still on older code whose creator died before recording itself), the next acquirer renames it to `recovered-guard-<time>.json` in the same store, like an interrupted reservation; recoverers serialize on an exclusive `guard-recovery.json` claim held only for that read, check and rename. A claim abandoned the same way is renamed to `recovered-claim-<time>.json` under a takeover claim named after its file identity (`guard-recovery-<ino>-<birth>.json`), so only one recoverer can move a given claim. A guard or claim whose owner is alive, whose owner identity cannot be read, or that is empty and younger than a minute is never recovered; if one persists, confirm the owner is gone, then rename it, never delete it.

Recovery reads the guard and its file identity through the same handle, then verifies that generation again after confirming its owner is gone. A successor guard created during the process lookup stays untouched. Normal guard cleanup also removes only its own file generation; an already absent guard needs no removal, while a replacement or unreadable identity is preserved and reported. Normal transactions do not acquire the recovery claim, so an abandoned claim continues to block recovery only.

Reusable evidence is tied to tracked and untracked working-tree file contents, including ignored assets and configuration, Git tracked-file membership, the saved manifest, the forwarded child environment, Node version/platform, and installed dependency metadata (paths, link targets, sizes, modification/change times, modes and file identities). Ignored files are included because tests or configuration can read them; edits to generated code, local configuration or output artifacts can conservatively invalidate a run too. Environment values enter only the digest and are never saved in logs or journals; changing the environment requires a fresh run rather than mixing results from different configurations. This supports dirty worktrees and conservatively invalidates the whole run when inputs change. Source hashes are cached only within a coordinator by filesystem change metadata. Dependency metadata avoids re-reading large installed binaries on every status check, including installations beside ignored package manifests. Git state directories, generated caches and Vite's timestamped config bundles are excluded. A changed identity makes the run stale and `resume` refuses it; old evidence is retained. Avoid modifying inputs during verification. Results do not attest to externally changed services or dependencies whose content and all filesystem identity metadata have been deliberately restored.

For baseline comparison, compare the Test Suite workflow's package results on the base branch and on the pushed head: confirm the same test files ran and compare exact failure inventories. Equal failure totals are insufficient. Include actual file/test totals, failure names, skips and incomplete jobs in the PR.

## Single-file and reproduction runs

The command form is `node scripts/test-suite.mjs run <package-dir> <test-file> [<test-file> ...] --wait <seconds>`. `<package-dir>` is the package directory, such as `packages/sparkdown`, rather than its workspace name. Both `run` and `start` require an existing directory containing a `package.json` file and refuse invalid paths before queue admission.

A reviewer runs only the probes it writes, so a sandboxed reviewer whose process census or reservation write is denied runs nothing and reports a probe it cannot run as a coverage gap. The launcher's [delegated execution service](../../review-pr/HANDOFF.md#delegated-tests-and-benchmarks) lets the coordinator run this same `run` command on a committed test file outside the reviewer sandbox, as its own evidence, retaining the census, reservation and caps; whoever reads that result inspects its returned output and exit result. Merely reading an absent reservation file is not admission; direct unlocked execution remains unsupported.

Run the test files under work with `run`, naming one or more; it refuses a call with none and a call naming more than eight, with no override, and the package result comes from the Test Suite workflow above. "Under work" means the test file you added or changed and the one or two existing files that exercise the same code; a longer list of existing files is a package run spelled out, and enumerating them does not make it local work. Test paths are relative to the package directory:

```bash
node scripts/test-suite.mjs run packages/sparkdown src/tests/compiler/constDeclarationValidity.test.ts --wait 600
```

Before queue admission, `run` checks every requested path names an existing literal test/spec TS or TSX file within the package, including its physical link target. Missing files, directories, options, wildcard filters and control characters are refused with the original argument shown escaped. The runner does not trim, drop or repair arguments; one invalid file refuses the entire request before taking a reservation or launching a child. Existing literal punctuation and spaces retain their spelling.

Windows namespace paths are refused: the question mark in their prefix is not a usable native Vitest file filter. Forwarding that spelling unchanged selects no files in Vitest 2.1.9; use an ordinary path spelling. The runner does not silently convert it.

File existence does not imply configured selection. The runner supports the repository's installed Vitest 2.1.9 and 3.2.6 specification APIs, preserves configured include/exclude and project semantics, and executes only specifications for each exact physical requested file. Substring filters cannot add overlapping files. A wholly excluded request is explicit not-run/75; a mixed executed/omitted request is incomplete/1. Other versions refuse before preparation, with a bound no-launch receipt for delegated callers. Inspect the final terminal summary and retained selection before claiming every requested file ran.

`run` prepares a fresh supervisor runtime before admission to the reservation, then serially performs configured selection, each exact file and combined reporting, each behind the unit gate. Each file has a fresh environment, a 1024 MB heap and one fork. Native blob aggregation applies original ordinary reporters and coverage thresholds once over the requested set, with a separately owned finalizer. `singleFork=true` shares environments and remains unsupported. Direct aggregation refuses configured `globalSetup` and BlobReporter before test effects because their command lifecycle cannot be preserved; `setupFiles` remains supported. Enabled coverage requires v8 or Istanbul with native merge capability; unsupported/custom providers refuse before tests. Exact v8 combined thresholds, reporting on failure and clean true/false have behavioral controls. Unimported-all/exclude sensitivity was measured with Vitest 2.1.9; the equivalent Vitest 3.2.6 surface, Istanbul, threshold auto-update and multi-project coverage remain unmeasured. Native blob identities encode file/project name; stronger project-root/pool identities come from separately bound selection metadata, not the blob format.

Public exit codes are 0 for complete confirmed passes, 1 for ordinary failure/incomplete/unknown or stale refusal, 124 for a confirmed execution-unit timeout, and 75 for definite pre-test admission refusal or authenticated wholly empty selection. Raw unit outcomes remain in evidence. A timeout takes precedence over earlier ordinary failures; unknown containment takes precedence over timeout. Final publication/release availability diagnostics preserve an independently verified complete aggregate result, including 124, while still blocking unsafe admission and shared writes. Require actual summaries and assertions, not exit status alone. The redgreen classifier's separate no-test issue remains tracked by I-366.

`--file-timeout <seconds>` accepts integers 1 through 7200, default 1800. It bounds engine import/configuration, collection, execution and teardown for every file, and also bounds selection/discovery and combined finalization. It begins before engine launch and never resets on progress. A separate 60-second preparation/admission deadline precedes authorization; synchronous filesystem/identity calls can delay the caller, but no late authorization is permitted. Preparation failures occur outside the test reservation and retain their process evidence. Explicit shorter caller deadlines remain shorter and can interrupt the coordinator before the file budget.

Windows launches the owned test ancestry atomically inside a kill-on-close Job Object without breakaway. Linux requires Python 3.9+, usable pidfd operations, subreaper capability and a readable valid `/proc/<helper-pid>/task/<helper-pid>/children` interface; unavailable capability refuses before tests, with no weaker fallback or automatic install. The fresh helper checks that interface before capability acknowledgement and requires no pre-launch children. Its availability depends on the kernel's separate [PROC_CHILDREN configuration](https://raw.githubusercontent.com/torvalds/linux/v6.12/fs/proc/Kconfig), not the pidfd kernel version alone. Linux cleanup uses the same validated reader, pins unreaped original child identities and reaps owned ancestry to ECHILD. Coordinator pipe loss triggers bounded cleanup; helper crash or missing proof stays unknown unless the reservation predates the current boot. The claim covers direct owned ancestry, not processes created through unrelated Windows services/WMI or arbitrary external job control. Original launcher and helper exits plus a bound empty-tree proof are required before successors or reservation reuse; coordinator close alone proves neither.

Direct terminal JSON names the execution budget, timed-out units, omitted/unfinished files, containment diagnostics and evidence directory. Caller-authored internal receipts additionally bind delegated operations to original coordinator identity, preparation and every attempt; unknown disposition blocks both the next delegated operation and service close.

`--wait <seconds>` also applies to `resume` and is independent of execution budgets. Without it, a full store, a full pool, a reading below the floor, a foreign Vitest process, an earlier waiter's turn or a held guard refuses at once. With it, admission waits up to that bound through those states, and each execution unit waits up to the same bound again for the floor and the census; `resume` waits the same way before each file. Ask for at most 600 seconds: when the run is refused, push and read the Test Suite workflow's run for the head rather than queueing again. Waiting rows name the reason (`reservation`, `pool slots`, `memory`, `vitest processes`, `queue`, `guard` or `reservation files`), the queue position and length, the holders with their pools and slots, the free-memory reading and the floor, and the first holder's current file/mode, acquisition age, unit elapsed time, execution budget and last genuine progress timestamp/age; missing legacy fields are unknown. Wait age advances while a silent holder's genuine progress timestamp stays fixed. Polls and heartbeats never fabricate progress; genuine events are coalesced for shared persistence. An ambiguous or unknown reservation refuses at once. Queue expiry does not authorize termination of another owner's process. When the run is not admitted within its wait, no test has run: the command prints `test-suite: not run: <reason>` and exits 75, naming the queue position, the holders with their pools, the last free-memory reading and the Test Suite workflow on the pushed head as the route for the files that did not run, and the same command can be run again. A holder stalled by the floor at a unit boundary past its wait ends as any other refusal between units: its completed files keep their verified results and the remaining files end not run. Single-file runs and suites share the same slots and queue; a direct `npx vitest` call bypasses them and, as a foreign process, makes other runs wait or refuse.

For a direct `run`, definite ownership loss before engine admission reports not-run/75. Availability errors after a validated root start await that original bounded unit and retain its observed result; they never trigger a successor or release a replacement owner's token. Protocol/identity failures remain strict unknown. Inspect independently validated tree proof, retained reservation and diagnostics before recovery.

A durable coordinator that encounters a reservation update error immediately records uncertainty and stops admitting files and writing shared run, attempt and summary journals, including cleanup writes if later verification fails. Before this invocation attempts any child, including discovery, the refusal is not-run/75. Once it attempts a child, it awaits that original child's completion, verifies its observed result, and returns/logs it in `unpersistedAttempts` beside `reservationError`. A report or output inspection error makes verification fail with `verificationError` while preserving the observed child exit. These results are evidence for that invocation, not reusable durable evidence for `resume`. Discovery uncertainty admits no test children. Remaining files make the returned summary incomplete; if every manifest file already completed, their verified pass/fail result remains visible beside the error. A successor's journals and reservation stay untouched.

A repository hook (`.agents/hooks/local-test-hook.mjs`) refuses a direct Vitest call with no file argument, a directory, a glob, a name that is not an existing test file, or more than eight files, and a package `npm test`, `npm run test`, `pnpm test` or `yarn test` whose script may run Vitest, and `node scripts/test-suite.mjs start` with no override; it allows the runner's `run` up to the same eight files, `status` and `resume`. The count covers only the runner's own arguments: a redirection (`> log`, `2>&1`, `1> out 2> err`, PowerShell's `*>`) is not a test file, so capturing a run's output in the same command does not use up the limit, and the refusal lists the arguments it counted. The hook reads a program name only at command position, so a command that merely mentions the binary's path (`Test-Path '<worktree>\node_modules\.bin\vitest.cmd'`, or `$p = '...\vitest.cmd'`) is not a Vitest call. The runner enforces the same bound itself, so a wrapper script or a `--test` string the hook cannot read is refused all the same. It reads command text statically, so a command built from a variable or an alias, or handed to another program as a string, is outside its coverage and this section is the rule.
