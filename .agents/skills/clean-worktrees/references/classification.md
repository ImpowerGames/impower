# Cleanup decisions and recovery

All commands run from the worktree root unless stated otherwise.

## What is removed and what is kept

A worktree is removed only when every commit on its branch and on its remote is on `origin/main` (the branch is merged, whether or not its remote still exists), its tree is clean, and nothing is using it. The merge test needs the branch's own commits on `origin/main`, which a merge commit gives; a branch merged by squash or rebase keeps its commits off `origin/main` and stays as unpushed work. Each of these keeps a worktree, and every reason that applies is printed:

- the main checkout, and any other path outside `../impower.worktrees/`; the worktrees under the main checkout's own `.claude/worktrees/` are listed this way and go by hand with `git worktree remove`;
- the default branch, `main` and whatever `origin/HEAD` names, wherever it is checked out; a clone records `origin/HEAD`, and a repository built with `git init` and `git remote add` has none, so there the dry run says that `main` alone counts and `--apply` refuses until `git remote set-head origin --auto` has recorded it;
- a locked worktree, one whose directory is already gone (`git worktree prune` drops that record, unless a `<path>.removing` sits beside it, which is the rename an interrupted probe left: rename it back and do not prune, because pruning drops the record the renamed tree points at), and one git no longer sees as a worktree though its directory is there (its `.git` link is gone; delete the directory by hand);
- a detached or unborn head, or a worktree git cannot answer for (a corrupt index, say): there is no branch to judge or no answer to judge it by, so it is listed for a person;
- uncommitted changes, counting untracked files; ignored files never count, so a `remove` row names every ignored path it takes with it (`node_modules/`, a driver's `.chrome-profile/`), and anything worth keeping among them is moved out before `--apply`;
- commits on neither `origin/main` nor the branch's remote, which is unpushed work whether the remote is gone or never existed;
- commits on the remote but not on `origin/main`, whether the local branch holds them or is behind the remote, which is a pull request still open or unmerged;
- a branch with no commit made on it, which is a fresh worktree a session may be working in, and is removed by hand when it is done: its tip sits on `origin/main`'s first-parent line, where a merged branch's tip (the second parent of its merge) never does, or its reflog reaches back to the branch's creation and records no commit since. A commit, a cherry-pick or a merge commit made on the branch counts as a commit; fast-forwarding, rebasing or resetting it does not. A branch whose reflog records neither a commit nor its creation (expired in full or in part) while its tip is off that line cannot be told from a merged one, so it is kept and listed for a person; a worktree checked out from a remote branch with no commit made locally looks fresh and goes by hand;
- dev servers one of the worktree's own drivers reports as up, or a state file whose launcher pid is still alive; every such server is its own row naming the driver (`drive-web-editor` for the web editor's servers, `drive-vscode-web` for the VS Code extension's, `resolve-issue` where the web editor driver sits in an older worktree), and `node <worktree>/.agents/skills/<driver>/driver.mjs down` settles it; a driver that cannot answer at all (it fails to load, its `status` hangs, or it reports its own state file unreadable) is judged by the state file it would read, which it writes at launch and removes when its server stops (the web editor driver's beside it, or under `resolve-issue/` where a server launched from there is still recorded): no file is no server, a file naming a live pid is a server row with the URL the file records, a file naming a dead pid is a stale record, and a file that cannot be read keeps the worktree with the reason; one driver's answer never stands in for another's;
- a running process whose command line names the directory, which is how servers started with `npm run web:dev`, and anything else launched with the path as an argument, are seen without a driver; the row names the pids, and it clears once they exit;
- a symlink or junction inside it that points outside it, which `git worktree remove` follows on Windows and empties, wherever the target is (a `node_modules` junctioned to another drive, an `npm link` to a package elsewhere), and a directory inside it that cannot be read, which may hold one. The walk that sizes a tree reads every link in it, so this is judged on the rows that would otherwise be removed, in the dry run and again under `--apply` moments before the removal; the row names the link and its target, and the link itself goes by hand first (`rmdir` removes a junction on Windows without touching its target).

Directories under `../impower.worktrees/` that are not worktrees are listed too, with their size, because an interrupted removal leaves one behind and no git command shows it; they go by hand, and the row says what the log knows about them: a `<path>.removing` is the directory an interrupted probe renamed and did not rename back, and a directory an earlier `--apply` failed to finish, or was removing when that run was killed, is named with the branch it stranded, whether the row lists the leftover itself or the type directory holding it. A branch such a removal left local with no worktree at all is listed from the log alone, keyed by the branch so that a worktree recreated at its old path does not hide it, with its commits read again: `git branch -D` is advised only when every commit on it is on `origin/main`, and a branch a registered worktree holds is judged by that worktree's row instead.

The refusals are not to be overridden by hand for a tree with changes in it. Commit or discard the changes so the next run judges the tree, and stop the servers so the next run sees them down. The session's own worktree goes only if its pull request has merged by the time the script runs; otherwise it stays for the next run, which is the reason this is not a step of `resolve-issue`.

## Gotchas

Three facts the script cannot decide for you; every refusal it can make is in the script and its check instead.

- `git fetch --prune origin` runs first, so the classification is against the `origin/main` and the remote branches of that moment; a pull request merged during the run is picked up by the next one.
- The rename probe that keeps `git worktree remove` from gutting a tree it cannot finish only detects a tree in use on Windows, where the rename is refused while any process has a file open or its current directory inside it; elsewhere the rename succeeds whatever holds the tree, and the process listing is the only check that a tree is in use. Where git refuses outright and keeps its record, nothing more is done to the tree; where it stops part-way (it deletes in directory order and drops its record whatever it managed), the script removes the rest directly and the row says what is left and where, the branch stays, and the next run lists the leftover with that branch.
- Sizing the removable worktrees walks their `node_modules`, so a dry run over twenty of them takes a minute or two; that walk is also where every link in them is read.
