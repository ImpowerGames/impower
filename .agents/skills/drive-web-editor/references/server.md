# Server setup and recovery

All commands run from the worktree root unless stated otherwise.

Each agent session keeps its own state file and browser profile in a directory keyed by checkout and session, under `%LOCALAPPDATA%\impower-driver` on Windows and the machine's temp directory elsewhere, never a checkout's `.tmp/` (`IMPOWER_DRIVER_HOME` overrides the root). The checkout directory holds `checkout.json`, naming the checkout it belongs to, so clean-worktrees can remove it once that checkout is gone. The session is `IMPOWER_DRIVER_SESSION` when set, otherwise the session variable a known runner exports (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`); with none, commands share a `shared` slot. Two sessions in one checkout therefore run their own servers on their own ports and never write into each other's OPFS project, and a new session starts with an empty profile, so seed the project it needs. The state file, `state.json` in that directory, records the editor URL, the launcher pid, when it was launched, the mode, the ports and the launching session. A tree launched by a driver that kept `.state.json` beside the script (under this skill or the resolve-issue skill) is still found there while the session directory holds no record, so `status` ends its line with `session=<id>  state=<path>` to say which file it read. `down` refuses to stop a tree whose record names another session and leaves both running; `down --force` stops it anyway. `status --all` lists every session's record for the checkout, answering servers first, and exits 0 when any answers; clean-worktrees asks it before removing a worktree.

The profile is `profile` in the same directory; a global `--profile <dir>` or `IMPOWER_DRIVER_PROFILE` names another. Opening a profile records the session in its `impower-driver-session.json`, and a launch into a profile another session opened within the last 30 minutes is refused, since its OPFS project may be that session's work. A claim file that cannot be read also refuses the launch; delete it once no other session drives that profile. On Windows a profile whose Cache Storage paths (139 characters past the profile) would pass 259 characters is refused at launch: past that limit `caches.open` fails, the service worker never installs and assets 404 while the game still mounts. A record stands while its pid is alive and the process behind it started when the record was written; the system reports a process's start time, and a freed pid goes to the next process the system starts, so a live pid alone can belong to anything by now. `up` reuses a standing record, waiting for its URL while the launcher lives, and replaces a stale one; `down` stops a tree only through a standing record, removes a stale one without signalling anything, and keeps the record when the kill is refused; `status` exits 0 only when the recorded URL answers.

Servers `up` launches stop themselves when idle. `up` starts the launcher with `--idle-exit-seconds 900`; once the editor answers, the launcher reads the system's TCP table every 30 seconds (`netstat -ano` on Windows, `ss -Htnap` on Linux) and stops both servers when, for 15 minutes, no client has held an established connection to the editor, player or HMR port: a loopback connection to one of those ports from a process other than the two servers, or a connection to one of them from another machine. A driver command's browser counts, and so does a tab a person left open, through its HMR socket; the editor's own proxy connections to the player do not, and neither does an unrelated process talking to some other host on a port with the same number. A census that fails, or that does not list the servers' own ports, leaves the servers running. The reviewer editor delegation starts its session with `up --keep`, since the coordinator stops that session itself at reviewer exit. Afterwards the record names a launcher that has exited: `status` reports `DOWN`, a browser command says the servers are not answering and names `up`, `up` replaces the record and relaunches, and `down` removes it without stopping anything. `up --keep` launches without the idle exit, and `npm run web:dev` by hand never has one.

On Linux, `down` verifies that the launcher owns its process group and session under the current user, checks kernel process identities before each signal, and waits until the group has no running members. Processes still running after one second receive `SIGKILL`. New members observed while a known member still identifies the group become part of that verification. A failed identity check, a tracked process becoming unreadable, a descendant outside the group or a shutdown timeout keeps the record and reports a recovery error. Protected entries belonging to unrelated users do not block the scan. Records without `startedAt` still use their file date. Windows stops the recorded tree with `taskkill /T /F`, after listing every process with its parent and creation time. taskkill exits nonzero (255) when one member, typically one already exiting, refuses termination while the rest are killed; `down` then lists the processes again for a few seconds and reports the tree stopped, removing the record, only when no member of the tree it listed still runs with its creation time unchanged and no member has started a new child. Members are tracked by pid and creation time, a process's parent being whichever process held its parent pid when it was created; new processes count through any number of generations, and one seen in one listing stays a member in the next, so a child it starts before it exits is still found, even on a pid an older member once held. A survivor, or a listing that fails, keeps the record and the failure.

Group shutdown covers the detached session that the driver launches. It refuses to signal the caller's own group. A helper that leaves the group must be stopped through the tool that owns it before retrying `down`; an already reparented daemon cannot always be identified from process ancestry. When every known member has disappeared before another member can be verified, the group number alone cannot prove ownership. Preserve the record, inspect the remaining processes and establish ownership before manual recovery; the driver deliberately supplies no force override that could signal a reused group.

Playwright is a declared root devDependency (`playwright: ^1.61.0`). Browsers come from the local `ms-playwright` cache; if it is empty on a new machine, `npx playwright install chromium`. Always run `npm install` with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` set, because a transitive `@playwright/browser-chromium` dependency otherwise tries to download its own Chromium build from a host this network blocks and the whole install fails. The driver itself does not need that variable. It picks the browser in this order: the executable named by `IMPOWER_DRIVER_CHROMIUM` (refused if missing); the build the installed `playwright` pins and would itself launch (for a headless launch, its `chromium_headless_shell-<rev>` build); the pinned full `chromium-<rev>` build; another `chromium-N` or `chromium_headless_shell-N` build in `PLAYWRIGHT_BROWSERS_PATH`, newest first; then a system `chromium`, `chromium-browser` or `google-chrome` on `PATH` or at `/usr/bin/`. `preflight` prints the chosen executable and why as `launches <path> (<reason>)`, and every browser launch logs the same as a `browser:` line; any of these is a pass. When none exists, the failure names every place looked at.

The driver must live inside the repo tree: Node resolves `playwright` relative to the script's directory, not the working directory, and a copy outside it says so rather than dying in a bare `ERR_MODULE_NOT_FOUND`. The same applies to any script of your own that imports the driver's exported helpers: put it under the worktree (and never `git add` it), not in the private scratch directory.
