# Server setup and recovery

All commands run from the worktree root unless stated otherwise.

Each agent session keeps its own state file and browser profile in a directory keyed by checkout and session, under `%LOCALAPPDATA%\impower-driver` on Windows and the system temp directory elsewhere (`IMPOWER_DRIVER_HOME` overrides the root). The session is `IMPOWER_DRIVER_SESSION` when set, otherwise the session variable a known runner exports (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`); with none, commands share a `shared` slot. Two sessions in one checkout therefore run their own servers on their own ports and never write into each other's OPFS project, and a new session starts with an empty profile, so seed the project it needs. The state file, `state.json` in that directory, records the editor URL, the launcher pid, when it was launched, the mode, the ports and the launching session. A tree launched by a driver that kept `.state.json` beside the script (under this skill or the resolve-issue skill) is still found there while the session directory holds no record, so `status` ends its line with `session=<id>  state=<path>` to say which file it read. `down` refuses to stop a tree whose record names another session and leaves both running; `down --force` stops it anyway. `status --all` lists every session's record for the checkout, answering servers first, and exits 0 when any answers; clean-worktrees asks it before removing a worktree.

The profile is `profile` in the same directory; a global `--profile <dir>` or `IMPOWER_DRIVER_PROFILE` names another. Opening a profile records the session in its `impower-driver-session.json`, and a launch into a profile another session opened within the last 30 minutes is refused, since its OPFS project may be that session's work. A claim file that cannot be read also refuses the launch; delete it once no other session drives that profile. On Windows a profile whose Cache Storage paths (139 characters past the profile) would pass 259 characters is refused at launch: past that limit `caches.open` fails, the service worker never installs and assets 404 while the game still mounts. A record stands while its pid is alive and the process behind it started when the record was written; the system reports a process's start time, and a freed pid goes to the next process the system starts, so a live pid alone can belong to anything by now. `up` reuses a standing record, waiting for its URL while the launcher lives, and replaces a stale one; `down` stops a tree only through a standing record, removes a stale one without signalling anything, and keeps the record when the kill is refused; `status` exits 0 only when the recorded URL answers.

On Linux, `down` verifies that the launcher owns its process group and session under the current user, checks kernel process identities before each signal, and waits until the group has no running members. Processes still running after one second receive `SIGKILL`. New members observed while a known member still identifies the group become part of that verification. A failed identity check, a tracked process becoming unreadable, a descendant outside the group or a shutdown timeout keeps the record and reports a recovery error. Protected entries belonging to unrelated users do not block the scan. Records without `startedAt` still use their file date. Windows stops the recorded tree with `taskkill /T /F`.

Group shutdown covers the detached session that the driver launches. It refuses to signal the caller's own group. A helper that leaves the group must be stopped through the tool that owns it before retrying `down`; an already reparented daemon cannot always be identified from process ancestry. When every known member has disappeared before another member can be verified, the group number alone cannot prove ownership. Preserve the record, inspect the remaining processes and establish ownership before manual recovery; the driver deliberately supplies no force override that could signal a reused group.

Playwright is a declared root devDependency (`playwright: ^1.61.0`). Browsers come from the local `ms-playwright` cache; if it is empty on a new machine, `npx playwright install chromium`. Always run `npm install` with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` set, because a transitive `@playwright/browser-chromium` dependency otherwise tries to download its own Chromium build from a host this network blocks and the whole install fails. The driver itself does not need that variable: if the pinned `playwright` version expects a Chromium revision the cache does not have, it launches whatever build the cache does have instead of failing, and `preflight` reports that as `launches (fallback build: ...)`, which is still a pass.

The driver must live inside the repo tree: Node resolves `playwright` relative to the script's directory, not the working directory, and a copy outside it says so rather than dying in a bare `ERR_MODULE_NOT_FOUND`. The same applies to any script of your own that imports the driver's exported helpers: put it under the worktree (and never `git add` it), not in the private scratch directory.
