# Drive editor panels and language surfaces

All commands run from the worktree root unless stated otherwise.

## The editor's own interface

`verify` reaches the game preview and nothing else. A change to the rail's Find view, the go-to-line panel, the file list, the asset views, or the screens the bottom tabs switch between is invisible to it, and a `verify` screenshot of such a change is not evidence. Use `ui` instead: it performs the steps you give it, in order, as a user would (panels open on their own shortcut, text goes in as real keystrokes, screens switch by clicking the tab) and then reads every surface back.

```bash
node .agents/skills/drive-web-editor/driver.mjs ui --sd repro.sd --open find --type "search=Hello" --type "replace=Goodbye" --shot-of find panel.png --shot page.png
```

Verified output shape (steps first, then the read-back; `url`, `startedOn`, `ui.tabs`, `ui.route`, `ui.editorView`, `script`, `consoleErrors` and `consoleNoise` are also present and omitted here, as is the run's top-level `editorSettled`, which is set only when an editor was expected where the run started):

```json
{
  "steps": [
    { "sd": "repro.sd", "wroteChars": 171, "editorSettled": true, "programLoaded": true, "previewSettled": true, "editorView": "main" },
    { "surface": "find", "open": true, "pressed": "Control+f" },
    { "field": "search", "typed": true, "text": "Hello", "readBack": "Hello", "matches": true },
    { "field": "replace", "typed": true, "text": "Goodbye", "readBack": "Goodbye", "matches": true },
    { "of": "find", "screenshot": "C:\\...\\panel.png" },
    { "of": "page", "screenshot": "C:\\...\\page.png" }
  ],
  "ui": {
    "screen": "logic",
    "panelTab": null,
    "find": { "open": true, "search": "Hello", "replace": "Goodbye", "matches": "1 of 3 matches in 2 scripts", "toggles": { "case": false, "word": false, "re": false } },
    "goto": { "open": false },
    "cursorLine": 5
  },
  "failed": []
}
```

The steps, each usable any number of times and in any order. Every name is checked before the browser launches, so a misspelt panel, field, button, screen or shot target, or a flag with no value, is refused at once rather than after the run:

| Step                     | Does                                                                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--fresh-sw` | unregister and reload, identify the controlling worker's installed script and capture its warnings and errors |
| `--hover <line>:<col>` | move the pointer over the requested position and read the hover and its image; also reports `diagnostics` (each settled diagnostic covering the position, with `message`, `severity` and its zero-based LSP `range`) and, when there is one, moves the pointer a second time (onto the last character inside the mark when the position is its end, which CodeMirror's lint hover excludes), reporting `tooltipPointer` and `diagnosticTooltip` (`present`, `text`) for CodeMirror's lint tooltip, so `--shot-of hover` after it captures the diagnostic. A diagnostic whose tooltip never opens fails the step; an empty language-server hover at a diagnostic does not |
| `--complete <line>:<col>=<text>` | type at the requested position and read completion options and the selected item's info panel |
| `--insert <line>:<col>=<text>` | insert 1 to 4096 characters at the position as one edit through the page's input path (no key events, so no auto-closed bracket or completion popup); a literal `\n` is a line break in the text and `\\` a backslash (so `\\n` inserts a backslash and an `n`); a backslash before any other character is kept. The edit is incremental, unlike the reload `--sd` does. Reports `inserted`, `version` (`before`, `after`), `textMatches` against the expected splice, `readBack` (the affected lines) and, once the preview settles, `preview` (`settled`, `route`); a position outside the document or a read-back that differs fails the step. The text stays in the document and is autosaved |
| `--scrub <line>` | move the preview to the line exactly as `verify --line` does (see [preview](preview.md)): the cursor notifications a real click sends, one retry for a line not yet rendered, a settle, then `route`, `visible` and `scrubCheck`. Reports the `clicked`, `cursorLine`, `previousPosition` and `position` fields of `verify`'s `scrub`; fails when the selection did not run (a running game: `--play stop` first), the line is past the end, the preview's position is not the line, or `scrubCheck` is `elsewhere`. `inconclusive` is not a failure; look at the screenshot |
| `--play <start\|stop>` | click the preview's top-bar Play (`Play From Here`) or Stop (`Stop`) control with a real pointer. `start` first waits up to 30 s for the player to report a launch state and a loaded program, since a press before that starts nothing while the control turns to Stop. It then reads every game state the player reports, by `preview/didChangeGameState` notification and by `preview/gameState`, for up to 30 s: `start` is reached when one shows a new `run` or a running state (`play`, `pause`, or `ended` when PLAY holds the frame its story ended on), so a story that starts and ends between two polls still counts; `stop` when one shows `preview`. Reports `clicked`, `reached`, `launchStateBefore`, `launchState`, `passedThrough` (the launch states seen after the press), `running` and `control`; a player that never loads, a missing control (`--play stop` with nothing running) or a transition that never arrives fails the step, so `clicked: true` alone is never evidence. PLAY starts from the preview's current line; put `--scrub <line>` before it to choose one |
| `--advance [count]` | click the centre of the game's view (`#game` in the `/__player/` frame) with a real pointer `count` times (default 1), letting the preview settle after each click. Reports `clicked` (the clicks made), the final `launchState`, and `clicks`, one entry per click with `at` (the page point clicked), `settled`, `visible` (the game's text, read as `--scrub` reads it), `launchState` from `preview/gameState` after the settle, and `notifications`: every `game/*` notification the editor received since the previous click (or since the step began), each as `method` and `params`, so a story's end shows as `game/finished` and `game/ended` with their `kind` (`fin`, `out` or `error`) and the click's `launchState` as `ended`. Clicks on an ended game are made, and change nothing. A click attempted with no game running (launch state other than `play`, `pause` or `ended`) fails the step with a reason naming the missing game, and the clicks after it are not made; so does a page with no same-origin player frame. A click that only finishes a line's typewriter reveal counts as a click; read `visible` to see where the story is |
| `--sd <file.sd>`         | load the script into OPFS and reload, as `verify` does; then waits for the editor view to settle (`editorSettled`) and, where the game preview is observable, for the game to mount with `verify`'s budget and reload retry (`neededReload: true` when the retry was needed, `switchedToLogic: true` when the retry had to click back to the editor; a game that never mounts fails the step with `programLoaded: null`, as it fails `verify`), for the program to reach the player (`programLoaded`; `programNote` says why when it did not within 90 s) and for the first compile (`previewSettled`; `previewNote` says when it is not observable: cross-origin mode, or the preview showing the screenplay) |
| `--project <dir-or-zip>` | replace the OPFS project with every file of a directory or an exported zip and reload, as `verify --project` does (see [project seeding](projects.md)); the step carries the `seed` report, fails without reloading on its `reason` (and the steps after it do not run), and needs no `main.sd` in the project when a `--sd` step follows it; a `--sd` before a `--project` is refused before the browser launches, since the seed would remove or replace the script it wrote. A `--project` or `--sd` step that throws (a reload that times out) keeps what it reported, fails, and stops the run the same way, since the page is not known to show what storage holds |
| `--screen <name>`        | click a tab: `logic`, `assets`, `share`, or a tab inside a pane (the Assets type tabs `image`, `audio`, `video`, `text`, `font` and `other`, or `game`, `screenplay`); a main screen counts as active once its own content is mounted. `main` opens `main.sd` in the script editor from the Scripts page and `scripts` goes to the Scripts page (`#scripts`); see below |
| `--open <panel>`         | `find` (Ctrl+F, the rail's Find view or the phone's find bar at phone widths, which search every script) or `goto` (Ctrl+G); waits for the panel to be on screen; needs the script editor, which `--screen main` reaches |
| `--close <panel>`        | Escape from inside it                                                                                                                                 |
| `--type <field>=<text>`  | real keystrokes into `search`, `replace`, or `line`; opens the panel if needed; a literal `\n` becomes Ctrl+Enter, the field's own line break           |
| `--press <combo>`        | one key combo, e.g. `Shift+Alt+f` (Format Document) or `Control+s` (format on save); a shifted lowercase letter is uppercased first; the `+` key is written `Control++`. Focuses the script editor first, so a key sent while a panel holds focus goes to the document (use `--click` or `--close` for panels). Reports `version` (`before`, `after`) and `textChanged`, plus the document `text` read back when it changed (first 8192 characters, `textTruncated` giving the full length); after the two format keys it waits up to 5 s for the language server's edit |
| `--click <button>`       | a panel button by name: `next`, `prev`, `replace`, `replaceAll`, `close`, `submit`; goes to whichever owning panel is open                              |
| `--toggle <option>`      | flip a Find switch: `case`, `re`, `word`; reports the state it ended in                                                                                |
| `--shot <out.png>`       | the whole page                                                                                                                                        |
| `--shot-of <what> <png>` | one surface: `find`, `goto`, `editor` (the script editor), `hover`, `completion`, or `page`                                                                                  |
| `--probe <file.js>`      | as in `verify`                                                                                                                                        |
| `--step <name>`          | a [named step](../SKILL.md#named-steps) for a redesign surface; reports `step` and fails with `not built yet`, naming the ticket, until that surface exists |
| `--tap`, `--long-press`, `--swipe`, `--rotate` | touch and display steps for `--device android` only, in the device screenshot's pixels; see [Android emulator](../SKILL.md#android-emulator). On a device `--shot` is the whole screen and `--shot-of screen` names it explicitly |

How to read it:

- Every `--type` reports `readBack` (the field's rendered text, which is what a user sees; the panel's own reader agrees with it on anything `--type` can type and differs only on a non-breaking space that arrives by paste) and `matches`. A `matches: false` carries a `reason` and lands in `failed`: either the keystrokes did not land or the field changed what it was given, and both are findings, not noise; a `--type` refused by the editor gate also reads `matches: false`, with `typed: false, gated: true` and the gate's reason, and typed nothing.
- `failed` lists every step that could not do what it was asked (a panel that never appeared, a tab not on the page, a read-back that differs, a step that threw). An empty list with the screenshot you wanted is the pass; a non-empty list means the screenshot is of something else. A step that fails never discards the report: the steps before it, their screenshots, and the read-back are still there.
- `ui.screen` is the selected screen tab in the bottom navigation (`logic`, `assets` or `share`), and null before the navigation has mounted, which is what a page still loading looks like. `ui.panelTab` is the selected tab inside it, null on the logic screen, which has none. `ui.route` is the page's route, the location hash without its `#`: `write` for the script editor, `scripts` for the Scripts page. `ui.find.matches` is the Find view's count across every script ("1 of 3 matches in 2 scripts"), or its status line when nothing matches, which is what tells you a search took.
- The script editor exists only on the logic screen's `#write` route, holding `main.sd` or the script last opened from the Scripts page (`#scripts`), and the persistent browser profile remembers which screen, route and script were last on display. `ui.editorView` names the script from the open document's URI as `editor/read` reports it: `main` for the project's own `main.sd`, `scripts-view` for any other script, or null when no editor answers. In `scripts-view` the editor on screen is the other file while `--sd` still writes `main.sd`; `--screen main` brings `main.sd` back, so leave the editor on it when you finish a run. A run that ends on `assets`, `share`, or the Scripts page leaves the next run starting there; a panel step then reports `the script editor is not on screen (active screen: assets, tab: image); put --screen logic before this step` (or `(active screen: logic, page: scripts); put --screen main before this step`) in `failed` rather than running. Put `--screen main` first when the previous run may have left the profile anywhere but `main.sd`: unless `main.sd` is already in the editor on the logic screen, it goes to `#scripts`, waits for the Scripts page and presses its Main row, reporting `opened: true`, then waits for the editor as below and reports `editorView`; a Main row that leaves another document in the editor fails the step, naming that document's URI. `--screen scripts` goes to `#scripts` and waits for the Scripts page, where no editor is expected. `--screen logic` clicks the logic tab, which lands on the editor; if it shows the Scripts page instead it reports `active: true, editorHere: false` with a `note` saying so. A switch that lands on the editor (`--screen logic` or `--screen main`) always waits up to 20 s for it and then settles it with a 15 s budget, whatever the run has settled before, because the switch mounted a fresh view; those are also the budgets a gated step uses before any settle has happened in the run; it fails the step with `editorHere: false` if the editor never mounts, or with `editorSettled: false` if it mounts but does not return settled diagnostics for 15 s, and reports `editorSettled: true` when the switch did the settling. A `--screen logic` that is followed at once by `--screen main` does not fail for an editor the main switch is about to wait for; it carries a `note` instead, and the main switch gives the verdict. Followed by anything else, a logic switch whose editor never mounts fails as any other. A `--shot` or `--shot-of` that follows no [named step](../SKILL.md#named-steps) is gated like this and also waits up to 5 s for the editor to have painted its lines and gutter, because a settled view can still be a blank pane, and fails the step if it has not; `verify` does the same wait before its screenshot and, since its evidence is the game preview, reports an `editorPaintWarning` instead of failing. A run does not fail at its start for a slow editor; a step that captures or acts on the screen (`--shot` and `--shot-of` after no named step, `--press`, `--hover`, `--complete`, `--insert`, `--scrub`, `--play`, `--advance`, and the panel-opening steps `--open` and `--type`) waits for an expected editor to mount and settle at the moment it runs, and fails with that reason if it does not, so the failure lands on the step that would otherwise have captured a page still loading. "Expected" is decided by the selected screen tab and the route: no editor is expected off the logic screen or on the Scripts page, and a page with no screen tab yet counts as expected and waits. The wait is paid once per run, and any settle the run already did counts (at the start, after `--sd`, or in a `--screen` step that landed on the editor, all with the gate's own 15 s budget): later steps re-check with 8 s budgets for the mount and the settle, and a failure names the budget it used. After one step has given up, later gated steps take a two-second look and, if the give-up was a view that never settled, a six-second re-settle; they fail at once with `still not up` or `still waiting for settled diagnostics` naming the step that first reported it, or clear the give-up and proceed with the run's current budgets (the shorter ones if any settle already happened) once the editor is back: a missing editor needs only the two-second look to have found it, a replaced one also needs the re-settle. A `--sd`, `--project` or `--fresh-sw` reload resets the gate, since the settled view is gone with the page. A step on a screen where no editor is expected is never refused, whatever an earlier step found. A gate failure keeps the presence check's navigational advice (`put --screen main before this step`) when there is one, and otherwise says once to re-run. The settle check requests diagnostics for the active document version through the protocol; preview animation does not affect it. `--probe` is never gated, so a probe can diagnose a page whose editor will not mount; on a project an earlier seed left marked, every step but `--probe` is refused until a `--project` step has seeded it, and the run stops at the first refused step. The start records `editorSettled` and, when the editor was expected and not yet up, or the run began on the Scripts page, a `startNote`. `verify` switches to `main.sd` on its own, as `--screen main` does, when the editor is absent or holds another script, and reports `switchedToLogic: true` for a press of the Main row, whether or not the editor then came up (`gameMounted` and `error` say that); if it still cannot reach the editor it prints a report with `gameMounted: false` and an `error` naming the screen, and exits 1. `verify` then reports `editorView` and, when another script is still in the editor, an `editorWarning` naming it; `ui --sd` fails its step in that state, since the file it wrote is not the one on screen, and says to put `--screen main` before it.
- `--step problems` presses the problems toggle under the game unless the panel is already open, and reports `surface` (`panel`, or `dialog` for the Problems to fix dialog a phone opens instead), `toggle` (the toggle's text), `cards` (each panel card's name and whether it is open) and `entries` (the problem and played entries drawn; the panel draws only the rows in view).
- `--step wheel-list` takes every vertical list in the topmost open dialog (or the page, with none open) that holds more than fits, outside the script editor, moves a real mouse over a clipped element inside it (`truncate`, `overflow-hidden`, `fade-edge`, a thumbnail; plain text when it has none), wheels, reads `scrollTop` back, then wheels past the end and restores every scroll position. Each list reports `over`, `scrollTop` (`before`, `afterWheel`, `atEnd`, `max`), `moved`, `chainedTo` (lists it sits in that took the rest of the scroll) and `leakedTo` (anything else, the page roots `page:html`, `page:body` and `page:main` included). It fails when no list overflows, when a wheel does not move its list, when the list stops before its end, or when a scroll leaks, so seed more rows than the screen shows first: a list that fits proves nothing. Touch drag cannot be synthesised headless; it belongs to the Android pass.
- A non-empty `failed` exits 1. `ui --sd x.sd --shot out.png && open out.png` cannot open a screenshot of the wrong document under a green shell.
- Every editor selector the driver uses is scoped to the script editor's own root (`.sparkdown-script-editor-root`): the screenplay preview in the right-hand pane is a CodeMirror editor too, and an unscoped `.cm-content` would find it from any screen and type into it.
- The preview pane remembers screenplay mode across runs as well. In that mode the game never mounts, so `verify` clicks the preview's "Preview Game" button itself and reports `switchedToGamePreview: true`; `ui --sd` does not switch (it may be what you are testing) and reports `previewNote` instead.

Then open the PNG and look, as with `verify`. `--shot-of find` crops to the Find view in the rail or the phone's find bar, which is the right picture for a panel change and useless for anything else; take `--shot` as well when the change could have moved something outside the panel.

The browser helpers `ui` is built from (`withEditor`, `writeMainSd`, `waitForEditor`, `openSurface`, `typeInto`, `pressKey`, `switchScreen`, `readSurfaces`, `shotOf` and the rest) are exported from `driver.mjs` for the case `ui` does not cover. Import them from a script that lives inside the repo tree (Node resolves `playwright` from the importing script's directory, not from the working directory), and prefer adding the missing step to `ui` over leaving the script behind.

`ui --hover 5:19` opens a hover with real pointer movement; `ui --complete 7:3=~fil` types real keystrokes at the requested position and waits for completion. Hover reads the script currently in the editor, including a script other than `main.sd`; `ui.editorView` identifies which. Completion typing requires `main.sd` in the editor and refuses any other script, reporting `editorView` and advising `--screen main`. The typed text stays in the document and is autosaved; restore the original text with `--sd` or `--project` before a run that needs it. Positions count lines and UTF-16 columns from one, matching the status bar. Both use protocol selection and report the verified `caret` before acting; hover also reports its `pointer`, and completion reports `typed` and `textMatches`, failing when the document read-back differs. Hover reports protocol `contents`, `present`, `text`, `imgSrc`, `naturalWidth` and `naturalHeight`; its `surfaceRect` and `imgRect` are null because these are model reads, not rendered measurements; completion reports `popupPresent`, label-only `options` and `selected`, `items` with separate labels and details, `optionsTruncated` when CodeMirror renders only a window of the offered list, `infoPanelPresent` and the same image fields. `surfaceRect` and `infoPanelRect` describe panels intersecting the viewport. `--shot-of hover hover.png` crops the visible hover; `--shot-of completion completion.png` includes the list and its visible info panel, or the list alone when no info panel is shown. The reader waits up to 15 s for viewport placement and up to 2 s for an optional completion info panel; crops allow 2 s for placement plus up to 2 s for optional completion information, including when an earlier completion step already waited. Off-screen surfaces do not count as present. Missing labels in a truncated list are not evidence that the server omitted them. A missing surface fails the step and reports `serverResponse: "unobserved"`: the DOM alone cannot distinguish an empty language-server answer from a request that failed, or correlate a displayed list with a particular request. Hover reads the language-server response through the protocol and reports `serverResponse: "received"` or `"empty"`; only completion still uses the rendered reader described above. A protocol hover response does not prove the tooltip was displayed. `--shot-of hover` separately waits for and captures the rendered tooltip.

When what you are checking is an image on one of those surfaces, measure the rendered rect, never `naturalWidth`/`naturalHeight`. An SVG whose root declares only a `viewBox` reports a non-zero natural size while laying out at 0 × 0, and an image that failed to load reports `complete: true` with a natural size of 0, so `natural` tells you neither what is drawn nor whether it loaded. `getBoundingClientRect()` on the `<img>` is the answer, and the screenshot is the check.
