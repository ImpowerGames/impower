# Frame pacing of played lines

All commands run from the worktree root unless stated otherwise.

The `pacing` command plays fixed lines of a game and reports, for each line, how long the click took to show it and whether the screen kept up once it fired (I-2809). It runs on two surfaces with one analysis module (`pacing-analysis.mjs`) and one run loop (`pacing-run.mjs`): the web editor's preview here, and VS Code's Game Preview through [the extension driver's pacing page](../../drive-vscode-web/references/pacing.md). Every change that claims to remove a stall during a line, or that could add one, reports before and after with it, taken in the same sitting on the same surface.

```bash
node .agents/skills/drive-web-editor/driver.mjs up
node .agents/skills/drive-web-editor/driver.mjs pacing --runs 2 --out <evidence-directory>
node .agents/skills/drive-web-editor/driver.mjs pacing --project <dir> --line 5649 --beats 16 --out <evidence-directory>
```

It needs the same-origin launch `up` makes by default. Each run takes a browser profile made for it and removed afterwards, seeds the project, puts the preview on the start line, presses Play From Here, waits for that first line to finish (it is not measured, since the first line after starting can take seconds), and then clicks the game once per line. The browser is visible by default, so frames reach a real display; `--headless` measures a browser that has none and its frame figures are not comparable.

## The fixture

Without `--project`, the command plays the fixture project in `.agents/skills/drive-vscode-web/fixtures/pacing/`: `project/` is the game, `lines.json` lists its start line and each measured line with its kind, and `SOURCE.md` says where its art and sounds come from (all generated by `generate.mjs` in that folder). The kinds are `talk` (a drawn portrait with a speech morph and a blink, six shadow `mask` elements and voice beeps, appearing as the line starts), `talk-pan` (the same line while a backdrop pan runs), `narration`, `sound`, `swap-layered` (a swap to a layered bitmap backdrop), `zoom-layered` (a zoom of a wide layered bitmap backdrop), `vector-backdrop` and `vector-element`; Ogg music and sound effects in the RFC 6716 codec, which VS Code decodes with the player's fallback decoder, load while lines play. A line the fixture does not list is reported as `unlisted`, and a listed line never measured fails the run.

`--project <dir> --line <n>` plays a real project instead, from line `n` of its `main.sd`, for `--beats` lines after the first. Lines then have no kind, so the repeatability verdict below is not given. Private projects stay out of the repository and out of published evidence.

## What one line measures

Before each click the command waits `--rest` milliseconds (1500 by default) so the screen is idle, starts a Chrome trace with the light category set (`benchmark`, `blink.user_timing`, `disabled-by-default-devtools.timeline`) and clicks. It waits for the line's `beat fired` mark, reads when the line's last letter finishes revealing, waits `--rest` past whichever is latest of that, the end of a pan or zoom and one second after the fire, stops the trace and reads it. A line whose trace ends before one second after the fire fails. A full trace category set is about 500 MB for 45 seconds and slows the page, so none is used; no screenshot is taken inside a measured window either, because one adds a hitch of 100 to 400 ms (the per-line screenshot is taken after the trace stops).

The player records three standard marks for each beat it is given, named with the beat's script and one-based line and a sequence number, such as `beat received main.sd:14 #3`, `beat ready main.sd:14 #3` and `beat fired main.sd:14 #3`, and a measure `beat wait main.sd:14 #3` from received to fired. A beat's entries are cleared once a later beat fires, so the buffer does not grow. The marks are recorded in every build, so a profile taken in DevTools can be cut by beat too. The command adds a `pacing click <n>` mark at each click, stamped with the input event's time.

Each line in the report gives:

- `waitMs`: the click to the `beat fired` mark. `beatWaitMs` is the `beat wait` measure, from the player receiving the beat to firing it.
- `firstSecond`, the second after the line fires:
  - `stalls`: count, longest and total. A stall is a stretch between two frames reaching the screen during which the trace reports at least one dropped frame. A stretch where nothing on screen changed is not a stall, because frames reach the screen only when something changed: 50 to 75 a second during plain typing is the letter cadence, not a stall. Frames reaching the screen are the ends of the page's `PipelineReporter` slices whose state is presented; several can end at one presentation, so ends within 2 ms are merged. A dropped frame is a slice whose state is dropped, placed at its start.
  - `droppedFrames` and `framesPerSecond`.
  - `graphicsMs` and `graphicsTasks`: `GPUTask` time on the graphics process's main thread (`CrGpuMain`), and each task of 25 ms or more with its start after the fire. Both are null when the trace has no graphics process thread.
- `pageThread`: `RunTask` time on the page's main thread from the click to one second after the fire, and each task of 50 ms or more. The page thread is the one the marks were recorded on.
- `typing`: the time the letters take to reveal, its dropped frames and frames a second.
- `motion`, on a line whose fixture entry has `motion`, or on a `--project` line where such an animation is found: the pan or zoom's own interval, read from the longest animation of half a second or more, other than a letter's, that starts within a second of the fire, with its target, frames a second (`motionFramesPerSecond`) and dropped frames over that interval. The command waits for the animation to end before it stops the trace. A fixture motion line with no such animation fails.
- `mouth`: each change inside a drawn picture's shadow root that swaps a pose (not a tween of a path's `d` and not a rebuild) while the letters reveal, and the graphics-process time in the 30 ms after each (`meanMs`, `medianMs`, `p90Ms`, `maxMs`). A blink is a swap too, so a line's count includes its blinks.
- `layers`: every layer that draws content and was painted while the line played, with its size, the number of paints and the element it belongs to; picture layers are the ones whose element names an `image`. Paint counts come from `LayerTree.layerTreeDidChange`, because `LayerTree.layerPainted` never fires on VS Code's webview target.

Page times and trace times are joined through the marks: the trace records each mark with its page time, and the command takes the median offset of the line's click, received and fired marks.

## Quiet machines and repeatability

Each run samples the machine's CPU load for three seconds after the first line has played and before the measured lines start. At or over `--quiet-limit` percent (25 by default) the run is marked not quiet in its report and its figures are not to be judged. The report also records the game view's size in CSS pixels with the device pixel ratio, the graphics chip, the display's refresh rate (from the page's animation frames while idle) and the CPU model.

`--runs <n>` plays the fixture `n` times, each in a fresh browser, and compares each occurrence of the talking line (the fixture's `talk` and `talk-pan` lines) with itself: it lists that occurrence's longest stall in the first second from every run and says the runs are repeatable only when every occurrence stays within 20 ms. That verdict is the check's repeatability statement; a single run does not give one, and a run that was not quiet or that failed leaves it unjudged. A single dropped frame is a stall of about 33 ms on a 60 Hz display, so on a fast machine an occurrence that drops one frame in one run and none in the other fails the rule; take more runs before reading a change into one occurrence.

## Reading the output

The command prints one row per line and writes `report.json` in `--out` with every figure, plus a screenshot of the page after each line. `--keep-trace` keeps each line's trace (`trace-NN.json`, a few megabytes each). It exits nonzero when a run fails: a click that fires no beat within 20 seconds, a line whose trace holds none of its marks or no frame of the page that reached the screen, a motion line with no pan or zoom, a fixture line never measured, or a setup failure, each named in the run's `failed`. A failed line has no figures, so a broken capture never reads as a line without stalls.

To compare a change, run the command on the base and on the change in the same sitting, on the same surface and machine, with both runs quiet, and compare like lines. Say which machine and surface the numbers come from.
