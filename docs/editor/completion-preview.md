# Autocomplete suggestion previews

This document specifies how the Game Preview shows an autocomplete suggestion before the author accepts it: what the editor reports, how the player compiles and shows a hypothetical program without letting it touch the real one, and what it costs. The author-facing description is [Previewing Suggestions](../../packages/sparkdown/docs/guide/SuggestionPreview.md). The feature is tracked by #633; the web editor is #634 and VS Code is #635.

## Design of record

Treat every highlighted completion as a request to preview its accepted text in a private document overlay. The normal stopped-preview pipeline decides the resulting scene. The editor sends no classification of whether the choice is visual. Closing requests the latest real document, and acceptance transfers ownership to the real accepted edit.

Each request is owned by what it would compile: the real document and version it applies to, the edit, the line shown and the project's file revision. Keep one active speculative evaluation and one replaceable pending request. Invalidate obsolete work before it can publish a program, route, assets or status. Restoration is not queued behind obsolete speculative work. Reuse workers, Game/Application instances, compiler state and bounded asset caches; never create these per candidate.

Canonical documents, diagnostics, route preferences, checkpoints and Play/export state are distinct from speculative state. Failed or incomplete candidates retain the last valid frame with a small status message. This retained frame may be speculative; it is a view only and cannot become canonical state. Successful actual or hypothetical results clear the status. Closing with an invalid actual document keeps the frame marked stale.

Only an already-open stopped preview participates. Native CodeMirror state provides the web lifecycle; VS Code uses the public inline-completion bridge described under [VS Code](#vs-code). Keep thumbnails. Consider a fallback only after demonstrating a missing native requirement and settling its interface.

## Protocol

The editor sends `textDocument/previewCompletion` (`packages/spark-editor-protocol/src/protocols/textDocument/PreviewCompletionMessage.ts`) for every newly highlighted option and for every close. A `focus` carries the real document's URI and version, the changes accepting the option would make against that version, and the cursor. `contentChanges: null` means the editor could not work out the edit; the player shows the unavailable state rather than guessing. A `close` carries, when an option was accepted, the version and changes of the accepting edit. Requests are numbered page-wide, so a replaced editor continues the count.

The web host forwards it to the player like every other `textDocument/` notification (`PreviewGame.tsx`).

## Editor

`completionPreview` (`packages/codemirror-vscode-lsp-client/src/completion.ts`) observes CodeMirror's completion state after every view update. It reports the first highlighted option, every change of highlight (including a return to an earlier option), and a highlighted option whose document changed underneath it; it reports a close when the completion state goes inactive, with the accepting transaction when there was one, and when the view is destroyed while a list is open. While a list waits for fresh results nothing is highlighted and nothing is reported.

`completionChanges` computes the edit by running the option's own edit against a stand-in view, so the result is the edit acceptance makes, including snippet placeholders, every cursor of a multiple selection and the text after the cursor. It never creates a transaction, dispatched or not: creating one runs the state's transaction extenders, and the web editor's extender announces every document change as an edit and a save. Only options built by the language-server source are known; any other returns null. Commands attached to a completion (such as re-triggering suggestions) belong to acceptance and never run while browsing.

## VS Code

VS Code has no public event for its suggestion list, but it tells inline completion providers which suggestion is highlighted (`InlineCompletionContext.selectedCompletionInfo`) while its inline completion model is active. `activateCompletionPreview` (`vscode-sparkdown/src/utils/activateCompletionPreview.ts`) registers a provider for Sparkdown documents that never returns an inline item and reports every call to `CompletionPreviewTracker` (`vscode-sparkdown/src/completion/CompletionPreviewTracker.ts`). When the language server answers a completion request with items while a connected, stopped Game Preview exists, the client middleware records the items and runs the public `editor.action.inlineSuggest.trigger`, which activates the model for the list about to open whether or not `editor.inlineSuggest.enabled` is on; no setting is read or written. Without the trigger a provider receives nothing while inline suggestions are disabled, and misses Escape while they are enabled.

The tracker reports a `focus` for a highlight it has not reported at the current document version, and a `close` when a call arrives with nothing highlighted, when the document with the open list stops being the active editor or is closed, and on a mouse selection change. A document change that is exactly the highlighted edit at the next version is acceptance: the `close` carries it as `accepted`. Any other change is an edit made while browsing; the list stays open and the next highlight is reported against the new version. Change events without changes (saves, the dirty marker) are ignored. While a list is open the trigger runs again every 500 ms: VS Code stops asking providers when the editor loses focus, and has no public event for that, but the trigger reaches the editor anyway and gets an answer with nothing highlighted. While the list stays open VS Code answers from its cache and the tracker sends nothing.

`selectedCompletionInfo` gives the replaced range and the text of the primary edit, and VS Code reports suggestions with equal primary edits identically. It is not always the text acceptance inserts: a snippet is reported re-indented but an as-is item is inserted unchanged, and plain multi-line text is reported unchanged but inserted re-indented. `completionChanges` (`vscode-sparkdown/src/completion/completionEdits.ts`) therefore matches the report against the language server's items (by the start of the replaced range when an item has one, and by inserted text, expanding snippets and ignoring indentation) and computes the edit from the matching item by VS Code's own insertion (`SnippetSession.createEditsAndSnippetsFromSelections` with the suggestion controller's options): the item's text at the primary cursor and at every other cursor, where a cursor replaces as many characters before and after itself as the primary does, on each side only where they are the same text; later lines are indented like the cursor's line and every adjusted line is written in the editor's indentation unit (its indent size, which is not always its tab size) and line breaks, unless the item keeps its whitespace (`InsertTextMode.asIs`, `keepWhitespace`), which another cursor still adjusts when its line's first text starts in another column than the primary's; then the item's secondary edits. When none match (a suggestion from another extension), matching items make different edits, or the report is not on the cursor's line with several cursors, `contentChanges` is null and the player shows the unavailable state. An item whose resolution adds secondary edits replaces the offered one and the highlight is reported again.

The Game Preview panel announces every open Sparkdown document to the player with `textDocument/didOpen` and `textDocument/didClose`, as the web editor does, so the player's workspace takes an open script's text from the editor and does not treat its saves as outside changes to project files, which would move the file revision and compile the wanted suggestion again. Only documents in a workspace folder are announced as opened, changed or closed, not views of a script under another scheme such as a diff, and not untitled buffers. Each time the panel's player is initialized, which includes a webview reload, the tracker sends the open list's highlight again, since VS Code does not report a highlight that has not changed.

The extension requires VS Code 1.100. Earlier versions answer a request with nothing highlighted from their cache when one was already answered at the same cursor and document version, so a second Escape at the same place never reaches the provider. Other inline completion providers are asked whenever the trigger runs, so their ghost text can appear beside the highlighted suggestion even with inline suggestions disabled; acceptance with Enter inserts only the suggestion.

## Compiler

`SparkdownCompiler.previewCompile` is a transaction (#666). It takes a snapshot of the script's parse in the document registry, applies the edit to the registry's copy of the script under a negative version, compiles the root through the ordinary incremental pipeline, and rolls back before returning, including when the edit or the compile throws. No other request can observe the edited text, because the worker handles one message at a time. A preview compile reparses once, so it costs what an edit costs, and no second compiler or second copy of the project exists.

The rollback covers what the preview wrote into state the next compile reads:

- The parse. The registry's tree, its fragments, the text the annotators were given and each annotator's ranges and caches are persistent values or are replaced by an update, so the snapshot holds references and `SparkdownDocumentRegistry.restore` puts them back (`SparkdownAnnotator.snapshot`, `restore`). Statement memos live on the blocks those ranges hold, so the canonical memos come back with them. The grammar parser's `Compiler`, which every tree of the document shares, is mutated in place by an incremental parse, so it keeps a journal while the snapshot is held (`Compiler.beginJournal`, `rollback`): the slide of the chunks after the edit, the restart snapshot it detaches, the close records a mid-scope splice patches, the counts each step restamps and the tokens added to a chunk it began with are recorded with their undo as they are made, and of the compiled buffer, the records the parse overwrites from its restart point on are saved on its first write. The rollback costs what the parse touched, and puts the compiler back in its epoch; epochs are drawn from one sequence, so no later reuse reaches the epoch of the tree the preview built. A from-scratch parse mints no split points inside a block, so the first incremental parse inside a long block reparses all of it and mints them as it goes; a rollback would discard them with the rest, and every preview there would reparse the block again. So when a parse of the preview's edit would reparse more than a few thousand characters (`Compiler.reparseRange`), the registry first parses the text as it is there, replacing one character with itself, and keeps that parse (`mintSplitPoints`): once per block, the first time a preview lands in it, it costs what the first incremental edit in that block costs, and the registry keeps its tree, which describes the same text, stamped with the compiler's new epoch. A stretch that parse leaves long all the same is remembered and not parsed again until a real edit changes the text.
- The names a compile numbers in place. `canonicalizeSyntheticFlowNames` renumbers synthetic names, tag containers and continuation groups in the parsed objects the preview shares with the last real compile. The restored blocks hold the last real compile's numbering, so the preview's renumbering is undone with them, and the resolver resolves the objects it renamed back again on the next compile (`_namesRolledBack`). A memo a preview's compile marks stale is unmarked.
- The keys of the user's defines. The scoping of define declarations (`DefineScopeRecord`, #709) finds each chunk's declarations once per block and classifies a chunk's declarations again only when the union of the user scripts' type names has moved since they last were. A preview reads that record and writes nothing of it that outlives the preview: it records no block's classification, and each declaration whose key it changes (a preview that adds an `as X` use of a leaf another chunk defines) is put back by the rollback and resolved again on the next compile (`_namesRolledBack`). The next real compile then scopes as if the preview had not happened. Which declarations a block holds is a fact of the block alone, so the record keeps it for the blocks a preview lowers too; those blocks are dropped with the preview. The prelude's defines are scoped once per parsed prelude, by type names that never change, and a preview does not journal them.
- Nothing of the program. A preview compile's root is built and dropped (`_previewing`) and the chunk store's current root stays the last real compile's.

The compiler's own caches (the flow runs, the census, the signatures, `_lastCompileResult`) keep what the preview compiled, as they did when a preview put the text back by parsing the inverse edit: every compile compares against the one before it, and the restored blocks, which the preview never placed, are blocks that compile does not know. The Luau readers are told the way back as an edit (`noteLuauDocumentEdit`), so they carry what they read over to the restored text. The per-chunk results of `validateReferences` (`ReferenceValidationCache`, #411) are the exception: a preview compile that validates neither reads nor keeps them, so the next real compile finds exactly what the last real compile kept, under the restored blocks it was kept for. The cache compares the context's base by the key that assembles it (its root, files epoch, configuration and contributing chunks) rather than by its revision, so a preview that edits a define, and assembles a base of its own, does not cost the next real compile its kept chunks.

The compile listeners are not told about a preview compile; `compiler/didPreviewCompile` listeners are. `_canonical` records the last real compile, and `isProgramOutdated` answers from it throughout. A preview compile builds a root of its own and leaves the chunk store's current root as it was, but the compiler's incremental state has read the suggested text, so `selectDocument` recompiles the real documents first when a preview compile has run since the last real compile and the real documents have not changed; if they have changed, the selection is outdated and the compile their edit scheduled brings the state back to the real text.

An earlier compile's program can still be run: a program's statement chunks are not written after they are built, and a later compile shares the chunks it keeps (docs/engine/binary-program.md, section 1), so a kept program stays exactly the program a cold compile of its text builds however many compiles follow, and needs no activation before it runs. The worker keeps the programs it may be asked to show again (`keptPrograms`) and lets every other go. `keptProgram.test.ts` holds a kept program to the cold compile of its text, by content (`describeRoot`) and by running it.

## Player worker

The Game Preview's game runs only in its worker (`installPlayerWorker.ts`). Its compiler builds statement chunks, as every compile does, and compiles, preview compiles and selections answer the page with the program's summary (`programSummary`: identity, version, the settings a preview starts from, and whether it runs) and no checkpoint. The page holds no program and builds no game; its `Application` reaches the worker's games only by messages.

The `compiler/didPreviewCompile` listener hands the hypothetical program to the checkpoint-builder game and replays the route to the requested line with `searchRouteTo`, using its own route log, so nothing is recorded in the log PLAY reuses.

The worker keeps each program it can be asked to display with its story: every real program the page can still name, the two newest suggestions, the suggestion the page shows (`keep` on each display request), the one displayed last and the one the newest display request asks for, and it keeps the story of the program its game holds. The real programs the page can still name are the last one it named and each compiled after it, since summaries reach the page in the order they compiled. The page names the real program it holds each time it takes a summary (`player/programHeld`), except while PLAY is starting or a display waits for the worker's application; PLAY names the program it asks for, and each display request names the real program the page holds (`real`). Whatever none of these keeps is released as soon as that changes: after a compile, a preview compile, a program the page takes, a display, PLAY, and a selection that gives the game the real program back. A display activates the program's story, gives it to the game when the game holds another, and uses the route replayed to that line, or replays one there first.

## The stopped preview

The controller keeps its state machine. `updatePreview` asks the worker to display a program (`player/displayPreview`, naming it by `programIdentity`), and the worker's game declares the preview, loads the route's checkpoint, connects, previews the point and closes the reconcile pass (`displayPreviewFrom`), with an overtake token of its own. A display is superseded by a later display, by PLAY taking the program, and by anything done to the worker's game outside a display: a program given to it in place, which cancels the preview under way, or a route replayed on it by a compile, a preview compile or a selection, which changes the state the display reads. A superseded display answers `displayed: false` and never paints, except when the game still holds a program with the identity the page asked for, as after a compile of unchanged documents: the page has nothing newer to ask for, so the display runs again from it in full. The first display to an application built since the last completed one (after STOP, for instance) connects in full (`fresh`). The page's `Application` binds to the worker's game through `WorkerGameLink`, which tells the game's stream from the compiler's traffic by its `epoch`. The controller reads the program on screen through `screenProgram`. The execution report carries the document locations of a failed route (`simulateLocation`, `startLocation`), which the page cannot look up in a summary; the debugger's requests go to the worker, and a request it fails is answered to the editor as a failure. The controller stops hearing the worker's game when the preview detaches (PLAY, STOP) and when the controller is disposed, and an application still being built then is disposed of when it finishes, before the next preview builds its own. The scene warm-up is the worker's `player/previewHint`, sent as soon as a selection arrives.

A display whose state before the beat is unchanged is beat-only (#657): the game redisplays in place of the connect (`Game.redisplay`). The modules do not connect. The layout tree, its handlers, the theme, the scene and the prediction window stand. The display opens a content pass on the page (`ui/reconcile-begin` with `content`), clears the transient targets the screen still shows something in, restores the checkpoint's text, pictures, style and attributes, previews the beat and sweeps, all in one composed `ui/beat`. The content pass reconciles written text and pictures by the rules of a full pass (the first write to a stale target replaces what it showed, a stale target no write reaches is cleared at the sweep) and leaves the elements alone, which a full display's creates leave alone too, their signatures unchanged. The worker lets a display be beat-only only when the page shows a display of the same game that went up whole (not `fresh`, not taken over, no PLAY since: `unshown`), of the same kind of program (`swap`), and the route reached the point (`checkpoint`). The game then refuses it, naming the reason, unless all of the following hold:
- the last display's beat changed only written content, and nothing was sent the page since it went up (`screen`);
- the bindings the standing tree was built with evaluated no call: no user function or tunnel, no builtin and no native that is not an operator, besides the builtins the compiler calls for a line's text, its directives, a plural and a define (`calls`). This is the gate on the kept tree, and the conditions on what building it wrote or read stay behind it. The beat's own statement may call anything: it runs again from the checkpoint as on a full display, and what it changes is what the `checkpoint` condition watches;
- building the tree under it wrote none of the story's state (a global, a table, a closed-over cell, the random state, a visit count or an error) and read nothing no story state holds, such as the host's clock or an object's identity (`bindings`);
- the program runs the declarations the tree was built under (`declarations`) in a context of the same base (`context`);
- it builds the same tree, every picture the tree resolved by name included (`layouts`);
- the display shows the same beat, reached along the same route steps with the same decisions, and neither replay drew from the story's seed or read a value no story state holds along the route, nor wrote the story's state from the step before the beat to the checkpoint, nor counted other visits there than the last display's replay, which is taken after the beat's own statement has run (`checkpoint`);
- no other flow changed (`flows`);
- the scenes are those observed, apart from the beat at the cursor (`scenes`).

The answer to `player/displayPreview` says which path the display took and why (`path`, `refused`), and the player records it as a measure. The game keeps its scene tracker and the asset module its prediction window across a program update whose scene map is unchanged (`Game.settleSceneMap`).

## PLAY

PLAY asks the worker to build its game (`player/play`), naming the program whose summary the page holds by `programIdentity`. That program is the last one that compiled and ran, even when a later compile failed. The worker builds PLAY's game beside the game that previews, and the game runs that program's statement chunks, which it reads by reference: no compile writes them, so a game that outlives compiles runs the program it was given. The worker puts the game at the start point from the route it replays there (`putAtStartPoint`). Each PLAY is a numbered run, which `player/connectPlay`, `player/startPlay` and `player/stopPlay` name. The page then builds its application, whose connect connects the game (`player/connectPlay`) on a `BroadcastChannel` of the page's own, and starts it (`player/startPlay`). PLAY stays cancellable at every step: STOP, a restart or the controller going ends a start at its next step, a start that ends after the worker built its run stops that run, and the worker answers `player/connectPlay` as soon as its run is stopped, so the page is not left waiting on a restore that will not finish. The game ticks on the page's frames as the page reports them (`game/pageFramed`), or on a timer when none arrive, while the page's managers keep their frame for the renderer.

While PLAY's game runs, the worker delivers what the page reports (input, the audio clock) to it, and answers the debugger's requests from it; the first display after STOP gives the game that previews the debugger settings made during the run (`restoreWorkerDebugger`). The game that previews sends the page nothing, and the worker answers a request it makes as the page answers one it will not act on; a display the page was still waiting for when PLAY began is answered on the page, which stops waiting when the preview detaches. A selection replays no route, since a route search on a long script holds the thread for hundreds of milliseconds; the selection's line is still where the next compile starts from. A compile still runs, because the restart that follows an edit needs its program. Pause, unpause and a clock step move both the page's application and the game; one made while PLAY starts is told to PLAY's game once it starts, and never to the game that previews. STOP asks the worker where the game last executed and ends it (`player/stopPlay`), and a restart that STOP overtakes does not start the game again.

A route replayed from the top of its scene starts from a game that has never run (`Game.replayRoute`): every module's saved state and the runtime record are reset first. The worker's game displays as well as routes, and without the reset a route saved different checkpoints depending on whether the game had last displayed a preview or replayed another route.

## Player controller

`GamePlayerController` owns scheduling and the screen:

- A suggestion is identified by `completionKey`: document, version, line, file revision and edit. The newest focus sets the wanted key. At most one suggestion compiles at a time; a newer focus replaces the waiting one. A result is shown only if its key is still wanted and the preview is still eligible; a file change during the compile compiles it again.
- A suggestion's draw is abandoned as soon as its key stops being wanted. `_completionShown` is the last suggestion drawn completely, with the program it was drawn from. A return to it reuses the frame only while the screen still shows its program; otherwise it is drawn again without compiling, from the story the worker kept for it. When the wanted suggestion cannot be shown (no edit, or a failed compile) after a draw was abandoned part way, the last complete frame is drawn again: the shown suggestion, or the real program when none was shown.
- The workspace moves `filesRevision` as a project file change begins and records the change until it has reached the compiler; `previewCompile` waits for recorded changes before sending. A real program that arrives while a list is open compiles the wanted suggestion again when the file revision moved since it was keyed.
- A user selection in another document than the open list's ends the suggestion preview.
- A suggestion's program gets a negative version that no real program has, and is remembered in a set, so the game swaps programs and the controller can tell when the game holds one. While it does, `game/executed` and `game/previewed` are not forwarded to the editor, which records their lines and route choices as the author's.
- `_program` always describes the real document. While a list is open, real programs that arrive are recorded but not shown. Closing shows the newest real program at once from what the controller holds. When the real document does not compile, closing marks the frame `stale` and keeps the last complete frame, whether or not a suggestion was shown. After an accepted option whose frame is on screen, the frame stays until a program compiled from the accepted version arrives.
- PLAY ends every suggestion preview before it starts the real program, `_program`. A hidden (zero-size) or running preview takes no part.
- The toolbar's `#completion-status` shows `preparing` (after 150 ms), `showing`, `unavailable` and `stale`. `preview/gameState` reports the same state as `completion`.

## Program transport

The player's worker sends its workspace summaries, which the program transport passes over. A compiler worker that sends whole programs, as the language server's does, sends them through `ProgramTransportEncoder` (worker) and `ProgramTransportDecoder` (workspace), which share each attribute vocabulary's large parts across programs by number, sending a part again only when its file changes, and send path locations as one typed array. Programs are decoded in the order they are encoded; after each program both sides keep only the parts that program used. The asset channel shares vocabularies with the context instead of copying them (`cloneSharingVocabularies`).

## Typed edits

An accepted suggestion and every other typed change reach the preview through the player's ordinary keystroke compile, not a preview compile. `SparkdownWorkspace.scheduleChangeCompile` holds a typed change for a trailing debounce, 50 ms by default, with a max-wait of four times the delay so the preview keeps following sustained typing. The workspace runs one keystroke compile at a time: when the debounce runs out while any compile is still running, the next one starts as soon as that compile returns, with the text as it is by then. Documents in different compile trees still compile one after another in a batch.

The delay is the workspace's default, which the player's workspace uses in the web editor and in VS Code's Game Preview. A host can change it with `compileDebounceDelay` in its initialize options. Both language-server hosts (`impower-dev/src/modules/spark-editor/workspace/WorkspaceLanguageServer.ts`, `vscode-sparkdown/src/utils/activateLanguageClient.ts`) pass 200 ms, so diagnostics follow typing at the pace they did before #1797. In the web editor, applying each language-server compile result costs the page about 100 ms of main thread. At a 50 ms delay the language server would compile after nearly every key and keep the page busy, so key presses would wait for it.

Measured on 2026-10-12 on the Raffles & Bunny project at `main.sd` line 3514 (accepting a suggestion, `driver.mjs measure --edit`) and with a 52-character clause typed at the end of line 3516, one key every 80 to 120 ms (`measure --burst`). Each figure is the median of three alternating runs on a shared machine.

| Player delay, language server delay | Key to painted edit | Compiles per 5 s burst | Stale on arrival | Longest burst stretch without a compile | Median input delay | Long tasks per burst |
| --- | --- | --- | --- | --- | --- | --- |
| 200, 200 (before #1797) | 351 ms | 7 | 2 | 912 ms | 0.5 ms | 0.7 s |
| 30, 200 | 160 ms | 34 | 15 | 377 ms | 0.6 ms | 0.6 s |
| **50, 200 (chosen)** | **188 ms** | **30** | **8** | **420 ms** | **0.6 ms** | **0.7 s** |
| 75, 200 | 214 ms | 28 | 7 | 430 ms | 0.6 ms | 0.7 s |
| 50, 50 (one shared delay) | 208 ms | 4 | 2 | 3.2 s | 56 ms | 2.8 s |

50 ms is the shortest delay whose compiles are no more often stale on arrival than at 200 ms (about three in ten; at 30 ms nearly half are). With the language server at 200 ms, compiles run for about a third of the burst or less at any of these player delays, and never two at once. A shared delay below 200 ms keeps the editor's main thread busy with language-server results: 2.8 s of long tasks per 5 s burst at 30 to 75 ms, 2.1 s at 125 and 1.4 to 1.9 s at 150. The player's compiles then wait on that thread and start only every few seconds.

## Performance

Measured on 2026-09-24 on the Raffles & Bunny project (main script 8,254 lines, 646 files, 149 MB of assets) at `main.sd` line 3515, highlighting a replacement for `raffles_concerned`, on a desktop Windows 11 machine in headless Chromium, with the editor driver's `measure` (key press to the `preview/didChangeGameState` that reports the suggestion on screen) and the worker benchmark (`scripts/bench/preview-bench.mjs`, which replays the worker's compile, route and display in Node).

| Per highlighted suggestion | Median, and range over three runs |
| --- | --- |
| Arrow key to painted result, warm | 445 to 863 ms |
| Compile and route in the worker | 319 ms (291 to 512) |
| Display in the worker: checkpoint load, connect, preview | 41 ms |
| Sent to the page | 193 messages, 233 KB |
| Long tasks on the player's main thread | none |

Re-measured on 2026-10-14 at line 3514 (`raffles_inquisitive`) after the beat-only display (#657), base `0f97fcb2f` against the change in alternating rounds:
- Every highlighted suggestion after the first is beat-only.
- In the worker, the display takes about 13 ms (load 7.9, redisplay 1.9, preview 3.4) against 18 ms, and sends 7 messages, 23.8 KB, against 20 messages and 246 KB.
- `player/displayPreview` takes 19.7 ms against 32.6 ms with the portrait resident, and 42.1 ms against 45.9 ms when it is loaded on the way.

The page receives only the display's messages; no program, checkpoint or path locations cross. The largest remaining costs are the compiler's incremental parse and runtime export and the route replay, both shared with ordinary edits.

No worker, game or application is created for a suggestion: the worker's game and the page's application are the ones the ordinary preview uses.
