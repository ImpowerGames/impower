# The binary program

This is the design of record for the binary program of #692: the form a compiled story takes, the instructions it is made of, the symbols and addresses that name positions in it, and the state of the engine that runs it. Every slice of #692 builds against this document; [What is built](#what-is-built) says what the slices so far run today and where they settle what the design leaves open.

Where a choice rests on a number, the number comes from a throwaway prototype under `scripts/bench` (`chunkProgram.ts`, `chunkStepper.ts`) measured beside #664's. [Measurements](#measurements) gives the figures and the command that reproduces each. Nothing under `packages/*/src` imports the prototype, and `scripts/bench/engine-bench.test.mjs` asserts that.

Each of the ten sections below ends with the decision, its reason, and the alternative it was chosen over.

## Terms

- Program chunk: the compiled form of one statement, an immutable `Int32Array`. A statement is one syntax node that `lowerStatements` lowers on its own, at the top level of a flow or inside a block (#656).
- Sequence: the ordered program chunks of one body. A flow has one sequence, and each block of a block statement (`if`, `choose`, a loop, a function) has one. A sequence has an id that stays with its body from one compile to the next.
- Root: one version of the whole program. It says what each sequence id holds, where that sequence sits and how many lines it spans, which sequence holds each chunk, where each symbol is defined, and where each flow starts in its script. A compile produces a new root that shares every chunk and every array it did not change.
- Symbol: an interned id for anything a chunk refers to outside itself.
- Address: a chunk id and an offset into that chunk's code. It names an execution position.
- Image: a capture of the engine's state, either whole or as what changed since the previous capture.
- Fingerprint: a hash of a statement's source, or of one part's, by which a save and a re-emit recognise it (section 1).
- Layout hash: a hash of a chunk's code, by which a save knows whether a frame saved inside a statement's code, inside a loop's pass or inside a function can resume there (section 1).
- Listing: the fingerprints of a sequence's entries in order, of which a save writes windows (section 8).

## 1. The program chunk

### Layout

A program chunk is one `Int32Array`, little-endian, read in place and never written after it is built.

| Words | Holds |
| --- | --- |
| 0 | code words, two per instruction |
| 1 | rows in the line table |
| 2 | rows in the export table |
| 3 | rows in the block table |
| 4 | rows in the reference table |
| 5 | chunk id |
| 6 to 7 | fingerprint of the statement's source, 64 bits, for the save format |
| 8 to 9 | layout hash of the code and tables, 64 bits, for the save format |
| 10 onwards | the code, then the four tables in the order above |

A line table row is six words: the offset of the first instruction it covers, an anchor, the first line as a delta from the anchor, the start column, the last line as the same kind of delta, and the end column. The anchor is the statement's first line or, for a part of a block statement that stands below one of its bodies (an `elseif` condition, a later choice's line, the `then` label, the condition of a `repeat` loop), the line after the last line of that body, named by the block's index. How many lines a body spans is the root's to say (see Blocks and sequences), so an edit inside a body moves the parts below it and rewrites nothing in the owner's chunk. Rows are sorted by offset and a row covers the code up to the next row. Every display call carries the row of its own source range, so any line of a joined beat maps to that beat (#685); an instruction with no range of its own falls under the statement's first row.

An export table row is two words: a symbol id and the offset in this chunk's code that defines it.

A block table row is five words: the id of the block's sequence; the offset at which this chunk resumes when that sequence runs out; the offset a `break` inside the block resumes at (or -1 when the block is no loop body); a word that holds the number of scopes this chunk has open where it enters the block, beside flags saying whether the block is a loop body, a loop body that runs each pass in a scope of its own, a choice body, a `then` clause or a function body; and the lines of the statement's own parts between the body above (or the statement's first line) and this body, which is 1 for an `else` line and more for a choice whose text runs over several.

A reference table row is two words: a symbol id this chunk refers to, and a hash of the facts about that symbol the emitted code depends on (see Identity).

The fingerprint is a 64-bit hash of the statement's source and of nothing else. For a plain statement it hashes the statement's text; for a block statement it hashes the statement's kind and the text of its own parts (its branches' conditions and `else`, its choices' lines, its loop header, its `then` label) and none of its bodies, whose statements are matched on their own. The text is normalized first: comments are removed, each line is trimmed, and a run of whitespace between tokens is one space, with the text of a string and of a displayed line left as written; so two statements that differ only in the spacing between their tokens are the same statement to a save, which is intended, and two that differ inside a string or a displayed line are not. It is what a durable save compares (section 8) and what aligns the parts of a re-emitted statement (section 2), so it is a fact about what the author wrote and not about what the writer emitted: it holds across sessions, across a reseed, across a release of the compiler that lowers the statement differently, and across a change to the value of a constant the statement reads, none of which a save should notice. A part of a block statement or of a statement that owns anonymous symbols (a branch's condition, a choice, an alternator, a function written inside the statement) has a fingerprint of its own, the same hash over the part's source alone, so that it does not change when another part is written or removed beside it (section 2). Sixty-four bits keep two statements of one sequence from reading the same by accident, where a 32-bit hash would do so in about one sequence of a thousand statements in ten thousand; two that do read the same are identical statements to a save, the stated limit of section 8.

The layout hash is a 64-bit hash of the chunk's code and export table, read with every id replaced by what it names: a string's text, a number's value, a symbol's qualified name or, for an anonymous symbol, the ordinal of its part in the statement and its own ordinal in that part. It changes whenever the statement's source or the compiler's lowering of it changes. A durable save writes it for the statement a position is in, for each owner on the frame's block stack that declares temporaries the frame holds (a loop), and for the chunk that bound the frame's parameters (a function's or tunnel's entry), and the loader compares each with the program it has (section 8): the offset, the temporaries and the eval stack a frame holds mean what they meant only on the layout they were made on.

### The instruction word

An instruction is two words. Word 0 holds the opcode in bits 0 to 7, flags in bits 8 to 15 whose meaning belongs to the opcode, and an unsigned 16-bit operand `aux` in bits 16 to 31. Word 1 is a signed 32-bit operand `arg`. The words are fixed-width and little-endian so that a native player stays possible. What an author can make as large as they like rides in `arg`: a jump's distance, a choice's target, the pairs of a table literal, the values a tuple packs. `aux` holds what the language keeps small, such as the arguments of a call and the arity of a builtin. An operand that still does not fit its field is a construct the writer does not emit, so the compile falls back and names it (section 9).

A jump inside a chunk is a signed count of words relative to the instruction after the jump. Nothing in a chunk names a position outside it: a target in another chunk is a symbol id, and a block is an index into the chunk's own block table.

### Blocks and sequences

The program is a tree of sequences, as a Lezer tree is a tree of nodes that hold positions relative to their parent. A block statement is one chunk. Its code holds the statement's own control flow, and where a body runs it says `EnterBlock k`. The statements of block `k` are chunks of their own in a sequence, which row `k` of the owner's block table names by id. The owner holds the id and no reference to what the sequence holds, so replacing a statement inside a block builds new arrays for that sequence and a new root, and no new owner.

Where a sequence sits is the root's to say, and the sequence's arrays say nothing about it, which is what lets two roots share them. A sequence id is given when a body is first emitted and stays with the body: the arrays that replace a sequence's arrays are held under the same id, and when a block statement is re-emitted in place each of its bodies goes with the part that heads it (the condition of its branch, its `else`, its choice, the `then` label), so a body keeps its id wherever the alignment of the old parts with the new ones puts that part (section 2), and a body whose part is gone gives its id up. A root holds two tables over these ids. The sequence table gives, per sequence id, the current arrays, the chunk id of the owner, the block index, the flow's symbol and the number of lines the body spans; and, for a flow's own sequence and for a script's declaration sequence, which have no owner, the script they are written in (the interned string of its uri) and their first line there. Beside it the root keeps, per script, that script's flows in the order of their first lines, which is where a lookup by line starts. The chunk table gives, per chunk id, the id of the sequence that holds the chunk, or -1. Neither holds an entry, because an insertion shifts entries: a chunk's entry is found by searching the chunk ids of the sequence that holds it, outward from the entry the position was last seen at where one is known (an image keeps it beside each address), and otherwise through an index that the arrays build on first use and that stays true because they never change. A compile copies the sequence table as it copies the symbol definitions (section 2), and the chunk table by pages of 1,024 ids, of which it copies the ones it writes. It rewrites the rows of the sequences it rebuilt, of the sequences that enclose an edit (their span grows, and their line starts below the owner move), of the blocks whose owner it re-emitted, and of the chunks it emitted, moved or dropped; and it clears the row of a sequence whose body is gone, so that a root holds the rows of the bodies its program has and no others, and a dropped body's arrays and chunks are the collector's once the roots that held them are. A body below or beside an edited sequence keeps its row: the row names the owner by chunk id, the new root's chunk table gives the sequence that holds the owner by id, and the new root's sequence table gives that id the new arrays. Nothing reached through a root is older than the root.

When a block's sequence runs out, the engine resumes the owner at the block row's resume offset. The engine keeps the blocks it is inside on a block stack in the current call frame, three numbers per entry: the owner's sequence, its entry in that sequence, and the resume offset. Scopes are opened and closed by instructions of the owner around the `EnterBlock` (an `if` opens one for a branch; a loop opens one for its hidden variables and one for each pass of its body, as `lowerLuauForLoop.ts` wraps them today), and the block row records how many the owner has open where it enters the block. The frame's scope depth at a position is the sum of those counts over the stack, plus the scopes the chunk at the position has opened before the offset (`BeginScope` less `EndScope`, which the reader counts once per chunk), so it is derived and kept nowhere else; at the resume offset of a block row that chunk count is the row's scope count, because the owner closes those scopes only after the body, except for a loop body that runs each pass in a scope of its own: the owner opens that scope right before `EnterBlock`, and it is closed before the owner resumes, by the engine when the body runs out and by the body's `break` or `continue` when it leaves, so the chunk count there is one less. Code that only a jump reaches takes the depth of the code that jumps there, as do a `choose` block's entries and clauses (section 4) and the exit of such a loop, which a `break` reaches: the writer makes the count read in order agree there with the `BeginScope` or `EndScope` it writes where no instruction runs, after the `Jump` or the `EnterBlock` before it (#1575). A chunk holds no operand on the eval stack across an `EnterBlock`: an owner that compares a value across its branches (the `match` form, section 3) pops it before it enters a branch, so at every statement boundary of a frame the eval stack stands at the height the frame was pushed with, which is what a placement after a statement relies on (section 8). The stack is derivable from the position through the root's two tables: the sequence that holds the chunk, that sequence's owner, the owner's entry in the sequence that holds it, and the owner's block row, whose offsets and scope count are static. That is how a jump that lands inside a block rebuilds the stack and the scope depth (section 5), and how a position restored from an image does. An engine is built on one root and runs on it for as long as it lives, as `Game.updateProgram` builds a `Story` per program today; a new root reaches a running game as an image restored into an engine built on that root (section 7). A block stack entry, which holds an entry of a sequence, therefore never meets a root it was not made on, and it is never written to an image or a save.

A flow (a scene, a branch, a function declared at the top level) is a sequence registered in the root under its symbol. Its first chunk binds its parameters (`SetVar` with the declare flag, last parameter first, as function entry does today): for a scene or a branch, a chunk of its own on the header's line, so that a jump to the flow binds them and a jump to a label inside it, which lands at the label's chunk, does not. A function written inside a statement is a function-body block of that statement's chunk: the chunk exports the function's symbol at the entry code that binds the parameters and enters the block, and the chunk's main path jumps over that entry code.

`break` and `continue` are statements inside a loop body's sequence, so their chunks cannot hold an offset of the loop. The lowerer already emits one `EndScope` per scoped block the jump skips, the pass scope of the loop it leaves included (`lowerLuauBreakContinue.ts`); after those, the writer emits `Leave` where the lowerer's divert targets the generated label of an enclosing loop. `Leave` pops the block stack to the nearest loop body and resumes its owner at that block row's break or resume offset.

Top-level declarations (`store`, `const`, `define`) are statements of their script's declaration sequence, which `ResetState` runs in the order it runs the `global decl` container today, constants first. A compile that re-emitted or dropped any declaration chunk or any function chunk, moved a chunk into a function or out of one, or reordered the declarations runs every script's declaration sequence again, in order, because an initializer may read another global or call a function whose body changed; a compile that re-emitted only chunks inside flow bodies runs none. The rule is whole-sequence rather than per statement so that no global keeps a value computed from an initializer that has since changed: on the Raffles and Bunny project the roughly 600 declarations run in a few milliseconds on this engine, which is what makes the coarse rule affordable.

### The order structure

What a sequence holds is two parallel plain arrays: the chunks, and each entry's first line relative to the first line of the body itself. A body runs from the line after the part of its owner that heads it to the line before the owner's next part, blank lines and comments included, so the lines of a block statement are those of its parts and its bodies with none left over. Where the body starts is not stored. It is the owner's first line, plus, for each body above it, the lines of the owner's parts that head that body (its block row says how many) and the lines that body spans (its row in the root says how many), plus the lines of the parts that head this one. A flow's first line in its script is the root's, per flow. So an edit inside one body changes no line start of a body beside it or below it, whose arrays and rows stay shared, and their lines still come out right. The arrays are never edited. A compile that changes a statement builds new arrays for that statement's sequence by copying, with the tail of the line starts shifted, new line starts for each sequence that encloses it and holds a statement below the owner, and a root that holds them under the sequences' ids with the longer spans. A preview compile does the same and its root is dropped afterwards, which leaves the real root, every sequence and every chunk exactly as they were, with nothing to roll back.

At the size of a real scene this costs microseconds. On the Raffles and Bunny project the flow that holds `main.sd` line 3515 is 15,954 records in #314's encoding and an estimated 813 statements in 4 sequences, the largest of 434; inserting a statement into that sequence costs 2.2 to 2.4 microseconds by copy and replacing one costs 0.8 to 1.0, against 5.2 microseconds for the bulk copy #314 pays to carry one unchanged flow of that size into every compile. A persistent 32-wide tree is cheaper still (0.7 to 1.0 microseconds to insert, 0.3 to 0.4 to replace) and barely grows with size, but every reader of a sequence is simpler over an array: the engine's next statement is an index plus one, and the line lookup is a binary search. The copy grows by 12 to 16 nanoseconds per entry, so an insert passes 50 microseconds between 3,500 and 4,500 statements in one sequence; a sequence that large is the point at which to put the tree behind the same reader interface.

The line starts are plain arrays of small integers and not typed arrays, because allocating a typed array costs more than copying a few hundred numbers.

### Identity

A statement keeps its program chunk across compiles while three things hold. Its own syntax reads as it did. The incremental parse builds the tree again, so no node object outlives an edit near it, and a statement is known by its syntax: the node's name, the column it starts at and its own text. For a plain statement that is its whole text; for a block statement it is its own parts (a condition, a choice's line, a loop's header, the `then` label), with the lines its bodies hold alone left out, so its blocks are the same in number and kind. A statement whose lowered block the compile carried from the compile before reads as it did by construction, and its syntax is not read again. The statements inside its blocks are chunks of their own and are judged on their own, which is what lets an edit inside a body leave the owner's chunk alone although the parse builds the owner a new node. Every part of the lowering context its lowering read is unchanged. The context records what a statement's lowering read as it reads it (the choose depth, the loop stack, the enclosing function scope, the declared locals, the define type names and the global callable names it consulted, what it found a name it calls to be among the enclosing function's variadic sub-flows, which a `local` of the name changes, the names each function it writes captures, as the lowering builds the function from them (a method's without its `self`), and the pointers a call to a variadic sub-flow, or a reference to one as a value, passes, which the function's body decides although its lines are not the statement's syntax), so the set of inputs is whatever the lowerers asked for and not a list kept by hand, and a statement is lowered again exactly when a recorded value differs (#656). And every fact about another symbol its emitted code depends on is unchanged. Those facts are what the generating classes read outside their own subtree: whether a name is a flow, a function, a label, a global, a constant or a builtin; a callee's parameters, which decide the arguments the call passes by reference (`Divert.EmitCall`; the call arranges the others for the callee when it runs); and a constant's value, which is inlined where it is read. The reference table records a hash of those facts per referenced symbol, recorded by the writer as it reads them from the symbol table, so the incremental pass compares hashes and re-emits a chunk only when one differs, and a new dependency needs no detector added by hand. A constant's value is not among them while constants are globals the declaration sequence initializes, which a read reads with `GetVar` (#309): its readers' code does not hold it. The rule holds from the first slice (#694): a chunk is either reused by it or emitted again, and no slice reuses a chunk by its syntax node alone.

Chunk ids and sequence ids come from counters in the chunk store that never go back, not at a reseed of the interning table either (section 2), so an id names one chunk or one body for as long as the store lives. A re-emitted statement gets a new id. An address kept across any number of compiles therefore either names a chunk the root at hand still holds or names none, never another statement's, and a root's chunk table starts at the first id its table generation gave out.

An address is a chunk id and an offset. Outside the engine it is one number, `chunkId * 2^21 + offset`, which a double holds exactly for 2^32 chunk ids and a consumer compares with `===`.

**Decision:** one immutable `Int32Array` per statement with two-word instructions, chunk-relative jumps, symbols for everything outside the chunk, blocks named by a sequence id that the root resolves, and copy-on-write array sequences under a persistent root.

**Reason:** an edit re-emits one chunk, copies the arrays of one sequence and shifts the line starts of each sequence that encloses it; nothing else is touched, a preview needs no rollback, and the garbage collector reclaims dropped chunks and roots with no arena to compact.

**Alternative:** one flat buffer with absolute indexes, which #664 measured and whose every insertion shifts every later index; a single arena of chunk spans, which saves the per-array overhead (about 200 bytes a chunk) at the price of compaction and of a preview writing into shared storage; a flat sequence with synthetic head, else and end chunks and skip spans, which makes one statement several chunks and makes an owner's spans change when its body does; the persistent tree, kept in reserve as above. inkcpp's six-byte unaligned instruction was not taken because a typed array reads aligned words and a `DataView` read per field costs more than the two bytes save; a single word with a 24-bit payload was not taken because an instruction such as `CallStd` (a name and an arity) or `Call` (a symbol and an argument count) needs a second operand.

## 2. Symbols

A symbol is what one chunk uses to refer to something another chunk defines. These receive one:

| Kind | Named | Counted |
| --- | --- | --- |
| Scene | `ACT_TWO` | yes |
| Branch | `ACT_TWO.cellar` | yes |
| Label, including the label of a `then` clause | `ACT_TWO.cellar.knock` | yes |
| Function | its name; one written inside a statement is anonymous | yes |
| Choice body, alternator | anonymous | yes |
| Global, constant | its name | no |

Symbols are interned in the persistent `ProgramTable` (`packages/sparkdown/src/binary/ProgramBinaryWriter.ts:44`) in a third pair beside strings and numbers: `symbols` (qualified names), `symbolIds`, and, for a counted kind, a dense count id. The table is append-only, so an id handed out stays valid for every chunk minted in that generation. What a program defines a symbol as belongs to the program's root, like where it is defined (see Resolution): an edit can turn a scene into a branch of the same name, and a preview root and the real root, or a root still in use and the one after it, then define the name as different kinds. A root's row for a flow records its kind.

An anonymous symbol belongs to the part of its statement that produced it: a choice, an alternator, a function written inside the statement. The chunk store allocates it when the part is first emitted. When the statement is re-emitted in place (one statement in the changed range before and one after), the old parts are aligned with the new ones as a diff aligns lines, and what belongs to a part goes with it: its anonymous symbols, and the id of the body it heads (section 1). Three passes do it. Parts whose own source is unchanged, by the part's fingerprint (section 1), and that still stand in the same order are matched first, the nearest in order where several read the same. A part that is left and has the same fingerprint as one left on the other side is matched next, wherever it now stands, so two choices that swap places each keep their own. Then, in each run of parts that is left between two matched ones, or between a matched one and the start or the end of the statement, or in the whole statement when nothing matched, the old parts are paired with the new ones in order, which is how an edited part keeps what it had. A new part left without a pair gets new symbols and a new body id, and an old one left without a pair gives up both. So a choice written above a once-only choice that was taken takes nothing from it; a choice whose text was edited keeps its count, whether it is the first, the last or the only one; the condition of an `if` with no `else` can be edited without its body changing id; and a function written above another leaves a closure made before the edit calling its own function. The rule has two limits. One compile that both inserts a part and edits the part beside it pairs the two the wrong way round. And parts that read the same cannot be told apart, as section 8 says of statements: of three identical once-only choices of which the second was taken, deleting the first leaves the taken one offered again and the one below it hidden. Nothing is renumbered by document order, which is what the generated function names do today (`SparkdownCompiler.ts:2062`) and what makes a preview compile rewrite them (#666). A durable save names an anonymous symbol by its statement and its part (section 8).

### Resolution

Where a symbol is defined belongs to a root, because a preview root and the real root can define the same label in different chunks. A root holds three `Int32Array`s indexed by symbol id: the defining sequence, the entry in it, and the offset in that entry's chunk, with -1 for a symbol the program does not define. A compile copies the arrays and rewrites the rows of the symbols that the chunks it emitted or moved export, plus the entry of every symbol defined after the edit in the same sequence. No chunk holds an entry, so no chunk changes.

A divert through a symbol is three typed-array reads more than a divert whose target was resolved at compile time. Measured in a table of the project's size, that is 1 to 6 nanoseconds on a divert of about 20, with the samples of the two overlapping.

### A symbol that disappears

The id stays interned and its definition row becomes -1 in the new root. At compile time the pass that resolves references finds the chunks that refer to it through the reverse index of the reference tables and reports the diagnostic the current compiler reports (`target not found`), with the source range of the referring instruction. Their chunks are not re-emitted: they hold the id, which has not changed. At run time a jump to an undefined symbol raises the engine's runtime error with the source line of the jump, as `Divert target doesn't exist` does today. A saved position inside the symbol's flow or body is placed by its listing (section 8), and a count saved under a name the program no longer has is dropped.

### Reseed

`reseedProgramTable` (`program/ProgramTable.ts`) starts a new generation. Every chunk holds ids of the old one, so the next compile is cold. The reseed interns the live entries again and returns, per table, an `Int32Array` from old id to new id with -1 for a dropped entry. An engine runs on one root (section 1), so it is an image that crosses a reseed: one taken in the older generation has its counts remapped through the array when it is restored into an engine built on a root of the newer one. Chunk ids and sequence ids are no part of the table and are not renumbered: their counters go on, so an address from before the reseed names a chunk that no newer root holds, and is translated like any other (section 8). A value that names a symbol holds the id and the generation the id belongs to, beside the qualified name when the symbol has one. When the generation differs it takes its id through the remap arrays, which the store keeps for every reseed of the session, so no walk of the table heap is needed and an anonymous symbol, which has no name to resolve by, crosses a reseed as well. The store's record of which part of which statement owns each anonymous symbol is remapped with the table, so the cold compile that follows a reseed hands every part the symbol it had, and a closure made before the reseed still calls its own function.

**Decision:** exact interned ids in `ProgramTable`, definitions per root in typed arrays, anonymous symbols owned by the part of the statement that produced them and handed on by aligning parts on re-emit, a reference to a vanished symbol reported and left in place.

### Generated names

An identifier an author writes matches `LUAU_IDENTIFIER`, `[a-zA-Z_][a-zA-Z0-9_]*` (`definitions/yaml/sparkdown.language-grammar.yaml`), so a character outside `[A-Za-z0-9_]` is one no author's name holds. Every name the compiler generates holds a `$`, as an anonymous symbol's key begins with a NUL, so no name an author writes can equal one, and the compiler has no reserved names, no diagnostic for them and no rename of an author's name (#1729):

| Family | Form |
| --- | --- |
| A name a lowering makes from a place (`syntheticId`): a function written inside a statement, a `define`'s method, a redefinition, a method call's receiver, a property or multiple assignment's temporaries, a loop's temporaries and labels | `__anon_fn_<document tag>$<offset>`, `__while_<document tag>$<offset>_loop` and the like |
| The same names numbered by document order (`canonicalizeSyntheticFlowNames`) | `__synth$<n>` |
| A continuation's group | `__group$<n>` |
| A UI binding's evaluator | `__binding$<document tag><kind>_<name>_<offset>` |
| A chunk's own name for a generated temporary | `__t$<n>`; a loop's hidden temporaries `__forIdx$`, `__forIn_iter$` and the like |

The `$` is infix, never the first character, so the checks that read a leading `$` as a temporary of the runtime's own, or a key of a struct's own, do not take a generated name for one. Where a generated name reaches an author it is shown in a readable form: a function the compiler named is `<anonymous>` in the frames view, a stack trace, `debug.info` and a function value's text, and the Variables view leaves out every name with a `$`. The names `__varargs__`, a vararg function's local, and `__run_<path>`, the wrapper of a `run` statement, are generated without a `$`: the first is read by saves and diagnostics, and the second is spliced into source text the parser reads.

**Reason:** a chunk never depends on where its target is, so an edit to the target re-emits only the target; ids are exact, so nothing is tie-broken.

**Alternative:** absolute offsets written into instructions at the end of a compile, which is what inkcpp's emitter does (`inkcpp_compiler/binary_emitter.cpp`, `process_paths`) and what a batch compiler can afford; 32-bit hashes of names, which inkcpp uses and has to tie-break by offset because paths repeat (`shared/private/header.h`, `container_hash_t`); ordinal names such as `g-0` and `c-1`, which one inserted gather renumbers.

## 3. The instruction set

The set is purpose-built and linear. It has no evaluation mode: where the current engine pushes content to the eval stack or to the output depending on `inExpressionEvaluation`, each instruction here names its own destination (`Text` writes output, `Str` pushes a value), so `EvalStart` and `EvalEnd` do not exist. A literal string is one `Str`. A table is built from a pair count known when it was lowered. A conditional is a relative jump.

Values are the engine's value classes, and a pushed constant is a value object created once per table entry, so pushing allocates nothing. "Pops n, pushes m" below is the effect on the eval stack. The output rules (a newline that is not repeated, does not open a line and is not written while a join is pending, the trimming of a function's trailing whitespace) are those of `StoryState.PushToOutputStreamIndividual` and `TrimWhitespaceFromFunctionEnd`, carried over with the instruction's operand in place of the runtime object.

| Instruction | Operands | Eval stack | Output | Call stack | Counts |

## 4. Weaves in linear code

A `choose` block is one statement and one chunk. For

```
choose
  + if has_key [Open the door]
    The door swings open.
  * Knock
    Nobody answers.
then (hallway)
  You step back.
end
```

the chunk is:

```
      BeginString  Text "Open the door"  EndString     the first choice's choice-only text
      GetVar has_key                                   its condition
      Choice   condition, choice-only, decision site   target A
      BeginString  Text "Knock"  EndString             the second choice's start content
      Choice   start content, once only                target B
      Done     hold
      Jump T
A:    Visit #1
      Newline
      EnterBlock 0
      Jump T
B:    Visit #2
      Text "Knock"
      Newline
      EnterBlock 1
      Jump T
T:    Visit ACT_TWO.hallway
      EnterBlock 2
```

The chunk exports `ACT_TWO.hallway` at `T`. A `Choice` holds its target in its 32-bit operand, so a `choose` of any size reaches its entry code, and it holds no symbol: the count a once-only choice reads is the symbol of the `Visit` its target opens with (`#1` and `#2` above are the two choices' anonymous symbols). Blocks 0 and 1 are the choices' bodies and block 2 is the `then` clause. Their statements are chunks of their own in the three sequences, so a plain line inside the clause does not depend on the choices before it, and a line after the `choose` block is the next entry of the parent sequence.

What the current weave computes as a fold over siblings falls out of the structure. A loose end is the end of a block: a choice's body ends, its owner resumes at `Jump T`, and with no `then` clause the owner's code ends and the parent sequence continues. A nested `choose` passes its loose ends to its ancestors the same way, by running out. A gather replaces no container, because a statement is never inside one. An `if` that gates a choice inside a `choose` block is a relative jump around that choice's code in the same chunk.

A `choose` block scopes as Luau scopes a block (#1575): a `local` is visible from its declaration to the end of the block that holds it and nowhere else. Where the current engine's weave scopes otherwise, the current engine is wrong (#1588) and the program does not copy it. An `if` that gates a choice opens a scope for its branch, which closes where the branch ends, before the next choice's condition, so a later condition, a later choice's body and the line after the block read the variable the branch's local shadowed. The choice's thread is forked inside the branch's scope, so the choice's entry runs at the depth the choice was raised at and its body reads the branch's locals, as the body is written inside the branch; the entry closes those scopes after the body, down to the depth of where it continues. A `do` block or a loop of the preamble closes its scope at its `end`. A `choose` block written in another block's preamble is part of that block's presentation, and its `then` clause runs after its own block: after a choice that belongs to the block is taken (one of its own, one an `if` of it gates, or one of a block written in its preamble), once, at the depth of scopes the block stands at, so it reads the locals of the branches around the block. It then continues where a choice of the block around it continues, at that block's clause or at the end of the `choose` statement, and it never runs while the choices are presented. Three such blocks, one in another's preamble, run clause after clause after a choice of the innermost.

The scopes open at every offset of the chunk are therefore exact, and they follow from the code as section 1 says, by the count read in order. An entry or a clause, which only a `Choice` or a `Jump` reaches, runs at the depth of the code that reaches it rather than that of the code above it, so the writer writes the `BeginScope` or `EndScope` that makes the count agree in the gap after the `Jump` before it, where no instruction runs. A body's block row records the depth its owner enters it at, so a position restored or a jump landing inside an entry or a body derives the scopes its frame holds from the block stack and the chunk's code, and no frame carries a depth of its own.

A choice is never raised from a body's own chunk, which does not hold its entry (#1503). The body of a `do` block or a loop of the preamble that offers choices, directly or in a block written there, is the `choose` statement's own code, as the branch of an `if` that gates a choice is: a `do` block's code stands between its scope markers, and a loop's is laid out as section 3 lays it out with its body written where its `EnterBlock` would be, the end of a pass running on into the step or the test and a `Jump` back to the head. A loop runs every pass and raises a choice on each from its one `Choice`, whose fork of the thread holds that pass's variables, so the choice's text, its entry and its body read them; the entry runs at the depth the choice was raised at, inside the loop's scopes, and closes them after the body, as a gated choice's entry does. The lines after a choice in such a body, up to the next choice, are the choice's body, a block of the statement; the lines after the `do` block's or the loop's `end` are the preamble's, and run before the choices are presented. Those lines are lowered as the choice's body and not as the preamble, in a gated `if` branch as in a `do` block or a loop (#1622): a `choose` block written there is a block of its own, run when the choice is taken, as it is in the body of a choice written directly in the block, and not one that offers its choices with the preamble's. The preamble resumes where the branch or the body ends. In the current engine's weave the choice keeps its loose end past such a block, whose end runs on out of it, so the choice's body continues after the block and then where the choice continues; the end of a block that offers no choice runs on out of it the same way, and is no loose end of its own. A `break` or `continue` of such a loop is the `EndScope`s its lowering writes and a `Jump` to the loop's exit or its next pass, and the code after the `Jump`, which only a jump could reach, is counted at the depth it stood at before those `EndScope`s, by `BeginScope`s written in the gap after it; a block of the body that holds such an exit, an `if` branch or a `do` block, is the statement's code too. An exit written in a choice's body or a `then` clause, which run after the loop has ended, is named. Where the current engine's weave nests in the choice the rest of a `do` block, or the rest of the pass and of the loop, the current engine is wrong (#1588), and where it cannot run a choice of a `repeat` or `for ... in` loop at all, it is wrong too (#1606).

The `Done` that ends the presentation carries the hold flag: it stops the flow, or ends the thread it runs in, only when a choice this chunk raised is waiting, and otherwise the block runs on through `Jump T`, as the current engine's hold for choices does (`HoldForChoices`): a block whose choices were all gated off, or whose choices a thread raised elsewhere, holds nothing.

A `label` statement is a chunk of its own that exports its symbol at a `Visit`, in the sequence where the author wrote it.

Nothing is named by ordinal. An unnamed gather needs no identity: it is an offset inside its chunk. A choice's count, which once-only reads, is an anonymous symbol that belongs to the choice and goes with it when the `choose` statement is re-emitted, so a choice written above it takes nothing from it (section 2). A choice's identity for the route planner, which is `Choice.sourcePath` today, is the address of its `Choice` instruction. An alternator's count and its shuffle seed come from its own anonymous symbol.

The start content of a choice is emitted twice, once inside the capture that builds the choice's text and once as output at its entry, where the current protocol runs one container twice through a return label held in a temporary.

The code before the `Done` that ends the presentation reads state and writes only the captured texts: no `Visit` and no assignment of the writer's own stands there, though a condition or a choice's text can call an author function that writes, counts or logs, and a thread that ran before the `choose` can have raised choices of its own. What the author writes there runs as written: the statements of the block's preamble (an assignment, a loop with its hidden temporaries, a label's `Visit`) and an alternator in a choice's text, which counts at its own `Visit` each time the choices are raised. A durable save therefore does not run the presentation again from the state it left: it holds the image of the beat before the choices, with the choices a thread raised before that beat's newline kept as they were, and running that beat's continue again raises the rest as the new program has them, from every thread, with each effect run once (section 8).

**Decision:** one chunk per `choose` with relative labels for its choices and its `then` clause, bodies as blocks, anonymous count symbols in place of ordinal names.

**Reason:** the fold's shared state (the current container, the loose ends, the ordinal counters of `Weave.ts:64`, `:75`, `:282`) has no counterpart, so inserting a statement or a gather renames nothing.

**Alternative:** porting the weave's containers and the `$r` return-label protocol as they are, which keeps the statement inside its gather's path; one chunk for the whole block with its bodies inline, which re-emits 1,100 lines for an edit to one. For a choice inside a `do` block or a loop of the preamble (#1503), a target in the `choose` chunk that a choice raised from the body's own chunk names, by an offset or by the choice's count symbol exported at its entry: the body's chunk would depend on the owner's layout, and the entry would run at the depth of scopes the body's chunks opened, which the owner's code does not count. Writing such a body in the `choose` chunk re-emits the chunk for an edit inside the body, as an edit inside a gated branch does.

## 5. Counts

Every symbol of a counted kind has a dense count id, given when it is interned. Visits are a `Uint32Array` and the turn of the last visit an `Int32Array` holding -1 for never, both indexed by count id and grown when the table grows.

Every counted symbol counts, always. No count flag exists and no pass decides which containers count. What the language reads is unchanged, because a count that no script reads is never observed; what changes is that a read added in one flow re-emits nothing in the counted flow, a count has its full history whenever a script first reads it, and `FlattenContainersIn` with its count-flag reconcile (about 8 percent of `ink/compile`, #664) has no successor, because there is no container to flatten and no flag to reconcile.

A label, a choice body and an alternator count at their start only, as their containers do today (`countingAtStartOnly`), so their count is a `Visit` at their position: flow that passes the position counts, whether it fell through or jumped there. A jump that lands on a label also counts the labels written directly before it in its sequence, each of which stands with nothing between it and the next, as the current engine's weave nests a label as the first content of the label before it and a divert counts each label container it enters at its start. A declaration that runs no code where it is written (`const`, `store`) is nothing between, since the current engine makes no runtime object of it; a line, a `local` or a function is something.

A flow counts when it is entered from outside, wherever the jump lands. A jump from inside the flow does not count it, not even one that lands on its first instruction, which is the current engine's rule: a container that holds the position the jump left is not visited again unless it counts at its start only (`Story.ts:1888-1892`). The engine decides that from the root's sequence table and chunk table (section 1), which are the container table of this design: a sequence's row gives its owner and its flow's symbol, the chunk table gives the sequence that holds the owner, the owner's block row gives the scopes it opens around the block, and a branch's symbol names its scene as parent. On `JumpSym`, `JumpVar`, a call, a chosen choice and a loaded position, the engine reads the target's sequence, walks owners to the flow to rebuild the block stack and the scope depth of the frame, and compares the flow and its parent scene with those of the position it left; each one newly entered gets a visit. That is `VisitChangedContainersDueToDivert` with sequences in place of containers, and inkcpp's `jump` (`inkcpp/runner_impl.cpp`) with the root's owner rows in place of start and end offsets.

**Decision:** typed-array counts indexed by a dense id that every counted symbol receives, `Visit` markers for the start-only kinds, and the root's sequence and chunk tables for flows entered by a jump.

**Reason:** a checkpoint's counts are an array copy and its delta an array difference, in place of two maps keyed by path string that are the largest part of a save today; nothing about counting is a whole-program pass.

**Alternative:** a count flag in the symbol table maintained from references, which the filing of #696 proposed. It gives the same reads, needs a reference count per symbol kept by the incremental pass, and leaves a count at zero when a script starts reading a container that was visited before the read existed. inkcpp's start and end container markers with offset ranges were not taken, because containment here is structural.

## 6. How a beat ends

Every displayed line is a `display(...)` call whose builtin writes its table and then a newline (#685). A call whose `CallStd` carries the open flag writes its table and, in place of the newline, leaves a join pending on the output. The writer sets the flag on each call the lowering marks as open (#779): the call of a line that ends with a trailing `..`, the call before a mid-line divert, a chosen choice's arrow or an alternator arm's divert tail, and the caption of a `choose` block, which is the last display statement written in the block before its first choice. A continuation is a call after a call that wrote no newline, and it joins the same beat (#686).

A continue runs until the output ends in a newline outside a capture, or until the flow can no longer continue: a `Done` that stops the flow, an `End`, or the end of content. While a join is pending, no newline is written, whichever instruction writes it: the `Newline` a multi-line `if` branch opens with (as `ConditionalSingleBranch` inserts one today), the one a chosen choice's target opens with (section 4), and any other the flow meets before the next visible output. That output consumes the join and continues the line, and its own closing newline is written as usual. It is text that is not whitespace, or any display table except one whose `text` is a string that is empty or whitespace; a table with no `text` field, such as the table of a `load` line (`buildLoadCall`, `displayCall.ts:165-177`), consumes it too. Whitespace text, or a table whose `text` is an empty or whitespace string, leaves the join pending. This is the rule `PushToOutputStreamIndividual` applies today (`StoryState.ts:1130-1132`). So the step runs on through any logic between the open call and the next visible output, and the output cannot end in a newline in between. That is how a trailing `..` joins whatever the story displays next, through an `if` or a divert, and how a mid-line divert, a chosen choice's arrow and an alternator arm's divert tail join what they lead to. A `choose` block's caption runs on through the logic before the choices, the choices are raised, and the continue ends at the block's `Done`, so the caption and its choices return together; a line written before the block returns alone, and the next continue raises the choices with no text. A `Done` that only pops a forked thread is no end: the flow goes on. Every continue starts from an empty output, as `Story.ContinueInternal` resets it today (`Story.ts:1273`), so a join still pending when a continue returns, such as a caption's, joins nothing in the next one.

Every instruction runs once, in order. Logic after a line's newline runs when the next continue starts, which is when a game that reads variables between continues expects its assignments to land. A builtin whose effect leaves the engine, such as `log` writing to the host's console (`StdLib.ts:3171-3182`), runs once like every other instruction.

A continue that ends at a newline returns with the position just after the instruction that wrote it. A statement whose last instruction wrote it rests at offset 0 of the next chunk, which is the address a consumer sees for "after this beat".

`LineStart` names a beat's address (section 8); executing it does nothing. The writer puts one ahead of every display call that starts a beat, before the call's argument: every call but one whose table carries `continues`, which is what a line written with a leading `..` lowers to and which joins the beat before it. A statement that a `>` break splits into two beats holds a call for each, and each has its `LineStart`. Whether a line joins the one before it through a trailing `..` depends on how the flow got there, through an `if` or a divert, so the line after an open call carries a `LineStart` of its own, and a beat that such a join makes runs two.

Choice presentation needs from the engine what it has today: each choice's text and tags, its index, whether it is an invisible default, the address of its `Choice` instruction as its identity, its target, and the thread it was raised in. A choice's text is built in a capture and stays flat text; how choices are transported is outside #685.

**Decision:** a continue that returns when the output ends in a newline outside a capture or when the flow can no longer continue; an open flag on the display call, which leaves a join pending in place of its newline, so that no newline is written until the next visible output joins the beat; and a `LineStart` emitted by the writer as the address a beat is known by.

**Reason:** a join is a property of the call that writes the line and is known when the call runs, so the engine never looks past a newline to learn whether the line is over. A beat is stepped once and saves nothing at its end, so the route simulator, the game's record of what a run met and the host's console each see a step exactly once, when it runs.

**Alternative:** a save point over restorable state, opened at each newline and resolved by a following join, a line start or the end of content, which would let a line begin with `..`. It is cheap: on the preview fixture's 755-line route a save and a restore of the restorable state cost 0.8 microseconds against 3.2 for the snapshot and restore of the engine at e1def4bce (measured on 2026-09-22 with that revision's `node scripts/bench/engine-bench.mjs --fixture --mode kinds,step,lookahead`). But the logic between two lines still runs twice, every table write and closed upvalue needs an undo log, a builtin whose effect a restore cannot reach has to end the speculation before it runs, and the route simulator's cursors have to be saved and restored with it, all for a form few scripts use. Running the logic after a newline for good and stopping at the next line start, which saves the restore but not the stepping past the newline; the game reads variables between continues, so a binding would show an assignment one beat early. Resolving the leading form at compile time by deciding at each `if` branch whether the line before it stays open, which works for a static `if` and not for a continuation at the top of a diverted scene, so either the engine keeps speculating for that case or one spelling behaves two ways.

## 7. State

Engine state is of two kinds. Positional state is small at the end of a line and an image copies it whole. Keyed state is large and changes little, so an image holds what was written since the image before it.

| State | Held as | In an image |
| --- | --- | --- |
| Position, and the previous position: sequence, entry, offset | three numbers each | the two addresses, each with its entry as the place to look for the chunk first (section 1) |
| Call frames: kind, return address, eval height, output start, scopes of temporaries, open upvalues, block stack | an array per thread | addresses, each with its entry, and the temporaries; the block stack is rebuilt |
| Threads, and the thread each choice holds | arrays of frames | as frames |
| Eval stack, output, captures, choices | arrays | copied |
| Pending join (section 6) | a flag beside the output | copied |
| Turn index, seed, previous random, safe-exit flag | numbers | copied |
| Visits, turns | typed arrays | whole in a keyframe; the changed ids in a delta |
| Globals | `VariablesState`, unchanged | whole in a keyframe; the names assigned since in a delta |
| Tables: their entries, and what a table is beside them, which is its metatable, whether it is frozen, and the two length hints that decide what `#` answers | `ObjectValue`, unchanged | the entries, metatable, frozen flag and length hints of each table written since the previous image |
| Closed upvalue cells: the value of a captured variable that outlived its frame, which the closures sharing it write through | the cell on the `VariablePointerValue`, unchanged | the value of each cell written since the previous image |
| Errors and warnings the current continue has raised | two arrays | not held: they belong to the continue that raised them, which hands them to `onError` when it returns and clears them (`Story.ts:1367-1379`) |
| The route simulator's cursors, which say which forced verdict each decision site takes next | the simulator's own maps, outside the engine | not held: the planner builds a node's simulator from the node's decisions and hashes its cursors into the fork site beside the state, as it does today (`planRoute.ts:679`, `:760`, `:853`) |

### The write barrier

The barrier is what marks the keyed state written since the last image. A visit, whether a `Visit` or a flow entered by a jump or a call (section 5), marks its count id, and a global assignment marks the global's name. Every write to a table goes through one barrier on the table: `StoreIndex`, `__newindex`, each builtin that changes a table in place (`table.insert`, `table.remove`, `table.sort`, `rawset` and the rest), and the writes that change what a table is and not what it holds: `setmetatable`, `table.freeze` (`ObjectValue`'s `_metatable` and `_frozen`, `Value.ts:498-504`), and the capacity and boundary hints that `table.clear` and the `#` operator itself leave on the map (`StdLib.ts:4787-4792`, `NativeFunctionCall.ts:903-912`). The durable form already writes all four beside the entries, because a table loaded without them answers differently (`JsonSerialisation.ts:424-446`), and a delta that missed a write made by a builtin would restore the table without it.

A closed upvalue is the other value that is written in place on the heap. When the frame that owned a captured variable is gone, an assignment through the closure writes the cell on the pointer itself (`VariablesState.ts:509-511`), past the globals and past every table. That write goes through the same barrier, which marks the cell as written for the next image; the image holds the cell's value and restores it in place, so closures that share a cell still share it.

The barrier only marks; the way back to an earlier state is to restore an image.

### Images

An image serves a route search node and a checkpoint alike. A keyframe holds everything in the last column above. A delta holds the positional state, which is small, and for the keyed state only what changed since the image it follows: the count ids, the global names, the tables and the cells the barrier marked since the last capture. The first time a table is written after a reset, the barrier keeps a copy of its pristine content, metatable, frozen flag and length hints, so that restoring an image taken before that write can put them back.

Restoring an image restores in place: counts are copied into the live arrays, globals reset and reassigned, and each table that was ever written is cleared and refilled, and given its metatable, frozen flag and length hints, from the newest copy at or before the image, or from its pristine copy. Identity is kept, so nothing is relinked, and a table created after the image is simply unreachable.

A route search node holds an image in place of `stateJson` (`planRoute.ts:21`). The search is breadth-first, so its nodes are live together and their images form a tree: a fork's image is a delta on the image its run started from, siblings share it, and `claimForkSite` hashes its content. A node run restores the chain from the nearest keyframe, which costs the changes along that path and not the size of the state. Forks are rare beside steps (the route to `main.sd` line 3515 is about 30,000 engine steps and one `choose`), so a fork pays a positional copy and a short delta.

A checkpoint is the same image taken at each beat: a keyframe every `baseInterval` beats and deltas between, as `CheckpointStore` arranges them today, without the JSON text and without the string splice that exists to keep the path-keyed count maps out of it. A beat's image is taken when its newline is written, so it holds nothing the logic after that newline does, which runs when the next continue starts (section 6). A choice raised before that newline, by a thread that finished earlier in the same continue, is state of the image, with its thread. A continue that ends with choices raised writes no newline, so a menu, with a caption or without one, is kept as the image before it, and restoring that image runs the continue that shows the caption and raises the choices again, in a session and from a durable save alike (below). A load seeds the store with the beats the save holds, so a save taken after a load and before another beat holds the same history. A checkpoint taken after a choice was made (`chosePathToContinue`) is the beat's image with the chosen choice named. Within a session a checkpoint holds addresses and count ids as they are. They survive a compile for every statement that was not re-emitted. When a root arrives, the store translates the addresses of chunks the new root no longer holds while it still has the old root to ask (section 8). The store runs during play as well as under the preview, in its incremental mode (today's default makes every capture a keyframe, `Game.ts:451`): the game captures the initial image when it starts, a beat in `displayHeld` and a checkpoint after every choice (`Game.ts`), so at any moment it holds the beats a durable save writes (below) and a rewind would read.

### The save format

A save is JSON with a header that names the format's version and the engine's, and it owes no compatibility to the current engine's saves, of which none exist outside development. What it owes compatibility to is the program: a game is updated after its release, and a save has to load into the new program at the place the player left, or at a beat they passed, with the state the player had at that beat. That contract is what sections 7 and 8 serve, and it is Ren'Py's (see What is taken from Ren'Py).

A save holds the last `saveHistory` beats the player passed (16 by default, a `GameConfiguration` field), written as the oldest keyframe those beats need and every delta after it, so the loader can step back through them (section 8); just after a keyframe that means the keyframe before it as well, since the newest keyframe has few beats after it. That costs at most `baseInterval` plus `saveHistory` small deltas beside one keyframe, which is the size a save has in any case. Each beat is written with its positions in the durable form of section 8. Values go through the existing `JsonSerialisation` round trip, which keeps table identity with `objref` and relinks instances of a define, with two additions. That round trip writes a variable pointer as its name and context index alone (`JsonSerialisation.ts:463-468`), so a closed upvalue loads open and empty and a closure loses what it captured; the save format writes a closed cell once, with its value, under a reference that every closure sharing the cell names, as `objref` does for a table, so a loaded closure keeps its captured value and two closures that shared a cell share it again. And the round trip writes one state of the heap where a save holds several: the keyframe writes every reachable table and cell whole under an `objid`, and a delta writes each table or cell written since the image before it under the `objid` the keyframe or an earlier delta gave it, whole (the entries, metatable, frozen flag and length hints of a table, the value of a cell), with a table or cell created after the keyframe written whole under a new `objid` (one that had an `objid` at the keyframe and is first written after it keeps that `objid`, and every variable that referred to it still does). Restoring a beat loads the keyframe's tables and replays the deltas up to that beat onto them in place, so a table two variables refer to is one table at every beat and two closures that share a cell share it at every beat. Positions and counted symbols are written in the durable form (section 8): a frame's position as the chain of sequences that holds it, each with a window of its listing, and an anchor in its statement; a count under its symbol's qualified name or under its statement and part; a symbol value by its name or by its statement and part. A beat at which choices are waiting is written as the image of the beat before it, or the initial image when nothing was displayed yet, which holds the choices raised before that beat's newline with their threads (section 8) and none of the choices the continue after it raised: running that continue again raises the rest, from every thread that contributes one, and runs their conditions' effects once. A checkpoint taken after a choice was made adds the chosen choice, by its statement and part. The header names the format's version, the engine's, and the game's own version string (`GameConfiguration.version`, empty when the game sets none), which a load keeps for the after-load hook below. The loader takes a save of an older format through a migration per version and refuses a newer one, naming the version; a fixture save of each format version that shipped stays in the tests.

Two things a released game needs beside the format are author-facing and so belong to a Feature of their own: a hook run after a load with the version the game saved under, so that a script can migrate its variables, and a hook that names where to start when no beat of a save can be placed, which Ren'Py has as its `_after_load` label with the `_version` field of a save and as `config.load_failed_label`. Until it exists, a load that cannot be placed is refused and names the flow (section 8).

### Rewind and roll forward

A rewind of the kind Ren'Py gives players (`renpy/rollback.py`) is a Feature of its own, and what it needs is what a save already needs, so the state design carries it and the format owes it four things beyond what the sections above give.

A rewind restores an earlier beat's image in place (Images above) and resumes at its position; for the beat before a menu that raises the menu again. The image was taken at the beat's newline, so the beat's line, tags and display tables are in its output, and the game re-presents a rewound beat from the image without running it, as it re-presents a loaded save. Restoring one beat back costs the deltas from the nearest keyframe, which `baseInterval` bounds. The store keeps the last `rewindBeats` beats restorable during play (a `GameConfiguration` field, 128 by default, which is Ren'Py's `rollback_length`), of which a save writes the last `saveHistory`, so a loaded game rewinds through the beats its save holds.

Roll forward lets a player who rewound advance again through the decisions they made without making them again. It is a record beside each beat of what the player decided at it: the chosen choice, by the address of its `Choice` instruction, which is a choice's identity (section 4), and any other input the game fed the story at that beat, which the game records in its own terms. When the story reaches a beat whose position is the next record's, the game supplies the recorded decision instead of waiting; when it reaches any other position, or the player decides differently, the record is dropped. That is Ren'Py's forward log, keyed there by statement name and here by address, and in a save by the saved form, which the checkpoint after a choice already writes (The save format), so a loaded save rolls forward as far as its beats reach.

What the format owes, beyond images that restore in place (above) and decision identities that survive a compile (section 8):

- Every random draw reads the image. `math.random`, ink's `RANDOM` and `ShuffleIndex` draw from the story seed and the previous random (`StdLib.ts:2739`, `Story.ts:3345`, `:5162`), both positional state, so a rewound beat draws again what it drew. `table:random()` draws from `Math.random` (`MethodDispatch.ts:604`) and does not; under this design it takes the story's draw, as its own comment asks, and no builtin draws from anything an image does not hold.
- Three flags per beat, in the image and in the save: whether the beat waited for the player, because a rewind stops at beats that did and passes over beats that advanced on their own, as Ren'Py stops at hard checkpoints; a rewind floor, set by a beat so that no rewind passes it (`renpy.block_rollback`); and decisions fixed, which lets a player rewind past a decision but not change it (`renpy.fix_rollback`). The builtins that set the last two belong to the rewind Feature; the flags exist in the image so that a save keeps them.
- The record of decisions beside each beat, above, in the image and in the save.
- Nothing the logic after a beat's newline did is in the beat's image, because that logic runs when the next continue starts (section 6), so a rewind undoes it and a roll forward runs it again, once, as a load does.

Outside the format, the game re-presents a rewound beat from the module state its checkpoint holds beside the story (`Game.buildSave` writes every module's state; what a beat of the UI and audio modules keeps for a rewind is the rewind Feature's to settle), suppresses transitions while it rolls forward, as Ren'Py's abnormal mode does, and re-dispatches the inputs it recorded.

**Decision:** copied positional state, keyed state marked behind one write barrier, keyframe and delta images for route search nodes and checkpoints, each beat's image taken at its newline with the beat's flags and decisions beside it, and a save that holds the last beats the player passed as a keyframe and deltas, each beat's positions in the durable form.

**Reason:** a fork and a checkpoint each cost what changed, and neither allocates a copy of the whole state. A continue returns at its newline and takes nothing back (section 6), so an image is the only capture the engine makes. A save gains the beats to fall back through at the price of the deltas the store already holds, and an image taken at the newline is what a menu can be raised again from, because nothing the presentation did is in it.

**Alternative:** inkcpp's restorable stack (`inkcpp/collections/restorable.h`), which keeps a saved region in place with a jump pointer so that a save is free, was not taken because the positional arrays an image copies hold a handful of entries at the end of a line, and copying them is simpler than keeping a saved region in place. A version tree of undo and redo logs, which would make any two states reachable from each other, was not chosen because a restore in place from the nearest keyframe is simpler and a fork is rare. Copy-on-write tables behind a handle were not chosen because the value model stays as it is.

## 8. Addresses

Outside the engine a position is a source location. The root offers two lookups, and one accessor answers from either engine until the current one is deleted:

- `addressAt(uri, line)` returns the address of the beat or statement on that line, or nothing. It takes the flows of the script the uri names, which the root keeps in line order with the script's declaration sequence (section 1), finds the one whose line range holds the line, then descends: a binary search of the sequence's line starts gives the statement, and when the line falls inside one of that statement's bodies (each body's first line and span follow from the owner's block rows and the root's rows, section 1) it goes on into that body's sequence, and otherwise reads the chunk's line table. A beat's address is the offset of its `LineStart`, so the cue line, the directive and the dialogue text of one beat return one address, and the lines of two beats return two.
- `locationOf(address)` returns the script and range of the line table row that covers the offset: the row's anchor resolved, the statement's line start in its sequence added, and then, for each owner up to the flow, where that body starts in its owner and the owner's own line start. The flow's row gives the script and the flow's first line in it, so two scripts that both have a statement on line 10 give two addresses, and each address gives its own script back.

A chunk's line table is relative to its statement's first line or to the end of one of its own bodies, a sequence's line starts are relative to its body's first line, and where a body starts follows from its owner. So an edit shifts no stored line in any chunk and no line start of a body beside or below it. It builds the line starts of the sequence it edited, shifts the tail of the line starts of each sequence that encloses it, lengthens the spans of those sequences in the root, and moves the first line of each later flow in the script, which the root holds per flow.

An address survives a compile for every statement that was not re-emitted. A route step's identity is the address of its position, folded as `extendSeq` folds path strings today, and a reused route step is one whose chunk is still in the root.

An address is a number (`ProgramAddress`), never a string: the deleted object engine named a position by its runtime path, and since #1709 no reader keeps a branch for one. A line that has no address, and no line below it that has one (front matter, a `define` block, the gap after the last scene), starts a run at the top of the top-level content, and `Game.setStartFrom` gives it the address `TOP_LEVEL_START`, -1. No chunk has a negative id, so `locationOf` and `sceneAt` find nothing for it, a route search to it never arrives and the failed search is reported as `unroutable`, and jumping to it (`StoryPositions.jumpTo`) starts the top-level flow, `"0"`. It was the string `"0"` while an address could be a string, and every reader of the start address keeps the meaning it had: a number keeps the start point a value the worker can send and compare by `===` like any other address, where a separate result type would have changed what every reader of the start address does with a line that has none. A flow is still named by its qualified name, a string, where a route starts (`Route.from`, `Game.jumpToFlow`) and where a scene is reported (`sceneAt`'s `"0"` for the top level); that name is not an address.

### The saved form

An address that outlives a session, or a chunk, is written as a place in the source, because the code of a statement changes whenever the statement or the compiler does and a save should notice neither. An offset appears in it in one case only, beside the layout hash that says whether it still means anything. The written form has three parts.

The chain: the sequence that holds the position and each sequence that holds that one, up to the flow, one level per sequence. A level is written as a window of the sequence's listing, the fingerprints of its entries in order from a first ordinal the window names, and the ordinal of the entry the position is in. A window covers the whole sequence up to 512 entries and otherwise 256 entries on each side of the position; the windows that the frames and beats of one save cut from one sequence are merged where they overlap and written once each, so every position keeps its own neighbours whatever else the save names in that sequence. The flow's level carries the flow's qualified name. A body's level carries the owner's part listing, the fingerprints of the owner's own parts in order (its branches' conditions and `else`, its choices' lines, its `then` label), the ordinal of the part that heads the body, which is what the three passes of section 2 need to place the body when parts were written, edited, reordered or removed beside it, and the owner's layout hash when the owner is a loop, whose hidden temporaries the frame holds. A frame also carries the layout hash of the chunk that bound its parameters: the first chunk of a function or tunnel declared at the top level, the owner statement's chunk for a function written inside a statement, and nothing for a scene or a branch. Every saved form, of a frame, of a choice, of a count or of a symbol value, cuts its own windows. The largest scene of the Raffles and Bunny project costs a save a few kilobytes of listings.

The statement: its fingerprint and its layout hash (section 1).

The anchor: where in the statement the position is. It is one of five. The statement's start. The end of the sequence, written as an ordinal equal to the number of entries, for a flow that has run out and for a body whose owner is about to resume. After the body headed by a part, or at that body's break, the part named by its fingerprint and its ordinal in the owner's part listing, for a position the owner resumes at when a body ends. The entry of the choice headed by a part, named the same way, for the thread a choice holds. Or inside the statement's code, written as the offset, for a frame whose return site is inside an expression, for a thread whose fork is still running (the original resumes at its `Thread`'s offset) and for anything else that is neither a statement boundary nor a body's end. The loader turns the first four back into offsets from the chunk the program has now (the entry code, the sequence's end, the matched part's block row or entry code), and takes the fifth as it is when the layout hash of the chunk the program has now equals the saved one, which says that the code, and so the offset, the temporaries and the eval stack the frame holds, are what they were; otherwise the frame is placed after its statement (step 5 below).

A choice raised before the beat's newline is written: its text, tags and flags as captured, its `Choice` instruction's statement in the saved form with the fingerprint and ordinal of its part, and its thread's frames, the top one anchored at the entry of that part. A choice raised after the newline, by the continue that follows, is in no beat's image and is not written. A beat at which choices are waiting is therefore written as the image of the beat before it, or the initial image (section 7), and loading it and continuing raises the choices the new program has that the image does not hold, from every thread that contributes one, from a state that predates their conditions' effects, so those run once; that is how Ren'Py resumes at the start of a `menu`, with the choices a thread raised before the line kept as they were. A choice the image holds whose part cannot be placed is dropped with a warning, which makes the beat a placement with a warning (step 6). A checkpoint taken after a choice was made is the same with the chosen choice added, named by its `Choice` instruction's statement in the saved form and by the fingerprint and ordinal of its part; loading runs the continue again and chooses the part that section 2's alignment matches among the choices then waiting, and is unplaced when none is or when the continue no longer raises it.

An anonymous symbol is written as the saved form of its statement with, in place of the anchor, the fingerprint of the part it belongs to and that part's ordinal among the statement's parts, beside the statement's part listing; the loader aligns the saved parts with the statement's parts as a re-emit does (section 2), so a choice's count goes to the choice with that fingerprint, the nearest ordinal first, and a part it cannot place starts fresh. A count under a qualified name loads under that name, after the names a placed flow renames (the renaming after the steps below) are rewritten.

Loading places each position of a beat, then chooses the beat:

1. The flow, by its qualified name, when the program has one.
2. Each level, by the matching blocks of the saved window and the sequence the program has now, in order, as Ren'Py aligns the statements of an old and a new script (`renpy/script.py`, `merge_names`); a statement inside a matching block is placed exactly. A body's level is placed by aligning the owner's saved part listing with the owner's parts in the three passes of section 2 (matching blocks, then equal parts wherever they stand, then the parts left between matches paired in order, which is what places a body whose choice was edited or moved) and taking the body of the matched part.
3. A statement that no block matched is looked for by itself, in every sequence of the program, its own first: the run of fingerprints around the position in its window, eight on each side, is matched against each sequence, and the statement is placed exactly where the longest run that covers it and at least two of its neighbours (or the whole window when the window is shorter) stands, when that run is longer than every other such run in every sequence, its own included; the chain above a placement in another sequence is then the one the root holds for that sequence, and the saved levels above are not used. That is how a save inside a renamed scene, one inside a body moved under another owner, one inside a block of statements moved to another flow, and one inside a run moved within its flow load, with a replacement in the vacated place or without. Two runs of the same length, in one sequence or in two, are a tie, and a tie leaves the statement to step 4.
4. A statement neither matched nor found is paired by its neighbours: in each run of entries left between two matched blocks of its own sequence, or between a block and either end, the old are paired with the new in order, and the statement is placed at the entry paired with it, at its start, as an edited statement. That is how a statement edited in place is found. A statement left without a pair, and a body whose heading part has none, leave the position unplaced.
5. The anchor, from the placed statement's chunk, as above, and the layout. A frame is compatible with the program when the chunk of each owner on its block stack that declares temporaries it holds (a loop) has the layout hash the save carries for it, an owner that the placement introduced and the save carries no hash for counting as differing, and when the chunk that bound the frame's parameters has the hash the save carries; an inside anchor is compatible when the statement's does. Otherwise the frame is placed after the innermost construct whose layout differs, or dropped: a frame whose position was inside a statement's code under a differing layout is placed after that statement, a body position under a loop whose layout differs after that loop, and a frame whose parameter-binding chunk differs is dropped, with the frame below it placed after the statement that called it. A placement after a statement runs the callee frames above it, if any, to their return and drops the value they return; the frame resumes at the next entry of its sequence, or at the owner's resume offset when the statement was the last of its body, with its eval stack cut to the height at which the frame itself was pushed, which is its height at any statement boundary of that frame (section 1), its open captures dropped, its scopes cut to the depth the position has, which is the block stack's sum plus the chunk's own count at the offset, at a resume offset the row's scope count, so that a loop's hidden and per-pass scopes stay open until the owner closes them (section 1), with the upvalues bound in the dropped scopes closed as `EndScope` closes them, and a warning that names the statement. That is Ren'Py's rule for a return site that is gone (`renpy/execution.py`, the return stack in `run`), which sends the return to the statement after the caller. A body under an `if` or a `choose` needs no layout check, because those owners declare nothing the frame holds, and a closure's frame is checked against the owners on its own block stack, which begin at its function-body block, and not against the lexical owners of the statement that wrote it. A placement after a statement, and a beat with a choice dropped, is a placement with a warning, not an exact one.
6. The beat. A beat is placed when every frame of every thread of its position is, exactly or with a warning. The loader takes the newest beat whose frames are all placed exactly, and when there is none the newest beat that is placed at all; it restores that beat's image (section 7) and resumes at its position, which for the beat before a menu means running the continue that raises the menu. A placed beat older than the newest carries its own variable values, counts and tables, so nothing runs in a state it did not run in. This is Ren'Py's load (`renpy/rollback.py`, `rollback_core`), which pops its log until it reaches a statement the script still has.
7. No beat is placed: the load is refused and names the flow of the newest beat. The engine does not guess a position it cannot name, which is inkcpp's rule as well (`inkcpp/story_impl.cpp`, `new_runner_from_snapshot`).

A flow placed by step 3 under a qualified name that differs from the saved one renames what the save says about it. The differing leading segments of the two names give a mapping from the old prefix to the new, which is a scene renamed together with every branch, label and function under it; the mapping is applied to every count key, symbol value and anonymous-symbol form of the save that carries the old prefix, so the counts and the values that drove the scene and its branches before the rename drive them after. It is applied only when the old prefix names nothing in the program and the new one exists: a branch moved under a scene that still exists rewrites its own name and nothing else. A label that was itself renamed keeps nothing, because its statement's fingerprint changed with its name, and the count under its old name is dropped.

What no saved form tells apart is a run of identical statements, and Ren'Py's cannot either: the alignment keeps order, so a save taken at the second of two identical lines, loaded after a third identical line was written between them, resumes a line early, and one taken at the second of three, loaded after the first was deleted, resumes a line late. What a player can see is one identical line more or fewer, and a statement with an effect runs once more or once less. Telling such statements apart needs an identity kept in the source, and the design keeps none. Three more limits are of the same kind. One compile that both inserts a statement and edits the one beside it pairs the two the wrong way round in step 4, as section 2 says of parts, and the save resumes a statement early or late. A run of fewer than three statements moved away from its neighbours is not found by step 3, and a save inside it falls back to an earlier beat. And a flow whose statements were deleted while another flow holds three identical statements in a row places a save in that flow, with the save's state. A statement split in two, or merged with its neighbour, is an edited statement to step 4: the save is placed at whichever new statement is paired with it, at its start. Within a session none of this arises, because a position whose chunk the new root still holds is not translated at all.

Within a session, when a root arrives, a checkpoint's address whose chunk the new root does not hold is translated once: the old root gives its saved form, windows and part listings included, and the new root places it by the same steps.

**Decision:** an opaque address of chunk id and offset for the running program, two lookups on the root in place of the path-location table, and a saved form of listing windows, part listings, fingerprints of the source, the layout hashes of the statement, the loops and the function a frame is in, and anchors in the statement's structure, with an offset only where the statement's layout hash validates it, which the loader matches by blocks, then by the statement's own neighbourhood in every sequence, then by its neighbours in its own, checks for layout and falls back through the beats the save holds.

**Reason:** consumers asked a path for two things, where a line runs and whether two lines run at the same place, and an address answers both without a table of every location in the program (2,083 KB of a 4,316 KB program today) or the two compile phases that build it; a saved form that names the source and carries its own history loads into a program that was edited, renamed or compiled by a later compiler at the place the player left, or at a beat they passed with the state of that beat.

**Alternative:** path strings kept at the boundary; a record index, which shifts on every edit; a statement ordinal alone as the saved form, which an insertion above shifts; the statement's fingerprint paired with its predecessor's, searched for near the ordinal with the ordinal itself as the fallback, which finds nothing once the statement or its neighbour was edited and then resumes at whatever stands at the ordinal, with the save's later state; an instruction offset as the anchor of a menu, which an edit to a choice's text or a compiler release invalidates at the place a player saves most; anchors that count a statement's calls or bodies by ordinal, which a compiler release that adds a call, or an author who adds a choice above, moves to another instruction; running a menu's statement again from the state it left, which repeats the effects of its conditions' calls and cannot rebuild a menu that threads contributed; a block statement's fingerprint as its kind alone, which is Ren'Py's rule for `if` and `menu` and works there because a whole file is aligned flat, children included, but maps a menu to its neighbour when owners are aligned in a sequence of their own; a listing written once per sequence and cut around one position, which loses the neighbours of another position in the same sequence; a fingerprint of the emitted code as the identity, which every compiler release changes; a durable id per statement kept in a file beside the script and carried across edits by the compiler, which is Ren'Py's `.rpyc` name (see What is taken from Ren'Py) and needs an artifact shipped with the game and kept through every build, where the listing in the save needs nothing kept and loads across builds that never saw each other.

## 9. The surfaces

### No configuration

No configuration names an engine. Every compile fills the chunk store and `program.chunks` refers to the root, and every host runs it on `ProgramStory`. The fields that chose between engines while both existed (`SparkdownCompilerConfig.programChunks` and `emitCompiledProgram`, `GameConfiguration.programChunks`, #314's `binaryProgram`) are gone, with the compiled story (`program.compiled`), its binary form (`compiledBuffer`) and the path-location table (`program.pathLocations`), #705.

### A construct the writer cannot emit

The writer emits what it can. The first parsed object it has no emit path for, at any depth, is a compile error at the line of the statement that holds it (`unsupportedConstructMessage`: an `external` function, the `LIST` type, or "This statement cannot be compiled: " and the construct's name, the parsed class's `typeName` or the builtin's or command's name), and the compile makes no program: `program.chunks` is absent and the game keeps the program it had. The error is reported after the compile's validators, and not over a line they reported an error at, or for a construct they reported in the same words (a stray choice mark), since that error is the reason. `preview-bench.mjs --mode coverage` reports the statements emitted and every statement the writer has no emit path for, counted by construct.

## 10. Function values

A function value is a symbol value: the class that replaces `DivertTargetValue` (`packages/sparkdown/src/runtime/Value.ts:373`) holds a symbol id, the table generation and, when the symbol has one, the qualified name, in place of a `Path`. It is what `Sym` pushes, what a scene or label held in a variable is, what `CountOf` and `TunnelReturn` pop, and what `GetVar` produces for a flow's name. Truthiness, equality and printing follow the name, as they follow the path today.

A closure stays the table it is (`__closure_fn`, `__closure_upvals`, `__closure_user_arity`), with a symbol value in `__closure_fn`. Its code is a function-body block of the statement that wrote it, exported under an anonymous symbol that belongs to the function as a part of that statement (section 2), so an edit elsewhere renames no function, a function written above it in the same statement takes nothing from it, and a preview rewrites none. A call resolves the symbol in the root the engine holds. A closure made before an edit to its own statement runs the statement's new code the next time it is called, which is what hot reload means for every other statement.

Upvalues are as they are: a `VariablePointerValue` names a variable and a frame, open upvalues are registered on their frame, and the three closing points (a frame pop, `EndScope`, a `local` declared again in the same scope) stay in `CallStack`. What changes is around them, in section 7: a write to a closed cell goes through the write barrier, and the save format writes closed cells. A call frame addresses code by address: the return position is a chunk id and an offset, beside the frame's kind, eval height, output start, scopes and block stack.

Temporaries stay maps keyed by name in each frame's scopes, as `CallStack.Element.temporaryScopes` holds them. An instruction carries the name's string id, which the table turns into the string without allocating. The hidden temporaries a loop declares are named by the writer from nothing outside the statement: `__forIdx`, `__forStop` and `__forStep` for a numeric `for`, and the iterator, state and control of a generic `for`, each in the scope the loop opens for them, so that an inner loop shadows an outer one's and reads its own. The lowerer's names carry the loop's source offset (`lowerLuauForLoop.ts:33-46`, `lowerLuauGenericForLoop.ts:164-167`), which would make a frame saved inside a loop's pass unreadable by the same loop moved one line down. A function's entry declares temporaries too: its parameters and, for a variadic function, the hidden local `__varargs__` that argument lowering binds and `...` reads (`lowerArguments.ts:15`, `:37`, `lowerExpression.ts:852`). A frame's temporaries are read by a chunk's code only while that chunk's layout is the one they were made on, which section 8's layout check enforces for a frame inside a statement's code, for a pass of a loop and for the function a frame runs in.

In a save a symbol value is its qualified name, or the saved form of its position when anonymous (section 8), and a frame's return position is the anchor of its call in the calling statement.

**Decision:** a symbol value in place of the path, closures and upvalues as they are but for the write barrier on a closed cell and its place in a save, frames that return to addresses, temporaries by name.

**Reason:** everything that held a `Path` needed only to name code, and a symbol does that across compiles.

**Alternative:** a direct reference from the value to its chunk, which would keep a deleted statement's code alive and running; numbered slots for temporaries, which would rewrite how the lowerers resolve names, against a route on which variable work is a handful of steps in 30,000 (#664).

## A statement inserted in the middle of a long `then` clause

`ACT_TWO` ends in a `choose` at line 2449 whose `then` clause runs to line 3556 and holds about 430 statements. The author inserts a two-line action statement at line 3000, which falls between entries 210 and 211 of the clause's sequence.

| What | Changes |
| --- | --- |
| Program chunks | One is emitted, for the new statement, with a new id. No existing chunk is re-emitted or rewritten: not the statements around it, which hold no position; not the `choose` chunk, whose code says `EnterBlock 2` and whose block table names the clause by an id that does not change; not any chunk that jumps to a label below line 3000, which holds the label's symbol |
| Sequences | The clause's sequence keeps its id and gets new arrays: a copy of the two with the new chunk at entry 211 and the line starts of entries 212 onwards raised by 2. The rows of the `if` blocks inside the clause are shared too, below the insertion as well as above it, because a body's lines are counted from its own first line. Such a row names its owner by chunk id; the new root's chunk table says the clause holds that owner, and its sequence table gives the clause the new arrays, so a story resumed inside one of those blocks runs on into the clause as edited |
| Root | A new root: the clause's row of the sequence table holds the new arrays and a span two lines longer, the row of `ACT_TWO`'s own sequence a span two lines longer, the chunk table has a row for the new chunk, and the first lines of the flows after `ACT_TWO` in `main.sd` are raised by 2. The `choose` chunk's block row still names the clause by the same id |
| Symbols | None is defined or removed. The definition rows of labels in the clause below the insertion have their entry raised by 1 in the new root. Their ids, and every chunk that refers to them, are unchanged |
| Line tables | None. A chunk's rows are relative to its own statement's first line or to the end of one of its own bodies, and the `choose` chunk has no part below the clause but its `end`, which has no code |
| Addresses | Every address stays valid, because no chunk changed. A checkpoint taken at a beat below line 3000 loads into the new root as it is |
| A durable save taken below line 3000 | Its ordinal in the clause is now one short. The loader aligns the saved listing of the clause with the clause as edited, which matches every entry but the new one, carries the ordinal across and resumes at the same statement (section 8, step 2) |
| The route | The change summary is derived from the compile: one emitted chunk, no dropped chunk, no symbol whose definition row moved, no declaration or function chunk among them. Every route step whose chunk is still in the root and that precedes the new statement in the route is reused, and the replay resumes from the last checkpoint taken before that point. Had a declaration or function chunk been re-emitted, no checkpoint would be reused, because the state a checkpoint holds was computed by the old initializers, and the route would replay from the top |
| Passes | The reference pass visits the one new chunk. No symbol's definedness changed, so it visits no other |

#694's criterion, and the one #692 sets for a statement inside a `then` clause, assert this by a counter of emitted chunks and by the identity of every other chunk.

The prototype runs the example on the generated scene before it times anything (`editProbe` in `scripts/bench/chunkStepBench.ts`). It inserts a display statement into the scene's `then` clause just below an `if` whose body runs and another just above it, each into a new root built as above. It then fails the run unless the new root shares every chunk and every chunks array but the clause's with the previous root, the previous root is as it was, the new root's run is the previous run with the two lines added, and a story resumed from inside the `if` through the new root runs the same lines to the end as the full run does, the line inserted below the `if` among them. Resuming through the previous root, which is what an owner link held in the body's own arrays would amount to, fails it.

The probe checks the lines as well. The compiled JSON tree carries no source lines, so the prototype lays its program out on synthetic ones (a line for a plain statement and for each of a block statement's own parts) and holds them as section 1 says: line starts from the body's first line, a span per body in the root, the lines of the owner's parts in its block rows. After each insertion every statement must start as many lines further down as inserted statements now stand above it, only the edited sequence and the sequences that enclose it with a statement below the owner may have new line starts, and every sequence's lines must equal a layout made again from nothing but the chunks. A third insertion goes into the first branch of an `if` that has an `else`: the `else` branch keeps its row and both its arrays, and its statements still move down a line. The clause stands in the last scene, so a fourth insertion goes into the first scene, where it has flows below it: each later scene must start a line further down, in a new row that holds the arrays it had. Leaving the edited body's span as it was fails the run, and so does leaving the later flows where they were.

## What is built

A program's display beats (#694), everything its statements compute with (#695), which is expressions, interpolation, tables, variables, the declarations, `if` blocks, `match` and the four loops, its functions (#698), which is named and anonymous functions, closures and their upvalues, calls of every callable, returns and multiple returns, variadics, method and builtin dispatch, `define` tables and the calls the game makes into the story, its flow (#696), which is scenes and branches, labels, diverts with fixed and variable targets, tunnels and their onward returns, threads, visit and turn counts and alternators of every kind, the parameters of scenes and branches and the arguments diverts, tunnels, threads and onward returns pass them (#1436), and its `choose` blocks (#697), which is their choices, conditional, once-only, sticky and fallback, the choices an `if` of a block's preamble gates, those a `do` block or a loop of the preamble raises (#1503) and those a thread raises, the bodies of choices and the `then` clause, and taking a choice, run from statement chunks, and a program that holds anything else is a compile error at the statement that holds it (section 9). The code is under `packages/sparkdown/src/program/`.

### Flows and statements

A flow is the top-level content of the script the compile starts from, named by the empty string, or a scene or a branch, named by its qualified name (`programFlows.ts`). Each flow is one sequence. Its line starts count from the line after the flow's header, and its span runs to the next header in its script or to the script's end. A statement is a block the compilation annotator lowered, with the parsed objects the assembled story placed for it. The compiler ends a flow that does not end itself with a `-> DONE`, and ends the top level with a gather and a `done`; a sequence that runs out ends its flow as those do, so they are left out. An object no statement placed is a compile error naming the object's `typeName` (section 9), and so is a statement listed among another script's, which the story's layout below never makes, naming `a statement of another script`. A scene whose content starts with a branch that takes no parameters, which the current engine's knot enters by a divert to its first stitch (`FlowBase.GenerateRuntimeObject`), has an empty sequence when it takes none itself, and its row in the root's definition arrays names that branch (`ProgramRoot.startOf`): a jump to the scene, a tunnel to it, `ChoosePathString` and `EvaluateFunction` enter the branch, from the scene.

The top-level content of an included script, the lines other than declarations written at the top of a script that `include` pulls in, is a flow of its own in that script (#1681), of the top-level kind, named `$include:` and the script's uri with each `.` written `%2E` (`includedFlowName`), which no name an author writes can be and whose qualified name has one segment. The story places each included script's content, followed by a newline, where the script is included, and a script's own includes before its own content, all of it before the content of the script the compile starts from (`Story.PreProcessTopLevelObjects`), so the content runs first, deepest first, in include order. The top-level flow of each script, the starting script's and an included one's, starts with one statement per script it includes whose top level runs anything, or includes a script that does, in include order (`IncludeEntry`): a `JumpSym` to the content's flow, then the `Visit` of a label of its own, which its chunk exports (`$include:...$end`); the content's flow ends with a statement (`IncludeExit`) that writes the newline and jumps to that label. So a script's includes are statements of its own flow, as its other top-level lines are. The current engine runs the content in place, in the top level's frame, and so do the jumps, which push no frame: a local the content declares is the top level's, a `done` in it ends the story, a tunnel or a thread returns into it, and a jump to a label of the content runs the rest of it and goes on after it. The current engine ends the story where the content of an included script that holds a label ends, and runs nothing of the including script's content after it; the program engine does not copy that. A script whose top level holds declarations alone, and includes no script that runs anything, has no flow and no entry, so a program whose included scripts only declare and define scenes builds the root it built before. A `run` statement is an include of the same kind: its Luau file is a script whose top level is the call of the function that wraps its text (`runWrapper.ts`), which the top level runs where the statement stands.

An entry stands on the line of its `include` or `run` statement, which the compiler records for each included script's top level (`SparkdownCompiler.recordIncludedAt`, `ProgramFlowsInput.includedAt`), and no lower than the statement after it, since the story runs the content before any content written above the include; the exit stands on the line after the content's last, which no line of the content maps to, as a flow's entry stands on the line before its body. Neither has line rows, so `addressAt` of an `include` line gives the first line below it that has one, and `locationOf` of an entry gives the line it stands on: its `include` line, or, for an include written below content of the script's own, the line of the first statement after the entries. The entries of includes written below content of the script's own all stand on that content's line, so the lines of an edit that reorders them, which the compile's changed blocks name, do not say which entries moved (`ChunkStore.reuseOf`); an entry is therefore carried only while the compiled block of its `include` or `run` statement is (its key belongs to that block, `includeEntry`), as a statement of any block is, so the entries of the statements an edit lowers anew are ones the window over the flow's entries holds, and the alignment gives each its chunk again by its syntax. A key the entry had under an earlier block is never one it has again, so an edit undone does not carry an entry back to a place it no longer stands. Every other statement of the content has the line table of any statement, relative to its first line in its own script, and its flow's row names that script and its first line, 0, so `addressAt` and `locationOf` read an included script's lines through the root's flows of that script, as for a scene written there. `ProgramRoot.sceneOf` names the top level (`"0"`) for an address in such a flow, since the top level is what runs it, so a route to a line of the content starts at the top. For the same reason the scene assets read the content where its entry jumps to it, under the top level (`captureProgramAssets`), so `program.sceneAssets["0"]` holds its beats in the order they run and a preview hint at one of its lines finds its own beat, and the debugger names its frame `0` (`ProgramStory.flowName`), so a data breakpoint set on a temporary inside the content holds after the jump back. A statement's compile record belongs to its own script's uri, and the store keys it as any other: its chunk by its compiled block, its sequence by its flow's name, which its script's uri gives, and the incremental window over its flow's entries by the changed blocks of its own script (`ProgramSource.changed`, `ChunkStore.reuseOf`). So an edit inside an included script re-emits the statements the incremental parse lowered anew and keeps every other chunk, and an entry or an exit, which holds no parsed object the statement watch reads, keeps its chunk by a key of its own (`programFlows.ts`): an exit's is its syntax, the flow it ends and the newlines it writes, in a map the compiler owns (`ProgramFlowsInput.includeKeys`), so the keys live as long as the compiler does, and an entry's is its syntax, the flow it runs, under the compiled block of its `include` or `run` statement, which the compiler records with the line (`recordIncludedAt`). A save names a position in the content by its flow's qualified name, as it names a position in a scene (section 8), and loads after an edit as one in a scene does.

A scene or a branch that takes parameters starts its sequence with a statement of its own that binds them (`FlowEntry`, `programFlows.ts`, #1436): a `SetVar` with the declare flag per parameter, last first as a divert pushed the arguments, the `...` with the varargs flag, as the current engine's flow container starts (`GenerateArgumentVariableAssignments`), and for a scene that starts with a branch that takes none, the `JumpSym` to that branch the current engine's knot makes after it binds, so such a scene has no row naming the branch. The entry stands on the flow's header line, a line start of -1, which no line of the body maps to, and has no line rows. A jump, a tunnel or a thread to the flow runs it, since the flow's symbol is defined at entry 0; a jump to a label of the flow lands at the label's own chunk and binds nothing, and the parameters hold what the frame last bound to them, as on the current engine. A host enters such a scene as the current engine's does: `ChoosePathString` pushes its arguments as they are for the entry to bind, and `EvaluateFunction` arranges them for what the entry binds (`ProgramStory.sceneTargetOf`), as `ContainerTarget` reads the knot's assignments. The entry records no resolution, since it holds no parsed object the store could read one from again; its syntax names the branch it jumps to. Its syntax is the flow's qualified name, its parameter list and the branch it goes on to, which is all its code depends on, so an edit to the header's parameters emits it again and an edit elsewhere in the flow leaves it.

A divert that passes arguments pushes them before its jump, its tunnel's `Call` or its thread's `Thread`, as the current engine pushes them before `StartThread`, and an onward return pushes them before the target and `TunnelReturn`, which leaves them for the flow it goes on to (`Divert.EmitArguments`). For a fixed target the divert reads the target's parameters from the symbol table (`FACT_PARAMS`, which the store's definition of a scene or a branch holds as a function's does), and pushes a `VarPtr` for a by-reference parameter, and for a variadic flow nil for each fixed parameter it does not reach and a `Pack` of the rest; the jump carries `JUMP_ARGUMENTS`. Its resolution names the parameters (`programJumpKey`) as a call's does (`callResolutionKey`). A variable target's flow is known only when the divert runs, so its arguments go as they are, as on the current engine. A divert that passes none reads no fact, so that its chunk stays while its target disappears and comes back; the current engine still pushes a `PackTuple(0)` for such a divert to a variadic flow, so the engine gives a variadic scene or branch that a `JumpSym` or a tunnel's `Call` without `JUMP_ARGUMENTS` enters at its start nil for each fixed parameter and an empty `...`, reading what its entry binds from the `SetVar`s it starts with (`ProgramStory.padVariadicFlow`). An onward return that passes none pushes nothing, as on the current engine. No syntax declares a by-reference parameter yet (`lowerArguments` makes each a value), so that path runs only where a definition says so. A divert whose generation never ran, such as the proxy divert of a builtin call that reported its arguments (`READ_COUNT(-> a > b)`), resolves nothing and lets the story's resolution go on (`Divert.ResolveReferences`). Before #1436 it threw, and `ExportRuntime` caught the throw and stopped resolving, so a cold compile read the names after it as unresolved while an incremental compile kept the resolutions of the statements it carried. The flow screenplay's randomized edits found this.

A block statement (an `if`, a loop, a `do` block) is one statement, and each of its bodies is a sequence of its own. `lowerStatements` records, as it lowers them, the statements of each body with the lowering inputs each one read, and the lines where each body starts and where the owner's next part starts (`StatementShape`, `compiler/lower/utils/statementShape.ts`). A statement of a body is a statement of the body's sequence with a chunk of its own, and the parsed objects its lowering made stand among the owner's, where the writer finds them and emits `EnterBlock` in their place. The root's rows give each body's first line and the lines it spans.

A function declared at the top level is a flow of its own, of the function kind, whose one statement is its definition. The definition's chunk exports the function's symbol at its entry, which binds the parameters, last first as the arguments were pushed, declares the locals the lowering hoisted to the top of the body for the functions the body declares without `local`, and enters the body, a block with the function flag whose natural end returns nothing. A function written at the top level inside a `do` block is one too: the story takes it out of the block as a flow of its own (`FlowBase.SplitWeaveAndSubFlowContent`), so its definition is the statement of the block's body that writes it, and the block's body holds nothing of it (`bodyStatements`). A function the story leaves in any other block (an `if` branch, a loop's body, a `do` block inside a scene) is no function of the story, and the current engine runs its container where it stands: the writer emits it there (`emitFunctionInPlace`), binding its parameters from the evaluation stack and running its body as a block of the statement, and its name defines nothing. A function a statement creates as a value (a closure, a `define`'s method, a comparator) is a function-body block of that statement's chunk under an anonymous symbol the statement owns (section 10), and so is one a function's body declares. A UI binding's evaluator, which the lowering hoists to the story's top level under a name of its own, is a flow of its own, whose definition is the binding's source (`FunctionShape.named`).

A `choose` block is one statement too (#697), laid out as section 4 lays it out: what it writes before its first choice (its caption and preamble) and each choice's text and condition and `Choice`, in order, then `Done` with the hold flag and a `Jump` to its end, then each choice's entry, which opens with the `Visit` of the choice's count symbol, writes the chosen line, enters the choice's body, closes the scopes of the branches around the choice and jumps to where it continues, then the `then` clauses of the blocks written in the preamble, and at the end the `Visit` that the `then` clause's label exports, when it has one, and the clause's body. The lowering records, as it lowers them, each choice's body (the lines after the choice up to the next choice, the `then` clause or the block's `end`) and the clause's body as bodies of the block (`choiceBodyOf`, `partOfBody`), and each choice's own source (`alternatorSourceOf`). An `if` written before a block's first choice that offers choices gates them: its branches are the block's own code, a jump around each choice's code, and not blocks (`inlineChoiceBranches`); the lines after a choice in its branch up to the next choice, which the current engine's weave nests in the choice, are that choice's body, a block as any other choice's is, and the lowering lowers them outside the preamble (`lowerStatements` clears the context's preamble flag after a choice of the block it lowers, #1622), so a `choose` block written there is a block of its own (`Weave.isChooseBlock`). What the branch closes after the choice (its scope) closes where the branch ends; the choice's entry runs at the depth the choice was raised at, which its body's block row records, and closes the branch's scopes after the body (section 4, #1575). The body of a `do` block or a loop of the preamble that offers choices is the block's own code the same way, and not a block (`inlinedBodies`, #1503): the `do` block's objects are written between its scope markers, and the loop's chunk code with its body in place of its `EnterBlock` (`emitLoopBody`), so a loop raises a choice on every pass from one `Choice`. So is such a block nested in another block of the preamble at any depth, an `if` branch or a loop's body around a `do` among them (#1681): a block statement's objects hold its bodies' objects, and only a choice that is no object of its bodies makes a statement of a gated branch or an inlined body a choice of the presentation, so a `do` that holds a choice is the presentation's code and its body in turn (`inlineChoiceBranches`); a loop around it raises its choice on every pass, which the current engine's weave does not (it offers the first pass's, and offers the block's own choices again once that one is taken). A block that offers a choice ends the body of the gated choice before it, as the next choice does (`opensChoices` in `BinaryProgramWriter.ts`). Inside such a loop's body, a block that holds a `break` or `continue` of the loop is the block's code too, and the exit, which the lowering ties to its loop (`inlineExitOf`) and whose `EndScope`s it counts (`loopExitUnwind`), is a `Jump` within the chunk (`emitLoopExit`); one written in a choice's body or a `then` clause is named. A block written in the preamble writes its objects as one list, so such a body of its own preamble, inside a loop's body too, is written whole, and its `then` clause is the gather whose body the lowering recorded, never the exit label of a loop its choices stand in. A block written in another block's preamble, which offers its choices with that block's and holds nothing of its own, is part of that block's code, and its choices' bodies and its `then` clause are that block's: a choice that belongs to it (its own, one an `if` of it gates, or one of a block written in its preamble) continues at its `then` clause when it has one, and where a choice of the block around it continues when it has none; the clause is written after the choices' entries, runs at the depth the block stands at and continues at the clause of the block it is written in, or at the block's end (`emitPreambleChoose`, `Weave.isPreambleChoose`). The current engine's weave runs such a clause where it stands when the block has no choice outside an `if`, and sends a gated choice past it, which #1588 records as its defect. The compiler places the content of the scene after a block that ends its chunk inside the weave it assembles for the block (`SparkdownCompiler.assemblyWeave`); the flow reads that content as the statements after the block, and the block's statement is the weave its chunk lowered (`Weave.assembledFrom`). A choice with no name counts under an anonymous symbol of its statement (`SymbolKind.Choice`), and a named one under its label's symbol, which its entry exports as a label's chunk does, so a divert reaches it and a read counts it. A choice's body is a block with the choice flag and the clause's with the then flag (`BLOCK_CHOICE`, `BLOCK_THEN`).

| `Gather` | for a `label`, a chunk that exports the label's symbol at its `Visit`; an unnamed gather outside a `choose` block emits only what it holds |
| `Sequence` | `Visit` and `VisitIndex` of its anonymous symbol, the clamp (`Native MIN` for a chain or a queue, `Native %` for a cycle), for a shuffle `ShuffleIndex` (past a test of the last index for a chain or a queue), and per arm `Dup`, `Int`, `Native ==`, `JumpIfFalse`, `Pop` and the arm's content inline |
| `ContentList` | its content's code |
| `Weave` that is a `choose` block | the block's chunk, as above |
| `Choice` | in its block's presentation, its start text and its choice-only text, each captured between `BeginString` and `EndString` when it has any, its condition, and `Choice`; at its entry, `Visit` of its count symbol, its chosen line and `EnterBlock` of its body |
| `ChoiceStartEcho` | the code of its choice's start text a second time, inside the string of the chosen line's call |
| `Weave` that is not a `choose` block | its content's code, with a `do` block's body entered by `EnterBlock` |
| `ConstantDeclaration`, `AuthorWarning` | nothing |

A loop is the objects its lowerer made, which the writer reads by the parts the lowerer recorded (`LoopShape`) and emits as one chunk. A `while` loop is its test, a `JumpIfFalse` past the loop that is a decision, the test's `Newline`, a `BeginScope` for the pass, `EnterBlock` of a body that resumes at the test, and an `EndScope` that never runs, since the body resumes the owner at the test and a `break` past it, which makes the count read in order the depth at the loop's exit (section 1); its block row carries the pass-scope flag, so the engine closes the pass scope when the body runs out, as the lowering has the body's `break` and `continue` close it before they leave. A numeric `for` opens a scope, sets its hidden index, stop and step, and then tests, jumps past the loop, writes the `Newline`, sets the loop variable from the index and enters a body that resumes at the step, which adds the step and jumps to the test; the scope closes after the loop. A generic `for` opens a scope, sets its hidden iterator, state and control, adjusts them with `CallStd __adjust_iter`, and then calls the iterator with `CallValue` into the loop variables, tests the first against nil as a decision, jumps past the loop when it is nil, sets the control from it and enters a body that resumes at the call. A `repeat` loop opens a scope and enters a body that resumes at its test, which is the negated condition, a decision and a `Jump` back. A `break` in a body resumes the owner past the loop. The bodies of the other loops open no scope per pass. A closure made in a pass keeps that pass's variable all the same: the `SetVar` that declares a local again in the same scope, as each pass declares its loop variable and its body's locals, closes the cell a closure captured against the old binding (`CallStack`), as on the current engine.

A construct the writer has no emit path for names itself: `ParsedObject.EmitProgram` names the class's `typeName`, a read count or turns-since call with other than one argument is named by its name, a label inside a function is named `a label inside a function`, a label whose qualified name another label or a flow of the program has is named `a label named as another`, the objects of a loop or a block that do not have the form the writer reads are named by the form (`a while loop`, `a do block`, `a branch's body`), an object of a body that the owner's code does not hold is named by its `typeName`, a call of an external function is named `external`, a divert to a function, which can only be called, is named `a divert to a function` and reported as "A function can't be diverted to: call it instead", an operand too large for its field is named `an operand of` its instruction, a statement of 2^21 code words or more, whose addresses would run into the next chunk's, is named `a statement longer than an address holds`, a choice outside any `choose` block's code (which a script holds only beside a compile error, or inside an `if` in a choice's body) is named `Choice`, and a label between two choices an `if` of a block's preamble gates (or a `do` block or a loop of it offers, #1503), which makes the current engine raise the later choice only once the earlier is taken, is named `a label between choices an if gates`, a choice inside a block a presentation enters that the writer does not make the presentation's own code, which that body's own statements would raise though their chunks do not hold its entry, is named `a choice inside a block of a presentation` (a `do` block's or a loop's body of a preamble is the presentation's code, #1503), and a `break` or `continue` of such a loop written in a choice's body or a `then` clause, which runs after the loop has ended, is named `a break or continue inside a choice's body`.

### The chunk

A chunk's line table holds the statement's own row and a row for each object with a range of its own. A row counts its lines from the statement's first line or, for a part of a block statement that stands below one of its bodies (an `elseif`, an `else`, a `repeat` loop's `until`), from the end of that body, named by the block's index. A row that runs into a body, as a loop's objects span the whole loop, ends at the end of the line above the body, and one that runs on through a body starting on its first line, as a closure written after the start of its statement does, ends at the end of that line, so an edit on the lines a body holds alone changes no row of its owner; a body written on a line of its owner's parts moves the columns of what follows it there, and an edit to it emits the owner again (see Identity below). The block table holds a row per body, as section 1 lays it out: the body's sequence id, the offset the owner resumes at when the body runs out, the offset a `break` resumes at for a loop body and -1 otherwise, the scopes the owner has open where it enters the body with the loop flag and, for a `while` body, the pass-scope flag, and the lines of the owner's parts above the body. The reference table holds, for each symbol the code refers to, a hash of the facts its emission read about the symbol from the symbol table, each with the value read (`ProgramEmitter.fact`, `ProgramFacts.ts`): `Call` and `Sym` of a function read the kind the program defines it as, and a call reads the kind of each of the function's parameters (a value, a reference, the `...`), from which it decides how it passes its arguments. The store keeps the names read beside the chunk and reads each again in the next program, so a fact a new emit path comes to read is compared with no list of dependencies kept anywhere. A jump, a tunnel, a count or a symbol value of a scene, a branch or a label reads no fact about its symbol, and its row holds the hash of no facts (`NO_FACTS`), which the store does not compare; a divert that passes arguments reads its target's parameters, as a call does (#1436). The export table holds a row per function the statement writes: its symbol and the offset of its entry, after the statement's own code, which jumps past the entries; and for a `label`, its symbol at the `Visit` that counts it. The fingerprint hashes the statement's source with each line trimmed and blank lines left out, and a block statement's source is its own parts, with the lines its bodies hold alone left out; removing comments and collapsing the whitespace between tokens, as section 1 specifies, belong with the save format (#699), which is the first reader of fingerprints. The layout hash covers the code, with each id read as what it names.

A name the compiler generates for a statement, which it numbers by document order (`__synth_<n>`: a compound or multiple assignment's stashed base and key, a method call's receiver), is emitted as `__t$<k>`, numbered by its first use in the chunk, and a loop's hidden variables are `__forIdx$`, `__forStop$`, `__forStep$`, `__forIn_iter$`, `__forIn_state$` and `__forIn_ctrl$`. An author cannot write `$` in a name, so none of these meets a name an author wrote, and a chunk's content depends on nothing outside its statement, which the shift oracle checks on this back end (`programShift.test.ts`).

### Symbols, jumps and counts

Scenes, branches, labels, functions and alternators are symbols of the compiler's persistent `ProgramTable`, each with a dense count id the table gives it when it is interned (`countIds`); a scene is named by its name, a branch by its scene's and its own joined by a dot, and a label by its flow's name and its own, or its own alone at the top level (`programSymbolName`). An alternator's symbol is anonymous and belongs to the statement that writes it: a statement emitted again in place hands its old alternators' symbols to the new ones they align with by their own source, as section 2 says and as its functions' are handed on (the alternator lowerer records the range, `alternatorSourceOf`), and a shuffle is seeded from the alternator's flow and that source, which no compile renumbers. A choice's count symbol is anonymous in the same way and belongs to the `choose` statement that raises it (#697): a statement emitted again in place hands its old choices' symbols to the new ones they align with by their own source, through the same three passes, and a choice's body takes the sequence id of the body of the choice it aligns with, so a choice written above a once-only choice that was taken takes nothing from it, a choice whose text was edited keeps its count and its body's id, and two that swap places each keep theirs; its other bodies, the `then` clauses (the block's own, and that of a block written in its preamble) and the bodies of the statement's own code (an `if` of its preamble that offers no choice), go with the parts that head them, by the one rule of the `ChunkStore` paragraph below (#1574). A `choose` statement records the blocks around it, how deep it stands in them and whether it stands in one's preamble, as a lowering input (`recordChooseContext`), since the same syntax lowers to a block of its own or to part of another block's presentation. A root holds definition arrays indexed by symbol id (`DefinitionArrays`): the chunk that exports a function or a label and the offset of its entry or its `Visit`, the sequence of a flow, what the program defines each symbol as, a branch's scene and the branch a scene with no content of its own enters. A label is defined by the chunk of its own statement, which exports its symbol at the `Visit` that counts it; a label whose qualified name another label or a flow has makes the program fall back.

A divert is `JumpSym` of its target's symbol, `JumpVar` of the variable that holds a symbol value, `Call` or `CallVar` with the tunnel flag for a tunnel, which pushes a tunnel frame that `TunnelReturn` pops, going on to the symbol value it pops when one was given, and for a thread `Thread` around the jump: the original thread is suspended where the fork's jump ends, and the fork, a copy of its frames and temporaries, runs until a `Done`, or a flow that runs out, ends it and resumes the original. A jump lands in the frame it is made in: the frame's block stack is rebuilt from the root's sequence and chunk tables, the scopes of the blocks the target shares with the position left keep their bindings, the scopes past them are closed, and the target's further blocks open theirs, as many as each owner has open where it enters the block. An onward return jumps from the caller its tunnel frame returned to. The current engine keeps the scopes a divert leaves and opens none for a body it lands in, which differs only for a `local` written inside a body a jump leaves or enters. A divert's chunk that passes no arguments refers to its target's symbol with no fact, and records the symbol its jump names as the resolution of its divert (`Divert.programJumpKey`): the qualified name of the target the compile found or, for a target it found none of, the name as written. So a target written in full that disappears leaves the referring chunk as it was, the jump raises the current engine's `Divert target not found.` at the jump's line when it runs, and the chunk is the same object when the target comes back; a target written relative to its flow names another symbol once it is not found, and its chunk is emitted again, as a cold compile emits it. The current engine reports that error at the line of the divert's scene, or at none, since the divert the lowering makes carries no range of its own, which the differential run leaves out of its comparison. A label's chunk records the symbol it exports, so a scene renamed emits again its labels and the chunks inside it that name them, and no other.

Visits are a `Uint32Array` and the turn of the last visit an `Int32Array` in the engine's state, indexed by count id and grown as ids arrive, and every counted symbol counts. A `Visit` counts a label and an alternator at their start, whether the flow falls through it or jumps to it. A jump, a tunnel, `ChoosePathString` and a call count the flows they enter from the position they leave (the flow entry rule of section 5; a `ChoosePathString` that keeps the call stack counts from the flow the last instruction ran in, which the state keeps as `previousFlow` for each thread, suspended with the thread a fork suspends and restored when it resumes, written by name for each thread a save holds, and cleared by a reset or a forced end, as the current engine's thread keeps its previous pointer): a flow and, for a branch, its scene, each the position left is not in; a call counts the function it enters unless the frame calling it runs that function. A read count is `GetCount`, so a read added in one flow emits nothing of the flow it counts, and reads every visit made before it existed. The current engine's weave nests a label as the first content of a label written right before it, and a divert counts each label container it enters at its start, so a jump to a label counts too the labels written right before it with nothing between; a jump here does the same (`countLabelsAbove`), which a `Visit` at the label's position alone would not. A declaration whose chunk has no code and no export (`const`, `store`) is nothing between, as the current engine makes no runtime object of it; a line, a `local` or a function is something. A host's evaluation of a scene that starts with a branch counts the branch and not the scene, as the current engine's does. A label's chunk is no function's, so an edit to a label runs no declaration again. `toJson` writes the counts by their symbols' names, or `#<id>` for an anonymous symbol of the root's generation, which `LoadJson` takes through the reseeds since then, dropping a count whose symbol the loading root does not define (the compiler's table keeps a removed name until its next reseed). A test injects one stream of draws into the shuffles (`shuffleDraws`), so that a shuffle picks the arms the test expects.

`Tag` writes a tag object to the output, the legacy tag an inline alternator's arm writes inside the string of its line, which the string's `EndString` moves out to the line's tags; section 3's table has no instruction for it.

The chunk store interns into the compiler's `_binaryTable` and keeps no table of its own, and `maybeReseedBinaryTable`, which runs after every build that makes a root, reseeds it through `ChunkStore.reseed`. A root holds the table's arrays as its generation had them (`snapshotTable`); a reseed installs new arrays on the table, so a root built before it, and every engine on that root, goes on reading the strings, numbers and symbols its chunks were minted with. The next compile finds every chunk of an older generation stale and emits it again, and a previous root's flows are found by name, since its ids are an older generation's.

### The declaration sequence

A script's top-level declaration statements (`store`, `const`, `define`, and the builtins prelude's when the compile seeds it) are the chunks of its declaration sequence, in line order, and a declaration written inside a block's body is placed with its block statement. The root's `initialization` lists the chunks in the order the current engine's `global decl` container assigns the globals, constants first. A declaration chunk is each global's initializer, then a `SetVar` with the declare and global flags under the name that container assigns it, which is the global's key in `variableDeclarations`: a `define` that reuses a name under another type is `$<type>_<name>` there, as the builtins' `typewriter` synth, typewriter, mixer and channel are, and a builtin an author's declaration shadows is `$prelude_<name>`, while each assignment's own name is the bare one. A statement whose globals the story initializes with another statement's between them, as a block that declares a constant and a variable has, since the story initializes every constant first, is a chunk per run of its globals, so that the chunks run in the story's order. With the field on, `ExportRuntime` leaves the story it builds unreset, so its `global decl` container runs only when the program falls back.

`ProgramStory.ResetState` builds the engine's state afresh (a call stack of its own and a `VariablesState` with the story's lists and constants, below), runs the declaration chunks in the root's order against its globals, and keeps what they assigned as the defaults. A compile runs them too (`ChunkStore.runDeclarations`), and counts the run in `initializerRuns`, when it emitted a declaration chunk again, changed the declarations' order, changed the compiled block of a function, or follows a run that raised an error; a compile that emitted only statements of flows runs none. A run that raises an error stops the compile, which logs the error and makes no program. An initializer that calls a function runs the function's chunks, and the rule for a function's block keeps such a global fresh: a compile that changes the block that defines a function runs the declarations again.

### Globals and functions

A root holds what its engine reads of the story besides its chunks (`ProgramRoot.tables`, which the resolver records): the story's list definitions, its struct definitions by type and name, and the names of its constants. Each reset of a `ProgramStory` builds a call stack of its own (`CallStack.ForProgram`, which stands at no runtime container) and a `VariablesState` over it with the root's list definitions and constant names, as the current engine's state builds them, so engines that share a root share nothing they write. The engine takes that `VariablesState` as its globals and the call stack as its frames, whose scopes hold the temporaries and whose open upvalue cells are the runtime layer's. A call enters a function by its symbol: `Call` and `Sym` name it, and a function value is a symbol value (section 10), which the root resolves to the offset its definition's chunk exports (`ProgramRoot.functionEntry`), through the table's remaps when it was minted before a reseed (`ProgramRoot.symbolFrom`). Entering pushes an element of the engine's call stack, beside which the state keeps the position the call returns to, the caller's block stack and the function's symbol (`ProgramFrame`); the callee starts with an empty block stack, and `Return` pops the element and resumes the caller where it called, with its blocks, as popping it closes the upvalue cells the frame's locals hold open. `CallVar`, `CallValue` and the calls builtins make (a comparator, a metamethod, a protected call, a generic `for`'s iterator) run the handlers `Story.ts` exports for both engines (`callVariableTarget`, `callValueAsFunction`, `lookupMetamethod`), which ask the engine for the function a value names (`FunctionTargetOf`) and have it enter it (`EnterFunction`), so padding, packing, `__call` and `__namecall` are the current engine's. Every call arranges the arguments its site pushed for what it calls, as Luau passes them, on both engines alike (#1215): `Call`, `CallVar` and `CallValue` carry their number, as the current engine's function-call divert does (`callArgCount`, `argc` in the story's JSON), and a function or a closure gets one value for each argument but the last (a multiple value's first, nil for a call that returned none), a last argument's multiple values spread and none for a call that returned none, the values past its parameters dropped and nil for the parameters past the values, or for a variadic function its fixed parameters with the rest packed for its `...` (`arrangeArgsFor`, `arrangeClosureArgs`). A builtin reached through a value takes the arguments a direct call gives it (those past its parameters evaluated and dropped, and a missing one raised for a builtin of numbers), and a builtin iterator two (#1216). A table's `__call` handler takes the table and the call's arguments, and a `__namecall` handler, which takes a method call its receiver has no method for, takes the receiver and the call's arguments: each argument but the last as one value and the last spread, as any call passes them, which `CallLuauFunction` arranges for the handler as it arranges a protected call's or a metamethod's for a function value. A builtin method takes the receiver and the call's arguments the same way (`callBuiltinMethod`). Where Luau takes one value, a multiple value gives its first and a call that returned none gives nil, on both engines (`oneValue`, `CallArgs.ts`): the value an assignment assigns, but for the binding of a variadic function's `...`; the base and key of an index; the base, key and value of a store; the value a call calls; a method call's receiver; an operand a metamethod is looked up on, and the left side an `and` or an `or` yields when it decides; a table constructor's computed key, and its keyed value, which the lowering adjusts, since only a list entry spreads; and what a function the engine calls for a value returns: an `__index` function, an operator's or the length's metamethod, `__tostring`, a sort comparator or `__lt`, the `__eq` `table.find` compares with, a `table.foreach` or `table.foreachi` callback, and an `xpcall` handler, while `xpcall`, as `pcall`, returns every value its function returns. The lowering adjusts a parenthesized call or `...`, each arm of an `if` expression and each value a backtick string interpolates to one value with `Unpack 1` (`SingleValueExpression`), so a backtick string writes nil for a call that returns none; a story line's interpolation writes nothing for it, since an author writes such a call in a line for its effect. The links written after a call, a method call or a `new` expression apply to its result, in an expression and in the target of an assignment (`f().x`, `o:get()(1)`, `new P(1):m()`, `f().a.x = 1`), as Luau reads them (#1263): every part of a link, which the grammar writes as one node for a run of accessors and indexers (`.a.x`, `.b[2]`), the value of such an assignment with the lines that continue it, and a compound assignment through such a target (`o.get().a.x += 2`), which reads and writes through the target's base and key, each evaluated once. A statement written with `&`, which a scene's top level needs for a call, takes its links as one written without it does (`& o:me():bump()`, `& o.get().a.x += 2`, `& (t)[k] = v`). A variadic closure called by name packs its extras as one called through a value does (#1217). A story's JSON written before calls carried their number has no `argc`, and the current engine runs its calls as it ran them then: the site packed a variadic function's extras, and a last multiple value spreads into a function that takes no `...` (`programCallArguments.test.ts` runs such a story). `HasFunction` and `EvaluateFunction`, which the UI module calls for an event handler and a binding's evaluator, find a function or scene flow by its name and run it in a frame of the game's evaluation type: a function until it returns, and a scene from its start until it ends, as the current engine runs a knot it evaluates. A function's parameters take the host's arguments as a call's do (`arrangeArgsFor`), and one that runs off its end returns nothing, on both engines; a scene that takes parameters takes them arranged in the same way for what its entry binds, and a scene that takes none takes them as they are (#1436). A symbol value names its function by its id when the id still names a symbol of its name, and by its name otherwise, so a value that a save of another program holds, whose table starts at the same generation, does not call whatever function its id names here. `debug.traceback` and `debug.info` read the frames through `CallStackTrace` and `CallFramePath`, which name each frame by its function's symbol: a function declared at the top level by its qualified name, and one a statement writes by the name the current engine gives its container. Where the call stands inside a block, the current engine's trace adds the path of the block's container (`outer.0.$b`) and `debug.info` names that container (`$b`), which is no name of the function; the program engine names the function there too, as it holds no path. `listDefinitions` and `structDefinitions` are the root's (`ProgramRoot.tables`).

### The engine

`ProgramStory` presents the members of `Story` that `Game.ts` uses to start a game, continue it, read a beat and run a preview compile's program, under the same names, with `ProgramStoryState` as its `state`. It runs a chunk's instructions from an integer cursor. `CallStd` calls the builtin's `STDLIB` entry with the story as its receiver, so `display` builds its instruction and applies `open`, `glue`, `caption`, `extend` and `continues` from its table as it does on the current engine; the engine does not read the open flag, which repeats what the table says. `Native`, `GetVar`, `Index`, `StoreIndex`, `MakeTable`, `Pack`, `Unpack`, `EndString`, the short circuit and the Luau test run the handlers `Story.ts` exports for both engines (`callNativeFunction`, `readVariable`, `indexValue`, `storeIndex`, `tableFromPairs`, `packTuple`, `unpackTuple`, `captureString`, `shortCircuitDecides`, `popLuauCondition`), and `SetVar` assigns through `VariablesState.Assign`, so a value is what the current engine makes it; one pop of an empty eval stack gives null, as the current engine's does. `EnterBlock` pushes the owner's sequence, its entry and the block's index on the state's block stack and enters the body; a body that runs out pops the stack, closes the pass scope when its block row has the pass-scope flag, and resumes its owner at the block row's resume offset; `Leave` pops the stack to the nearest loop body and resumes its owner at the row's break or resume offset, after the `EndScope` the lowering places for each scope the jump leaves. The stack is the running frame's: a call keeps the caller's in its frame and a return restores it. A `JumpIfFalse` with the decision flag is a decision: with `pauseBeforeEvaluatingConditions` set a continue stops before it and `pausedBeforeCondition` names its address (`ProgramStory.addressOf`, `chunkId * 2^21 + offset`), the route simulator's `forceCondition` is asked by the same address, and `onEvaluateCondition` hears the verdict. A continue returns at its line's newline without running the statement after it, so a variable that statement assigns holds its old value until the next continue (#779). The output rules are the current engine's: `PushToOutputStream`, the pending line end and the join, the cut at a line's newline with the step carried past it into the next continue, `CleanOutputWhitespace` and the continue loop. A runtime error or warning is prefixed with the script and line of the line table row that covers the instruction, as the current engine prefixes it from debug metadata. `ChoosePathString` takes a flow's qualified name, `""` or `"0"` for the top level, or a path that the compile's path locations place at a line and column where its content starts. A line can hold several statements (tags written after inline text) and several beats (a `>` break), which the column tells apart: of the statements that start on the line where the statement holding the location starts, the engine takes the last one that starts at or before the location, and runs from its last `LineStart` at or before the location, or from its start when it has none (a continuation, which joins the beat before it, or tags). So PLAY from a line starts at its first beat and a preview of it at its last, as `Game.setStartFrom` chooses them. A saved state holds its position as a chunk id, entry, offset and sequence id, and each frame's temporaries by scope, its open upvalue cells, the position it returns to and its function's symbol, and `LoadJson` finds each chunk in the root it runs on and rebuilds each block stack from the sequence that holds the position (`blockStackOf`); a flow resting past its last statement, as it does after its last beat, has no chunk and is saved as chunk id -1 with its sequence's id, and loads at the end of that sequence. `ChoosePathString` to a line inside a body enters the blocks that hold it, with the scopes their owners have open there; one that resets the call stack ends the flow as the current engine's does, resetting the engine's call stack, so the flow it chooses starts with a fresh frame. `Choice` raises a choice as `Story.ProcessChoice` does (`ProgramChoice`): it pops the condition, which is a decision the route simulator can force and pause before, as a conditional choice point is, and each captured text with the tags a `EndTag` inside its capture pushed below it (`captureTag`, which both engines share), hides a once-only choice whose count is not zero, and holds a copy of the current thread with its frames (`ForkChoiceThread`), its entry, the blocks the entry is inside, the chunk that raised it and the flow it was raised in; its `sourcePath` is the address of its `Choice`. `currentChoices` gives the waiting choices without the invisible defaults, each with its index. Taking one (`ChooseChoiceIndex`) makes its thread the only one, clears the choices, starts a new turn and counts the flows its entry is in that the flow last run in is not; a continue that can go no further with only invisible defaults waiting takes the first, in the same turn, entered from the flow it was raised in (`Story.TryFollowDefaultInvisibleChoice`), and a route simulation takes the choice its route forces, asked by the address of the `Done` that held. `ChoosePathString` and a forced end drop the waiting choices. `toJson` writes the waiting choices, each with its text, tags, identity, entry, flow and the frames of its thread, and `LoadJson` reads them back; a menu is kept as the image of the beat before it (State and saves, below).

### Identity

The rule of section 1 holds for every statement the writer emits (`ChunkStore`). A statement whose compiled block is the one the store emitted a chunk for keeps that chunk. The statements the reparse window lowered again are aligned with the previous root's, every flow's statements as one list, so a statement keeps its chunk when an edit renames its flow or moves it into another: between two statements that kept their chunks, the old and new ones are matched from both ends and then in order by their syntax, which is the node's name, the column it starts at and its text, and then the one statement left on each side of the run with the one old statement left, and the statements no run matched are then matched in order by their syntax with the old chunks no run took, wherever those stood, which keeps the chunks of statements an edit moved past a statement that kept its own, as breaking a scene's header moves the scene's statements into the flow above (#1221). A matched statement keeps the old chunk when it can and is otherwise emitted again in place; the one statement left on each side is emitted again in place only when both have parts. Matching by position can pair a statement for an edit in place with the chunk another statement can keep, as when an edit reorders statements of one syntax, so every statement that can keep an old chunk it does not hold then takes it where that leaves nothing behind (#1496): a chunk no statement holds, when the statement holds none or holds one without parts, or, by exchange, the chunk another statement holds to be emitted again in place, when that statement can take the one this statement leaves, by keeping it or by being emitted again in place from it. A statement that holds no chunk takes none another statement holds, and a statement that holds a chunk with parts keeps it over a chunk no statement holds: the edited statement keeps the parts of its old self, whose body sequence ids and function symbols a saved state may name, so an edited function beside a copy of its old version, or beside a deleted statement it now reads as, keeps its symbol. A chunk left behind goes to a statement no pass matched, by its syntax. Whether a statement can keep a chunk is one comparison of the statement's syntax, lowering reads and the values listed below against the chunk's, with the chunk's own facts read again at most once per build (a carried statement's are read only when a symbol it read about changed, The incremental passes below); a statement's identity is built only when an old chunk reads as it in syntax and lowering reads, and each statement is screened so, and each statement's and each chunk's identity built and looked up, at most once however many times an exchange passes it on, whether or not an old chunk has that identity. The column belongs to the syntax because a statement that shares its first line with another, such as tags written after inline text, moves along the line when the other one changes, and its line rows hold columns. A block statement's text is its own parts, with the lines between the part that heads each body and the part after it cut out, so an edit inside a body leaves the owner's syntax as it was. A line that holds a part stays whole, with whatever a body writes on it (`if x then n = 1 end`, an `else` with its indentation): the owner's rows hold the columns its parts start and end at, so an edit on such a line, to the part or to the body beside it, emits the owner again; the list is in pre-order, each block statement before the statements of its bodies, so a statement of a body keeps its chunk by the same rule as a statement of a flow, and an owner emitted again in place (matched by its syntax, or the one statement left on each side of a run) hands each of its bodies a sequence id by one rule, whatever the statement (#1574): the body takes the id of the old body whose heading part its own heading part aligns with in the three passes of section 2 (`alignParts`), and a new id when its part has no pair, while an old body whose part has no pair gives its id up. A choice's body is aligned by the choice's own source, a function's by the function's own source, and every other body by the source of the part that heads it, which the lowering records with the body (`BodyShape.headStart`): a branch's condition or its `else`, a loop's header, a `do`, a `then` clause with its label, the clause also by the depth of the `choose` block it closes, so a clause of a block written in another's preamble is told from that block's own. No body id is handed on by position outside the third pass, the pairing of parts left between matches, which is the stated limit of section 2; the store records how it handed on each body id of its last build (`ChunkStore.handedOnLastBuild`). A matched statement takes the old chunk when the lowering inputs it recorded read the same: the global callable names and define type names it consulted, and the routing of the line that a continuation after a `>` break joins, which `lowerDisplay` reads outside the continuation's own syntax and records as a `LoweringRead`, naming the node that read it (a continuation inside a block statement stands below the chunk's top-level node); the compilation annotator lowers a block again when the node that read an answer now answers differently. A `done` or `fin` records the same way the range of the statements after it in its scope, which its unreachable hint covers, so an edit below it that changes them lowers it again with the hint a cold compile raises; that read decides the hint and not the code, so the store does not compare it. The annotator keeps these reads for every compile. A chunk is kept while the values its emission recorded read the same, which are the texts the compiler names by document order after lowering (a continuation's group, `__group_<n>`) and how each name its code reads resolved (a temporary, a global, a constant, or nothing, with a generated name's number left out), since an edit elsewhere, such as a `local` written above, can make a name read another variable without changing the statement; a declaration chunk is kept only while it assigns the same globals, by name and in order, since which of a statement's globals one declaration holds and the name each is assigned under depend on declarations elsewhere (a constant between a block's constant and variable, a `define` of the name under another type, an author's declaration that shadows a builtin); and while the hash of the facts about each symbol in its reference table is unchanged: the kind the program being built defines it as, which an edit turning a scene into a branch of the same name changes, or that the program does not define it. A chunk is also kept only while the names its code assigns are assigned as they were, declared as a local or assigned to a variable already there, since a function a function declares without `local` assigns the local its lowering hoisted to the top of the function around it, while the parameters each function the statement writes or runs in place binds at its entry, and the locals it declares there, in order, are the same (a function whose header the parser cannot read takes the parameters of the first parameter list in its body, which the statement's syntax leaves out), and while the statement defines the same function declared at the top level, or none. A function keeps its symbol with its statement's chunk. A statement emitted again in place hands its old functions' anonymous symbols to its new ones, aligned by each function's own source as section 2 aligns parts (`alignParts`), so a function inserted before another in the same statement takes a new symbol and the other keeps its own, and a closure made before the edit calls its own function's new code; a name's symbol goes only to the function declared under the name, so a function an edit moves inside another takes an anonymous symbol, as in a cold compile. A chunk that calls another statement's function by an anonymous symbol that function no longer has is emitted again. The store reads which of those a chunk calls from the statement's objects as the writer emits them: the chunk of a function the story leaves in a block binds its parameters, declares its hoisted locals and enters its body, so it refers to none of the functions its body declares or the closures they create, which are other chunks' code; and a declaration written in a block, such as a `define` in a `do` block, emits nothing where it is written, so its statement's chunk refers to none of the functions its initializer creates, which the declaration's chunk writes. An edit elsewhere leaves either chunk as it was. A call in a flow whose run a compile reuses resolves its target again after the top-level assignments that make globals of their names (`x = …` with no declaration) have resolved, which is after every call the compile generates has found its target; there a function of the name wins over such a global, as it does for a call generated in the compile, so the call's chunk is the one a cold compile emits. A call's code depends on its callee's parameters, whose by-reference ones take a pointer, and the callee's facts in the caller's reference table hold them all, so a change to a function's parameter list emits its callers again and nothing else; and a closure's statement records whether each name its function reads resolved to a function declared at the top level, which decides whether the closure captures it, so adding or removing such a function emits again every chunk whose closure captured the name or stops capturing it (#935). `ChunkStore.reseed` starts a new table generation that interns again the symbols the current root holds, its flows', those of the labels and functions its chunks export and those of the alternators and choices its statements write, and drops every other entry (`reseedProgramTable`), so the next compile emits every chunk again and hands each function the symbol it had; the store keeps each reseed's remap, which the roots it builds carry, so a symbol value made before the reseed finds its function after it. No chunk stands in two places of one root, and chunk, sequence and root ids come from counters that never go back.

### The incremental passes

A build of the root is proportional to the edit (#701). The facts a chunk's reference table records are the ones its emission read (`ProgramEmitter.fact`, The chunk above), and the store keeps the reverse index of those reads, from each symbol to the chunks of the current root that read a fact about it (`ChunkStore._readers`). A build gives each symbol the program defines its facts (`definitionFacts`: a flow's kind and a function's parameters, and the facts of each function a statement writes, which the build plans with the statement), compares them with the current root's program's, and reads again the facts of the chunks that read a fact about a symbol whose facts changed, and of no other chunk.

How each name a chunk's code reads resolved, and each text the compiler names by document order, are values its statement's parsed objects report once the compile has resolved and named them again. The store watches the objects of each statement it emitted or matched with the reader of each value the chunk recorded (`StatementWatch`), and the compile's own passes report each object they resolve or rename (`resolveChild` in `ParsedHierarchy/Object.ts`, `SparkdownCompiler.canonicalizeSyntheticFlowNames`): an object whose value now reads otherwise marks its statement. The resolver (The resolver, below) resolves only the statements whose resolution can read otherwise, so the watch hears of no other. A name, a call or a jump is read with what it found, by its symbol's name for a scene, a branch, a label or a function declared at the top level, and by the object itself for a function a statement writes, whose anonymous symbol belongs to that object for as long as its statement is kept: the compile also places such a function among the story's flows, under a name it numbers by document order (`__synth_<n>`), which a function written above renumbers. A preview compile's reports go to the watch of that compile alone, and the values the watch compares with are the ones the current root's chunks recorded, so a preview leaves the next compile's decisions as they were.

A statement whose lowered block the compile carried from the compile before, whose chunk the current root holds, that the watch did not mark and whose chunk read no fact about a symbol whose facts changed, keeps its chunk with nothing read again (`keepCarried`); only the statements that are not so carried are aligned with the old chunks by their identity as above. The statements of a block statement's bodies are statements of their own, carried or not; in a block the reparse window lowered again, a statement the compile served from its memo (The statement memo, below) is known by the memo, which is the block its chunk was emitted for, and keeps its chunk as a carried statement does, and every statement the compile lowered is one to align, whose identity is a read such an edit costs.

A sequence is built again only where it holds a statement that is not carried, and a carried statement's bodies are not visited unless a statement inside them is not carried or the flow, the kind or the script of the sequence that holds it changed, which its bodies' rows name and its alternators' shuffles are seeded from, or whether the sequence is inside a function, which decides whether its chunks hold a function's code. A body's row holds no line of its own (`ProgramRoot.firstLineOf` derives where it starts), so the rows of the bodies below an edit are the current root's rows. The new root's rows, chunk table and definition arrays start as the current root's, and a build writes over them the rows of the sequences it built again, the rows of the chunks it placed where the current root does not hold them and of the chunks it dropped (a chunk a sequence built again no longer holds and no sequence took, with the bodies it owned that no owner took), and the definitions those chunks export; a sequence whose chunks did not change shares the current root's chunks array even when its line starts moved. `ChunkStore.passesLastBuild` counts the statements whose identity a build read, the chunks whose facts it read, the statements whose references to other statements' functions it read, the chunks it emitted and placed, and the rows of the definition arrays and the chunk table it wrote. Two counts there are of bookkeeping: the current root's statements a build lists to align the statements that are not carried with (`order`), and the entries it reads from the statements the compile hands over to assemble a sequence's arrays (`assembly`), a script's declarations among them; neither reads a chunk's facts or values or writes a row. Both scale with the edit (#1599) when the compile hands the store the changed blocks (`ProgramSource.changed`): per script, the lines of each top-level block it lowered anew since the compile that built the store's current root, which the compiler finds against that compile's blocks (`SparkdownCompiler._chunkStoreBlocks`) rather than the last compile's, since a preview's compile in between moves the one and not the root. Every line whose text changed since that root is in one, as the incremental parse lowers anew the blocks around an edit. The statements still come whole (`programFlows`), and each is still checked for whether it is carried, which is a few lookups; what the changed blocks bound is the following.

- The alignment reads the old statements only between the carried statements around the window: from the first statement that is not carried to the last, with the statements of the last one's bodies (`ChunkStore.alignmentWindow`). Every statement outside the window is carried, and keeps the place it had in the order above, so aligning the window with the old statements between the same two carried statements pairs each statement as aligning the whole program does: every run the passes above match falls inside it, and outside it every old chunk is used. The root walks the old order from where its chunk table places the carried statement before the window to the one after it (`ProgramRoot.statementOrderBetween`). That the statements around the window kept their places is checked on the lists that hold them, by the first and the last statement of each part: the flows are the old ones in order; a flow outside the window holds as many statements as its old sequence, with the same first and last; each list that holds the window's first statement or the statement after the window, or an owner of either, holds the old entries above it or below it; and of the declarations whose bodies hold statements, which the order lists after the flows, those wholly above the window are the first of the old ones and those wholly below it the last, by their chunks, while the window may hold the bodies of declarations lowered anew. The old statements between are then counted from the old root's count. A check that fails lists the whole old root, as without the changed blocks.
- A sequence keeps the entries above its window and below it as the current root's arrays hold them (`ChunkStore.reuseOf`), where its window runs from the first entry to the last that is not settled (not carried, or holding a statement that is not) and over each entry a changed block touches, from the one that holds the block's first line to the last that starts by its last line. Outside the window the text between the entries is the text the current root was built from, so the entries above are the old ones and those below are as many of the old ones, each line start moved by as many lines as the first of them, which the first and last entry of each part confirm; the new arrays are the old ones with the window's entries put in place of the old ones between, as the order structure (section 1) builds them, and only the window's entries are placed or dropped. A script's declaration sequence, whose line starts are the script's own lines, has its window by line, from the first line of the first changed block or declaration not carried to the last (`ChunkStore.keptDeclarations`): the old entries above it are kept, those below it are kept with their lines moved by the lines the script gained, and the declarations that start in it are read and put between, when the counts add up to the script's declarations.

What the changed blocks cannot bound is what the parse lowers anew. An edit to a line of top-level content outside the scenes, or to a declaration written there, was measured to lower anew every top-level block of the run of declarations below it, so such an edit still reads, aligns and assembles each of them, as the count of statements whose identity a build read (`identity`) shows; an edit inside a scene above them lowers none of them.

Without the changed blocks (a cold build, or a caller that cannot say), a build lists every old statement and assembles every entry, and builds the same root. On the Raffles and Bunny project the edit at `main.sd` line 3515 below lists 307 statements and assembles 307 entries, the `choose` block the incremental parse lowered again and one more, where it listed 2,530 and assembled 2,385 before #1599; `program/chunks` measured within the noise of the run either way (Measured below). `ChunkStore.verifyBuilds` (on in the tests' harness) derives every root a build makes from its sequences alone and fails the build when the tables it wrote, or the set of chunks that hold a function's code, differ; it also checks every sequence's arrays against the statements the compile handed over, and aligns the whole program again after a window's alignment and fails the build when the two pair any statement otherwise.

A function declared at the top level keeps its body's id when its definition is emitted again in place, as when its header is edited: the function is the part its name names, and the body goes with it as a body goes with the part that heads it (section 2), where until #701 it took a new id.

The compile makes no runtime story: the program path's resolver resolves its references (The resolver, below) and records the program's lists, structs and constants for the root (`ProgramRoot.tables`), since the program counts every counted symbol and runs nothing of a runtime tree. The compile's events and result say whether it produced a program that runs (`produced`), which a host reads in place of a story: the player's worker keeps, displays and runs a program from its chunks. The compile's struct definitions, which the asset checks read, are the root's. The builtins prelude is compiled with statement chunks too, and the global names an unseeded compile declares for it are the globals its declaration chunks declare (`declaredGlobalNames`). The naming collision check finds the lists, list items and structs a declaration's name collides with through an index of the declarations by name (`Story.collisionIndex`) in place of a scan of every list and struct per declaration, and reports each collision with the place of the declaration it collides with, as before.

What stays a pass over the whole program on this path is bookkeeping, a lookup or two per statement: the resolver's walk of the story's flows and of the top-level objects of their weaves; the story's tables, which every compile declares anew from what each statement declared; and the listing of the statements the compile hands the store (`programFlows`), which keeps the source it built for a carried statement while the statement stands on the same line, since a carried block keeps its record (`SparkdownCompiler.statementRecord`), whose readers read where the block stands now. `populateLocations` and `sortPathLocations`, which built the path locations a game placed a line by, no longer run, since addresses replace them (#700, Addresses), and neither does the noting of each flow's shape for the current engine's change summary (`ink/flowShapes`), which the chunks' own summary replaces (`rootChanges`). The program layer reads no parsed object of a carried statement, and the resolver generates and resolves none.

### The resolver

A compile resolves its references with the program path's resolver (`ProgramResolver`, #1607) and calls neither `ExportRuntime` nor `ResolveReferences`. It makes the passes of a cold `ExportRuntime` in their order: it declares the story's constants, lists and structs (`Story.DeclareStoryTables`), names each flow's labels (`Weave.NameWeavePoints`), prepares the statements, which declares their globals, locals and externals and reports what generation reports, declares the parent types no statement defines (`DeclareImplicitParents`), prepares the globals' initializers (`PrepareGlobals`, which walks the globals as `InitializeGlobals` does, through the traversal both share, `Story.EachGlobal`), and resolves every statement's references; so it reports the same diagnostics, in the same order and at the same places. `programDiagnosticsParity.test.ts` holds it to the diagnostics `ExportRuntime` reported at 99397ed89 for every fixture of the differential run and a screenplay of auto-globals, compiled with the language server's configuration (`fixtures/resolver-diagnostics.json`).

A class resolves its references in one place (`ParsedObject.ResolveWith`): the program path's resolver resolves each object a statement holds at its top with `resolveChild(obj, story, true)`, which reads and writes nothing of a runtime tree, so that resolving one statement reads no runtime object of another. A flow's checks of its own names after its content (`FlowBase.CheckOwnNames`), its report of a return outside a function and of a flow written twice under it (`ReportReturnOutsideFunction`, `ReportDuplicateChildFlow`) are shared the same way. The resolver builds no runtime object (#705): it prepares each statement it resolves (`ParsedObject.prepare`), which does what generating the statement did besides building its runtime objects, in generation's order: the globals, locals and externals it declares, the diagnostics it reports, a divert's early resolution of its target and the checks of its arguments, a call's counted target taken into its content and its proxy divert taken out, and the parsed fields resolution and the writer read afterwards (a divert's variable target and whether it calls an external, `Divert.variableDivertName`, `isExternal`). The taps hear a preparation as they heard a generation; `Story.PrepareGlobals` hands the resolver the globals' initializers with no container. Generation, `ExportRuntime` and the runtime objects for code went with the current engine (#705); `programWithoutGeneration.test.ts` holds every fixture of the differential run to no runtime object read and no runtime container filled.

The resolver knows the story statement by statement, as the chunk store does: the objects the assembly placed for one block where they stand in a weave, a function the top level or a statement declares, whole, and the header of a scene or a branch. A statement is generated and resolved anew when the incremental parse lowered it anew, when the flows around it changed (a scene's header removed above it), when a pass of the compile renamed something of it (`canonicalizeSyntheticFlowNames`, `scopeDefineInstances`), when a name it read declares otherwise, or when a position its diagnostics report or print belongs to a statement lowered anew or moved (`already exists on line 4`); every other statement is replayed: what its last resolution recorded is done again in the story's order without visiting it. A resolution records the names it looked up in the story's tables (`ResolutionTap`, through `RecordingMap` tables and the lookups that read a flow's parameters or its own name), and the things it did that the story keeps for the rest of the compile: the diagnostics it raised, those the story reported and those an earlier diagnostic of the same source kept back (one error and one warning per object a compile, `ParsedObject.Error`), which a replay raises again where they were raised, so that the story decides again, in its order, which to report, each at its source's position as it reads now, or, for a position the report made (a name built for `target not found`), moved as far as the statement moved; the globals and locals it declared and the externals it added, which every compile declares anew; the global it made of a bare assignment's name, made again while the name is still undeclared there; and the divert a builtin's global captures. A statement lowered anew or gone declares the names its syntax declares (`UnitShape.defs`), each with how: a global by its kind, a local and a bare assignment with the flows around it and the statement's place in the story's order, a local also with whether it is still in scope after its statement (a block written around it closes it, which decides what a library-named read after it reads), a label with its flow, a flow with its parameters and the lowering it came from, since a resolution holds the flow it found, which the writer finds the flow's symbol by; a name whose declarations differ from what the statements before declared is declared otherwise, and the statements that read it are resolved anew, through an index of the names each statement read. So are the statements that read a constant the story can register now and could not before, or the other way round, which the story decides from the constants together (`Story.unregisterableConstants`) once it has declared them; each constant's initializer is walked for the names it reads once, the first time the story declares it (`ConstantDeclaration.referencedNames`), and a carried statement's initializers are not written again: what writing one recorded is replayed, found by the initializer, since the global a constant or a struct's property initializes is made anew by every compile. The few lookups of a resolution that walk past its statement read instead what each statement held once it was generated, which the resolver reads then (`ProgramResolver.readFacts`): a library-named local's scope (`FlowBase.IsLocalInScope`) asks the locals each object a statement holds declares (`ResolutionTap.declaredLocals`), what lies under one with no position (`unplaced`) and the function value that names a flow (`functionValue`), and the assignments a divert to a builtin's global is checked against (`Story.globalAssignmentNames`) are each statement's (`assignments`); the tests check each against the walk it replaces after every resolve (`ProgramResolver.verifyFacts`). A lookup that goes through a table whole (the deep search of a scene's branches, a list item looked up in every list) reads every name of the table's kind, and the few that read the whole story (the flow a nested function is written in, the assignments `-> game` is checked against) read every name. A carried statement's parsed objects keep the resolution the resolve that last resolved them gave (`Divert.targetContent`, `VariableReference.resolvedAs`), which the store and the writer read: a divert's resolution belongs to a resolution epoch that only a cold resolve moves (`CompileEpoch.ts`); the counter is the process's, which another compiler's resolve moves between two compiles (a cold compile, the prelude's `ExportRuntime`), so each move takes a value no resolution had and a compile enters its resolver's epoch again before it reads a divert it carried (`ProgramResolver.enterEpoch`); and a statement resolved anew is cleared first (`ParsedObject.ResetRuntime`), which an edit no longer does to a carried block's objects on this path; a statement new to the resolver too, since it can hold objects resolved before (a function whose body an edit extended over statements that stood at the top level).

A bare assignment makes a global of its name where resolution reaches it. The resolver resolves and replays in the story's order, and makes each recorded global again where its statement stands, so a read above the assignment reads no global and one below it reads the global, as in a cold compile; and a call of a name a function has finds the function when its statement is generated, before any assignment makes a global of the name, so the function wins, as in a cold compile. `programIncrementalOracles.test.ts` runs the three incremental oracles over a screenplay of auto-globals read before and after their assignments, inside functions and blocks, and globals named like functions (`autoGlobalScreenplay.ts`). A struct's runtime definition is kept with its statement and built again only when the statement is generated anew.

A resolution that throws stops there, as `ExportRuntime`'s does, and the next resolve resolves every statement. The first resolve of a compiler, one after a reconfiguration and one after a compile whose program fell back resolve every statement too (`passesLastResolve.cold`). `ProgramResolver.passesLastResolve` counts the statements the walk listed, the ones generated and resolved and why, the ones replayed, the parsed objects generated and resolved, the objects the compile adds to the story itself (a flow's closing `-> DONE`), the objects generated or resolved outside any statement's generation and resolution (`outside`: those under the objects the compile adds, and an initializer written with no statement's record), and the names declared otherwise; `programResolver.test.ts` asserts that an edit inside one beat of a flat 2,000-line scene, and inside the `then` clause at its bottom, generates and resolves only the statements the parse lowered anew and visits no object of another, inside a statement's resolution or outside it (`visitedLastResolve`, `visitedOutsideLastResolve`), and that the resolve reads the `content` of no object of a statement it carries, which any walk of a subtree reads, also for a story whose constants read one another.

### The statement memo

The compilation annotator lowers a top-level node whole whenever the incremental parse rebuilt any of it, so before #656 an edit to one line of a long block statement lowered every statement of the block again. Each statement of a block's body (a choice's, a `then` clause's, a branch's, a loop's, a function's) is lowered through the statement memo of the node being lowered (`StatementMemoSession`, `compiler/lower/statementMemo.ts`), and a statement the parse did not rebuild is served from its memo, without being lowered, while every read its last lowering recorded reads the same. It then lowers to a `MemoizedStatement`, which holds none of its objects and stands where they would; its memo holds its chunk, which the store keeps. The check for Luau blocks left open (`validateBlockEnds`) does not walk the node of a served statement that its last lowering found to hold no block the check reads (`holdsCheckedBlock`), as its syntax still does. `CompilationAnnotator.memoStats` counts the statements an update lowered and those it served, with where each lowered statement starts.

A statement of a body is lowered with a context that records what its lowering reads (`recordLowering`, `compiler/lower/recordingContext.ts`): every field of the context it reads, followed down to the value it ends at, an entry of an array, a member of a table or a map, a method's answer for the primitive arguments it was asked with (`globalCallableNames.has(name)`). No field is listed anywhere: a field added to the context is recorded the first time a lowerer reads it, and `programStatementMemo.test.ts` adds one that a lowerer reads and shows the statement that read it lowered again when its value changes, with every other statement kept. What is not a value of the context is the document, whose text a lowering reads through `read`, `lineNumber` and `characterNumber`: a read of the statement's own range is its syntax, and a read outside it is recorded with offsets relative to the statement's start, so that a statement an edit above it moves keeps its memo. The diagnostics a lowering pushes are recorded and reported again; the statement's own shape on the statement stack is its own record; the `LoweringRead`s it reports (`routing`, `unreachable`) are asked of the document again. A lowering that writes into the context, a push onto a shared stack or buffer or a field it sets and leaves changed, or that reads a value the record cannot compare (a parsed object, a syntax node), records nothing a memo can be served by. A statement of a body is lowered with a recording of the context itself, not of the recording of the statement whose body holds it, so what a body's statements read is theirs and no read of their owner's, whose chunk holds none of their code.

A memo is known by the statement's syntax, the names of its nodes and of their children, its parent node's name, the column it starts at and its text, and is served when each recorded read, asked again of the context as the lowering asked it, reads the same; asking records the names the statement consulted in its record and in its block's, as its lowering would. A memo is found by its syntax and by where its statement started in the document before the update (`memoKey`, the update's changes mapped back), and a statement the parse rebuilt takes none, so two statements that read alike each find their own memo whatever an edit wrote or took away between them. The store's identity of a statement holds the same reads (`StatementReads.recorded`, as a set), so a statement lowered again keeps its chunk only while they read the same, whatever field they read. A statement of a `choose` block's preamble, which is the block's own code, and a statement the parse rebuilt (inside the update's window) are lowered whatever their memos say. The first incremental parse of a block after a cold parse reparses the whole block, since the parse records places to restart from inside a block only once it has reparsed it, on the Raffles and Bunny project too.

A memo holds no parsed object: the chunk, which holds the symbols the statement exports and refers to; the reads its lowering recorded; the diagnostics its lowering reported, with lines counted from the statement's own; and what its generation and its resolution reported, at positions counted from the statement's first line, with the names they read (`MemoResolution`). The compile that lowered a statement completes its memo once its build is committed: the resolver tells what each statement it was told of reported and read from what happens while the statement's objects are generated and resolved (`ResolutionTap.visited` and `left`, `ProgramResolver.memoResolutionsLastResolve`), and the store gives the chunk (`ChunkStore.memoChunk`). A statement is remembered only when what else reads its parsed objects reads nothing its memo cannot stand for: its lowering wrote nothing into the context, and nothing its owner's lowering or the story's weave reads of a statement's objects is among them (a choice, a gather, a weave, a divert that is not a call's, a tunnel return, an author warning, a flow), but for the three statements below that stand as objects of their class, a loop's `break` or `continue`, which is a jump within the loop's blocks and stands as a statement, and the parts of a loop's or a `choose` block's own objects its stand-in holds again (below); it holds nothing the story's passes over the whole program take of a statement (a declaration of any kind, a flow, a return, a function value, a local), but a plain assignment and a label, which stand as one; its generation and resolution declared nothing, reported no position outside the statement, printed no position, and read no fact of another statement that no name stands for (a function value, the story's assignments) and no name of a list or a struct, whose values the story decides from the declarations together (a constant's reader reads it as a global, and a change of whether the story can register it declares its name otherwise); it holds no name the compile numbers by document order (`canonicalizeSyntheticFlowNames`), which a served statement would hold back from the numbering, but a loop's own names and the label a `break` or `continue` leaves by (`ownsItsNumbering`), which a loop's stand-in names again; and its chunk has no function or alternator of its own, no choice but a `choose` block's, no block but those its heads or its choices head, no export but a label's or the labels a `choose` block's stand-in names, and refers to no other statement's function by an anonymous symbol.

A statement whose objects another pass reads for what they are stands, when it is served, as an object of that class built from what its memo recorded of it, whose generation and resolution go through its memo as a `MemoizedStatement`'s do (`memoOf`, #1676): a divert with no arguments as a divert to the same target, of the same kind (`MemoizedDivert`), which is what the weave (whether a weave point runs on), the flow's checks and the writer read of it; a plain assignment or a local declaration as an assignment of the same name and kind (`MemoizedAssignment`, `MemoizedMultiAssignment` for one of several names, and a group of them for a statement of several, `& local a = 1; local b = 2`), which is what `Story.globalAssignmentNames`, the resolver's signs of a bare assignment and of a local, and a later statement's search for the locals in scope (`localsDeclaredIn`) read of it, and which makes again, where its resolution would, the auto-global the assignment made, while no name resolves its name, and declares again, where its generation would, the local the declaration declared, so that a statement after it lowered anew resolves the name to it; and a label as a gather of the same name and depth (`MemoizedGather`), which is what the weave builds its weave points from and the story's passes name the label by, and which makes the container the weave places it by. A block statement (an `if` block and its branches) is served with the statements of its bodies: its memo holds their memos, the parts around its bodies, and what their lowerings read of the context as the block statement found it (`MemoOwner`), which a read of what the block statement set up for its bodies (the scope it opened, the stacks it pushed) is left out of, since its own reads and its syntax, which is the text of its bodies too, decide it. It is served when its own reads and theirs read the same and each of their memos is complete, and none of them declares a local, whose scope the block's branches open and its stand-in does not (such a block is lowered, its bodies' statements served inside it); its stand-in holds their stand-ins, its served shape their shapes, each known by its memo, and the store keeps its chunk with the blocks its heads head (`StatementSource.stands` leaves their stand-ins out of its values). The resolver gives a block statement's memo what the statements inside it reported and read, in the order they reported it. On the Raffles and Bunny project that is every statement of the `then` clause at line 2449 but the one an edit rebuilds.

A loop (`while`, `for`, `for ... in`, `repeat`) and a `choose` block written in a body are block statements served the same way, with the statements of their bodies (#1683). What the story's passes still read of their own objects, now that #705 deleted the code generation that linked a weave by runtime containers, is the labels the flow's weave names and the story counts among its declared names, the locals the flow declares (`FlowBase.variableDeclarations`, which a later statement's lookup of a name reads), the census of the flow's names, and the names `canonicalizeSyntheticFlowNames` numbers; none of them reaches the program, whose chunk for a loop names none of its labels (`isLoopInternal`) and gives each hidden temporary a name of the chunk's own. So the memo holds those parts (`MemoHolder`): for a loop, each label, local and local's assignment its lowering made for itself (`recordLoop` marks them), and for a `choose` block, each named choice and its labelled `then` clause, with where each stood relative to the statement. A served block statement's stand-in holds an object of each part's class (a holder), holding nothing, never generated or resolved as itself, among the stand-ins of the statements inside it: a name made from the loop's place where the compile's numbering first meets it (before a statement inside the loop, inside one, as a `break` names the loop's exit before the loop's own objects do, or after them all), and any other part where its object stood, which is the order the story names a block's labels in; a loop's holders and everything inside the loop stand in a scope of the loop's own, so a local declared inside it is in scope after it for no statement, as with the loop's objects, and such a loop is served whatever its body declares (an `if` block or a `choose` block whose bodies declare a local is still lowered). The stand-in declares the loop's locals again where the loop's generation declares them (`repeatMemo`). A loop's names are made from its place in the document (`syntheticId`: the document's tag, `$`, then the place), so the memo holds each as its text around the place and the place's distance from the statement's start, and the holder is named as the loop's lowering names it where the loop stands now: the compile gives each name of a served loop the number a cold compile gives it, and so every other statement's names too (`programStatementMemo.test.ts` compares the number of every name a lowering made from its place with a cold compile's). The names the program path's resolver read that the statement holds as a loop's own are left out of its memo's reads, since its syntax decides them. A lowering's reads record such a name with its place counted from the reading statement's start, as they record a read of the document outside the statement (`recordLowering`), so a `break` that reads the label its loop pushed onto `loopStack` keeps its memo when an edit above moves the loop and the `break` together; and a read of an array's length after the lowering itself pushed onto it is recorded as the length before, which is its input (a `for` loop pushes a block onto `blockEndStack` and then reads the stack's top). A served `choose` block keeps its chunk, with the count symbols of its choices, as the store keeps any chunk (`ChunkInfo.choices`), and hands them on when the block is lowered again. A loop or a `choose` block whose own objects hold any other name the compile numbers (a method call's receiver, a function written as a value), a choice's divert, a tunnel return or an author warning, or whose chunk writes a function or an alternator, is still lowered whenever its block is.

The resolver repeats a served statement's generation and resolution where it stands (`ResolutionTap.memo`), in the story's order: it reports again what the memo recorded, at the statement's current position, and adds the names it read to the record of the statement whose objects hold it, which is then resolved again when one of them is declared otherwise. A served statement reads otherwise by the rule a carried statement is resolved again by: a name it read is declared otherwise, any name is for a lookup that read every name (`*`), a constant's validity changing reads otherwise for its readers and for those that read the globals whole, and the flows around it changed. Such a memo is stale (`ProgramResolver.staleMemosLastResolve`). A compile that meets a statement it cannot compile without its objects, a stale memo, a chunk the store would not keep (`ChunkStore.memosKept`) stops (`StatementMemoRetry`): the compiler marks those memos stale, lowers again the blocks that hold them (`SparkdownCombinedAnnotator.relowerCompilations`) and compiles again (`SparkdownCompiler.compileStory`), at most twice, the second time serving no memo in those blocks. An attempt that stops puts back what it recorded for the next compile (the declared-name census, the flow signatures, the root blocks, the switches that refuse construction reuse) and the parents of the containers it took for reuse, so that the attempt after it compares with the compile before, as the first did; and the store's statement watch keeps the marks of every attempt, since the resolver resolved, in the first, the statements whose names the edit declared otherwise, and does not resolve them again in the next. Neither the memos nor the compiler's bookkeeping of them keeps a parsed object past the compile: `programStatementMemo.test.ts` takes weak references to every parsed object a block's lowering holds, lowers the block again and finds none after a forced collection. Nor does anything else of the compiler or the store keep a parsed object an earlier compile's story held that this compile's story does not (#1675): a divert the resolver keeps resolved while its statement is carried held the target the resolve that resolved it found, a flow every compile assembles anew, and through it that compile's objects of the flow's statements, so after each resolve the resolver moves each such target onto the object that stands for it in this compile's story, a flow by its path, read through the story's tables without recording a read, anything else by the divert's own path (`ProgramResolver.retarget`); the target is the same one by name, so what the store and the statement watch read of it reads the same. Criterion 2 of #656 is read as: nothing the memo holds, and nothing reachable from the chunk store or the compiler through the memo, is a parsed object of an earlier compile; a top-level block the annotator carried whole is the chunk mechanism #656 leaves out ("changing what a chunk is for the annotator"), whose parsed objects stand in this compile's story too. Retiring that carry is #1684. `programStatementMemo.test.ts` walks every compile's parsed story over two scenes, the first diverting to the second, whose clause is edited twice, and finds nothing an earlier story held reachable after the last compile but what the last story holds.

### The write barrier

Section 7's barrier marks, while `VariablesState.trackWrites` is set, every table written in place and every closed upvalue cell written through a closure, and `TakeWrites` hands the marked ones over and clears the marks (`VariablesState.WriteBarrier`, `CellWriteBarrier`). The writes are the engines' shared ones: `StoreIndex` and a `__newindex` that stores on a table (`storeIndex`, `Story.ts`), a builtin iterator's step, which keeps its cursor in its table, a `#` that leaves a new length hint, and every builtin that changes a table in place or changes what a table is, `table.insert`, `table.remove`, `table.sort`, `table.clear`, `table.move`, `table.freeze`, `rawset`, `setmetatable`, `__def`, `__defs` and the links and defaults the struct builtins keep on their tables, and `display` when it joins a table's parts or drops the `continues` of a line that joins nothing, each marking the table once per call; an assignment to a variable whose frame is gone marks its cell. Each of them calls the barrier before it writes, so that an image can keep a table's content from before its first write; a `#`, which learns only after it runs whether it left a new hint, and `display`, which learns only after it joins whether it joined anything, keep the table first (`PrepareTableWrite`) and mark it after. A global assignment marks the global's name (`VariablesState.imageBarrier`), and a cell is marked before every change of its state, a closure's write, its closing when its scope or frame ends or its thread does, and its reopening when a taken choice's thread binds it again (`CallStack.cellBarrier`).

### State and saves

An image (`ProgramImages`) copies the positional state whole: the position, the eval stack, the output with its line end and what a cut carried, the turn, the seed and the previous random draw, `previousFlow`, and every thread's frames with their temporaries scope by scope, the cells open on each frame and those it borrowed, the program frame beside each with the position it returns to and its function, where a suspended thread resumes, and each waiting choice with its thread. A position is a chunk id, its entry and offset and its sequence id; the blocks it is inside follow from its sequence and are not copied, and a frame's scopes are copied as they stand with the temporaries they hold; their number is the depth the frame's position derives (section 1), inside a choice's entry or body too (section 4, #1575). The keyed state is the counts, the globals, the tables and the closed cells: a keyframe copies the counts and globals whole and the written tables and cells the state reaches, and a delta on the image before it holds the count ids, global names, tables and cells the barrier marked since. A chain takes a keyframe after 64 deltas, so neither a restore nor a digest walks a longer one. A keyframe keeps nothing before it alive: it holds the image it was taken on weakly, with the keys written between them, so an image a caller let go of is collected and one a caller still holds restores across the keyframe at the cost of the changes between them. The first time the barrier hears of a table or a cell, `ProgramImages` keeps its pristine copy, held weakly, and it is shared by the engines of one game (`Game.updateProgram` hands it to the next program's engine). Restoring an image restores in place, so identity is kept and nothing is relinked. When the state and the image meet on one chain (the state's last image is the image or descends from it, or both descend from one image, across keyframes the run took since while something holds the images between), only the keys the images between them wrote and what was marked since are given the image's values, from the newest copy on the image's chain, or a table's or a cell's pristine copy; otherwise every table and cell ever written, every global and every count is. A load keeps the pristine copy of each table and cell the program initialized before it restores saved content into it, so an image taken before a load restores after it, and a durable load that fails past placement puts back the state as it stood, a line in progress included, and one that succeeds ends the line in progress. A restore that names a chunk or a sequence the root does not hold translates the position through its saved form in the root it was taken in (#1429, below), and returns false and changes nothing when that places nothing, so a checkpoint taken before a compile restores after it and a caller replays only what cannot be placed; chunk ids are never given again, not across a reseed either, and a count id of an older table generation is taken through the reseeds' remaps.

`ProgramStory.capture` takes an image, `restore` restores one, and with `keepBeatImages` set a continue that starts a line keeps the image of the beat before it, which `captureBeat` gives while the continue that followed it ended with choices raised: a menu, captioned or not, is the image of the beat before it and holds none of its choices, and restoring it runs the continue that raises them again, their conditions with them. A continue that ended at its newline, or with the flow ended and no choice waiting, and a choice taken, leave the state as it stands as the beat's image. A route search node holds an image (`planRoute`, `SearchNode.state`): a fork is a delta on the image its run started from, siblings share it, and the fork site is claimed by a digest of the state the image holds (`imageDigest`), which reads the positional state and the keyed state where it differs from the keyframe's, a table or cell the keyframe's state reached by its identity and one made since by its content as the image holds it, where the state first reaches it, with a second reference read as a reference, as the JSON's `objref` did, and a table's keys in their order, since `next` and `pairs` read them so; neither the order of the writes nor that of the allocations changes what it reads. The JSON round trip stays for the current engine and for `stateImages: false`. The engine runs on through a decision the route simulator forces, asked by the decision's address. A game on the program engine checkpoints its beats as images (`CheckpointStore`): a keyframe every `baseInterval` beats and deltas between, beside the module state and the runtime collections; the executed positions, choices and conditions grow with every beat run, so no entry holds them whole: each entry, a keyframe too, holds their changes since the entry before, a checkpoint's collections are those changes replayed from the start of their chain, and a keyframe starts a chain of its own, whole, only when the live collections differ from that replay (#1694), so the store grows with the beats and not with their square; with the full save of a checkpoint written from its image when a caller asks for one, and none for an image the story cannot place even through its saved form, which the caller replays to; `Game.restoreCheckpoint` restores one in place. `t:random()` picks by the story's draw (`drawStoryRandom`), as `math.random` and a shuffle do.

A save (`ProgramSave`, `ProgramStory.toSave`, `loadSave`, and a game's `save` and `load` on the program engine) holds the last `saveHistory` beats of the story's history (`BeatHistory`, below), the newest the current beat, the beat before a menu when choices are waiting, or that beat with the choice taken at it when a choice was just made (`chosen`, which a load takes again). The oldest beat is written whole as the state's JSON (`ProgramStoryState.writeHead`, every global but a constant, those equal to the initial value included so that a release that changes an initial value still reads the beat's, `writeTail`, the counts), and so is the save's keyframe whatever keyframes the images had, which is never larger than the oldest keyframe the beats need; each beat after it is its positional state and what changed since the beat before: the globals whose value differs, the counts, each table and cell the save wrote before that changed since, whole again under its `objid` (`JsonSerialisation.WriteTableDefinition`), and a table or cell first met in the beat whole where it is met, compared by their content, an unambiguous JSON signature of each, rather than by the images' marks, so a beat's delta does not depend on which images the run took. A load opens one registry of `objid`s for every beat, reads the oldest whole, replays each delta onto it in place through the write barrier (`RedefineLoadSessionTable`), its globals, counts, tables and cells before its frames, so that the cuts of a placement close the cells of the scopes they drop on the beat's own values, a global the program now declares a constant, and a cell a constant reaches, keeping the compiled value in every beat as `SetJsonToken` keeps it in the oldest (each reading the saved value still, for the tables and cells it defines that other values of the save share), and a define's `store` field the delta no longer holds taken out of the table, and takes an image of each placed beat up to the one it restores, which seed the history, so a save taken after a load holds the same beats; a beat that is not placed is read only for the tables and cells it defines (`ReadDefinitions`). Each beat carries its flags and the decisions taken at it, each chosen choice in the saved form of its `Choice`. A position is written as the chain of levels from the flow, by its qualified name, or a script's declaration sequence, by its uri, each level the index of a listing and the entry's ordinal, a body's level the part of its owner that heads it, by kind and ordinal in the owner's part listing (`chunkParts` records, as the chunk store emits a chunk, every part with the fingerprint `alignParts` aligns it by and the block it heads: its functions, alternators, choices, and the parts that head its other bodies), and for a loop's body the owner's layout hash; the listings, written once per sequence the save names, with its length and the merged windows of fingerprints, and the part listings, once per owner and kind, as part fingerprints; and the anchor, the statement's start, the sequence's end, the end of the statement's code (`done`, where a call that is the statement's last instruction returns, which needs no layout since the statement has run), after or at the break of a body by its part, a choice's entry by its part, or an offset with the statement's layout hash. A frame names its function and the layout hash of the chunk that bound its parameters (`bindingLayout`): a function's definition, or for a tunnel's frame the entry of its scene or branch (`FlowEntry`, #1436), `none` for one that binds nothing, a named symbol its qualified name, an anonymous one its statement, the part's kind and ordinal and the part listing, and a count its symbol. The header names the format's version (2), the engine's and `GameConfiguration.version`; a save of format 1 (#699, one beat, a body named by its block and an anonymous symbol by its part's hash alone) loads through its migration, and `fixtures/program-save-v1.json` and `-v2.json` stay in the tests.

The loader (`FormPlacer`) places a statement by the steps of section 8: the flow by its name; each level by the matching blocks of its window and the sequence the program has now (`difflib`'s longest-match recursion, with no junk heuristic); a statement no block matched by its own neighbourhood, eight fingerprints each side, in every sequence of the root, through an index of fingerprints kept per root and per sequence's arrays; and one still left by its neighbours, in the run between two blocks, or a block and an end of the sequence when the window reaches it. A body is placed by aligning the saved part listing with the owner's parts as a re-emit does, which places a body whose choice was edited, or whose `if` condition was, or whose function's header was (a function declared at the top level is the one part of its definition, which the third pass pairs). A statement found by its neighbourhood under another flow renames the save's names (`settleRenames`), and the renames rewrite count keys, function values, frames' functions, anonymous-symbol forms and each `previousFlow`: every beat up to the one loaded is placed, every position of it whatever frames are dropped, and when that finds a rename the beats are placed again under it, so a flow that only an older beat, or only a dropped frame's position, stands in still renames what the save holds. Then the anchor and the layout: an offset whose statement's layout differs places the frame after the statement, and a body position under a loop whose layout differs, or that the placement put in a loop the save names no layout for, after the outermost such loop on the frame's block stack, since a frame after an inner loop is still inside the outer one whose temporaries it holds. A frame whose function cannot be placed, or binds its parameters in other code, is dropped with every frame above it, its open cells closed, and the frame below resumes after the statement that called it. A frame placed after a statement or loop has its scopes cut to the depth the new position has (`scopeDepthAt`), the upvalues of the dropped scopes closed as `EndScope` closes them; the frame it called runs to its return, which drops what it returns and cuts the eval stack to the caller's height (`ProgramFrame.dropResult`), and at the top of the current thread the stack is cut at the load. That height is a frame's at every statement boundary: the engine records it when a function's body is entered, once the entry has bound the parameters, and for a tunnel's frame at the push, less what the flow's entry binds. A cut is the placement's, not the run's: once a beat's image is taken, the cells its cuts closed are put back as the save holds them, so a later beat that still holds one open closes it on its own value. A choice whose part cannot be placed is dropped with a warning. A beat whose every frame is placed, exactly or with a warning, is placed; an edited statement paired by its neighbours counts as exact, a placement after a construct or a dropped frame or choice does not. The loader takes the newest exact beat, or else the newest placed, and refuses a save with none, naming the newest beat's flow; `loadedSaveReport` says which beat, whether it was exact and what was warned of. A save taken after a choice runs the continue that raises the menu again and takes the choice whose `Choice` its part places, and stays at the menu, reported unplaced, when the part is gone or the menu no longer offers it. A function value that cannot be placed loads as one that names nothing, which raises the engine's error when it is called and is saved again as one that names nothing (`gone`). The fingerprint (`normalizeSource`) drops comments and the spacing between tokens in a line of logic, one that starts with `&`, with `--` or with a keyword of the logic, keeping one space only where dropping it would join two tokens into others (two words, or `- -` against `--`), and keeps a string, a long string's lines included, and a regex literal (`@/ /`) as written; in any other line, a displayed one, it drops a `//` comment only when nothing before it outside the line's interpolations is markup whose text a `//` may be part of (a raw span, styling, an escape, a parenthetical, a tag, a command, an alternator, a break: any character but a letter, a digit, whitespace or plain punctuation), and otherwise keeps the line, comment and all, so an edit to such a comment places the statement as an edited one; it reads the comment outside the line's interpolations (`{...}`, which are Luau, where `//` is an operator, and a string, a long string, a block comment or a regex literal is read whole, braces and `//` included, a template string's interpolations and those of a `"` string with it, as the grammar nests them) and leaves the text as written. The statement is read as one text: a token that runs past its line (a long string, a block comment, a string continued by `\z` or by an escaped line end, an interpolation) takes the lines it runs over, as written, so a `--` or `//` that starts one of them is no comment. Every line of a statement whose first line is logic, but for a menu (`choose`, whose choices are displayed lines), is logic, so a field of a `define`'s body or a line a table literal runs on, which start with neither mark, read as the logic they are, `//` there floor division or a string's text. Format 1 hashed its fingerprints before this, so a format 1 save's statements are placed as edited ones, its blocks by index and its parts by ordinal where their hashes differ.

The story keeps the beats it passed (`BeatHistory`, `ProgramStory.beats`), the last `rewindBeats` of them (`GameConfiguration.rewindBeats`, 128), when `keepBeatImages` is set: a continue that ends at its newline records the image of its beat with the waited flag, which the next continue's image of the same beat replaces, so a host's writes between continues belong to the beat; a continue that starts from a state no beat holds (the start, a choice taken) records that state with no flag; and a choice taken records its `Choice`'s address beside the beat before its menu. Each record's image names it (`ProgramImage.beat`), `setBeatFlags` sets the current beat's flags, and the engines of one game share the history as they share their images, so a game's checkpoint images are its records. Restoring an image rewinds to it and forgets the records taken after it: the record of its beat is kept with its flags, and holds the image again when the next continue took the beat once more after the host wrote to it, and for an image no record holds (taken after a choice, or in a playthrough a reset or another rewind left) the records taken before it are kept, since the records are one line of play in the order images are taken and a forgotten record never returns. `ResetState` starts a fresh playthrough, whose history starts empty; an engine built for a new program keeps the history the engine before it hands on. `RANDOM` is not a builtin of the language, so the draws a restored beat repeats are `math.random`'s, a shuffle's and `table:random()`'s.

A checkpoint's full save (`saveOfImage`, which `CheckpointStore` asks for) is that one beat, as before, with the flags and decisions of its beat's record even once the history no longer holds that record (`ProgramImage.beat`; each record names the root its decisions are in, `BeatRecord.root`), and a continue from a restore of such an image takes its beat into the history again with them (an image `captureBeat` takes of the state a restore left, until a step moves the story on, is that same beat however it was taken, a keyframe, after the host wrote to the state or by the engine of another program, and takes the place of its record's image when that record is the history's newest; `setBeatFlags` then sets that beat's flags; and in ordinary play the same holds for the beat the engine's last continue ended, whose record the next continue takes again; an engine a history was handed to stands at no beat of it until it restores one or ends its own, and neither its saves, its continues nor its `setBeatFlags` touch the record another engine ended; a load stands at its loaded beat, a state loaded in place at none, and a host's function evaluation takes no beat and leaves the story at the one it stood at), and for an image `captureBeat` took just after a choice (`ProgramImage.afterChoice`) the beat before its menu with the choice, as `toSave` writes one, so a load of it raises the menu and is unplaced when the choice is not offered; a restore of that image within a session is the state after the choice, as the store took it, and a `toSave` before the next continue writes it as `saveOfImage` does, the menu's beat with the choice; `toSave`, and `saveOfImage` asked `withHistory`, write the history. Within a session, an image whose position names a chunk the new root does not hold is translated (`translatePositional`): each such position is written in the saved form of the root the image was taken in, which the image's engine holds, windows and part listings included, and placed in the new root by the same steps, with the cuts they make; a frame symbol and `previousFlow` of an older table generation go through the reseeds' remaps, and a waiting choice takes the address of the `Choice` its part places, as does the choice a checkpoint taken just after it names, when it is restored or exported (`translateChoiceAddress`), and each decision of the history an engine hands to the engine of the next program (`BeatHistory.translateTo`), a decision whose choice the new root no longer holds forgotten. `canRestore` and `restore` place an image so, and an image that still cannot be placed restores nothing. Route resumption does not (`Game.readResumePoint` passes `translate: false`): the steps after a checkpoint are judged by their addresses, so it resumes only from one whose positions the new root holds as they are, as #700 built it, and `restoreCheckpoint` and a rewind translate. A line in progress, which a stop at a breakpoint or at the execution step ceiling leaves between the steps of an asynchronous continue, refuses neither save (#1693): `saveOfImage` writes the image it is given, and `toSave` the image of the beat the line started from, which a story that keeps beat images holds (one that does not still refuses), and each puts the state back as it stood, the line still in progress, as a route search restores between steps. `saveOfImage`, and `toSave` with a line in progress, refuse only a call from inside a continue; `toSave` with no line in progress keeps its guard against an asynchronous continue.

### Where it runs

`Game` builds a `ProgramStory` from the program's chunks (`updateProgram`, which refuses a program with none), so the editor's preview, PLAY, the VS Code game webview and the player app run the program engine; since #705 it is the only engine. A line table row whose range takes its last line's break ends with the line before, as the current engine's locations did. The game reads its positions through addresses (Addresses, below): it enters the scene an address stands in, routes to and jumps to addresses, and places a runtime error at the address of the step that raised it. The debugger reads the engine's frames view (`ProgramStory.debugFrames`, #702): each call frame's symbol and name, the address it stands at (the frame running at the instruction that ran last, a frame below at the call that pushed the one above, and after a load, which keeps no last instruction, where the runtime record last ran) and the call stack element whose scopes hold its temporaries, whose scope a data breakpoint names by the frame's name. A line or function breakpoint is a set of addresses (`programBreakpoints.ts`): a line's from `addressAt` with `functions` (a line of the declarations is refused, since they run before a debugger can stop the story), and a function's where its code starts: a function declared at the top level found by its name, and one written inside a statement (a `local function` in a function's body), whose symbol is anonymous, as the innermost function whose entry spans the position its name is declared at (`functionLocations`), since the functions enclosing it, which can start on the same line, span it too. The engine calls no hook per step: the game installs no `onExecute` on it, and gives it a log (`executedLog`) for the length of each step, to which the step appends the address of each instruction it runs, a Luau callback's among them; the game records them in the executed-line record and stops when the set holds one, so with no breakpoint set a step builds no string and calls nothing. A function a host calls between steps (`EvaluateFunction`, a UI handler's) runs with no log and is not recorded. A data breakpoint watches its variable rather than the instructions that name it, since a temporary can shadow a global of the same name: a global, or a temporary of the frame its scope names, and the game stops after a step that wrote another value to it. The engine says which binding a write reached (#1664): while a data breakpoint is set, the game installs a write watch on the story's variables for the length of each step (`VariablesState.writeWatch`), which every assignment to a variable already bound reports with its binding, the block scope that holds a temporary, the closed upvalue cell of a captured variable whose frame is gone, or the globals, and the variable's name there. A declaration binds a new variable and is not reported. Between steps the game notes where the watched variable is bound: a global by its name, a temporary in the block scope it was found in, so an inner block's temporary of the same name is not it, and through a pointer (a variable passed by reference, or one a closure captured) where the pointer leads (`VariablesState.BindingOf`, which follows it as `Assign` does). A variable a closure captured outlives the closure's frame, so while no frame named by the scope runs, the watch follows the pointer that frame held, and a later call of the same closure (a builtin's callback, which runs and returns within one step) writes the variable watched; another closure of the function captures a variable of its own. A load reads the cells of captured variables anew, under the ids the save gave them, so a save written while such a watch holds its cell notes, beside the story, the breakpoint's data id, the id the story's save gave that cell (`SaveData.watchedCells`, which the story save hands the game through `ProgramStoryState.cellsWritten`) and a tag the game gives the cell, and a load binds the watch to the cell it read under that id (`cellsRead`, #1719) when the watch still holds the cell the tag names, and gives the loaded cell the tag, so a second load of the save finds it too; a builtin's call of the closure right after the load stops on its write. A data id names a scope and a variable, not one closure's cell, so a watch of the same data id that has since bound another closure's cell (a frame of that closure ran between steps) is not the watch the save noted. The story's save format is unchanged, and a save written with no such watch carries no note. A watch the save does not name, set after the save was written or on a cell the save does not hold, drops the pointer and holds no binding until a frame named by its scope runs between steps, since nothing a save holds says which loaded cell is the variable watched. A step that reported a write to that binding and left another value object in it stops the game. So a temporary declared again, in its own block, an inner one or another invocation of its function (a recursive call within one builtin step, such as a `table.sort` comparator's), is not taken for a write, and a write through a closure to the watched invocation's temporary is. With no data breakpoint the field is null, and an assignment tests it and calls nothing. The lines offered for a breakpoint are the first lines of the rows of the line tables of the script's flows, bodies and functions and the headers of its scenes and branches, which for a script of beats are the current engine's; the current engine places a statement of logic in a scene on the scene's header, which the program engine places on its own line. A step in, over or out runs until it stops, and announces where, as the debugger's one request waits for. The breakpoints set last are resolved again for each program the game is given. The UI module's event handlers and reactive bindings reach their functions through `HasFunction` and `EvaluateFunction`, and `buildDefinesContext` reads the `__def` tables the declaration chunks build. The engine calls the execution watch (#679) on the steps the current engine called it on, Luau callbacks' steps included, so the worker hears a loop that does not end, and its notice names the location of the story's last step (`Game.storyLocation`). ### Addresses

Everything outside the engine and the compiler reaches a position through one accessor (`ProgramLocator`, `programLocator(program)`): `addressAt(uri, line)`, `locationOf(address)` and `sceneAt(address)`, the scene an address stands in, which is the flow a route to it starts at. The root answers (`ProgramRoot.addressAt`, `locationOf`, `sceneAt`) and an address is a number; a program the compile made no root for answers nothing. `addressAt` finds the flow whose lines hold the line, the statement by its line starts, the body that holds it and so on inward, and reads that statement's line table: of the rows on the line, a row that holds a `LineStart` names a beat by its offset, so the lines of one beat (a cue, a directive, the dialogue) give one address; a line on no beat's row gives the statement's start on its first line and otherwise the part whose row covers the fewest lines (an `elseif` condition, a later choice's entry, a `then` clause's label). Several statements on one line (a `..` continuation and its tags) give the first one's for the first beat and the last one's for the last. A line no row covers (a blank line, a comment, a scene's header, a line of a function's body unless `functions` is asked for) gives the address of the first line below it that has one, as the path table answered. A `then` clause whose gather the parse gave no range has a row over the line that heads it, anchored to the body above.

No body's row holds its first line: `SequenceRow.firstLine` is a flow's or a declaration sequence's, -1 for a body, and the root derives a body's from its owner (`firstLineOf`), so the chunk store keeps the previous root's row whenever it says the same (`ChunkStore.setRow`, #701), and an edit above a body or inside a body beside it leaves the body's arrays and row the same objects while `locationOf` of its addresses moves with the lines inserted. Chunk ids start at 1, so no address is 0.

`ProgramStory` names the instruction that ran last (`previousAddress`, kept in an image and the session JSON, not in a save), the one that runs next (`currentAddress`) and the positions it will come back to (`stackAddresses`), hears `onExecute(address)` for every instruction but the declarations', and moves to an address (`ChooseAddress`); `ChoosePathString` takes a flow's or a label's name. The game keeps its start, preview and executing positions, its recency set of executed positions and its scene tracking as addresses (`StoryPositions`). A save, and a checkpoint's full save, writes the recency set's addresses in a durable form (`durableAddress`): the levels from the flow or the script's declaration sequence down to the statement, its fingerprint and the offset. Loading places each in the program it loads into (`placeDurableAddress`) and drops one it cannot place, since a chunk id names a statement only in the process that gave it. The game's execution report carries `simulateFlow`, the failed route's locations and `lastExecutedAddress`, with no path. The language server answers previous and next beat and, for a client that holds no program, `sparkdown/addressAt` and `sparkdown/locationOf`. A compile builds no path-location table and runs neither `populateLocations` nor `sortPathLocations`, and reads its scene assets from its chunks (`captureProgramAssets`), each beat under its `LineStart`'s address.

The route planner knows a step by its address, folded into the step's identity, and keeps to its scene by the scene of the sequence the story stands in. A compile that built chunks stamps what changed in them on its change summary (`ProgramChangeSummary.chunks`, `rootChanges`): the chunks of the root measured against that its root no longer holds, the chunks it emitted, the symbols whose definition moved, and whether a declaration or function chunk was among them, a chunk both roots hold moved into a function or out of one, or the declarations run in another order (`initializers`). A route replayed in one program resumes in the next from the steps whose chunks the new root holds and whose moves between chunks it still makes, from a statement to the next in its sequence, into a sequence at its first entry and out of one from its last (`validAddressPrefixLength`), and, for a step at the top of a branch, whose scene may have entered it by its start binding, while the scene still starts at that branch; a compile with `initializers` keeps no step, and the route replays from the top with the new initial state. The replay restores a checkpoint's image in place. A beat's image rests at the start of the statement after the beat, and an image holds the chunk before such a position (`PositionCopy.after`) and is placed after it while the new root holds both, so a statement inserted there, or appended to the sequence, runs; an image whose next statement was emitted again stays unplaced, as any position on a chunk the root no longer holds does, since the replay restores without translation (`Game.readResumePoint` passes `translate: false`; section 8, Within a session, translates for `restoreCheckpoint` and a rewind), and the game resumes from an earlier checkpoint. A checkpoint whose next step the new program takes some other way, and that rests anywhere else, is not resumed from. The search keeps no beat images, and a table the engine made since its last image is not kept as written until it is written after one, since no earlier image reaches it.

## The bypass profile

#692 deferred lowering from the Lezer tree straight to program chunks, with no parsed object between them, to a profile taken once the current engine was gone (#705). This is that profile (#1712), taken at 14cb575f7: the object engine deleted, statements served from the statement memo inside blocks, loops and nested `choose` blocks included (#656, #1683), the resolver per statement (#1607), and the parsed-flow reuse kept. The recommendation below is the maintainer's to accept.

### How it was measured

```bash
node scripts/bench/preview-bench.mjs --project <Raffles and Bunny project> --line 3515 --word concerned --mode edit --samples 12 [--no-flow-reuse]
node scripts/bench/preview-bench.mjs --project <Raffles and Bunny project> --line 1159 --word panicking --mode edit --samples 12 [--no-flow-reuse]
node scripts/bench/preview-bench.mjs --project <Raffles and Bunny project> --mode cold --samples 10 --warmup 2
node scripts/bench/preview-bench.mjs --fixture --mode edit --samples 12 [--no-flow-reuse]
node scripts/bench/preview-bench.mjs --fixture --mode cold --samples 10 --warmup 2
```

Each configuration ran once per round, in that order, in three rounds in one sitting on 2026-10-09 (an Intel i9-13900HX, Windows 10, Node 24.18.0), 4 warm-up samples before the edits' 12; the figures are the medians of the three rounds' medians, in milliseconds. `--mode cold` compiles the project on a compiler of its own for each sample, with no game (the builtins prelude's context is cached by the module, as in a worker, so only the warm-up builds it); `--no-flow-reuse` sets `_disableFlowReuseNextCompile` before every compile. The fixture is the one `scripts/bench/preview-fixture.mjs` writes, edited at its own target line.

The attribution comes from the same commands with `--samples 30` (cold: `--samples 6 --warmup 2`) and `--cpu-prof <dir>`, read with

```bash
node scripts/bench/profile-shares.mjs <dir>/<mode>.cpuprofile --under <function> --windows --by-path --groups scripts/bench/profile-groups.mjs:BYPASS
```

for `updateSyntaxTree` (`incrementalParse`, `fullParse`), `lowerTopLevel` (the lowering inside it), `parseIncrementally` (`ink/parse`), `canonicalizeSyntheticFlowNames`, `resolve` (`program/resolve`) and `buildProgramChunks` (`program/chunks`). `--windows` counts only the profiler samples taken during the benchmark's measured samples, and `--by-path` names each function by its source path, which the `BYPASS` groups match by directory: the parsed hierarchy (`inkjs/compiler/Parser/ParsedHierarchy`, the weave apart and the memo's `Memoized*` stand-ins counted with the memo), the lowerers (`compiler/lower`), `SparkdownCompiler.ts`, `ProgramResolver.ts`, the rest of `program/` (the writer, emitter, chunk store and root), the grammar and Lezer, and the rest. A profiled bundle keeps names and runs slower, so each group's share of a phase is applied to that phase's unprofiled median. Self time only: "assemble" is `SparkdownCompiler.ts` and the parsed classes under `parseIncrementally` outside the parse, which holds the flow reuse's scan and the statement records as well as the assembly, so it bounds the assembly from above. `--under` matches a bare function name; within the measured samples, `resolve` is `ProgramResolver.resolve` (3.5 profiled ms per sample at line 3515, against the phase's 3.0).

Each row of the tables below is a group's profiled milliseconds per sample (`underMsPerSample` times the group's share, from `--json`) scaled by the phase's unprofiled median over its profiled total:

- construct: the two parsed-hierarchy groups under `lowerTopLevel`, scaled by `incrementalParse` (cold: `fullParse`) over the time under `updateSyntaxTree`;
- assemble: `SparkdownCompiler.ts` and the two parsed-hierarchy groups under `parseIncrementally`, scaled by `ink/parse` over the time under it (cold: less what each of them, and the phases, take under `updateSyntaxTree`);
- prepare and resolve: the parsed-hierarchy groups under `resolve`, by `program/resolve`; writing: those under `buildProgramChunks`, by `program/chunks`; numbering: the `ink/canonicalizeSyntheticNames` median itself;
- the lowerers' own code and the statement memo: their groups under `lowerTopLevel` (on an edit, the memo under `updateSyntaxTree`), by the parse; the resolver and the writer: their groups under `resolve` and `buildProgramChunks`, by their phases.

### What the parsed objects hold

```bash
node scripts/bench/preview-bench.mjs --project <Raffles and Bunny project> --line 3515 --word concerned --mode edit --samples 12 --heap-probe <file>
node scripts/bench/preview-bench.mjs --project <Raffles and Bunny project> --mode cold --samples 2 --warmup 1 --heap-probe <file>

The carry is bounded: over 200 edits at line 3515 (`--samples 200`), the heap after full collections read 166.1 MB after the first, 169.3, 169.9, 170.0 and 170.6 MB after every 50th and 170.3 MB after the last.

The probe of #1684 (comment 6072116784), re-created on this base in `programStatementMemo.test.ts` and not committed: four compiles of two scenes, the first diverting to the second, whose `then` clause is edited twice. Their stories hold 1,107, 1,107, 389 and 600 parsed objects; after a forced collection 251 distinct objects of the first three are alive, every one held by the last story through the top-level blocks the annotator carried (the 753 #1684 recorded counts each of them once for each earlier story that held it). The existing test "of an earlier compile is reachable after a compile, but the objects this compile's story holds" passes: nothing but the last story keeps an earlier compile's object, so no generation is kept per edit.

### What a bypass would rewrite

Counted at 14cb575f7 under `packages/sparkdown/src` with `find`, `wc -l` and `grep`: a file constructs parsed objects when `grep -E "new (<class>|...)\("` finds one of the 66 classes an `export class` or `export abstract class` in `ParsedHierarchy` declares. The sizes of the services are line spans of their methods.

- `compiler/lower`: 80 files, 20,499 lines (`lowerers/` 37 files and 9,519 lines, `expression/` 4 and 1,984, `utils/` 35 and 5,886, and `context.ts`, `lower.ts`, `recordingContext.ts`, `statementMemo.ts`). 39 files construct parsed objects, 50 distinct classes of them. Of the 41 that construct none, 27 (3,208 lines, mostly validators and source helpers) mention no `ParsedHierarchy` import, `ParsedObject`, `instanceof` or helper that builds a parsed object (`buildDivert`, `wrapIn*`, `buildSparkleBody`, `lowerDivertPath`) and would stay as they are; the other 14 (`context.ts`, `lower.ts`, `recordingContext.ts` and `statementShape.ts` among them) handle parsed objects through those.
- `ParsedHierarchy`: 67 files, 9,219 lines. The writer emits through the parsed classes: `BinaryProgramWriter.emitObject` calls `EmitProgram` (27 classes) and expressions `EmitExpression` (19 classes), 514 lines of code generation in 42 files, all of which would move to emitters the lowerers call; the chunk store and `programFlows.ts` (1,285 lines) read 12 and 13 parsed classes by `instanceof`.
- The services the hierarchy gives the compile, each of which needs a replacement that works on chunks or syntax: reference resolution (`ResolveWith` in 23 classes and the divert checks beside it, about 1,040 lines, with `FlowBase.ResolveVariableWithName` and scope lookups, and `ProgramResolver.ts`, 2,522 lines, whose units are parsed objects); naming collisions (`Story.CheckForNamingCollisions` and the flows' own checks, about 455 lines); the weave's gather and choice linking and weave point naming (`Weave.ts`, 282 lines, `FlowBase.SplitWeaveAndSubFlowContent`, and the assembly in `SparkdownCompiler.parseIncrementally`, 1,057 lines); synthetic-name numbering (`canonicalizeSyntheticFlowNames`, 298 lines, and `syntheticNameFields.ts`, which the memo reads too); the `Prepare` passes (35 overrides, 250 lines, and 20 `PrepareIntoContainer`, 132 lines); and the story's tables, globals and locals (`Story.DeclareStoryTables` and its neighbours, about 340 lines, `FlowBase.variableDeclarations`).
- The statement memo's stand-ins (`MemoizedStatement`, `MemoizedDivert`, `MemoizedAssignment`, `MemoizedGather` and the holders of #1683) are parsed objects, and the parsed-flow reuse (about 540 lines of `SparkdownCompiler.ts`) hands parsed flows on, so both would be redesigned with it.

#692 estimated 61 lowerer files and 15,171 lines; the lowering has grown since, by #656's memo and #1683's holders among others.

### Recommendation

Keep the parsed hierarchy, and do not plan a bypass, now or after preparatory tasks. On an edit the parsed objects cost 6.5 ms of the compile's 45 to 49 ms of phases on the project and 3.2 of 23.3 on the fixture, nearly all of it assembling the story, which a bypass would still do for the program's flows, weaves and names in another form; constructing them while lowering does not register (under 0.05 profiled ms). A cold compile spends 5.6% on them (126 of 2,238 ms) and 7% on the lowerers' own code, which a bypass rewrites rather than removes. What they hold is 33 to 37 MB of the project's 214 to 247 MB, bounded across edits. A bypass would rewrite 39 lowerer files and move 514 lines of code generation and the services above, to save at most those figures. The time is elsewhere: the grammar's tokenizer, the Lezer tree and the other annotators (about two thirds of a cold compile's profiled time), the validation window's lexing of the whole document on every edit (about 10 ms), the writer and the statement memo.

Keep the parsed-flow reuse: it saves 6 to 8 ms per edit on the project.

For #1684, keep the annotator's carry. Retiring it costs either lowering every untouched block again (277.5 ms of `incrementalParse` against 28.7, #1684's measurement) or stand-ins for top-level flows, weave points and `choose` blocks that would rebuild what this profile shows is cheap to keep and give up the flow reuse's saving; and it frees no heap a compile does not rebuild, since the last story's objects are needed by the next compile either way. The property #312 needed, that no generation of parsed objects is kept per edit, holds and is tested by the existing "but the objects this compile's story holds" probe, and the 200-edit heap shows the carry bounded. The recommendation for #1684 is to close it as not planned with this record, unless the maintainer wants the last story built only from the current source for its own sake, in which case top-level stand-ins after #1683 are the route, as a Task of their own.
